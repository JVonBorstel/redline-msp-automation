# B-62 Device remediation script levers

Status: **built** (PowerShell module, registry fragment, notice templates, mock device and session state, tests). Synthetic data only. Every vendor field and Windows detail is UNVERIFIED.

> Independently built prototype. Not affiliated with any vendor's or real company's systems. Synthetic data only.

Inventory (impact chains): `W-SD-11` (Tier 1 device fixes from the service desk), `W-EP-03` (endpoint remediation), `W-EP-07` (reboots). Controls: `C-05` (dry-run by default), `C-06` (lead approval bound to lever, client and params), `C-17`, `C-32` (blast-radius caps), `C-41`. Depends on `B-61` (RMM mock adapter and device reconciliation), `B-28` (runner idempotency, per-client lock, approver rules) and `B-42` (caps, windows). Standards: `STD-LV`, `STD-PS`, `STD-SC`, `STD-TS`. Decisions: `D6-08` (window rules live in the runner), `D6-26` (existing RMM components are never run until vetted into the registry), `MP-13` (remote-support session record).

## Why

Tier 1 device fixes (a printer that will not print, a drive that fell off, an Outlook that will not open, a full disk, a hung service, a reboot) are done in a remote session by hand many times a week. Each becomes one named script that a lead approves once, with a diff the approver reads, a check that it worked, and a plain note on how to go back.

## Behaviour

- **Module** `levers/powershell/DeviceOps/` (`DeviceOps.psm1`, `.psd1`, `vetted-scripts.json`, `README.md`, `SOURCES.md`, `mock/`, `tests/`): seven functions, each `[CmdletBinding(SupportsShouldProcess)]`, each returning `{ data, diff, applied }`, or `{ refusal }` for a rule that lives in the data. They read and write only the mock RMM state `<tenant folder>/<client>/devices.json` (the folder in `$env:REDLINE_MOCK_TENANT_DIR` when the file exists there, else the committed `mock/<client>/`) through JsonNode with one atomic replace, and read `remote-sessions.json` beside it. No network, no credentials, no clock.
- **Levers** `levers/registry.d/device.json`, all `runtime: powershell`, `approval: lead`, agent dry-run, technician execute, `idempotency_keys` = all params, one device per call:

  | Lever | Risk | Params | Caps per client per hour | Window |
  | --- | --- | --- | --- | --- |
  | `device.restart-spooler` | R1 | `device` | 10 | none |
  | `device.repair-mapped-drive` | R1 | `device`, `drive` (D to Z) | 10 | none |
  | `device.reset-outlook-profile` | R2 | `device`, `user` | 5 | none |
  | `device.cleanup-temp` | R1 | `device` | 5 | none |
  | `device.restart-service` | R1 | `device`, `service` (enum of five names) | 3 | none |
  | `device.reboot` | R2 | `device` | 6 | `business-hours` |
  | `device.reboot-server` | R2 | `device` | 2 | `maintenance` |

- **Vetted scripts (B62-1).** `vetted-scripts.json` has one entry per lever: `script_id`, `version`, the `steps` a person approves, and a SHA-256 over them. The module verifies every entry on every call and refuses all of them if one no longer matches. No lever has a script, command or path parameter; a test scans parameter names, requires every parameter to be an enum or a bounded pattern, and scans the module for shell, network and dynamic-execution calls. The steps are descriptions: nothing is executed anywhere.
- **Dry-run (B62-2).** The proposal's `data` says what would run (`would_run`, the script id, version and digest) and on which device (uid, hostname, class). The change is a list of field edits worked out from the state; `-WhatIf` returns it and execute applies exactly that list, so the diffs are identical by construction, and the runner compares them again. A repeat is an empty diff.
- **Windows.** `device.reboot` carries `window: business-hours` and `device.reboot-server` carries `window: maintenance`. The runner (B-42, B42-4) applies them with the client record; the module holds no time logic (a test forbids clock, day and window words in the code). The module only checks the device class: `device.reboot` refuses a server and `device.reboot-server` refuses a workstation, each naming the other lever. An offline device is refused.
- **Approval binding.** The runner binds an approval to lever, client and params (here the device uid and any drive, user or service); an approval for another device, drive, lever or client is denied. `data.plan_digest` (24 hex) pins lever, client, device, script hash and diff so the proposal a lead read can be matched to the audit record.
- **Verification.** After applying, the module re-reads the state from disk and evaluates each declared check (`data.verification.checks`). A failure returns a refusal starting `Verification failed`; the runner has already written its audit record, so it records an error after it. Mock devices can carry `faults` (for example `spooler-fails`) so this path is tested.
- **Rollback proposal.** `data.rollback` is text for a person: `kind` is `none-needed` (spooler, drive, service), `restore-from-backup` (Outlook profile: the dated backup name; temp: the quarantine folder) or `cannot-undo` (reboots). `automated` is always `false` and `undo_lever` is `null`: no undo lever is registered because none of these is undone by another approved script.
- **Per-client scope.** The client id is a slug before it is a path. A device of another client, a device of another RMM site that sits in the same file, and an unknown uid answer with one sentence. Each client's file is separate; a write to one never touches another.
- **Mock RMM only.** The device identity fields match `fixtures/rmm/<client>.json` (a test reads them through `RmmMock`). There is no real adapter path in this item; B-61's builder already fails closed (`real adapter not configured`).
- **Remote-support session (B62-4).** `data.remote_session` is the latest session on that device (matched by computer name) that ended at or before the as-of moment, from `remote-sessions.json`, a fixture shaped like a Splashtop session log (MP-13). It is `null` when none exists. Fields are UNVERIFIED (`SOURCES.md`).
- **Notices** `workflows/notify/templates/device.<action>.md`, one per lever (the notify module looks for `templates/<lever>.md`, as for `mailbox.*`).

## Acceptance

- **B62-1** Levers for print spooler restart, mapped-drive repair, Outlook profile reset, temp cleanup, service restart and reboot run only vetted scripts named in the registry (no free-form script parameter).
- **B62-2** Each dry-run returns what would run and on which device; reboot is flagged `window: business-hours` (servers `window: maintenance`) and the runner rule B42-4 applies it, with an approval override; the lever holds no time logic (D6-08).
- **B62-3** Per-script golden tests on mock RMM output; caps per client per hour apply.
- **B62-4** A remediation proposal links the technician's remote-support session record when one exists, from a fixture shaped like a Splashtop session log (MP-13; cited, unverified fields marked UNVERIFIED).

Tests: `tests/py/devices/test_b62_remed.py` (every test named `test_b62_<k>_...`) and `levers/powershell/DeviceOps/tests/DeviceOps.Tests.ps1`.

## Known limits and open points

- **Window wording.** The roadmap text says the runner "refuses [the reboot] inside the client's business hours"; what B-42 implements is the opposite: `window: business-hours` allows a lever only inside business hours and `window: maintenance` only inside the maintenance window. The flags are set as the roadmap names them; whether a workstation reboot should instead be allowed only outside business hours needs a decision, and would be a runner or registry change, not a module change.
- **Notices cannot be drafted yet.** The notify module (B-04) fills a notice only for a proposal with a `upn` param, and device levers have none. The seven templates exist so every write lever has one, but no draft is produced for a device change until notify learns to name the person from the device.
- **Reboot is not convergent in real life.** The mock treats a second reboot with the same as-of moment as no change; a real second reboot would restart again. The runner's replay guard (B-28) is what stops a repeat.
- **Registry-only vetting.** "Vetted" here means the steps are in this repo, hash-pinned and covered by tests. There is no review workflow for adding a script or for promoting an existing RMM component (D6-26); that remains a reviewed code change.
- **Quarantine is not purged.** Nothing removes quarantined temp files; a person or a later job does.
- Every device-state field, Windows service name and the session log shape is UNVERIFIED (`levers/powershell/DeviceOps/SOURCES.md`).

## Out of scope

Running any script on a real device or RMM, listing or running existing RMM components (`adapters/rmm` stays read-only), patching, software install (B-63), disk or user deletion, network device changes (never-automate list), and any scheduler for these levers.
