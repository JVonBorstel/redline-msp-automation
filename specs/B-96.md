# B-96 Staff training, client conversation guide, explainer and data-handling summary

Status: **document-only** for the four pages (plain-language text for people), **built** for the checker, the exercise replay and the tests, on fixtures. Nobody has taken this training and no real client has seen these pages. Synthetic data only.

> Independently built prototype. Not affiliated with any vendor's or real company's systems. Synthetic data only.

Inventory: `W-TRN-01` (technician training: reading suggestions and approvals), `W-TRN-02` (account manager training: explaining AI to clients). Control: `C-42` (staff training and acceptable use). Reads `B-92` (policy, acceptable use, DLP mapping) and `B-94` (incident runbook) as the rules it teaches, and `B-95` as the pattern for a checker that fails when a cited file or test does not exist.

## Why

Staff and clients should hear the same true account of what the AI does, and every sentence about the system should be checkable. A page that says "the program cannot approve its own work" is only worth reading if a test shows it.

## Behaviour

Pages (hand-written, not generated):

- `governance/STAFF_TRAINING.md`: the seven topics of the planned outline in order, a ten-minute exercise on three synthetic tickets (`T-3101`, `T-3127`, `T-3128` from `fixtures/tickets/contoso-dental.json`) with an answer key, and Limits.
- `governance/CLIENT_CONVERSATION_GUIDE.md`: the five topics of the planned outline, a question table (training on my data, who can see it, what if it is wrong, opting out, the record, outside AI tools, leaks, compliance), what to commit to in writing, and Limits.
- `docs/AI_EXPLAINER.md` and `docs/CLIENT_DATA_HANDLING.md`: one page each for a client owner.

Checker: `workflows/training/` (`claims.py`, `__main__.py`). `uv run --frozen python -m workflows.training check [--root DIR]` exits 0 or 1.

- A statement about the system sits in a list item or table row and ends with `(proof: ...)`, which must name at least one `path::test_name`, or `(policy: ...)`, which must name a file (a rule for people, or a gap that is not built). Lines that start "Your part:" are advice and need no tag.
- Fails when a cited path is missing or leaves the repo, when a `::name` is not defined in its file (a `def name(` match, the same rule as B-95), when a proof names no test, when a tag is empty, when a list item or table row has no tag, and when a loose paragraph uses a word that marks a claim about the system (system, software, tool, model, audit, log, never, always, cannot, every, only, sends, refuses) with no tag.
- Fails on over-claims that are not negated (production use, certified, compliant, attested, guarantee, customers use it, real-world results), on a money figure, on a percentage without `fixture-based` on the same line, and when the prototype label, `Synthetic data only`, the Status line or a `## Limits` section is missing.
- Reading grade is Flesch-Kincaid computed over the reader's words (code, tags, headings and link targets removed; each line ends a sentence), with the same syllable rule as the B-04 and B-94 tests. The two client pages must be grade 8 or lower and at most 450 words; the other two grade 10 or lower.

## Known limits

- **UNVERIFIED:** the checker proves a cited test is defined in its file, not that it passes and not that it still checks the claim. Whether a cited test is the right proof for a sentence is a reader's judgement; a review should read each pair.
- The paragraph check is a word list. A claim phrased without those words in a loose paragraph is not caught; the pages are written so that claims live in tagged lines.
- The over-claim and negation checks are patterns, not understanding. A sentence with "not" anywhere in it passes the over-claim check.
- The reading grade is a formula (it rewards short words and sentences) and the syllable count is a heuristic. It says nothing about whether a client owner understands the page. No client owner has read these pages.
- No one has taken the training, and completion records are planned (`C-42` evidence in `map/controls.json`). The exercise runs on the built-in mock model; real tickets and a real model would differ.
- The client answers rest on tests with fixtures; some are narrow (for example the isolation test for notices uses two named clients). The pages say "in our tests" where the test is narrow.
- Retention, an opt-out switch and per-client model settings are not built (`governance/AI_POLICY.md` section 5); the guide says so and tells account managers not to promise them.
- Run on Windows with uv's managed Python. Not run on a Linux runner. The exercise commands were not run on a Linux shell.
