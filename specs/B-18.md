# B-18 Adapter base, per-client bindings and the PSA mock

Status: **mocked** (adapter base, binding loader and PSA mock built and tested; no real PSA implementation exists). The real PSA binding is open question Q-01; this item builds the seam it plugs into.

> Independently built prototype. Not affiliated with any vendor's or real company's systems. Synthetic data only.

Inventory: `W-TOOL-11` (PSA, RMM and Graph integration maintenance), `W-SD-01` (ticket intake). Controls: `C-04` (client isolation), `C-27`, `C-10`. Standards: `STD-ID`, `STD-ER`, `STD-CF`, `STD-FX`, `STD-SC`. Decisions: `D6-01` (adapters shaped after Autotask behind vendor-neutral interfaces), `D6-15` (the PSA company id is the client's source of truth). Depends on `B-13` (`schemas/client.schema.json`).

## Why

Priya Nair's ticket T-3101 lives in the PSA. Every workflow that reads it must read Contoso Dental's ticket, never Fabrikam Capital's, and no code path should be able to choose a different client's PSA company by accident. So an adapter is constructed once, for one client, from that client's binding, and keeps no other client's data in reach. When the MSP's real PSA arrives (Q-01), only the implementation named in the binding changes.

## Behaviour

- `adapters/base.py`: `AdapterResult` (`ok`, `reason`, `data`), `AdapterError` (construction errors only) and `Adapter` (holds one client and one `BoundBinding`; a call is wrapped so an unexpected exception becomes `"<Class> crashed: <ExceptionType>"`).
- `adapters/binding.py`: `ClientConfig` (pydantic, frozen, `extra="forbid"`) for `config/clients/<id>.json`, agreeing with `schemas/client.schema.json`; `load_client(client, root)` fails closed with `ClientConfigError` naming the file; `BoundBinding` is what an adapter is built from. A `credential_ref` is a secret NAME of the form `client-<id>-<purpose>` that must carry this client's own id; error messages never echo the offending value.
- `adapters/psa/base.py`: vendor-neutral `PsaAdapter` (company, contacts, tickets, ticket notes, resources, SLA settings; read-only).
- `adapters/psa/mock.py`: `PsaMock(client, binding)` serves `fixtures/psa/<client>.json`. The fixture's `client` and `company.id` must match the client and the binding's `external_id`, or construction raises `AdapterError`. Every record is filtered by the bound company id, so a ticket of another company is reported with the same words as an absent one (`no such ticket for this client`).
- `adapters.build_adapter(client, system, config_dir=...)`: reads the client config and returns a `BuildResult` (never raises). `mock` builds the mock; any other implementation returns `real adapter not configured`; a system with no adapter yet returns `no '<system>' adapter yet`.
- `config/clients/*.json` files are not created here (protected `config/**`, owner step W2-E1). Tests use private copies under `tmp_path`.

## Acceptance

- **B18-1** an adapter instance is built for exactly one client from that client's binding (`config/clients/<id>.json`: implementation, external ids, credential reference name); asking it for another client's object is refused at construction (TEN-04).
- **B18-2** the PSA mock serves tickets, contacts, companies and SLA settings from `fixtures/psa/` and returns typed results with `ok` and `reason` (STD-ER-1), never raising to the caller.
- **B18-3** a binding that holds a credential value instead of a reference name fails validation (STD-CF-7); real implementations are absent and selecting one fails closed with `real adapter not configured`.
- **B18-4** the PSA mock's entities and fields follow the public Autotask REST API shape (Companies, Contacts, Tickets, TicketNotes, Resources), each field marked Verified or UNVERIFIED in the spec; the adapter interface stays vendor-neutral, so a ConnectWise or Halo binding is the same seam (D6-01).

Tests: `tests/py/adapters/test_b18_psa.py`, every test named `test_b18_<k>_...`.
