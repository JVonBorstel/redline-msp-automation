# B-72 QBR draft and weekly "what we did for you" digest

Status: **built** (two workflows, CLIs, tests). Draft files only: nothing is sent, posted or queued, no model is called, and nothing in a tenant, PSA, device or backup is changed. Synthetic data only. Every figure is **fixture-based**.

> Independently built prototype. Not affiliated with any vendor's or real company's systems. Synthetic data only.

Inventory: `W-RPT-02` (QBR draft), `W-RPT-03` (weekly digest). Controls: `C-21` (every figure recomputed from its source), `C-45`. Depends on `B-71` (the client health report). Standards: `STD-DC`, `STD-TS`.

## Why

Account managers spend their time on the conversation, not the slides. A draft that already holds the quarter's figures, the change since the last quarter and a plain list of what was closed is only worth starting from if every number in it can be traced, so both builds refuse to write a page whose numbers differ from their sources, and a person reads the draft before it goes anywhere.

## Behaviour

### QBR draft: `python -m workflows.reporting.qbr` (package `workflows/reporting/qbr/`)

- **`build <client> --quarter YYYY-Qn [--generated-on YYYY-MM-DD] [--out DIR]`** writes `<out>/<quarter>/<client>.draft.html` and `<client>.draft.json` (default `build/qbr`). **`verify <draft.html>`** re-checks a written draft. Exit 0 ok, 1 mismatch, 2 bad input or a draft that did not reconcile. One client per run; there is no `--all` and no MSP-wide review.
- **Reuses B-71 (B72-1).** Each month of the quarter, and of the quarter before it, is a `workflows.reporting.health.build_report(...)` result. The QBR takes the typed `Section.metrics` from those reports and adds no figure that B-71 does not already compute. Months after `generated_on` are not read (they have not happened yet); `generated_on` may not be before the quarter starts and is never read from the clock inside the library.
- **Where a month's files come from.** `QbrSources(history_dir, default)`: a month with a folder `qbr/data/<YYYY-MM>/{data,tickets,backup}` reads its files there; every other month reads B-71's own fixtures. The committed `qbr/data/2026-09/` holds invented September 2026 files for the three clients (tickets with only id, channel, status and dates and no text), written by script from the October set and labelled as such in each file's `_note`. October comes from B-71's fixtures. Nothing is dated July, August, November or December.
- **Period comparison.** For each figure the page shows this quarter, the previous quarter and the change. *Counts* (tickets opened and resolved, backup jobs by outcome, simulated emails sent and clicked) add up the months that have data. *Latest-run figures* (baseline findings, devices, critical updates waiting, vault score) are the last month with data. *Percentages* are recomputed from the summed counts, one decimal, half up, `n/a` for a division by zero. A change is shown only when both quarters have data for that part and, for counts, the same number of months; otherwise it says `n/a` (a quarter with one month of tickets is not set against one with three). A table shows how many months of each part have data, and a month-by-month trend table shows `no data` (never 0) for a month with no source dated in it.
- **Wins, risks, suggestions.** Fixed rules in `qbr/policy.py` (`RULES`): a win is a figure that moved the right way or a clean backup record; a risk is a figure that moved the wrong way or is over a B-71 stand-in threshold; a part with no data this quarter is listed as a gap, not a zero. Every risk maps to one suggestion, a topic for the account manager to raise ("Suggestions to discuss", "not commitments"). Suggestions carry no figure and no promise.
- **Reconciliation (B72-1).** After rendering, `qbr.reconcile.reconcile_html` reads the finished HTML and the raw source files and recomputes every month figure, quarter total, change, coverage count, "no data" month, win, risk and suggestion (and the exact sentence of each) with its own code. It does not call the builder, `build_report` or B-71's validator. It fails if any figure differs, is missing or is invented, if a list differs from what the rules give, or if a listed source's hash or date is not what the file has now, or a file that is not a source is listed. `create_draft` runs it on the final HTML and writes nothing on a mismatch. `verify_draft` also checks the HTML bytes against `html_sha256` in the JSON record.

### Weekly digest: `python -m workflows.reporting.digest` (package `workflows/reporting/digest/`)

- **`build <client> | --all --week YYYY-Www [--generated-on YYYY-MM-DD] [--out DIR]`** writes `<out>/<week>/<client>.draft.html` and `.draft.json` (default `build/digest`; `--all` is one separate digest per client in the ticket folder). **`verify <draft.html>`** re-checks. Exit codes as above. The week is an ISO week (Monday to Sunday); `generated_on` may not be before it.
- **Closed tickets (B72-2).** The tickets with status `resolved` whose last update (a stand-in for the PSA completed date, as in B-71) falls in the week. Each is listed by ticket id, the channel it arrived by, the day it was opened, the day it was closed and the hours between. **Ticket subject, body, requester, affected user, technician and labels are never read.** A ticket id must match `T-<digits>` and a channel must be a plain lower-case word, or the run is refused, so nothing from a ticket field can reach the page as text. The page also gives the count, the count per channel and the median hours.
- **Changes.** If the client's tenant baseline run (the B-71 baseline fixture) is dated in the week, the digest gives its counts: new findings, resolved findings and Conditional Access changes since the previous run, "for a person to confirm". No policy names or subjects are copied. Otherwise it says no baseline run was recorded that week.
- **Backup jobs.** Jobs scheduled in the week, counted by outcome, read through that client's `BackupMock` adapter as B-71 does (the adapter drops other organizations' rows). A client with no backup fixture (Litware Legal) says so.
- **Partial weeks.** A source is used for a week if it is dated on or after the Monday. If it is dated before the Sunday, the section says so (`data-partial="yes"`) because later days are not in it. A source dated before the week has "No ... data for this week", never a zero. The ticket export is cut at 2026-10-16, so 2026-W41 is complete, W42 is partial and W43 has no ticket data (but has the baseline run dated 2026-10-22).
- **Reconciliation.** `digest.reconcile.reconcile_html` recomputes the figures and the exact list of closed tickets (id, channel, opened, closed, in order), each section's status and partial flag, and every source's hash and date, with its own code and plain `json`. `create_draft` writes nothing on a mismatch.
- **It is a draft** (an Outlook draft arrives in W9). The page is a list of records, not a measure of value.

### Both documents (B72-3)

- **Draft label first.** The `<title>` starts `DRAFT - `, the first text in the page is the banner "DRAFT. Not sent. A person reviews this ... before it goes anywhere." and the JSON record has `status: draft`, `reviewed_by: null`, `reviewed_on: null`. The footer says "Reviewed by: nobody yet." There is no approve, reviewer or send step. The HTML has no script, link, form, image or external resource. Both packages import no network, mail, queue, scheduler, gateway or lever module (a test parses the imports and checks them against a deny list and a short allow list).
- **No cross-client data.** One client per document; every source file must name that client (a file or a ticket of another client refuses the run, via B-71's checks), and the backup adapter drops other organizations' rows. A test searches every document and JSON record for the other clients' names, ticket ids and backup organization names.
- **Honest wording.** No savings, cost, return, "prevented", "guaranteed" or money wording (a test scans the visible text); every page says fixture-based and synthetic and carries the prototype label. Thresholds are B-71's stand-ins (UNVERIFIED), imported, not copied.
- **Deterministic.** Dates are inputs; the same inputs give identical bytes.

## Public interface

`workflows.reporting.qbr`: `build_qbr(client, quarter, *, generated_on, sources=) -> Qbr` (frozen dataclass; `values` is every figure on the page keyed `q.<quarter>.<metric>`, `m.<month>.<metric>`, `d.<metric>`, `cov.<quarter>.<section>`), `render_html`, `qbr_to_dict`, `create_draft`, `reconcile_html`, `verify_draft`, `QbrSources`, `QbrError`, `VerifyError`, `Mismatch`, `main`.

`workflows.reporting.digest`: `build_digest(client, week, *, generated_on, sources=) -> Digest`, `render_html`, `digest_to_dict`, `create_draft`, `reconcile_html`, `verify_draft`, `week_bounds`, `DigestError`, `VerifyError`, `Mismatch`, `main`.

`QbrError` and `DigestError` are `HealthError`s. The digest uses B-71's `Sources`, per-client file checks and backup adapter; it does not call `build_report` because B-71 reports a month and the digest reports a week.

## Acceptance

- **B72-1** the QBR draft reuses the health data for the quarter with trends; every number reconciles
- **B72-2** the weekly digest lists closed tickets and changes in plain words without ticket free text; it is a draft (an Outlook draft arrives in W9)
- **B72-3** both start with the draft label

Tests: `tests/py/reporting/test_b72_qbr.py` (`uv run --frozen pytest -p no:cacheprovider tests/py/reporting/test_b72_qbr.py`), functions named `test_b72_<k>_...`. The expected figures, closed tickets and week bounds in the tests are recomputed from the raw files by the tests' own code; the tests never call the workflows' figure helpers or validators for them. Failing-first: the tests were written before the packages existed and failed on import.

## Known limits

- The QBR has real data for one month per quarter: October (B-71's fixtures; the ticket set ends 2026-10-16, the rest 2026-10-21/22) against an invented September. It is therefore a one-month-against-one-month comparison and the page says how many months each quarter has. It is not a full quarter's trend, and the September files are hand-made, not captured from any run (UNVERIFIED shapes, as in B-71: no RMM, patch-tool, phishing-simulation, vault or backup export format was checked against a vendor).
- A "win" means a fixture figure moved the right way; it is not evidence of value delivered, and nothing here estimates time or money.
- Resolved time uses the ticket's last update as a stand-in for the PSA completed date. The digest's "changes" are what the baseline run found, not a change log of work done; there is no change-record fixture yet.
- Thresholds are B-71's stand-ins. The suggestions are fixed wording, not tuned on real clients.
- The weekly digest cannot show which kind of request a ticket was (that would need ticket text or labels, which are not read).
- Reviewing is a person's job outside these packages. No Outlook draft is made here (W9).
