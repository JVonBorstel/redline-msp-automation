# B-78 Routing evals and escalation thresholds

Status: **built** (eval, report, proposed-thresholds file, tests) on **mock tiers only**. Nothing calls a model; no local model was run. Synthetic data only.

> Independently built prototype. Not affiliated with any vendor's or real company's systems. Synthetic data only. Every number here is fixture-based.

Inventory: `W-TOOL-02`, `W-TOOL-14`. Controls: `C-16`, `C-41`, `C-15`. Standards: `STD-TS`, `STD-DC`. Design rule served: "most intelligent model only where needed; routing thresholds are set by eval results, not opinion" (docs/BLUEPRINT.md section 3).

## Why

The program routes rules and scripts first, a small model for classify and summarize, and a strong model only for hard reasoning. Without a measurement, "when to escalate" is a guess. This eval scores the three kinds of decider against the gold ticket labels and derives the escalation thresholds from the scores, so a change to the thresholds can point at the run that justifies it.

## Behaviour

`uv run python -m evals.routing` (module `evals/routing/run.py`):

- **Gold set.** The synthetic tickets in `fixtures/tickets/*.json` (60: Contoso Dental, Fabrikam Capital), with technician corrections from `evals/triage/corrections.jsonl` applied if the file exists (it does not today). The task scored is the ticket `category`.
- **Three tiers, all mock.** `evals/routing/mock_backends.json` holds ordered keyword rules, each with a declared confidence, for `rules` (rules-first, cost 0), `small` (cost 1) and `strong` (cost 20). They are stand-ins written by the repo author, not models. Costs are assumed relative units, not money.
- **Report** `evals/routing/report.md`: accuracy and relative cost per tier, a cascade row, a per-category table (each tier's accuracy, share left by rules, share reaching strong, cascade accuracy), the derived thresholds, a holdout check, and the cascade's misses. Latency is printed as `not measured (mock)`.
- **Thresholds.** For a cheaper tier (rules, small) and each category it predicts, the threshold is the lowest declared confidence at which the decisions accepted (confidence at or above it) are at least 95% correct and number at least 3. If none qualifies the value is `null`: that tier always escalates for that category. `TARGET_ACCURACY` and `MIN_SUPPORT` are constants in `run.py` and are written into the output.
- **Cascade.** rules, then small, then strong; a tier's answer is accepted at or above its threshold, otherwise the ticket escalates; strong is final.
- **Holdout.** Thresholds derived from the even-position tickets (id order) are scored on the odd-position ones.
- **Proposal** `evals/routing/routing.proposed.json`: `status: proposed`, `applied: false`, `basis: fixture-based`, the thresholds, and an `eval_run` block (command, report path, ticket count, target, minimum support, SHA-256 of the ticket fixtures, corrections file and backend fixture, in-sample and holdout cascade accuracy, costs). Nothing reads this file. `config/routing.json` is never opened for writing; applying a threshold is a person's edit.
- **Local model.** The report has one row, `local model`, reading `skipped: no local model`. This eval has no code path that calls a local model.
- **Deterministic.** Same inputs give the same bytes. No clock, no randomness.

## Acceptance

- **B78-1** the golden sets run on the mock and, when installed, the local model; a table reports accuracy, latency and estimated cost per task and model, labelled fixture-based. Built for the mock tiers (accuracy, relative cost; latency is stated as not measured). The local-model part is **not built**: see B78-3.
- **B78-2** escalation thresholds are written to a proposed routing change file for review, never applied automatically. Built: `evals/routing/routing.proposed.json`.
- **B78-3** without a local model the report says `skipped: no local model`, never a number. Built as a constant: the eval never runs a local model, so the row is always skipped.

Tests: `tests/py/evals/test_b78_routing.py` (`uv run --frozen pytest -p no:cacheprovider tests/py/evals`), functions named `test_b78_<k>_...`. They fail first on a missing module; they include threshold derivation on synthetic rows (lowest qualifying confidence, `null` when the target or the minimum support is not met, change when gold labels change), the cascade rules, determinism, that the committed report and proposal equal a fresh run, that `config/routing.json` is untouched, and that the eval imports no model or network library.

## Known limits

- **Mock tiers, same author as the tickets.** The thresholds are a mechanical function of hand-written keyword rules and confidences that the author declared. They say how the method behaves, not how any real model behaves. UNVERIFIED: whether a real small or strong model's confidence is calibrated enough for a threshold like this to mean anything.
- **Small sample.** 60 tickets, 4 to 9 per category. The minimum-support rule makes several categories `null` (always escalate). The holdout is 30 tickets and is a rough check, not an interval. In-sample accuracy is flattering because the thresholds were fitted on the same tickets.
- **Cascade beats strong in the report.** That is because the mock strong tier is wrong on a few tickets where a cheaper mock tier happens to be right. It is not a finding about real models.
- **Injection tickets** are scored as ordinary tickets (gold is the underlying request). The eval does not run the injection scan; a real wrapped prompt may behave differently.
- **Cost and latency.** Relative cost units are assumed in the fixture. No latency is measured, no money estimated.
- **Only the classify task** is scored. Summarize and reason have no gold set here.
- **Not wired in.** Nothing consumes the proposal. `config/routing.json` still maps tasks to provider and alias only, and has no threshold field; adding one belongs to the gateway work (B-80) and to a reviewer.
- **File location.** The proposal lives under `evals/routing/`, not `config/`, because `config/**` is protected. Moving it is the reviewer's step.
