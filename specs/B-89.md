# B-89 Entra sign-in for approvers (design and mock token validation)

Status: **built** for the validator, the page gate and the approval record; **mocked** for the issuer (a local RSA key made at run time stands in for Microsoft Entra ID). Nothing here has run against a real Entra tenant.

> Independently built prototype. Not affiliated with any vendor's or real company's systems. Synthetic data only: every tenant id, app id, object id and session id in the tests is invented or random.

Inventory: `W-TOOL-06` (approval queue operation). Controls: `C-44` (authenticated approvers), `C-19` (tenant scoping), `C-07` (human approval). Depends on `B-03` (the approval page). Standards: STD-ID (STD-ID-7 demo sign-in is not authentication), STD-SC (STD-SC-1, STD-SC-6), STD-AU-4 (tokens are never logged), STD-PY, STD-TS. Decisions in force: D-024, D6-05 (approvers must be authenticated; R3 needs two signed-in leads, which B-28 enforces on top of this item).

## Why

Before this item the approver on the page was whoever was picked in a demo list (STD-ID-7, the D-023 known gap). An approval of Priya Nair's MFA reset is a real person's act, and an auditor expects proof of who it was and how they signed in. This item makes the page accept a decision only from a person whose Entra ID token validates, records how they signed in, and keeps the picker for the synthetic demo only, behind an explicit `--demo` flag.

## Design (target, W9) and what this item builds (W2)

Target flow, not built here: the page is an Entra ID app registration (single tenant, the MSP's own tenant, D6-11). A lead signs in with the OpenID Connect authorization code flow with PKCE; Conditional Access requires MFA for the app; the server validates the ID token, opens a server-side session (HttpOnly, SameSite=Strict cookie, bound to `sid`) and signs the session out when Entra signals it. Signing keys come from the tenant's published key set (`https://login.microsoftonline.com/<tenant>/discovery/v2.0/keys`), cached and refreshed on an unknown `kid`. Approver-to-client scope later comes from Entra security groups (D6-14).

What this item builds, offline:

- `core/auth/`:
  - `jws.py`: compact JWS parsing (strict base64url, size cap) and RS256 (RSASSA-PKCS1-v1_5 with SHA-256) verification on the standard library only. The verifier rebuilds the whole expected encoded message and compares it, so short-exponent forgeries do not pass. Keys under 2048 bits are refused.
  - `validator.py`: `AuthConfig` (tenant id, app id = audience, the key set in JWK form, the map from Entra object id to repo identity, leeway, maximum lifetime, required `amr` values) and `TokenValidator.validate(token, now)`. It returns an `ApproverAuth` or raises `AuthError` with a fixed reason code. Checks, in order: size and shape; header (`alg` exactly `RS256`, `kid` in the key set, no `crit`); signature; then claims: `iss` exactly `https://login.microsoftonline.com/<tenant>/v2.0`, `aud` exactly the app id, `tid` equal to the tenant, `ver` `2.0`, `exp` in the future, `nbf` and `iat` not in the future (each with the leeway), `exp - iat` within the maximum lifetime, `amr` containing a required method (default `mfa`), `sid` present, and `oid` mapped to a known identity. Time is an explicit `now` (STD-PY-9).
  - `models.py`: `ApproverAuth` (method `entra-id-token` or `demo-picker`, identity, `oid`, `tid`, `amr`, `sid`, issued and expiry times). It never holds the token.
  - `mock_issuer.py`: `MockIssuer`, a stand-in for Entra that makes an RSA key at run time (never committed), publishes its JWK and signs tokens for tests. Labelled mock everywhere.
- The page (`ui/app.py`, `ui/__main__.py`), outside `owns`, minimal: `App(queue, auth=validator)` turns on token mode. In token mode every page that lists proposals and every `POST /decide` needs `Authorization: Bearer <ID token>`; the approver is the token's identity, and a form `actor` that names someone else is refused. The demo picker is shown and honoured only without a validator. `python -m ui` needs exactly one of `--demo` or `--auth-config <file>`; with neither it exits 2 before binding.
- The approval record (`core/queue/store.py`, outside `owns`, minimal): `Proposal.approver_auth` is set on every decided line (`approved`, `executed`, `failed`, `rejected`); a reject's audit record carries it too.

The token travels in a header because the page has no script and this item does not build the browser sign-in (W9). A token can be replayed until it expires; the target session design above closes that.

## Acceptance

- **B89-1** an approval decision requires a validated token: issuer, audience, tenant, expiry (and not-before, issued-at, maximum lifetime), and an RS256 signature against the test key; `alg` other than `RS256` (including `none` and `HS256`), an unknown `kid`, a tampered payload, a key under 2048 bits, a missing `mfa` method or an unmapped object id are refused with a stable reason. The demo picker works only when the page is started with an explicit `--demo` flag; `python -m ui` with neither `--demo` nor `--auth-config` exits 2, and in token mode `?as=` grants nothing.
- **B89-2** the approval record carries the authentication method claim (`amr`) and session id (`sid`), with the method `entra-id-token`, the object id and the tenant, on the `approved` and final queue lines and on a reject's audit record. A demo decision is recorded as `demo-picker` with no `amr` or `sid`. The token itself never reaches the queue file or the audit log (STD-AU-4).
- **B89-3** a `POST /decide` with no token, a malformed token, an expired token or a wrong-audience token cannot decide: the answer is 401, the proposal stays pending, the tenant is untouched and the refusal is audited (agent `unauthenticated`, status `denied`, the reason code, never the token).
