# B-43 Security alert adapter mock, grouping and after-hours summary

Status: **mocked** (alerts adapter interface and mock, grouping workflow, on-call summary, CLI, eval, tests). Read-only: it groups and describes alerts, it never closes, contains or acknowledges one. Synthetic data only.

> Independently built prototype. Not affiliated with any vendor's or real company's systems. Synthetic data only.

Inventory (impact chains): `W-SEC-01` (security alert triage), `W-SD-12` (after-hours and on-call handling), `W-EP-02` (endpoint agent and sensor health). Controls: `C-12` (untrusted input), `C-13`, `C-27` (one client per unit of work), `C-41` (eval before promotion). Depends on `B-18` (adapter base). Decisions: `D6-04` (tiers 1 to 3 plus an external 24/7 SOC; the SOC stays the responder). Standards: `STD-ER`, `STD-FX`, `STD-SC`, `STD-TS`.

## Why

On-call engineers wake up to five grouped events, not fifty alerts. An identity alert, a SIEM alert and a mailbox-rule alert about one person in one hour are one story. A monitoring agent that went quiet and an endpoint sensor that stopped on the same server are one story too, but a health story, not a break-in. And when the external SOC already has a case, the engineer must see that first, so nobody contradicts the SOC's containment.

## Behaviour

`python -m workflows.alerts <client> [--since T] [--until T] [--after-hours] [--text]` prints the on-call summary.

- **Adapter** (`adapters/alerts/`). `AlertsAdapter` (system `alerts`) has `list_alerts(since, until)` and `get_alert(id)`, both returning `AdapterResult`. `AlertsMock` serves `fixtures/alerts/<client>.json`, is built for one client from that client's binding, refuses a fixture whose `account_id` is not the binding's `external_id`, drops any row naming another client, and answers another client's alert id exactly like an absent one.
- **Source types, not products.** `edr-mdr`, `m365-itdr`, `siem`, `rmm-monitor`, `backup`, `saas-monitoring`. A vendor is a later adapter that maps onto these.
- **Pool (isolation).** `pool_for(client, alerts)` drops every alert of another client before anything is keyed, then sorts by time and notes which alerts the injection detector flags.
- **Groups.** Key = group type + entity kind + entity id (case-insensitive). Alerts under one key whose neighbours are within `window_minutes` (config, 60) form one group; a lone alert is a group of one. Group type is `health` when the alert category is in `health_categories` (`agent-offline`, `sensor-health`), else `incident`; the two never merge, even on the same device. Severity is the highest in the group. Grouping reads no free text.
- **SOC.** An alert with `soc_case_id` makes its group carry that id; the group's responder is `external-soc`, else `on-call`.
- **Summary.** Groups ordered most severe first; per group: facts used (counts, source types, entity, first and last time, categories, highest severity, SOC case), the read levers that would enrich it, the responder note, and each alert's text only inside `wrap_untrusted("alert", ...)`. A flagged alert is grouped but its text is withheld and its id listed for a person. `--after-hours` keeps groups whose first alert fell outside business hours (config placeholder: 13:00 to 22:00 UTC, weekdays; the MSP's real hours are UNKNOWN).
- **Enrichment levers.** `workflows/alerts/config.json` lists lever names per entity kind. A name is offered as `available` only if it is registered with class `read`; otherwise it is listed as `planned_not_built`. Today only `kb.search` is available.

## Acceptance

- **B43-1** Alerts are grouped per client by entity and time window; a group never mixes clients. Other clients' alerts are dropped before keying (a spy on the keying function never sees one), the window is workflow config and changing it changes the result, and two clients with the same host name at overlapping times get separate groups.
- **B43-2** The on-call summary lists groups by severity with the facts used and the read levers that would enrich them; alert text is wrapped untrusted. A flagged alert's text is withheld; alert text cannot change a group, a severity or a responder.
- **B43-3** Fixture-based grouping precision and recall against gold groups are reported (labelled fixture-based, `evals/alerts/report.md`; the test checks the committed report equals a fresh run). RMM agent and endpoint sensor health alerts form their own group type.
- **B43-4** Alert sources are modelled as types, not products: EDR/MDR, Microsoft 365 identity threat detection, SIEM, RMM monitors and backup (plus SaaS monitoring, B43-5). When an external SOC already owns an alert, the group carries its case id and the summary says the SOC is the responder (D6-04).
- **B43-5** SaaS-monitoring alerts (MP-20; vendor possibly SaaS Alerts, UNVERIFIED) are one more source type through the same grouping path: no source-specific code.

Tests: `tests/py/alerts/test_b43_alerts.py` (run with `uv run --frozen pytest -p no:cacheprovider tests/py/alerts`). Eval: `uv run --frozen python -m evals.alerts.report`.

## Field status

Every alert field is this repo's own neutral name. No vendor documentation was read, so every vendor mapping is UNVERIFIED. The per-field table is `fixtures/alerts/SOURCES.md`.

## Known limits

- Grouping needs a shared entity id. A device alert and the sign-in alert of the person using it do not group (the eval's one missed pair); linking them is enrichment, B-44.
- The fixtures, the gold groups and the rule have one author, so the eval is a pipeline check, not model quality (D-022).
- One window for all sources; no re-opening of a group after the window; no deduplication of identical repeats beyond grouping.
- `adapters/binding.py` `System` does not list `alerts` yet, so `build_adapter(client, "alerts")` and `config/clients/*.json` bindings for alerts do not exist (outside `owns`). Tests and the CLI build a `BoundBinding` directly.
- Enrichment levers other than `kb.search` are not built; the summary says so instead of implying they run.
- Business hours and the time zone are placeholders.
