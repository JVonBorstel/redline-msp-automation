# B-24 SLA breach watch and backlog grooming report

Status: **built** (workflow, CLI, tests). Nothing is sent (HO-9); a person reads the report and sends any draft. Synthetic data only. Fixture-based, not a measure of real SLA performance.

> Independently built prototype. Not affiliated with any vendor's or real company's systems. Synthetic data only.

Inventory (impact chains): `W-SD-06` (SLA breach watch), `W-SD-10` (backlog grooming, waiting-on-client or vendor follow-up). Controls: `C-27` (one client per read and per list), `C-21` (every number reconciles). Depends on `B-18` (PSA adapter and the SLA settings in `fixtures/psa/`) and `B-21` (Phase 2 tickets).

## What it does

`python -m workflows.sla --as-of <UTC time> [--hours N] [--waiting-hours H] --state <dir>` writes `<dir>/sla/report.json`, `report.md` and `drafts/<ticket>.followup.md`, checks the report against the fixtures, and prints it.

- Per client, the SLA matrix comes from that client's own PSA adapter (`adapters.build_adapter`, `get_sla_settings`). Tickets come from `fixtures/tickets/**` (labels and free text ignored) and from the same adapter (`list_tickets`, `list_ticket_notes`, `list_contacts`).
- **Breach watch.** An open ticket has a first-response deadline (`created + firstResponseHours`) unless it has had a response, and a resolution deadline (`created + resolutionHours`). A deadline in `(as_of, as_of + N hours]` is `at_risk`; one at or before `as_of` is `breached` (listed separately, never hidden).
- **Backlog grooming.** A ticket in `waiting-client` or `waiting-vendor` whose last update is more than `--waiting-hours` before `as_of` (strictly more) is listed, oldest first, with a follow-up draft.
- If `config/clients` does not exist (it is an owner step), the CLI writes synthetic mock bindings under `<state>/sla/clients/` and uses those.

## Assumptions (all UNVERIFIED; the MSP's real SLA numbers are UNKNOWN)

1. Hours are wall-clock. The matrix names say "8x5" and "7x12" but no business-hour calendar is modelled, so a deadline can be earlier than a business-hours reading: the watch warns early, never late.
2. A `new` file ticket has had no first response; a PSA ticket has had one when a resource note exists (note time is not compared with `as_of`). A late response that already happened is history, not listed.
3. The resolution clock pauses while `waiting-client` (counted as `resolution_clock_paused`) and runs while `waiting-vendor`.
4. A waiting ticket's age is `as_of - updated`.
5. A file ticket carries no SLA id, so it gets its client's SLA only when the client has exactly one active SLA. A client with no PSA fixture (Litware Legal) is counted as `open_no_sla`, not guessed.

## Acceptance

- **B24-1** Given an `as_of`, the report lists, per client, the open tickets that will breach first response or resolution within the next N hours per that client's SLA matrix (boundaries pinned: a deadline exactly at `as_of` is breached, exactly at `as_of + N` is at risk). Already-breached deadlines are listed separately. Resolved tickets, tickets created after `as_of` and tickets without timestamps are not watched but are counted. Each client uses only its own SLA matrix and lists never mix clients. A client with no SLA matrix is counted, not guessed. Naive or non-UTC times, and non-positive thresholds, are refused.
- **B24-2** The grooming section lists tickets waiting on the client or on a vendor longer than the threshold (not those exactly at it), each with a follow-up draft that starts with `Draft. A person reviews and sends this.`. Drafts contain only the ticket id, the person's first name, a day count and the client's own fast-path contact (or "reply here" when the client has none); ticket subject and body never reach a draft or the report. The package imports no mail, socket, HTTP, subprocess or model-gateway module and defines no send function. The CLI writes only under `<state>/sla/`.
- **B24-3** Every count in the report reconciles to the ticket fixtures: `validate_report` recomputes all counts, the listed ticket ids, the identities (`tickets_read` = untimed + created_after_as_of + resolved + open; `open` = open_assessed + open_no_sla; drafts = stale waiting tickets) and the totals from the raw JSON files with code that does not use the workflow or the adapter. A changed count, an invented or dropped ticket, a dropped draft or a changed fixture makes it return problems; the CLI exits 1 and prints them.
