# B-34 Requester authorization check and authorized contacts

Status: **built** (`levers/python/contact.py`, `levers/registry.d/contact.json`, `fixtures/psa/contacts-authorized.json`, `tests/py/levers/test_b34_contacts.py`). Mock only; no real PSA is called.

> Independently built prototype. Not affiliated with any vendor's or real company's systems. Synthetic data only.

Inventory: `W-ONB-01`, `W-KB-06`, `W-IDM-04`. Controls: `C-30`, `C-04`, `C-27`. Depends on `B-28`, `B-18`, `B-14`. Standards: `STD-LV`, `STD-ID`, `STD-TS`. Decisions in force: identity changes are R3 with two signed-in approvers; verification is callback-on-file (D6-06).

## Why

An outsider can ask for a new account or access in someone else's name. Before the callback, the technician needs a fast answer to "is this person on the client's list for this kind of change?" That answer is evidence for the human verification; it is not the verification.

## Design

- `contact.check(requester, change_type)`: R0 read lever, technician role. `requester` is an email address; `change_type` is one of `new-account`, `access-change`, `mfa-reset`, `password-reset`, `disable-account`.
- The client is the runner's client (`_meta.client` of the state it hands over). There is no client parameter, so the caller cannot pick a list. Only that client's entry in `fixtures/psa/contacts-authorized.json` is used.
- Authorized only if the requester's email matches (case-insensitive) an `active: true` contact whose `changeTypes` holds the change type. Anything else (unknown, inactive, wrong change type) returns the same words, `not authorized: confirm with the client's primary contact`, so the answer does not say which case it was.
- Result: `{authorized, message, evidence}`. `evidence` has `kind: requester-authorization`, client, requester, change type, source, `contact_id` (authorized only), `sets_verification: false` and a note that it does not verify. The runner audits who asked about whom, not a verification.
- The fixture shape is this prototype's own and the authorization fields are UNVERIFIED as a PSA field (see the fixture `_meta.note`).

## Acceptance

- **B34-1** `contact.check` (R0) answers whether a named requester may request a given change type for a client, from that client's authorized-contacts list only
- **B34-2** an unknown requester returns `not authorized: confirm with the client's primary contact`, never a guess; another client's list is never read
- **B34-3** the result is shown on the approval page as evidence for the verification record; it never sets verification by itself (verification stays a human act, W-IDM-04)

Tests: `tests/py/levers/test_b34_contacts.py`, `test_b34_<k>_...` per id.

## Limits and open points

- The approval page (`ui/app.py`) is outside this item. This item produces the evidence object (`evidence`) a page can print; wiring it into the page is a follow-up for the page's owner. Test B34-3 proves the evidence cannot set verification: an identity change with an authorized answer but no recorded verification is still denied.
- The handler opens the whole fixture file but takes only the runner's client entry; the test replaces the other client's entry with garbage to show it is never used. A real PSA adapter would query by company id instead.
- The requester parameter is an email only (the registry pattern rejects spaces and display names); a phone-call requester must be resolved to an address first.
- Linking the list to the client record's `authorized_contacts` ids (B-28 callback confirmation) is not done here.
