# B-81 Scheduler with per-client fan-out and job keys

Status: **built** (library, tests) with in-memory stores only. Nothing is wired to the real queue, a real clock loop or a CLI. Synthetic data only.

> Independently built prototype. Not affiliated with any vendor's or real company's systems. Synthetic data only.

Inventory: `W-TOOL-09`, `W-IDM-09`, `W-M365-11`. Controls: `C-32` (blast-radius caps), `C-18`, `C-27`. Depends on `B-42` (per-client audit chains). Standards: `STD-PY`, `STD-ID`, `STD-TS`.

## Why

Daily baselines and quarterly reviews must run for every client without a person remembering, without one client's failure stopping the rest, and without a retry doubling a result. The scheduler is the only thing that decides what is due; it never decides what happens to a finding.

## Behaviour

Package `core/scheduler/` (`models.py`, `stores.py`, `scheduler.py`, `jobs.example.json`).

- **Config.** `load_config(path)` reads `{"version": 1, "global_cap", "per_client_cap", "jobs": [...]}`. A job has `name`, `workflow`, `every` (`daily`, `weekly`, `monthly`, `quarterly`), `not_before_hour` (UTC, default 0), `clients` (`"all"` or a list), `disabled_clients` (always wins) and `job_cap` (most units of this job per tick). Unknown fields, duplicate job names, a name with `/` or an unsafe client id are refused. Every job's `workflow` must be in the workflow table passed to `Scheduler`, or construction fails.
- **Time.** `Scheduler(..., clock=...)` takes an injected clock; `tick(now=None)` also takes an explicit time. Only timezone-aware UTC is accepted. Nothing sleeps and nothing runs in parallel. Period labels: `YYYY-MM-DD`, ISO week `YYYY-Www` (ISO year), `YYYY-MM`, `YYYY-Qn`.
- **Fan-out.** `tick()` visits jobs in config order and clients sorted, and starts one unit per eligible client with key `job/client/period` (B81-1). Client ids that are not safe ids are never keyed and are reported in `invalid_clients`; clients named in a job but not known are reported in `unknown_clients`.
- **Idempotency.** A key already in the job store (running, ok or failed) is skipped and reported in `skipped`. Claiming goes through `JobStore.claim`, which must be atomic. A failed unit is not retried in the same period.
- **Caps.** `global_cap` and `per_client_cap` (units started per tick, over all jobs) and `job_cap`. These are admission caps per tick, not parallelism: a unit over a cap is not claimed, is listed in `deferred`, and a later tick takes it. A skipped duplicate uses no cap.
- **Isolation.** An `Exception` from a workflow, a refused result, a failing sink or a failing audit write fails that one unit; the record keeps a short code or the error class name, never the error text. Other clients and other jobs for the same client carry on. `KeyboardInterrupt` and similar are not swallowed.
- **Reports and proposals (B81-3).** A workflow returns `UnitResult(report, proposals)`. The report is cut to one line of at most 200 characters. Each `ProposedAction` is checked before anything is queued: the lever must be registered (`Registry`), its `client_scope` must cover the unit's client, its params must pass `validate_params`, and a write lever must support dry-run. One bad proposal fails the unit and queues none of that unit's proposals. Accepted ones go to a `ProposalSink`; the in-memory sink de-duplicates by the queue's `proposal_id`. The scheduler imports no runner and has no call that runs a lever; approval and execution stay with the lever runner and a lead.
- **Audit.** With `RouterAudit(AuditRouter)` wired, each finished unit writes one `job.run` record (agent `scheduler`, mode `dry-run`, `actor_kind` agent) to that client's own chain. Params carry `job` and `period`, never the full key: the redactor blanks long letter-and-digit runs (STD-AU-5) and the key is rebuilt from job, client and period. A skipped duplicate writes nothing. A failing audit write marks the unit failed.
- **Storage seam.** `JobStore`, `ProposalSink` and `UnitAudit` are Protocols. Only in-memory implementations exist. The SQLite queue (B-82) is built separately and is not touched or imported.

## Acceptance

- **B81-1** jobs are config (name, workflow, schedule, per-client enable, concurrency cap); a run fans out one unit per client with key `job/client/period`
- **B81-2** a repeated key is skipped (idempotent); caps per client and global are honoured in a test with 300 synthetic clients
- **B81-3** results become reports or proposals, never direct writes

Tests: `tests/py/scheduler/test_b81_scheduler.py` (`uv run --frozen pytest -p no:cacheprovider tests/py/scheduler`), functions named `test_b81_<k>_...`.

## Known limits

- UNVERIFIED: any behaviour under a real clock loop, real daylight-saving changes (the scheduler is UTC only; a client's local business day is not modelled) or two processes ticking at once. Atomicity of `claim` is a contract the in-memory store keeps inside one process; it is not proven for a durable store.
- A crash between claim and finish leaves a key `running` forever. Nothing reclaims it. A durable store needs a lease or an explicit reset (B-82 or later).
- A failed unit is never retried within its period and there is no command to re-run one.
- "Concurrency" is a per-tick admission cap, not parallel workers. A job that is deferred each tick by a busy client can wait several ticks; there is no fairness beyond config order and sorted client ids.
- `ProposalSink` has only an in-memory implementation. Wiring to `core.queue.store.ProposalQueue` is not done: its `Source` is limited to `triage`, `baseline`, `rollback`, and adding a `scheduler` source is a change to queue code owned by B-42/B-82. The sink is called after validation but a dry-run through the runner (STD-PR-1) is the queue adapter's job and is not exercised here.
- No workflow is registered. `jobs.example.json` names `tenant-baseline` and `access-review` as examples only; no existing workflow is called, and nothing ships a CLI or a daemon.
- Proposal validation uses the registry's schema checker; it does not check lever `window`, caps or approval rules, which the runner enforces when a lead approves.
