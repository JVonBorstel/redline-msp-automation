# B-39 Sign-in failure and lockout investigation

Status: **built** (read lever, mock fixtures, workflow, CLI, tests). Reads and explains; never changes anything. Synthetic data only.

> Independently built prototype. Not affiliated with any vendor's or real company's systems. Synthetic data only.

Inventory: `W-IDM-03`. Controls: `C-20`, `C-27`, `C-12`. Depends on `B-19` (family files), `B-14` (registry fragments). Standards: `STD-LV`, `STD-FX`, `STD-SC`.

## Why

"I can't sign in" is the most common call. The answer is in the sign-in log, but reading error codes takes minutes and the wrong fix (unlocking an account that is being guessed at) hurts. The tool reads one user's recent sign-ins, says in plain words what each failure means, and names the lever a lead could approve. It does not run it.

## Behaviour

- **`signins.list`** (`levers/registry.d/signin.json`, `levers/python/signin.py`): class read, `R0`, approval none, `required_role` technician (the result holds IP addresses and places, DC-3). Params `upn` (required) and `limit` (1 to 50, default 10). Returns the user's sign-ins newest first. A user of another client answers like an absent one.
- **Data.** `fixtures/tenant/<client>/signins.json`, a B-19 family file shaped like Microsoft Graph v1.0 `signIn` (subset). Property names `id, createdDateTime, userDisplayName, userPrincipalName, userId, appDisplayName, ipAddress, clientAppUsed, conditionalAccessStatus, isInteractive, status{errorCode, failureReason, additionalDetails}, location{city, state, countryOrRegion}` are VERIFIED against the signIn, signInStatus and filter docs (read 2026-10-21). Values are invented; IPs are documentation ranges. `errorCode` 0 on success is UNVERIFIED.
- **Runner change (outside `owns`).** The runner gave handlers only the base tenant file. For `read` levers only, `MockTenant.load_for_read` now adds the client's own family files under `_families` (each must name the client in `_meta.client`). Write levers and saves are unchanged.
- **`python -m workflows.lockout <client> <upn>`** (`workflows/lockout/`): calls `signins.list` as a technician, groups failures by code, maps each to a plain cause and next step from `codes.json`, suggests levers, and flags a possible password-guessing pattern (config: at least 3 password failures from at least 2 IP addresses). `--prompt` prints only the model-safe text.
- **Code table** (`workflows/lockout/codes.json`): 15 codes, source <https://learn.microsoft.com/en-us/entra/identity-platform/reference-error-codes> read 2026-10-21. 14 are `verified` (code and meaning found on the page); `500121` is `UNVERIFIED` (not found on the page). A code absent from the table is reported `unknown` and `UNVERIFIED`. The plain wording is this repo's.
- **Suggestions** are names plus params with `executed: false`. Only registered levers are suggested (`user.reset-mfa` for MFA enrolment codes 50079, 50072, 50074). Account unlock, enable, password reset and Conditional Access have no lever here and are left to a person.

## Acceptance

- **B39-1** `signins.list` (R0) returns one user's recent sign-ins from the client's mock; read results are never written to the audit
- **B39-2** the lockout summary maps failure codes to plain causes from a cited table (Microsoft Learn sign-in error codes, marked UNVERIFIED per code where not checked) and suggests the right lever, never executes
- **B39-3** IP addresses and locations appear only in the technician's view, not in prompts (DC-3 minimum necessary)

Tests: `tests/py/lockout/test_b39_lockout.py`, named `test_b39_<k>_...`.

## Known limits

- Mock only: no Entra log is called. A real read needs `AuditLog.Read.All` and Entra ID P1 or P2 (signIn docs); the real adapter is a later item.
- The password-guessing thresholds are plain config chosen on the fixtures, not tuned on real traffic. A traveller on hotel Wi-Fi can look like guessing; the flag says "tell the security lead", never "block".
- The fixture user for 50057 (disabled) is still `accountEnabled: true` in the base tenant file; the workflow does not cross-check it.
