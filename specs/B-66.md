# B-66 macOS and Linux levers through a bash runtime

Status: **built on mock data** (`core/levers/bridge.py` `BashBridge`, `core/levers/registry.py`, `core/levers/runner.py`, `levers/bash/`, `levers/registry.d/unix.json`, `tests/py/levers/test_b66_bash.py`). No real Mac or Linux host is touched.

> Independently built prototype. Not affiliated with any vendor's or real company's systems. Synthetic data only.

Inventory: `W-EP-09` (Mac and Linux endpoint actions). Controls: `C-05` (a lever is the only way to act), `C-17` (typed boundary between languages), `C-01` (agents never run free-form shell). Depends on `B-61` (device mocks) and, through the runner, `B-16` (the PowerShell bridge this one mirrors). Standards: `STD-LV`, `STD-XL`, `STD-SC`.

## Why

Mac and Linux users get the same safe automation as Windows users. A lever for a Mac or Linux host is a reviewed bash script plus one registry entry. Every permission decision (registry, role, client scope, approval, pause, verification, caps, audit) stays in Python and happens before any process exists; bash only does the last step. A fooled model can press the buttons it was allowed to press and cannot type a command.

## Behaviour

- **Registry.** A lever may carry `runtime: "bash"` and `entry: "<name>.sh"`, a bare file name (`[a-z][a-z0-9-]{1,48}.sh`; no path, no flag). `Registry.load` checks that `levers/bash/manifest.json` lists the script and that the script's and the libraries' bytes still hash to the pinned SHA-256. Any miss fails the whole load. `Registry.runtime(name)` is `"bash"` and `Registry.bash_entry(name)` returns the `BashEntry`. Python and PowerShell levers are unchanged.
- **Allowlist and hash pinning.** `levers/bash/manifest.json` is the allowlist: `scripts` (the only files a lever may name) and `libs` (what they may source), each with a SHA-256. The bridge re-checks the hashes on every call, copies the exact verified bytes into a private temporary folder and runs the copy, so a file edited between the check and the start cannot run. A symlink, a missing file or a mismatch is an `error` result and nothing starts.
- **Bridge** (`BashBridge.call`, same signature as the PowerShell bridge, same `BridgeResult`). It starts `bash --noprofile --norc <script> [--what-if]` with no shell between, writes one JSON request line to stdin, reads exactly one JSON result line, and applies the same result checks as the PowerShell bridge (same lever, client and mode; exit code agrees with status; no `applied` in a dry-run; at most 1 MB; anything else discarded as `error`). It never raises.
- **Dry-run is `--what-if`.** The script gets `--what-if` exactly when the mode is `dry-run`; it must report the diff and change nothing. The script's shared library refuses a request whose mode and flag disagree. A read lever is sent as `execute` (no flag), like a PowerShell read, and a diff or `applied` from it is discarded.
- **Dry-run diff equality.** The runner is the same code path as for PowerShell (`LeverRunner._run_bridge`): a write lever's execute is a dry-run call for the diff, the audit record, then the real call, which must report `applied: true` and exactly the same diff, otherwise a second audit record says `error` ("apply did not match the dry-run diff"). A script that changes state in `--what-if` is therefore caught the first time it is executed (tested with a deliberately dishonest fixture script).
- **Scrubbed environment.** The child sees `LANG=C`, `LC_ALL=C`, `REDLINE_UNIX_MOCK_DIR` (the folder of the synthetic hosts) and a fixed `PATH` (`/usr/bin:/bin` on macOS and Linux; the parent's `PATH` plus the few variables Git Bash needs on Windows). No token, key, `BASH_ENV` or `ENV` reaches it.
- **Timeout.** The child is killed at the lever's `timeout_s` (the whole process group on macOS and Linux) and the result is `error`, "timed out ... the bash process was killed; nothing was reported as applied".
- **Parameters are data, passed safely.** They travel only in the JSON request on stdin, never on argv, in the environment, in a file name or in an evaluated string. Before bash starts the bridge refuses any string value outside `[A-Za-z0-9._:@+-]` (at most 64 characters), any parameter name outside `[a-z][a-z0-9_]*`, a client id that is not a plain slug, and a lever name or request id outside their patterns. No quote, backslash, `$`, backtick, brace, newline or space can be present, so the request line is read by one anchored pattern match in the library (`levers/bash/lib/lever.sh`), never `eval`ed. The scripts then check the value against their own allowlist (`case` on the exact names) and use paths only from fixed prefixes plus a listing of the folder.
- **No free-form command parameter (B66-3).** At registry load, a bash lever is refused if a parameter is named like a command, script, path or argument (`command`, `cmd`, `shell`, `script`, `exec`, `eval`, `args`, `argv`, `code`, `run`, `bash`, `path`, `file`, `dir` and similar), if a string parameter has neither an `enum` nor a `pattern` with a `max_length` of at most 64, if an enum value is outside the safe character set, or if its pattern admits any shell or JSON metacharacter (probed with each of `; & | $ \` ( ) < > \ " ' newline tab space * ? { } [ ] ~ ! # % ^ = ,` and a non-ASCII letter). A test also scans the scripts for `eval`, `exec`, `bash -c`, backticks and sourcing anything but the library.
- **Mock hosts.** `levers/bash/mock/<client>/` holds one synthetic Mac or Linux host per client (Contoso Dental, Fabrikam Capital): `disk.tsv`, `services.tsv`, `cache/user-cache/`, `cache/app-cache/`. A client without a folder (Litware Legal) is an `error`, never an empty report. The scripts read the host of the request's one client only. The scripts call no `systemctl`, `launchctl`, `df` or other system command; they are the lever contract on mock state, not a Linux administration tool.

## The three levers

| Lever | Class | Script | Parameters | Diff paths |
|---|---|---|---|---|
| `unix.disk-usage` | read, R0 | `disk-usage-report.sh` | `threshold_pct` (integer 1 to 100, default 80) | none; data lists mounts with `used_pct` and `over_threshold` |
| `unix.restart-service` | write, R2, lead approval | `restart-service.sh` | `service` (enum `cups`, `chronyd`, `rsyslog`) | `/services/<name>/restarts` (+1) and, if it was stopped, `/services/<name>/state` |
| `unix.clear-cache` | write, R2, lead approval | `clear-cache.sh` | `scope` (enum `user-cache`, `app-cache`) | `/cache/<scope>/<file>` (`remove`, with `size_bytes`) |

`clear-cache` removes only direct children that are regular files with a name in `[A-Za-z0-9._-]{1,64}`; folders, links and odd names are left and counted in `data.skipped`. Both write levers have a notice template in `workflows/notify/templates/`.

## Acceptance

- **B66-1** `runtime: "bash"` levers run a vetted script named in the registry, through the bridge, with the same JSON request and result schemas; dry-run is a `--what-if` flag the script must honour
- **B66-2** three levers (disk usage report, service restart, cache clear) with golden-output tests; if shellcheck is not installed the test reports skipped, never passed
- **B66-3** no script accepts a free-form command parameter

Tests: `tests/py/levers/test_b66_bash.py` (names start with the acceptance id; `uv run --frozen pytest tests/py/levers/test_b66_bash.py -rs`). Golden files are in `levers/bash/golden/`. Tests that start bash skip when no usable bash exists; the shellcheck test is skipped (never passed) without shellcheck.

## Known limits

- **Mock only.** Nothing here proves the scripts against a real Mac or Linux host, a real service manager or a real cache layout. A real backend would be a reviewed change to the scripts and the manifest.
- **Request schema.** `schemas/lever-request.schema.json` requires an `entry` object with a PowerShell `module` and `function`. The bash request is the same document without `entry` (the script is chosen by the registry and the argv, never by the request). A test checks that its fields are a subset of the schema's and equal its required fields minus `entry`. Making `entry` a `oneOf` in the schema is a follow-up outside this item's `owns`.
- **Windows and bash.** On Windows only Git Bash is accepted (the WSL launcher `System32\bash.exe` is refused). The bridge and scripts were run here on Git Bash (MSYS2 bash 5.x). bash 3.2 (macOS `/bin/bash`) and a real Linux were not run; the scripts use only bash 3.2 features (no associative arrays, no `mapfile`) but that is by reading, not by test.
- **Windows process kill.** On Windows the timeout kills the bash process but not necessarily a grandchild (POSIX kills the group). The shipped scripts start no child processes except `wc` and `rm`.
- **Hash pin is not a signature.** The manifest sits in the same repository as the scripts; it stops accidental or later edits and forces a reviewed change to both, it does not stop someone who may edit both. Review of the manifest is the control.
- **`--what-if` is a contract.** The bridge cannot prove a script honours it; the runner's diff equality check and the per-lever tests catch a script that does not.
- **`clear-cache` reversibility.** Registered `reversible` on the reasoning that cache files are disposable and rebuilt by the application. That is a judgement, not something measured; a lead may prefer `irreversible` (R3, two approvers) once a real backend exists.
- **Size limits.** String values are limited to 64 characters of a narrow set; a lever that needs more (a host name with a space, a free-text reason) is out of scope by design.
- The shared mock folder is committed state: running the real runner on the default `BashBridge()` changes files under `levers/bash/mock`. Tests always use copies.
