# B-42 Runner: blast-radius caps and per-client audit chains

Status: **built** (`core/levers/caps.py`, `core/audit/router.py`, `core/levers/runner.py`, `core/levers/models.py`, `core/levers/__main__.py`, `core/queue/store.py`, `ui/app.py`, `tests/py/levers/test_b42_caps.py`). Offline, mock tenant, synthetic data only. Not run against a real tenant.

> Independently built prototype. Not affiliated with any vendor's or real company's systems. Synthetic data only.

Inventory: `W-TOOL-01`, `W-CMP-01`. Controls: `C-32`, `C-39`, `C-27`, `C-08`. Depends on `B-28`. Standards: `STD-LV`, `STD-AU`, `STD-ID`, `STD-TS`. Decisions in force: D6-08, RQ-13, HO-6, SL-01.

## Why

One runaway or one mistake must not spread across 300 tenants. Caps limit how much one lever can do in an hour and in a day, one audit chain per client lets a client's evidence be handed over without anyone else's, a time window keeps risky changes inside hours the client agreed, and a pre-authorized containment lets an on-call lead stop an account compromise at 2 a.m. with a second look due the next business day.

## Registry fields (all optional; the registry stays version 1)

```json
{
  "name": "user.disable",
  "caps": {"targets_per_run": 1, "executes_per_client_per_hour": 10, "clients_per_day": 20},
  "window": "business-hours",
  "preauthorized_containment": true
}
```

- `caps`: all three numbers, each an integer of at least 1; an unknown key, a missing key or a zero fails the load. A write lever without `caps` gets the default for its risk class (`DEFAULT_CAPS` in `core/levers/caps.py`: R1 25/60/50, R2 10/30/25, R3 5/10/10), and the denial says `(default)` or `(registry)`.
- `window`: `business-hours` or `maintenance`; write levers only.
- `preauthorized_containment`: write levers only, never used for an `irreversible` one: the registry loads the flag (an existing B-01 test makes `user.disable` irreversible and expects a load), and the runner refuses the path in code and says so in the denial.
- Shipped: `user.disable` and `user.revoke-sessions` carry caps and `preauthorized_containment: true`; `user.enable` and `user.set-properties` carry caps. No shipped lever carries `window` yet; flagging one is a registry edit plus the client record keys below.

## Client record keys (read by `RunnerPolicy(client_records=...)`)

```json
{
  "contoso-dental": {
    "time_zone": "America/Los_Angeles",
    "business_hours": {"days": ["mon", "tue", "wed", "thu", "fri"], "start": "08:00", "end": "17:00"},
    "maintenance_window": {"days": ["sun"], "start": "22:00", "end": "02:00"},
    "containment_preauthorized": true
  }
}
```

- `time_zone` is an IANA name or a fixed `UTC+HH:MM` / `UTC-HH:MM`. Whether IANA names resolve depends on `tzdata` being installed; if not, the window is refused with `time_zone ... is not known on this machine`.
- A window is days plus a daily `start` and `end` (24-hour `HH:MM`, end exclusive). A maintenance window may run past midnight (end before start); business hours may not.
- A missing or invalid window or time zone is refused with a plain reason, never defaulted. `containment_preauthorized` must be `true` or `false`; anything else fails the policy load.
- `schemas/client.schema.json` does not list these keys yet (it is closed), so a real client file carrying them fails that schema until a later item adds them.

## Rules

- **Order on an execute of a write lever**, inside the per-client lock and before anything is applied: replay guard (B-28), window, caps, second review opened, then the run. A denial writes one audit record with `result.kind` (`window-denied`, `cap-denied`, `cap-unreadable`, `review-failed`).
- **Counting.** The ledger counts audit records with `mode: execute` and a status other than `denied`, read from the client's chain (hour) and the client chains modified today (day, UTC). A denied call is not counted. The hour is the 60 minutes before the runner's clock.
- **Override.** `Approval.window_override` is a short name (`^[a-z0-9][a-z0-9-]{0,39}$`), never free text. It lets the call through, including for a client with no window, and the audit record keeps `window_override: {name, window, bypassed}`. It is recorded only when it was needed.
- **Containment.** With the lever flag, the client flag, valid `business_hours` and `time_zone`, and an approval marked `on_call`, one approval replaces the R3 default of two. A lever `min_approvers` or a client `approver_minimum` above the default still applies. Sign-in (R2/R3) and `verification` are not relaxed. The runner opens a second review due at the end of business hours on the next business day (the next day listed in `business_hours`; holidays are not modelled), writes it to `<audit>/_reviews.jsonl` and audits it. If any condition is missing, the normal count applies and the denial says which condition.
- **Second review.** `LeverRunner.complete_review(id, identity)` needs a lead scoped to the client who is neither the on-call approver nor the requester. A containment that changed nothing voids its review (audited). `LeverRunner.check_reviews(now)` audits each overdue review once, to `_msp.jsonl` (`result.kind: second-review-overdue`), and returns every overdue one.
- **Alert.** Here "alert" means the audit record, the banner on the pending and audit pages, and exit code 1 from `python -m core.levers reviews`. Sending it outward (chat, email, PSA) is a later item.
- **Router.** `AuditRouter(dir)` has the same `append` and `path` as `AuditLog`. A valid client id goes to `<dir>/<client>.jsonl` with its own `.head`; no client, MSP-level events and any id that is not a safe file name (`../x`, `con`, uppercase, over 63 characters) go to `_msp.jsonl`. `export_client` copies one chain and its head, nothing else. Appends hold a cross-process lock (`<log>.lock`); a lock not had within the timeout raises `AuditError`.
- **State folder layout** (`open_queue`, the CLI): `<state>/audit/<client>.jsonl`, `<state>/audit/_msp.jsonl`, `<state>/audit/pauses.json`, `<state>/audit/_reviews.jsonl`. Older state with `<state>/audit.jsonl` is not migrated and not read.

## CLI

`python -m core.levers verify | export --client C --out DIR | reviews | complete-review ID --as LEAD`, and `--clients FILE [--demo]` plus `invoke ... --on-call --window-override NAME` to exercise B42-4 and B42-5. `verify` and `reviews` exit 1 when a chain is broken or a review is overdue.

## Limits and open points

- Second-review and cap records use existing audit `event` and `mode` values (`proposal.decide` / `approve`), with the meaning in `result.kind`, because `core/audit/chain.py` is not in this item. A `review.*` event belongs to a later item.
- `targets_per_run` counts list-valued parameters; `ParamSpec` has no list type yet, so every real call is one target and the check is proved on the ledger directly.
- The cap check and the execute are atomic inside one process (the per-client lock) but not across processes: two processes can both pass the check in the same instant. The audit append itself is safe across processes.
- The day count reads every client chain modified today; at 300 clients that is 300 small reads per capped execute. An index file would remove it; not built.
- The on-call mark is asserted on the approval by a lead; there is no on-call roster to check it against.
