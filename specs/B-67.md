# B-67 Patch review pack, compliance report, failed-patch triage, server windows, firmware report

Status: **mocked** (workflow, CLI, fixtures, tests; no RMM, Intune or vendor call is made). Reports and drafts only: nothing is approved, deployed, scheduled, sent or upgraded. Synthetic data only.

> Independently built prototype. Not affiliated with any vendor's or real company's systems. Synthetic data only.

Inventory: `W-PAT-01` (monthly patch review and ring approval), `W-PAT-02` (patch compliance per client), `W-PAT-03` (failed patch remediation), `W-PAT-06` (server patch windows and client notice), `W-PAT-07` (network device firmware). Controls: `C-21` (output reconciliation, no invented numbers), `C-05` (changes are proposals first), `C-37` (change enablement: ring approval is a person's decision). Depends on `B-61` (RMM mock adapter: the client's own device list). Standards: `STD-DC`, `STD-TS`, `STD-FX`.

## Why

Patching becomes a reviewed monthly rhythm with proof per client. Today the release notes are read by hand, the compliance numbers come from a cleaned-up RMM export and disagree between tools, the same failed-patch fix is applied by hand hundreds of times, and a server reboot lands in business hours. Here one command per client writes one pack: the releases by ring with their known issues for a human to approve, the compliance counts, the failures grouped by error code with the lever a technician would ask for, a server window with a notice draft, and a firmware version report. A person decides every step.

## Behaviour

`uv run --frozen python -m workflows.patching build <client> [--out <dir>]` writes `<out>/<cycle>/<client>.json` and `<client>.md`, each with a `.sha256` sidecar (`sha256sum` format). `verify <file>` re-hashes a file against its sidecar (exit 0 match, 1 mismatch, 2 bad input). `clients` lists the clients that have patch fixtures. Default `<out>` is `build/patching`.

- **Inputs.** `fixtures/patches/releases.json` (the cycle's released updates, rings, known issues), `fixtures/patches/<client>.json` (per-device update state, server window, network devices), and that client's device list read through `adapters.rmm` (`RmmMock.for_fixture`, B-61). `workflows/patching/config.json` holds the thresholds and the error-code table. The date is the fixture's `as_of`, never the clock (STD-TS-4).
- **Outputs are hashed.** JSON is canonical (sorted keys, two-space indent, ASCII, one trailing newline), so the same inputs give the same bytes. The Markdown is rendered from the JSON and ends with the JSON's SHA-256. The JSON lists the SHA-256 of every source file it read.
- **Read-only, proposal-only.** The module imports no lever runner, process, network or socket code. Every proposal carries `deployed: false`; every approval field is `null` until a person fills it in elsewhere.

### Review pack (B67-1)

`review_pack.updates[]`: one row per released update with KB id, title, classification, product, release date, severity, the known issues from the fixture (id, summary, status, `fixed_in`), the rings it targets (the rings whose products include its product), how many of this client's devices have it installed, pending, failed or not reported, one `proposed_action` per ring with the reason, and empty `decision` and `approver` fields. `by_ring` groups the updates by ring in ring order. Rules for `proposed_action`, in order: a non-required classification is `defer` (not a security or servicing-stack update); an open known issue is `hold` (a person must read it); a known issue whose status is `fixed` and `fixed_in` is also in the release list is not open; otherwise `approve-first-ring` for the first ring of its product and `promote-after-soak` for later rings. These are proposals: promoting to a later ring is an engineer's decision (C-37). Free text from the fixture (known-issue summaries) goes through `core.guard.detect_injection`; flagged text is replaced by `(text withheld: injection signs)` and counted.

### Compliance (B67-1)

A device is **required** to have every update whose classification is in `required_classifications`, whose product matches the device's product (mapped from the RMM `operatingSystem` string) and which was released at least `grace_days` before `as_of`. Each RMM device of the client ends in exactly one status: `compliant`, `non-compliant` (a required update is not installed), `stale` (not seen for `stale_days`; listed and excluded from the rate) or `no-patch-data` (no patch record, or its OS maps to no product). `counts.rmm_devices` equals the sum of the four, and equals the length of the RMM device list; the rate is `compliant / (compliant + non-compliant)` as a fraction and a one-decimal percentage. Patch records for a device that is not in this client's RMM site (including a decoy of another client) are never looked up elsewhere: they are counted in `patch_records_unmatched` and named nowhere.

### Failed-patch triage (B67-2)

`failed_patches.groups[]`: every `failed` update row of an evaluated (not stale) device grouped by `error_code`: count of rows, device hostnames, KBs, the meaning (UNVERIFIED, from the config table), and `suggested_lever` with `lever_status`: `registered` when the name is in `levers/registry.json` plus its `registry.d`, else `proposed (not in registry)`. An error code not in the table is grouped too, with no lever and `manual triage`. Error text from the fixture is never copied; only the code is used. A technician asks for the retry per batch; this module runs nothing.

### Server windows (B67-2)

`server_windows`: every RMM device of category `Server` with the client's declared window (weekday, local start, duration, fixed UTC offset): the first date on that weekday at least `notice_lead_days` after `as_of`. Each server lists the required updates still missing, whether a reboot is expected, and the read-only post-checks (service names) from the fixture. `notice_draft` is a client notice in plain text with `status: "draft - not sent"` and `requires: "lead approval, then a person sends it"`. A client with no server gets no window and no draft. The notice names only that client's servers and declared services.

### Firmware report (B67-3)

`firmware.devices[]`: each network device (firewall, switch, access point) with vendor, model, installed version, the latest version the fixture knows, the advisory fixed-in version when there is one, and a `status`: `advisory-open` (installed is older than the advisory fix), `behind`, `current` or `unknown` (a version that is not dotted numbers is not compared). The section has `automation: "none"` and no lever, no schedule and no upgrade step; a device that is behind says `a person plans and performs the upgrade`. Network firmware is never upgraded by automation (R3).

## Acceptance

- **B67-1** monthly review pack lists released updates by ring with known issues (fixture) for a human approval; compliance per client reconciles to the fixture
- **B67-2** failed patches are grouped by error code with a suggested remediation lever; server windows produce a client notice draft
- **B67-3** network firmware is a version report only (never upgraded by automation)

Tests: `tests/py/patching/test_b67_patching.py` (`uv run --frozen pytest -p no:cacheprovider tests/py/patching`), functions named `test_b67_<k>_...`. Counts are recomputed from the raw fixture files in the tests without using the module's own logic.

## Known limits

- UNVERIFIED: how a real RMM or Intune reports patch state, update classification, rings or install errors. `fixtures/patches/` is a neutral shape of this repo; no vendor schema is claimed (`fixtures/patches/SOURCES.md`). The fixture KB ids (`KB-SYN-*`) are invented and match no real update.
- UNVERIFIED: the meaning of each error code in `config.json` is written from general knowledge, with no vendor page opened. A wrong meaning changes the text of a suggestion, not a count.
- The suggested levers are names. At this commit none of the device remediation levers is in the registry (they belong to B-62), so every suggestion says `proposed (not in registry)` until the registry has it; nothing here can run one.
- Product is mapped from the RMM OS string with a small table (Windows 11, Windows Server 2022); other systems are `no-patch-data`. No Intune compliance state, no update ring policy from a real tenant, no third-party application patching (B-63), no emergency patching (B-47).
- The server window is a fixed UTC offset from the fixture; daylight saving, holidays and client business hours (B-62 / B42-4) are not modelled. The notice is plain text, not a template in `workflows/notify`.
- Known-issue and "fixed in" data is the fixture author's, not a vendor feed. No model, no eval and no accuracy claim; all figures are fixture-based.
- The pack is a file in `build/`. It is not written to an audit chain, because it changes no state and has no actor beyond the person who runs it.
