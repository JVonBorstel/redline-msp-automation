# B-84 Load, failure and retry tests; eval gates in CI

Status: **built** (load/failure harness, tests, benchmark script, eval-gate definitions and runner) on **synthetic data and a synthetic adapter**. The CI workflow is **proposed only**: `docs/changes/B-84.ci-eval-gate.yml` for the owner to apply; nothing under `.github/` was touched.

> Independently built prototype. Not affiliated with any vendor's or real company's systems. Synthetic data only. Every number here is fixture-based and, for timings, from one machine.

Inventory: `W-TOOL-04`, `W-TOOL-07`. Controls: `C-41`, `C-17`, `C-18`. Depends on `B-82` (SQLite queue and audit store); also uses `B-80` (circuit breaker), `B-78` (routing eval), and the existing guard evals. Standard: `STD-TS`.

## Why

Quality is enforced by CI, not remembered. B-82 made many leads and many jobs possible without a forked chain; this item shows it under load and under failure, and turns the eval reports into thresholds that fail a run.

## Behaviour

### The harness (`evals/load/harness.py`)

A model of "clients submit lever calls; workers claim them, call an adapter, write an audit record, acknowledge". The queue (`SqliteJobQueue`), audit store (`SqliteAuditStore`) and breaker (`CircuitBreaker`) are the real classes. The lever call and the adapter are synthetic: the adapter is a SQLite file that applies an effect once per `(client, idempotency key)`. The real `LeverRunner` is **not** in the loop.

- **Deterministic.** A fault is a pure function of `(seed, client, key, attempt)`; time is an injected `SimClock` that only the driver advances; randomness is `random.Random(seed)`. Same seed gives the same outcomes and the same audit chain heads (`LoadReport.digest`).
- **Fault kinds per attempt:** `timeout` (adapter silent), `adapter_crash` (adapter raises), `worker_crash_before` (worker dies after claiming), `worker_crash_after` (worker dies after the effect, before acknowledging). A poison job fails every attempt. An outage window makes every call time out.
- **Oracle.** `FaultPlan.expected(client, key, max_attempts)` gives each job's ending, attempt count, whether its effect was applied and how many audit records it leaves. The single-threaded run checks every job against it (`oracle_mismatches`).
- **Invariants checked after a run:** every audit chain verifies (`chain_breaks`); records written equal records in each chain (`audit_count_mismatches`); no result, audit record or effect carries another client's marker (`cross_client_results`; the same key text recurs in every client on purpose); no effect applied twice (`double_applies`); every job ended `done` or `dead` (`lost_jobs`); a repeated key collapsed to one job and a changed request under a used key was refused (`submission_violations`).
- **Two drivers.** `run_simulation` is single-threaded and exact. `run_threaded` uses real threads on shared stores; it asserts invariants only because its schedule is not deterministic.

### Tests (`tests/py/load/test_b84_load.py`, `tests/py/load/test_b84_bench.py`, `tests/py/tools/test_b84_eval_gate.py`)

- **Load:** 600 calls over 300 clients with all four fault kinds and poison jobs; opt-in 10,000 calls over 300 clients (`B84_FULL_SCALE=1`); same seed same run, different seed different run; every job ends as the oracle says; threads contending for the same clients; the verifier still catches a rewritten line after a load run (a clean report that could never fail would prove nothing).
- **Failure and retry, exact timelines on the injected clock:** timeout then adapter crash then success with doubling backoff and no early claim; retries stop at `max_attempts` and the job goes to the dead letters, then a person's `requeue_dead` completes it once; worker crash before the call (nothing applied, lease expiry retries it); worker crash after the effect (replay, one application, three deliveries); the same crash script against a non-idempotent adapter double-applies (the control that shows the detector can fail); a zombie worker that lost its lease gets `LeaseLost` on `complete` and `fail`; a job that keeps killing its worker is dead-lettered by lease expiry and audited once; a poison job does not block the client's other jobs; a submission storm makes one job per key and keys are per client; a worker never sees another client's job.
- **Breaker with the queue:** during a 30 s simulated outage the run with the B-80 breaker dead-letters nothing, the same run without it dead-letters work; the breaker's half-open probe slot is handed back when there is nothing to claim.
- **Real process death:** a child process applies the effect and `os._exit(3)`s before acknowledging; the parent jumps its clock past the lease, reclaims, and the effect is applied once with two deliveries.

### Benchmark (`tools/bench_load.py`)

Runs `clean-sequential`, `faulty-sequential` and `faulty-threaded` on fresh temporary SQLite files and writes `evals/load/bench_report.json` and `.md`: invariants, wall time, calls per second, and p50/p95/p99/max latency of each store call. The report is labelled "measured on this machine only, once; fixture-based; not a capacity claim", lists its caveats, and names no host or user. `--jobs 10000 --clients 300` is the B84-2 size. Timings are never gated.

### Eval gates (`evals/gates.json`, `tools/eval_gate.py`)

- `evals/gates.json` is data: `version`, `basis` (must say fixture-based), `gates[]`. Each gate has `id`, `workflow`, `source`, `metric`, `op` (`>=` or `<=`), `threshold` and a `why` (including the value measured when it was set).
- Sources: `routing` (B-78: cascade accuracy in-sample and holdout, cost against always-strong, per-tier accuracy), `injection` (precision, recall, false negatives), `redaction` (leaks, route refusal and success rates), `phishing` (verdict accuracy, injected-email flag rate, benign flagged), `load` (the invariants above on a seeded 120-call run).
- `uv run --frozen python tools/eval_gate.py` runs the sources and prints PASS/FAIL per gate; exit 0 all passed, 1 any failed, 2 bad usage or config. `--source` limits to a source, `--json` prints verdicts, `--results file.json` gates metrics that a CI step already produced and runs nothing.
- A missing source, a missing metric, NaN, infinity, a boolean or a string **fails** its gate. A source that raises fails its gates and the verdict names the exception class. The gate file is validated strictly (unknown keys, duplicate ids, unknown source or op, non-numeric threshold are errors).
- `docs/changes/B-84.ci-eval-gate.yml` is the proposed workflow (read-only token). The owner decides whether to add it.

- **B84-2** load test: 10,000 synthetic lever calls across 300 clients complete with zero chain breaks and zero cross-client results. Built; the 10,000-call test is opt-in and was run once on 2026-10-27 (see `docs/changes/B-84.md` for the result). The default run uses the same code at 600 calls over the same 300 clients. ## Calls versus jobs

A "synthetic lever call" here is one job through the queue. The count asked for (10,000) is the number of submissions of distinct calls; about 4% are submitted twice (collapsed to one job) and about 1% are re-sent with a changed request (refused), so repeat submissions are extra traffic on top of the 10,000.

## Findings from building it

- **A dead letter can have its effect applied.** A worker that dies after the effect on its last attempt leaves a job that is dead-lettered although the change happened (`dead_but_applied` in the report). Requeuing it is safe only because the adapter honours the idempotency key; a person looking at the dead letters needs to know that.
- **A crash leaves no audit record.** Only a stuck lease shows it. The audit shows the attempt after it. A write-ahead "intent" record before the effect would close this; it is not built (one more commit per call).
- **No release-without-penalty.** `claim` counts an attempt. A worker that claims during a provider outage burns the retry budget, so the harness asks the breaker before claiming. A queue method that returns a job unclaimed would be cleaner; not added because B-82's store is not this item's to change.
- **No reaper.** A job whose lease expires on its last attempt is dead-lettered only when something next calls `claim` for that client. The harness records it then. A deployment needs a periodic claim or a sweep.

## Known limits

- UNVERIFIED: behaviour on Linux or on a CI runner. All measurements and runs were on the author's Windows machine; the proposed workflow has never run on GitHub Actions.
- UNVERIFIED: behaviour with several OS processes writing the same database at this scale. One test uses two processes in sequence; the contention test uses threads.
- The adapter is a stand-in. Real adapters add network time, rate limits and idempotency semantics that may differ (a vendor API may not honour a key at all).
- The real `LeverRunner` (identity, approvals, registry, verification) is not in the loop; its timeout and idempotency behaviour is covered by B-02 and B-28 tests.
- Routing and guard gates inherit the limits of their evals: mock tiers and hand-written corpora by one author. A gate at 0.95 on those sets is a regression alarm, not a quality claim.
- Timings come from one run on one machine with no repeats.
- The thresholds were set from the values measured on 2026-10-27; they are not derived from any requirement.
