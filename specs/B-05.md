# B-05 Triage output shows the impact trace and the verification needed

Status: **built** (triage text and `--json` output, tested). The runner gate that refuses an execute without a recorded verification is `B-02`; the approval page showing the same trace is `B-03`.

> Independently built prototype. Not affiliated with any vendor's or real company's systems. Synthetic data only.

Inventory: `W-SD-02` (ticket triage), `W-SD-07` (escalation with a context package). Controls: `C-14` (model output cannot choose the lever), `C-30` (requester verification), `C-45` (synthetic data, honest labels). Depends on `B-01` (the lever's `impact`, `risk_class` and `verification` fields).

## Why

Step 2 of the demo shows the person behind the proposal before anyone approves it. When triage proposes `user.reset-mfa` for Priya Nair (synthetic, T-3101), the technician and the lead see, in the same output, who a wrong reset hurts at each level and that the caller must be verified by a callback to the number on file first. That callback is the control against help-desk social engineering.

## Behaviour

When, and only when, triage returns a proposal, `TriageResult` (`workflows/triage/triage.py`) carries three fields read from the proposed lever's entry in `levers/registry.json`:

| Field | Value | From |
|---|---|---|
| `who_this_affects` | `{"L1": ..., "L2": ..., "L3": ..., "L4": ...}` | the lever's `impact` (null if the lever has none) |
| `risk_class` | `R1`-`R3` | the lever's `risk_class` |
| `before_approval` | `"call back on the number on file"`, or null | set when the lever's `verification` is `"requester"` |

- Text output (`explain()`) adds, after the proposal and its dry-run diff, a block `Who this affects (<lever>, risk class <R>, from the lever's registry entry):` with one line per level (`L1 one person`, `L2 the client`, `L3 the MSP`, `L4 the community`), then `Before approval: call back on the number on file, never a number given in the ticket (the lever requires requester verification, C-30).`
- `--json` output carries the same three keys at the top level; they are null when there is no proposal.
- No ticket text (subject, body, requester-supplied numbers) is ever copied into these fields: they are a lookup on the lever name, and the lever name comes from the fixed category rule (`C-14`), never from the model or the ticket.
- A flagged ticket gets no lever, so no trace. No other triage behaviour changes: category, priority, queue, why, data used, proposal and dry-run are as before.

## Acceptance

- **B05-1** For T-3101 the triage output adds `who this affects` (the lever's L1-L4 lines, in order, equal to the registry entry) and `before approval: call back on the number on file`, because `user.reset-mfa` declares `verification: "requester"` (the check is case-insensitive on the labels). A lever without `verification` shows the impact but no callback line; a lever built without `impact` still proposes but shows no trace. The CLI text output shows both.
- **B05-2** The 8 injection tickets still get no lever and no trace (all three fields null, no trace lines in the text). The number of proposals is unchanged (one per clean ticket that expects a lever) and every proposal carries its lever's trace. `evals/triage/report.md` is regenerated byte-for-byte unchanged, and the SA-1 to SA-4 tests in `tests/phase1/test_triage.py` (7 tests) still pass.
- **B05-3** The JSON output (`to_json()` and `--json`) carries the same fields as the text. No ticket free text is copied into them: a ticket stuffed with its own marker text and a callback number gets exactly the registry values, and across the fixture set every trace equals its lever's registry entry.

Tests: `tests/py/triage/test_b05_trace.py` (run with `uv run --frozen pytest tests/py/triage -o addopts=`; `pyproject.toml` limits the default `pytest` run to `tests/phase1` until `B-06` adds `tests/py/Test-Py.ps1`).
