# B-01 Registry fields: risk class, undo, impact trace, verification rule

Status: **built** (registry fields and load rules, tested). Runner enforcement of `verification` is `B-02`; showing `impact` and `undo` on the approval page is `B-03`.

> Independently built prototype. Not affiliated with any vendor's or real company's systems. Synthetic data only.

Inventory: `W-TOOL-01`, `W-GOV-03`, `W-IDM-04`. Controls: `C-29` (risk class on every lever), `C-30` (requester verification), `C-02` (schema validation), `C-01` (registry, default deny). Decision: `D-024` (identity changes are `R3`).

## Why

The lever already carries its permissions. This item puts two more things on it, where a reviewer reads them before a lead approves:

- the **trace** from one person to the community (`impact` L1-L4) and how bad a mistake is (`risk_class`, `reversibility`, `undo`);
- the **social-engineering rule**: a lever that changes someone's sign-in says it needs the requester verified out of band (`verification: "requester"`), and an approval can carry how that was done.

## Fields (all in `levers/registry.json`, `LeverDef` in `core/levers/models.py`)

| Field | Values | Default when absent | Rule |
|---|---|---|---|
| `risk_class` | `R0`-`R3` (`docs/map/05-governance.md` 6.1) | `R0` for a read lever; none for a write lever | read is `R0`; write is `R1`-`R3`; required on write levers when the registry file is loaded |
| `reversibility` | `reversible`, `irreversible`, `n/a` | `n/a` for read, `reversible` for write | read is `n/a`; write is `reversible` or `irreversible`; `irreversible` must be `R3` and has no `undo` |
| `undo` | a lever name or `null` | `null` | must name another registered **write** lever (checked when the registry is built); `null` means the undo is manual and documented |
| `lever_version` | integer >= 1 | `1` | bumped when behaviour changes (STD-LV-10) |
| `impact` | object `{L1, L2, L3, L4}` | none | each one line (1-200 characters, no line break); required on write levers when the registry file is loaded |
| `verification` | `"requester"` or `null` | `null` | write levers only |

`Approval` (same module) gains `verification`: optional object `{method, by, at, ref}`. `method` is one of `callback-on-file`, `in-person`, `manager-confirmed`, `finding-reference`; `by` is the identity id that verified (1-64 characters); `at` is a timezone-aware ISO 8601 time; `ref` is a short reference without spaces (required for `finding-reference`, optional otherwise). Unknown keys are rejected.

Why the two-step "required on load" rule: `B01-4` says the Phase 1 tests pass unchanged, and they build test write levers in code without the new fields. The registry **file** is the only source the program loads levers from (`Registry.load`), so the requirement is enforced there, with an error that names the lever. A lever built in code is checked for class agreement (`B01-2`) but not for presence.

## Acceptance

- **B01-1** Every lever in `levers/registry.json` declares `risk_class` (R0-R3), `reversibility`, `undo` (lever name or null), `lever_version` and `impact` (one line each for L1-L4). A write lever without `risk_class` or `impact` fails `Registry.load` with a `RegistryError` whose message names the lever. An impact line that is empty, longer than 200 characters or contains a line break fails the load.
- **B01-2** A `read` lever declaring R1-R3, or a `write` lever declaring R0, fails the load (class and risk must agree). Also: a read lever not `n/a`, a write lever `n/a`, an `irreversible` lever below R3 or with an `undo`, and an `undo` that names an unknown lever, a read lever or itself, each fail the load with an error naming the lever.
- **B01-3** `verification: "requester"` is accepted on write levers only (a read lever declaring it fails the load; any other value fails). `Approval` accepts an optional `verification` object `{method, by, at, ref}`; `method` outside the four values, a missing `by` or `at`, a naive `at`, an extra key, or `finding-reference` without `ref` is rejected. An approval without `verification` behaves exactly as before.
- **B01-4** All tests in `tests/phase1` pass unchanged; the four levers keep their names, params, roles and approval rules.
