# B-03 Approval page: verification capture, scoped listing, diff, undo and impact shown

Status: **built** (queue, seed CLI, page, tests).

> Independently built prototype. Not affiliated with any vendor's or real company's systems. Synthetic data only.

Inventory: `W-TOOL-06`, `W-IDM-02`, `W-IDM-04`. Controls: `C-30` (requester verification), `C-06`, `C-07` (human approval, explainable), `C-19` (tenant scoping), `C-27`. Depends on `B-01` (the `verification`, `undo` and `impact` fields) and `B-02` (the runner refuses an unverified identity execute). Drift items closed: `DR-12` (listing not scoped), `DR-15` (seed without a dry-run). Standards: STD-PR, STD-ID, STD-SC, STD-AU, STD-TS.

## Why

The lead's approval is the last human step before a person's sign-in changes. B-02 made the runner refuse an identity change with no recorded verification; this item makes the page the place where the lead records it, sees only their own clients, and sees exactly what will happen to which person before deciding.

## Behaviour

### Scoped listing (B03-1)

- `ProposalQueue.list(status=None, viewer=None)`. With `viewer`, only proposals whose client is in that identity's own list. An unknown viewer gets nothing (fail closed). Without `viewer` (CLI, tests) the whole queue, as before.
- CLI: `python -m core.queue list [--status S] [--viewer ID]`.
- Page: `GET /?as=<lead>` picks the demo sign-in (a GET form with the lead list); the default is the first lead by id. A viewer that is not a lead is a 400. The pending cards, the Decided table and the outcome banner all use the scoped list. Each decision form carries the viewer as a hidden `actor`.
- A `POST /decide` for a client outside the actor's list is refused (403) by the queue's existing check and audited (`mode` = `approve`/`reject`, `status` = `denied`); the proposal stays pending and the tenant is untouched.

### Verification capture (B03-2)

- Each pending proposal for a lever with `verification: "requester"` has a fieldset with two selects and nothing else: `verified` (the methods in `VerificationMethod`: `callback-on-file`, `in-person`, `manager-confirmed`, `finding-reference`) and `number_source` (`psa-contact`, `onboarding-form`, `client-contact-list`; `NUMBER_ON_FILE_SOURCES` in `core/queue/store.py`). There is no text field.
- Server-side, on approve:
  - a requester-verified lever with no method is refused;
  - a method outside the list is refused;
  - `callback-on-file` without a source from the list is refused; a source with any other method is refused; a source with no method is refused;
  - any form field other than `csrf`, `actor`, `act`, `verified`, `number_source` is refused before anything else (so a typed phone number never reaches the queue or the audit log).
  Each refusal (after the CSRF check) is a 400, writes one audit record through `ProposalQueue.refuse` (`mode` `approve`, `status` `denied`, the reason) and leaves the proposal pending. If the actor may not decide at all, that denial is recorded instead (403).
- An accepted verification is `Verification(method, by=<deciding lead>, at=now, ref)`. `ref` is `number-on-file:<source>` for a callback, the proposal's `ref` for `finding-reference`, and empty otherwise. It is never free text.
- The decision record holds it: `Proposal.verification` (new, optional) is set on the `approved` and the final `executed`/`failed` lines of `queue.jsonl`, and the runner's execute record carries it as `result.verification` (B-02). A pending or rejected proposal never has one. The outcome banner names the method, the ref and the verifier.
- Reject needs no verification.

### What the lead sees (B03-3)

Each pending proposal is a card that shows:

- **Person affected**: the `upn` parameter (or `no single person in the parameters`).
- **What it means for them (L1)**: the lever's `impact.L1` line from the registry.
- **What will change (dry-run)**: the latest allowed dry-run audit record for this exact lever, client and params (canonical JSON), with its seq, agent and time. The changes are the audit's masked copy (DR-02), so phone numbers and method details never show. Removals read `-> removed`, additions `added ->`. With no such record: `No dry-run on record for this exact action. Do not approve it.`
- **Undo**: `undo lever: <name>` when the registry names one, else `no undo lever: manual undo`, with the reversibility.
- Parameters, source and ref, requester and the reason.

The page still has no script; every response carries the same Content-Security-Policy; every value is HTML-escaped.

### Seed through the runner (B03-4)

- `ProposalQueue.propose(proposal, agent)`: a proposal already in the queue is returned unchanged with no new dry-run; otherwise it is dry-run through the runner as `agent` (one audit record) and queued only if the dry-run is `ok`. A refused dry-run raises `QueueError` and nothing is queued.
- `python -m core.queue seed --demo` proposes each demo proposal as `triage-bot` and prints the dry-run seq (`already queued` on a re-run). It exits 1 if any dry-run was refused (for example, a paused lever).
- SC-1, SC-2 and SC-3 still pass on a seeded state.

## Acceptance

- **B03-1** a lead sees only proposals for clients in their own list (DR-12); a decide POST for another client is refused and audited.
- **B03-2** for a lever with `verification: "requester"`, approve is refused server-side unless the form carries a method from the allowed list and, for callback-on-file, the number-on-file source (never the number itself); the decision record holds the verification.
- **B03-3** each pending proposal shows the dry-run diff, the undo lever (or `no undo lever: manual undo`), the affected person's UPN and the lever's L1 impact line; the page still sends a CSP with no script and every value is escaped.
- **B03-4** `seed --demo` sends each seeded proposal through the runner as triage-bot in dry-run first (DR-15), so every seeded proposal has a dry-run audit record; SC-1, SC-2 and SC-3 still pass.

Tests: `tests/py/queue/test_b03_approval_page.py`, one or more `test_b03_<k>_...` per id. Run with `uv run --frozen pytest tests/py/queue`.

## Out of scope

- Real sign-in (STD-ID-7): the viewer picker is a demo sign-in. Anyone at the page can pick any lead.
- Proving the callback happened, or limiting the verification's age (an attestation, as in B-02).
- Showing the full, unmasked diff to the lead; refusing an approve that has no dry-run record (shown as a warning only).
- `workflows/triage --enqueue` still uses `add` after its own dry-run (the page finds that dry-run in the audit log); moving it onto `propose` belongs to the triage owner.
