# B-77 MSP client onboarding discovery, offboarding checklist, migration pre-flight checks

Status: **mocked** (Python workflow over synthetic fixtures, CLI, human runbook, tests). Read-only: it changes no tenant, device or licence and registers no lever. Synthetic data only.

> Independently built prototype. Not affiliated with any vendor's or real company's systems. Synthetic data only.

Inventory: `W-PRJ-01` (new client onboarding: discovery and baseline), `W-PRJ-02` (client offboarding from the MSP, kept human), `W-PRJ-03` (Microsoft 365 migrations; executing them is `NN-04`). Controls: `C-20` (read levers cannot write), `C-27` (tenant isolation), `C-45` (synthetic data only and honest labels). Standards: `STD-DC`, `STD-TS`. Depends on nothing; reuses `B-38` (baseline findings reader), `B-55` (data classes) and `B-61` (device reconciliation; on main since PR #62).

## Why

A new client starts with a clear baseline; a departing client leaves cleanly. Today discovery for a new client takes weeks and gaps get missed (`W-PRJ-01`); when a contract ends, access must truly end (`W-PRJ-02`); a migration loses data when a mailbox is too big, a seat is missing or an address already exists (`W-PRJ-03`).

## Behaviour

- **Package** `workflows/client_lifecycle/` (`discovery.py`, `preflight.py`, `__main__.py`, `config.json`, `data/migrations/<client>.json`, `README.md`). No model is called. Nothing here imports the lever runner, the approval queue or an audit writer.
- **Discovery pack** `discover(client, out_dir, as_of=...)` runs three read-only steps for one client and writes `<out>/<client>/discovery.json`:
  1. **baseline**: runs `Invoke-TenantBaseline -Tenant <client>` (the read-only Slice B module) in a child `pwsh` with a fixed command; the client id and output folder reach it as environment values, never as command text. Its `findings.json` is read with the B-38 reader, which refuses a file for another tenant. Each finding becomes a gap; its fix lever is shown as "proposal only".
  2. **devices**: the B-61 device reconciliation (`workflows.device_reconcile`) over the client's RMM, Intune and PSA mocks. Each mismatch (only in one system, stale, duplicate) becomes a gap. If B-61 is absent, the step is `not-run` with that reason. **Dates:** stale ages are measured against the RMM snapshot's own pinned time (B-61's rule), not `--as-of`, so the device step's `counts.as_of` can differ from the pack-level `as_of` (which dates the licence retention windows); both are printed.
  3. **licences**: a licence report from `fixtures/tenant/<client>/licenses.json` and the client's directory (`fixtures/tenant/<client>.json`): seats per SKU (enabled, assigned, free), and gaps for over-assigned SKUs, unused seats, holders not in the directory (with the retention window, if any), disabled holders, enabled users with no licence and assignments to an unknown SKU. Data that is missing or invalid is a gap, never a guess: a SKU whose `prepaidUnits.enabled` is missing or not a whole number >= 0 is a High `LIC-SEATS` gap ("seat count unknown") and gets no over/unused verdict; an unreadable `retentionEndsOn` is a High `LIC-BADDATE` gap for that assignment and does not stop the pack; a directory user whose `accountEnabled` is not true/false is a Medium `LIC-ACCOUNTSTATE` gap (not assumed enabled); a directory entry or assignment with no `userPrincipalName` is a Medium `LIC-NOUPN` gap.
  A step that cannot run (no `pwsh`, unknown tenant, no fixture, a file for another client) is `not-run` or `failed` with the reason and is itself listed as a High gap: missing data is a gap, never an all clear. The pack carries `read_only: true`, the steps, every gap with a stable id, counts by severity, the B-55 data class of its own text (no client record is read, so the fail-closed floor DC-5 applies unless a shape raises it), and a `sha256` over its body. The date comes from `--as-of` or the baseline config's `asOf`, never the clock.
- **Offboarding checklist** (`docs/runbooks/client-offboarding.md`): a human runbook for ending the MSP relationship: hand back admin credentials, remove GDAP relationships, export documentation, remove RMM agents and other MSP tooling, and confirm in writing. It names roles, never people. Nothing is automated: no lever, no workflow command, no queue source.
- **Migration pre-flight** `preflight(client, plan_path)` (exported by the package as `run_preflight`, so the name does not shadow the submodule) reads a migration plan (`data/migrations/<client>.json`: the mailboxes to move and a read-only snapshot of the destination: domain, mailbox quota, target SKU seats, addresses already in use) and the client's own `mailboxes.json`. Three checks, each `pass` or `fail` with every problem listed:
  - **mailbox-sizes**: every planned mailbox exists in this client's mailbox list and fits the destination quota; total size is shown. A mailbox with no recorded size is a problem (an unknown size does not pass); a size that is present but not a non-negative number raises `PreflightError` (exit 2).
  - **licence-availability**: user mailboxes need a seat in the target SKU (shared mailboxes are counted apart; whether they need a licence is UNVERIFIED and left to a person); free seats = enabled minus assigned. A mailbox with no recipient type is a problem and is counted as needing a seat until a person says otherwise. If the destination has more assigned than enabled, that over-assignment is its own problem (free seats are then 0) and is never shown as a negative free count.
  - **conflicting-addresses**: each mailbox's address at the destination domain is not already in use there and no two planned mailboxes map to the same address.
  `ready` is true only when all three pass. A plan whose `client` is not the requested client is refused. There is no execute step: executing migrations is `NN-04` (not now).
- **CLI**: `python -m workflows.client_lifecycle discover --client <id> [--as-of YYYY-MM-DD] [--out DIR]` and `python -m workflows.client_lifecycle preflight --client <id> [--plan FILE]`. Each prints JSON. Exit 0 = ran (gaps or a failed check are results, listed in the output); 2 = bad input.

## Acceptance

- **B77-1** A discovery pack for a new client runs the baseline, device reconciliation and licence report in read-only mode and lists gaps.
- **B77-2** The MSP offboarding checklist (credentials handed back, GDAP removed, documentation exported) is a human runbook; nothing is automated.
- **B77-3** Migration pre-flight checks (mailbox sizes, licence availability, conflicting addresses) are read-only; executing migrations stays in not-now.

Tests: `tests/py/projects/test_b77_client_lifecycle.py` (every acceptance test is named `test_b77_<k>_...`). The test that runs the real baseline skips when `pwsh` is missing; the tests that run the real B-61 reconciliation skip only if `workflows.device_reconcile` is absent.

## Deviations (for a reviewer to overrule)

- **Device step and B-61.** B-61 (PR #62) was open when this was built and is on main now. The device step imports it at run time and reports `not-run` when it is absent; the not-run path is tested with a stand-in. B-61 is now on main, so the real-module tests run against the real RMM, Intune and PSA mocks and assert `ran` and the gap ids and counts.
- **Migration plan is this repo's own shape.** No vendor migration tool is named (`NN-04` waits for the MSP's tool), so the plan and the destination snapshot are invented, labelled synthetic, and kept beside the workflow.
- **No audit record.** Discovery and pre-flight call no lever, so they write no audit record; the pack's `sha256` and the fixture hashes in the tests are the read-only proof.

## Out of scope

Fixing any gap (each baseline fix stays a dry-run proposal for a lead through B-38 and the levers), running or scheduling a migration (`NN-04`), removing GDAP or agents (human, `W-PRJ-02`), per-user onboarding and offboarding (`B-35`, `B-36`), and a real Graph, RMM or Exchange connection.
