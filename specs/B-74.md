# B-74 Operations metrics, Power BI exports, problem and CSAT analysis

Status: **built** (workflow, CLI, tests). Read-only: it reads fixtures and writes export files under `build/`; no ticket, PSA record or tenant is changed and no problem record is created (the record is only proposed). Synthetic data only. Every figure is **fixture-based**.

> Independently built prototype. Not affiliated with any vendor's or real company's systems. Synthetic data only.

Inventory: `W-RPT-06`, `W-SD-13`, `W-SD-14`, `W-TRN-03`, `W-TRN-04`. Controls: `C-21` (figures recomputed from raw files), `C-41`. Standards: `STD-DC`, `STD-TS`. Never-automate: `NN-03` (no coaching or ranking of technicians from ticket metrics).

## Why

Leadership needs to see where time goes: volumes, SLA attainment, how fast a person gets an answer and can work again, how often tickets reopen, which problems keep coming back, and how users rate the service, per client and across the MSP, in a shape Power BI can import. Nobody is ranked: no export has a per-technician column.

## Behaviour

`python -m workflows.reporting.ops` (module `workflows/reporting/ops/ops.py`):

- **`export <client> --as-of YYYY-MM-DD [--out DIR]`** writes `<out>/<client>/` and **`export --msp --as-of ...`** writes `<out>/_msp/` (default `build/ops-metrics`). Tickets created after the end of `as_of` and CSAT answers submitted after it are left out; the wall clock is never read.
- **Inputs (all committed fixtures, never labels):** `<client>.json` under `fixtures/tickets/` (the one whose tickets carry created times; id, status, created, updated, source, requester, subject, body), the client's PSA SLA in `fixtures/psa/<client>.json` (used only when it has exactly one active SLA), and two synthetic overlays in `workflows/reporting/ops/data/`: `<client>.events.json` (first response time, reopen count, the proposed `user_confirmed_working_at`) and `<client>.csat.json` (a mock CSAT-tool export: ticket id, score 1-5, comment, submitted time; no technician field, D6-21). Topic words, cluster thresholds and CSAT theme words are in `workflows/reporting/ops/config.json`.
- **Definitions.** Hours are wall-clock. `completed` is the ticket's `updated` time when its status is `resolved` (stand-in for the PSA completed date). `first_response_hours` = first response minus created. `completed_hours` = completed minus created. `user_confirmed_working_hours` = proposed `user confirmed working` time minus created (empty when absent). SLA first response met when `first_response_hours <= firstResponseHours`; resolution met when `completed_hours <= resolutionHours`; no SLA (Litware Legal has no PSA mock) gives empty cells and a `no-sla` reason, never a guess. Reopen rate = tickets with `reopen_count >= 1` / tickets resolved or reopened. Mean and median are rounded to 2 places.
- **Tables** (each a `.csv` and a flat `.json` array of the same rows, in `ops.TABLES`): `ticket_facts`, `weekly_metrics`, `summary`, `volume_by_category`, `problem_clusters`, `problem_cluster_tickets`, `csat_weekly`, `csat_themes`. In the MSP export every table has the `client` column and `summary` also has an `ALL` row; the client export has only that client's rows and no MSP-wide row. Every row has `data_basis = fixture-based`.
- **Repeat-problem clusters.** The B-23 topic classifier (`workflows.duplicates.classify`) groups a client's tickets (resolved included, injection-flagged left out and counted) by topic. A topic with at least `cluster_min_tickets` tickets from at least `cluster_min_requesters` people becomes a cluster with a **proposed** problem record: id `PRB-PROPOSED-<client>-<topic>`, a title from the configured topic id, `status = proposed`, no root cause. Nothing creates it; a person decides.
- **CSAT.** Weekly count, mean score, share scoring 4 or 5, response rate (answers / resolved tickets); theme counts from configured words (first matching theme, else `other`). Comments are untrusted text and are never exported.
- **No technician anywhere (B74-3).** The ticket's technician field is never read. `assert_no_person_columns` refuses any table whose column name looks like a person (technician, assignee, resource, owner, agent, staff...), and the data dictionary is built from the same schema as the files.
- **Per-client isolation (B74-4).** Each client is loaded alone; an events or CSAT row for a ticket that is not that client's, or a ticket file for a different client, refuses the export (nothing is written). A client export names no other client.
- **Dictionary and manifest.** `data_dictionary.csv/.json` (table, column, type, unit, description, source). `manifest.json` lists every file's SHA-256 and row count, the source files read (CRLF-normalised hashes), `as_of`, `scope` and the fixture-based label; `manifest.json.sha256` is in `sha256sum` format. Canonical output: same inputs give the same bytes (LF, sorted keys).
- **`verify <dir>`** re-hashes every file against the manifest and the manifest against its sidecar; an extra or missing file fails. Exit 0 ok, 1 mismatch, 2 bad input.

## Acceptance

- **B74-1** flat CSV/JSON tables for Power BI with a data dictionary and a hashed manifest; semantic model in `docs/POWERBI_SEMANTIC_MODEL.md`, files in `docs/EXPORTS.md`.
- **B74-2** repeat-problem clusters per client with a proposed problem record; CSAT by week and theme with counts; volumes, SLA attainment, response/resolution time and reopen rate reconcile to the raw fixtures in a test.
- **B74-3** no export has a technician (or any person) column or value.
- **B74-4** per-person metric is time until the person can work again (completed minus created, plus the proposed confirmed-working field); CSAT is from the mock export only. Per-client data never appears in another client's export.

Tests: `tests/py/reporting/test_b74_ops.py` (`uv run --frozen pytest -p no:cacheprovider tests/py/reporting`), functions named `test_b74_<k>_...`.
