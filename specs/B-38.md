# B-38 Guests, stale accounts and baseline-sourced proposals

Status: **built** (`workflows/baseline_proposals/`, `tests/py/baseline/test_b38_baseline_proposals.py`). Proposes `user.disable`; never executes it. Synthetic data only.

> Independently built prototype. Not affiliated with any vendor's or real company's systems. Synthetic data only.

Inventory: `W-ONB-17`, `W-IDM-11`. Controls: `C-30`, `C-05`, `C-32`. Depends on `B-29`, `B-40`. Standards: `STD-PR`, `STD-LV`, `STD-TS`.

## Why

Dormant accounts (members who stopped signing in, guests whose access ended) stay open doors. The baseline already flags stale members in `findings.json` with `FixLever: user.disable`, but nothing turned those findings into reviewed proposals. This workflow does, one account at a time, through the normal queue, without a bulk change nobody reviewed.

## Behaviour

`plan(client, findings_path, queue=None, config=None, tenant_dir=..., baseline_config=..., as_of=None)` returns a `Plan`:

1. **Inputs.** `findings.json` from `Invoke-TenantBaseline` (each finding checked against `schemas/finding.schema.json`; the file's `tenant` must equal the client), the client's `fixtures/tenant/<client>/guests.json`, and the baseline's own config (`TenantBaseline.config.json`) for the break-glass rule and the client's graph snapshot. A bad file is a loud `BaselineProposalsError`, never an empty result.
2. **Candidates.** Findings with `CheckId` `STALE` and `FixLever` `user.disable`; guests that are enabled and whose `expiresOn` is before the as-of date (the findings' `asOf`, or `--as-of`; the clock is never read). An account in both is proposed once, under its finding id.
3. **Break-glass exclusion.** A UPN starting with `breakGlass.namePrefix`, or a display name matching `breakGlass.candidateDisplayNamePattern`, is never proposed. A finding whose account is not in the client's directory snapshot is skipped, because break-glass cannot be checked.
4. **Order and cap.** Findings by severity then id, then guests by expiry then id. The first `max_proposals_per_client_per_run` become proposals; the rest are `deferred`, each with its ref, UPN and reason, and are not dry-run.
5. **Proposals.** `Proposal.new(source="baseline", ref=<finding id>, lever="user.disable", params={upn, reason})`, dry-run through the runner as `requested_by` (audited, STD-PR-1) and queued pending via `queue.propose`. A dry-run the runner refuses is listed under `skipped` as "not queued: ..." and does not use the cap. Proposals already in the queue are listed under `already_queued` and do not use the cap, so a second run is idempotent and moves on to the next batch.
6. **Verification.** A pending proposal cannot hold a `verification` (`core/queue/store.py`), so each `Proposed` offers `verification(by, at)`: method `finding-reference`, `ref` = the finding id. The lead passes it to `queue.decide`; the result JSON shows the method and ref.
7. **Guest ref.** If the baseline has no finding for an expired guest, the `ref` is the guest record id (`GST-...`), so the approval still has a pointer to record.

`python -m workflows.baseline_proposals --client X --findings PATH [--state DIR] [--as-of DATE]` prints the plan as JSON. Exit 0 = proposed, nothing to do or deferred; 2 = bad input.

## Acceptance

- **B38-1** from findings.json (TenantBaseline) and guest fixtures, the workflow proposes `user.disable` for stale members and expired guests, each with `verification.method: finding-reference` and the finding id
- **B38-2** break-glass accounts are never proposed (pattern from the baseline config)
- **B38-3** at most N proposals per client per run (blast-radius cap from the workflow config), the rest listed as deferred

Tests: `tests/py/baseline/test_b38_baseline_proposals.py`, named `test_b38_<k>_...`.

## Known limits

- `user.disable`'s registry `upn` pattern has no `#`, so a real guest UPN (`..#EXT#@..`) is refused at the dry-run and reported under `skipped`. Fixing it is a registry change outside this item.
- The committed mock tenant `fixtures/tenant/contoso-dental.json` holds none of the baseline's graph-fixture users, so on it their dry-run is refused and reported. Tests use a tenant copy that has them.
- `expiresOn` is this repo's own guest field, UNVERIFIED against Graph. The default cap of 5 is a synthetic starting value.
- The person announcement (B-04) and bulk apply are not part of this item; the workflow only proposes.
