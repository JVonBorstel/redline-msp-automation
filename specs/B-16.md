# B-16 Python bridge and runner dispatch by runtime

Status: **built** (`core/levers/bridge.py`, `core/levers/runner.py`, `core/levers/registry.py`, `levers/powershell/Sample/`, `tests/py/levers/test_b16_bridge.py`).

> Independently built prototype. Not affiliated with any vendor's or real company's systems. Synthetic data only.

Inventory: `W-TOOL-01` (lever toolkit). Controls: `C-17` (typed boundary between languages), `C-05` (a lever is the only way to act), `C-04`, `C-08` (every call audited). Depends on `B-15` (the PowerShell host) and `B-14` (registry fragments). Standards: `STD-LV-7`, `STD-LV-11`, `STD-ER-1`, `STD-ER-5`, `STD-ER-7`, `STD-XL`.

## Why

Python orchestrates and PowerShell acts. After this item a lever for an identity, device or Microsoft 365 change is a PowerShell function plus one registry entry, with no change to the runner. Every permission decision stays in Python, before any process exists. Picture one person (Priya Nair, a hygienist at Contoso Dental, synthetic): a title change, a license or an MFA reset for her goes through the same registry, role, scope, approval, pause, verification and audit checks as a Python lever, and only then reaches PowerShell, scoped to her client's tenant.

## Behaviour

- **Registry.** A lever entry may carry `runtime: "powershell"` and `entry: "<Module>\\<Verb-Noun>"` (JSON-escaped backslash). `Registry.load` checks the format (the `Module` and `Function` patterns of `schemas/lever-request.schema.json`, so no path can be named) and that `levers/powershell/<Module>/<Module>.psd1` exists; whether the function is exported is the host's job at run time. `Registry.runtime(name)` and `Registry.powershell_entry(name)` expose the binding. A PowerShell lever uses a stand-in handler that is never called. Python levers are unchanged; `runtime: "ruby"` and a missing or malformed entry still fail the whole load. `Registry.load(..., powershell_root=...)` points at another modules folder (tests).
- **Bridge** (`core/levers/bridge.py`, `PowerShellBridge.call`). Builds one `lever-request` (`version 1`, `request_id`, `lever`, `lever_version`, `client`, `mode`, `params`, `entry`), starts `pwsh -NoProfile -NonInteractive -File levers/powershell/LeverHost/Invoke-LeverRequest.ps1 -ModulesRoot ... -TimeoutSeconds ...`, writes it to stdin, reads exactly one JSON line from stdout. It returns a `BridgeResult` (the host's subset of lever-result) and never raises: a missing `pwsh`, a start failure, a timeout, extra or missing output, output over 1 MB, an unknown field, a result for a different lever, client or mode, an exit code that disagrees with the status (0 only with `ok`, 1 with `denied` or `error`, 2 with `error`), and `applied: true` in a dry-run are all `error` with the host's answer discarded.
- **Kill at the timeout.** The child is killed at `timeout_s` of the lever (wall clock, including about one second of `pwsh` start-up, so a PowerShell lever needs a `timeout_s` of a few seconds at least). The result is `error`, "timed out after Ns; the pwsh process was killed; nothing was reported as applied" (SL-06). The host's own `-TimeoutSeconds` is set to the same value.
- **Scrubbed environment.** The child inherits only the variables `pwsh` needs to start (for example `PATH`, `SystemRoot`, `TEMP`, `HOME`), telemetry opt-outs, and `REDLINE_MOCK_TENANT_DIR` (the folder of the runner's mock tenant, for the offline sample levers). No token, key or other variable reaches it.
- **Runner dispatch.** `LeverRunner(..., bridge=None)` (default `PowerShellBridge(tenant_dir=tenant.root)`). All of `_authorize` runs first and unchanged: registry, mode, pause, schema, identity and role, client scope, lever scope, approval (four-eyes), requester verification. Only then does `_run` look at the runtime. For a PowerShell lever:
  - **read:** one host call sent as `execute` (a read has no `-WhatIf`, B-15); a diff or `applied` in the answer is an error ("read lever tried to change state; discarded"); the reasons mirror a Python read.
  - **write, dry-run:** one host call as `dry-run` (`-WhatIf`); the diff, sorted by path, is the result.
  - **write, execute:** a host dry-run first for the diff; empty means "no change: already in the desired state" and no real call is made; otherwise the audit record is written with `applied: true` (audit first), then the real call; it must report `applied: true` and exactly the same diff, otherwise a second audit record says `error` ("apply did not match the dry-run diff after audit seq N; check the target before retrying"), and a failed or killed real call gives "apply failed after audit seq N: ...".
  - The audit record carries `request_id` (also sent to the host) and `lever_version`; the audit copy of the diff is masked exactly like a Python lever's (DR-02). The host result gains `identity`, `approver` and `audit_seq` here (B-15 decision); the host never invents them.
- **Sample module** (`levers/powershell/Sample/`): `Get-SampleUser` (lever `sampleuser.get`, read) and `Set-SampleUserTitle` (lever `sampleuser.set-title`, write, R1, `ShouldProcess`), over the mock tenant. The registry fragment is `Sample.registry.json`, kept with the module so the live registry and the demo UI do not list sample levers; tests load it, and copying it to `levers/registry.d/` enables it. The write returns the same diff as a Python lever, `{"op": "replace" | "add", "path": "/users/<id>/jobTitle", ...}` (users keyed by id, STD-LV-5), applies it in one atomic file replace, and the same title again is an empty diff.

## Acceptance

- **B16-1** A lever with `runtime: "powershell"` runs through `pwsh -NoProfile -NonInteractive` with every runner check (registry, schema, role, scope, approval, pause, verification, audit) done in Python first.
- **B16-2** The child process is killed at `timeout_s` and the result is `error` with nothing applied (SL-06).
- **B16-3** A sample read lever and a sample write lever in `levers/powershell/Sample/` produce the same diff shape in dry-run as a Python lever, and an execute applies exactly the dry-run diff.

Tests: `tests/py/levers/test_b16_bridge.py` (names start with the acceptance id). The ones that start `pwsh` skip when it is missing; the dispatch logic (order of calls, audit first, diff matching, second record) is also tested with a fake bridge that needs no PowerShell.

## Not in scope

- Moving `runtime` and `entry` into `LeverDef` and regenerating `schemas/lever-registry.schema.json`: the loader still strips them before `LeverDef`, so the generated schema is unchanged (B-14 note). A later item can do it together with the `adapter` field.
- Passing the per-client adapter binding (`adapter` in the request) and Key Vault credentials: arrives with the first real adapter lever (TEN-04, STD-PS-7).
- Wiring `tests/ps` into CI: owner step W2-E1.
