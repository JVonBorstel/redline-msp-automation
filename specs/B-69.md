# B-69 Restore requests to an alternate location and scheduled restore tests

Status: **built** (restore lever, restore-request proposal, restore-test workflow with evidence files, CLI, notice template, tests). Mock only: no backup product is called and nothing real is restored. Synthetic data only. Every catalog field name is UNVERIFIED.

> Independently built prototype. Not affiliated with any vendor's or real company's systems. Synthetic data only.

Inventory (impact chains): `W-BDR-03` (restore request), `W-BDR-04` (scheduled restore test). Controls: `C-05` (approval for writes), `C-06`, `C-30` (requester verified out of band), `C-08`. Depends on `B-68` (backup adapter mock). Standards: `STD-LV`, `STD-AU`, `STD-TS`. Decision: `D6-24`.

## Why

The person gets their file back, and the client knows restores actually work. Two failures are worth designing against: a restore that overwrites the live copy (newer work lost, cause of the loss hidden), and a backup that nobody ever tried to restore. So a restore always lands beside the original, and each client gets a regular, recorded proof that a restore works.

## Behaviour

- **`restore.to-alternate`** (`levers/registry.d/restore.json`, `levers/python/restore.py`): params `item_id` (`^RI-[0-9]{4,6}$`) and `alternate_location` (`^ALT-[A-Z0-9][A-Z0-9-]{2,39}$`). Class write, risk `R2`, approval lead, an agent may dry-run it, a technician executes, `verification: requester` (B69-3). It records `restoreRequests["<item>@<location>"]` in the client's own mock tenant state, so the dry-run diff is one `add`, and asking again changes nothing. **There is no in-place overwrite lever:** a location that is not an `ALT-` name is refused by the lever's schema, and the handler re-checks the prefix. A test lists the registry and finds `restore.to-alternate` as the only restore lever.
- **Original location.** `propose_restore` refuses a request whose location is the item's original location (case, slash and whitespace variants included) or is not an `ALT-` name, with the reason that overwriting the original needs its own approval outside this workflow, and it does not call the lever. Nothing in this item overwrites an original.
- **Restore catalog** `workflows/restore_tests/catalog/<client>.json` (Contoso Dental, Fabrikam Capital) and `catalog.py` (`RestoreCatalog`): what the backup holds that can be restored, as three item kinds: `file`, `mailbox-item`, `vm`. Built on that client's `BackupAdapter` (B-68): the organization id comes from the adapter, an item of another organization is dropped and answered like an absent one (`no such restorable item for this client`), and an item is restorable only if its `sourceJobId` is a job of this client with status `success`. Each file holds one decoy item of the other client's organization (Contoso also one item whose backup job failed, so it is not restorable). Every item carries a short invented `content` and the `sha256` of it "recorded at backup time". `restore` copies the bytes into a caller-owned dictionary standing for the alternate location; nothing is written to disk.
- **Restore test** (`workflows/restore_tests/restore.py`, `python -m workflows.restore_tests run <client>`): picks one restorable item per client (`sha256(client|date|seed)` modulo the sorted restorable ids: pseudo-random across days, identical for the same day, so a re-run changes nothing), restores it in the mock to `ALT-RESTORE-TEST` (`config.json`), hashes the bytes that came back and compares with the recorded hash. Result `passed`, `failed` (hash differs, or the mock restore did not complete) or `not-run` (nothing restorable). The evidence file `<out>/<client>/<date>.json` holds item, selection, location, both hashes, result, reason and the SHA-256 of the catalog it ran against; a `.sha256` sidecar in `sha256sum` format; and one `restore-test.run` record in the client's audit chain pins the file's SHA-256 (written as eight groups of eight hex digits to survive the redactor, STD-AU-5). The test hands the restored data to nobody, so it needs no requester (B69-3 is about user-data restores).
- **Evidence integrity** (`verify_evidence`, `python -m workflows.restore_tests verify <file> [--audit-dir d]`): re-hashes against the sidecar; checks canonical form; checks the file agrees with itself (`passed` iff the two hashes match; the restore went to an `ALT-` location that is not the original); with `--audit-dir` also that the hash is pinned in a verifying audit chain. A failed test verifies fine as evidence: it says the restore failed.
- **Never overwritten.** A different result for a day that already has evidence is refused and audited; a failed test is not retried until it passes.
- **Who runs it.** The configured agent (`triage-bot`) must exist and be scoped to the client, else the run is refused and the refusal is audited. The test changes no tenant state and no fixture.
- **Scheduler seam.** `restore_test_workflow()` returns a `core.scheduler` workflow (`Unit -> UnitResult`) for one client and period (`config.json`: `every: monthly`). It proposes no action. A failed test shows in the report (`FAILED`) and in the evidence; the scheduler job itself is not registered here (`core/scheduler/jobs.example.json` is not in `owns`).
- **Notice template** `workflows/notify/templates/restore.to-alternate.md` (every write lever needs one, B04-2).

## Acceptance

- **B69-1** `restore.to-alternate` (R2) restores a file, mailbox item or VM to an alternate location only; in-place overwrite is not a lever.
- **B69-2** A scheduled restore test picks a random synthetic item per client, restores it to the alternate location in the mock, verifies its hash and records evidence.
- **B69-3** The requester is verified for user-data restores.

Tests: `tests/py/backup/test_b69_restore.py`, every test named `test_b69_<k>_...` (run: `uv run --frozen pytest -p no:cacheprovider tests/py/backup`).

## Known limits

- The restore is a mock copy of invented text held in memory. It proves the pipeline (pick, restore, hash, record, verify), not that any real backup product restores correctly. VM and mailbox restores of a real product (boot, permissions, folder structure) are not modelled beyond a hash of an invented manifest.
- Mock catalog items are tiny; real restores take time, can partially fail and need a restore window and free space. None of that is modelled.
- The pseudo-random pick is deterministic per client, date and seed; it is not cryptographic and not tuned to spread across item kinds or data volume.
- The requester check is the runner's `verification: requester` (a human scoped to the client records how the requester was verified). Whether the requester owns the item is not checked: the catalog has no item owner field. A real adapter would add one.
- The scheduler job is not registered and `adapters.build_adapter` has no `backup` system yet (`adapters/__init__.py` and `core/scheduler/jobs.example.json` are not in `owns`); catalogs are built with `RestoreCatalog.for_fixture`.
- Overwriting an original location stays a person's decision with its own approval, outside this item. No lever, undo or ticket is created here.
- `undo`: none. A restored copy in an alternate location is deleted by a technician in the backup product.
