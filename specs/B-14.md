# B-14 Registry fragments, Python lever modules and the never-automate gate

Status: **built** (loader, gate, tests). No new lever is registered by this item; it makes room for them. Synthetic data only.

> Independently built prototype. Not affiliated with any vendor's or real company's systems.

Inventory: `W-TOOL-01` (lever authoring), and the human-only work the gate protects: `W-ONB-15`, `W-IDM-04`, `W-IDM-06`, `W-IDM-07`, `W-M365-12`, `W-BDR-07`, `W-SEC-07`, `W-CMP-07`, `W-VND-02`, `W-KB-07`, `W-BIL-04`, `W-TRN-04` (and ten more `none-keep-human` ids, see below). Controls: `C-01` (least privilege by registration), `C-29` (risk classes and what is never automated), `C-20`. Depends on `B-13` (schemas). Standards: `STD-LV-2`, `STD-LV-10`, `STD-CF-2` to `STD-CF-5`, `STD-TS`.

## Why

Every new lever family used to mean editing one `levers/registry.json` and one `handlers.py`, so parallel work collided and a reviewer could not tell a new family from a change to an old one. And "never automate" was a sentence in a document: nothing stopped someone registering `role.grant-admin`. After this item a family is one fragment file plus one module, and the human-only work is a hard gate that fails the whole load.

## Behaviour

### Fragments (B14-1)

- `Registry.load(path)` reads `path` (default `levers/registry.json`) and every `*.json` in `registry.d/` beside it (or `fragments_dir`), in file-name order, as **one registry**. Other files in the folder (the README) are ignored.
- A fragment has the shape of the main file: `{"version": 1, "levers": [...]}`. `version` is required. A top-level `_note` string is allowed and ignored (`STD-CF-5`); any other unknown key fails.
- One bad file, one bad lever or one duplicate and **nothing loads** (`STD-CF-3`). A name in two files is `lever 'x' is registered twice (in a.json and b.json)`. Errors from a fragment start with the file name.
- Every rule of the main file applies to fragments: `LeverDef` is `extra="forbid"`, write levers need `risk_class` and `impact`, `undo` must be a registered write lever.
- The JSON Schema `schemas/lever-registry.schema.json` is unchanged: `runtime` and `entry` are read by the loader and removed before `LeverDef` validation (see Out of scope).

### Python entries (B14-2)

- A lever may carry `"runtime": "python"` (default) and `"entry": "levers.python.<module>:<function>"`. With no `entry`, the handler is `HANDLERS[name]` as before.
- `core.levers.handlers.resolve_python_entry` accepts only a lowercase `levers.python[.<module>]:<function>` string, imports the module, and requires (a) the module file to sit under a `levers.python` package path, (b) the attribute to be callable and (c) its `__module__` to be inside `levers.python`. So `os:getcwd`, `core.levers.handlers:ticket_get` and a function that a family module merely imports are all refused with the lever name in the error.
- `runtime` other than `python` is refused ("python only until B-16"). An `entry` for a name that also has a built-in handler is refused.

### The never-automate gate (B14-3)

- `governance/never-automate.json` (`version` 1, `entries`): each entry has `inventory_id`, `name`, `reason` and `patterns` (fnmatch, lowercase lever-name characters and `*`, at least one `.`, never a bare `*`). It lists **every** inventory item whose `automation_pattern` includes `none-keep-human` (22 ids at this commit); a test fails if the inventory and the list disagree.
- A lever whose name matches a pattern is refused with `lever 'role.grant-admin' is never automated: W-IDM-07 <name> (matches pattern 'role.grant*'): <reason>`.
- The gate runs in `Registry.load` (per lever, before validation, so the match is reported even for an otherwise broken lever) and in `Registry.__init__` (so a registry built in code cannot bypass it). A missing or malformed list stops the load. `Registry.load(..., never=NeverAutomate.load(path))` swaps the list for a test.
- Patterns block names, not intent: read-only fact packs and reports for this work (`B-37`, `B-48`) must use other names, for example `role.list` and `ca.list` are not blocked.

### Existing levers (B14-4)

- The four levers load unchanged with the same handlers; `levers/registry.d/` ships only a README. `P1-1` to `P1-9` pass.

## Acceptance

- **B14-1** levers/registry.json plus every levers/registry.d/*.json load as one registry; a duplicate name across files, a fragment without `version`, or an unknown field fails the whole load
- **B14-2** a Python lever's `entry` resolves only to a callable inside the `levers.python` package; any other module path is refused at load
- **B14-3** governance/never-automate.json lists each never-automate inventory id with lever-name patterns (for example `role.grant*`, `ca.set*`, `hold.*`, `vault.*`, `license.purchase*`); the loader refuses any lever matching a pattern, with the inventory id and reason in the error
- **B14-4** the four existing levers load unchanged and P1-1 to P1-9 pass

Tests: `tests/py/levers/test_b14_fragments.py`, `test_b14_<k>_...` per id. Run with `uv run --frozen pytest tests/py/levers`.

## Out of scope

- PowerShell levers and dispatch by runtime (`B-15`, `B-16`). When `LeverDef` gains `runtime` and `entry` fields there, the `_split_implementation` step in `core/levers/registry.py` moves into the model and the JSON Schema is regenerated.
- A JSON Schema file for `governance/never-automate.json` (`STD-CF-2`/`STD-XL-1`); it is validated by a pydantic model at load for now.
- The first lever family built on fragments (`B-31` onward).
