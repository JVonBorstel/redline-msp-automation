# B-95 Use-case intake, ROI tracker, SOC 2 control mapping and risk register

Status: **built** (typed intake, scorer, ROI tracker, mapping and register generators, checker, tests), on fixtures. The SOC 2 mapping and the register are **document-only** claims for people to review: not a certification, not an attestation, not an audit result. Synthetic data only.

> Independently built prototype. Not affiliated with any vendor's or real company's systems. Synthetic data only.

Inventory: `W-TOOL-13` (use-case intake and ROI scoring). Controls: `C-37` (lever change management), `C-45` (synthetic data and honest labels). Depends on `B-06` (risk classes). Also reads `B-92` (never-automate list, data classes), `B-94` (incident runbook) and `B-51` (evidence bundle) as things the mapping cites. Standards: `STD-DC`.

## Why

Leadership needs to rank the next automation by measured value and risk, and an assessor or a client will ask which controls this system claims and what proves each. Both answers should come from files that cannot drift from the code and the map, and both should say loudly what they do not show.

## Behaviour

Code: `workflows/assurance/` (`rubric.py`, `intake.py`, `roi.py`, `soc2.py`, `risk.py`, `render.py`, `__main__.py`). Data: `governance/intake_rubric.json`, `governance/roi_fixtures.json`, `governance/soc2_mapping.json`, `governance/risk_register.json`, and ten synthetic intakes in `fixtures/governance/intakes/`.

- **Intake.** `UseCaseIntake` is a pydantic model (unknown fields refused, `data_basis` must be `synthetic`, roles not names). `governance/use_case_intake.schema.json` is generated from it.
- **Score.** `score()` is a pure function of the intake, the rubric file, the ROI rows and `governance/never-automate.json`. Output: risk class R0-R3 (`RC-1` to `RC-3`), data sensitivity (`DS-1`), value band from assumed hours (`VB-1`), fixture acceptance (`AC-1`), blocks (`BL-NEVER`, `BL-DC6`, `BL-HOSTED`), a verdict (`VD-*`), a priority (`PR-1`) and `reasons`, one line per rule that fired. A blocked idea gets no priority and no rank.
- **ROI tracker.** Each row names an eval report and one line of it (the anchor) that must appear verbatim; both counts must be numbers in that line. Minutes, runs and effort are invented placeholders and are marked (assumed). Every row says `fixture-based`; the page says it is not a saving and contains no money figure.
- **SOC 2 mapping.** One row per control of `map/controls.json` (all 45): status as the map derives it, the SOC 2 criterion ids from `framework_refs`, the claim (the control's objective), the tests (`path::name`) and files that back it, and a Not demonstrated cell that is never empty. A second table groups by criterion. A section lists what is not demonstrated for every row.
- **Risk register.** The twelve `AIR-n` rows come from the AIR table of `docs/map/05-governance.md` (risk, controls, residual) with each control's state from the map; owner role, treatment, rationale and next step come from `governance/risk_register.json`; four `RR-n` rows cover this tooling's own risks. No likelihood or impact rating is given.
- **Checker.** `uv run --frozen python -m workflows.assurance check` fails when a mapped control cites a test file that does not exist, a test name the file does not define, or a file or folder that does not exist (paths that leave the repo are refused); when a control is unmapped, unknown or unexplained; when a risk is missing from the register, lacks an owner or treatment, or cites an unknown control; when a ROI anchor is not in its report; and when any generated page differs from its generator. `generate` is a dry run unless `--write`.
- **CLI.** `python -m workflows.assurance score [FILE ...] [--json]` prints the ranked table with the reasons.

## Acceptance

- **B95-1** Intake scores a use case by hours (assumed), acceptance rate (measured on fixtures), effort and risk weight. Checked by: the formula and weights tests, the risk-class table, the ten examples each getting its expected verdict (candidate, below-acceptance-bar, needs-measurement, design-review-required, needs-inventory-mapping, three blocked kinds), determinism and input-order independence, every verdict carrying its rules, blocked ideas never ranked, and the schema equal to the model.
- **B95-2** The ROI tracker is filled from this repo's eval reports and labelled fixture-based on every row. Checked by: each anchor in its report with both counts in the anchor, `fixture-based` on every row, `(assumed)` and `(fixture)` in the header, no `$`, the page equal to the generated one, and the check failing on a spoiled anchor, count, report path or duplicate id.
- **B95-3** The SOC 2 mapping and risk register are generated from `map/controls.json` and the governance map AIR table, so they cannot drift. Checked by: every control mapped, every cited test and file existing, the check failing on a missing test file, test name, file, folder, unmapped control or empty Not demonstrated, the AIR ids equal to the map's, a spoiled register or map failing, generated files equal to committed files, and no certification wording.

## Known limits

- **UNVERIFIED:** the SOC 2 criterion ids are copied from the map's `framework_refs`. The AICPA criteria text is not in the repo and was not read, so whether each id fits its control is the map author's judgement. The MSP's own SOC audit status is U-01.
- The checker proves a cited test is defined in its file (a `def name(` match, so a parametrized or class-nested test matches by name alone). It does not run it, and it does not prove the test still checks the claim.
- Statuses follow `map/controls.json`, which lags the code: B-94 built a runbook and templates (C-34, C-35) and B-92 the policy text (C-42), yet the map reads planned. Backing was added by hand for C-25, C-34, C-35 and C-42 only. The other 41 controls were not re-audited against the items merged since the map was written; some may be understated.
- The rubric weights (R0-R3 = 1, 2, 4, 8), the 90% bar and the value bands are proposals. No the MSP ranking policy or risk appetite is known (GQ-01).
- ROI minutes, runs and effort are invented placeholders. Acceptance is the share right against author-written gold labels with mock providers, not a technician's acceptance of real output. All six tracked automations are R0, so the risk weight does not separate them.
- The never-automate check reads declared lever names and inventory ids, not the free-text problem. A submitter who leaves them out gets `needs-inventory-mapping`; one who lies passes. A person reads every intake.
- Owner roles are proposals (D6-17); who holds them at the MSP is unknown (GQ-01). The register gives no likelihood or impact rating because no incident or loss data exists.
- Run on Windows with uv's managed Python. Not run on a Linux runner; generated files are written with LF.
