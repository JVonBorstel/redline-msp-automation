# B-68 Backup adapter mock, daily job review and failed-backup triage

Status: **built** (adapter mock, review workflow, CLI, `backup.retry-job` lever, notice template, tests). The review is read-only; the one write is an approved retry. Synthetic data only. Every backup field name is UNVERIFIED.

> Independently built prototype. Not affiliated with any vendor's or real company's systems. Synthetic data only.

Inventory (impact chains): `W-BDR-01` (daily backup job review), `W-BDR-02` (failed-backup triage). Controls: `C-27` (one client per unit of work), `C-21`, `C-05` (approval for writes). Depends on `B-18` (adapter base, bindings), `B-14` (registry fragments). Standards: `STD-ER`, `STD-FX`, `STD-LV`. Decision: `D6-24` (backup is in scope; the review is read-only first).

## Why

A failed backup is fixed the same day, not discovered during a restore. The MSP sells backup and disaster recovery and managed Microsoft 365 backup (service CONFIRMED, vendors INFERRED or UNKNOWN, map 07 MP-15, MP-16). The dentist whose imaging server failed to back up two nights running should hear about it from the morning review, not from a restore that cannot be done. The false positive matters too: a retry on a struggling production server at 9 a.m. can slow the practice down, so the review only proposes and a lead approves.

## Behaviour

- **Adapter** `adapters/backup/` (`BackupAdapter`, `BackupMock`): built for one client from that client's backup binding; the fixture's `client` and `organization.id` must match or construction raises `AdapterError`. `get_organization`, `list_jobs(job_type=None)`, `get_job(job_id)`; typed results, never raising; a job of another organization is dropped before it is returned, and `get_job` answers it exactly like an absent job (`no such backup job for this client`). Read-only.
- **Two job types** (`jobType`): `image-appliance` (an image-based appliance/agent backup with a `bootCheck` result and screenshot reference) and `m365-saas` (a Microsoft 365 SaaS backup job for one `protectedService`).
- **Fixtures** `fixtures/backup/<client>.json` (Contoso Dental, Fabrikam Capital), pinned to `asOf` 2026-10-21T07:00:00Z, each with one decoy job of the other client's organization. `fixtures/backup/SOURCES.md` says what is and is not claimed.
- **Review** `workflows/backup_review/` (`python -m workflows.backup_review <client> [--as-of ...]`): jobs scheduled in the last `review_window_hours` (24) are each put in exactly one bucket.
  - `failed`: status failed, or a finished backup whose boot check failed (the backup exists but the image does not start).
  - `missed`: status missed, or status scheduled with no start `missed_grace_minutes` (60) after its time.
  - `long-running`: running longer than `long_running_factor` (2) times `expectedDurationMinutes`.
  - `in-progress` and `healthy`: counted, not listed.
  - Each listed job carries the reason from the job record. Error text that the injection detector flags is replaced by a fixed sentence and the job id is listed for a person (C-12). A status the review does not know counts as failed, never healthy.
- **Triage**: `draft_tickets` groups every failed or missed run of one protected item in the last `lookback_days` (7) into ONE ticket draft (`repeated` at `repeat_min_failures`, 2, priority high). Only items with a finding in today's review get a draft. A draft is text for a person ("Draft. A person reviews and creates this ticket."); nothing creates a ticket.
- **`backup.retry-job`** (`levers/registry.d/backup.json`, `levers/python/backup.py`): param `job_id` (`^BJ-[0-9]{4,6}$`). Class write, risk `R2`, approval lead, an agent may dry-run it, a technician executes. It records `backupRetryRequests[<job id>]` in the client's own mock tenant state, so the dry-run diff is one `add`, and asking again changes nothing. `propose_retry` looks the job up in the client's own adapter first (STD-LV-9) and only dry-runs for a failed or missed job; the workflow cannot execute (a test reads its source). One dry-run per ticket draft, so three failed nights are one retry request.
- **Notice template** `workflows/notify/templates/backup.retry-job.md` (every write lever needs one, B04-2).

## Acceptance

- **B68-1** The daily review lists failed, missed and long-running jobs per client with the reason from the job record.
- **B68-2** `backup.retry-job` (R2) dry-runs and needs approval; repeated failures are grouped into one ticket draft.
- **B68-3** Counts reconcile (every reviewed job is in exactly one bucket, overall and per job type; reviewed plus history equals the adapter's job list); job data of another client is never shown.
- **B68-4** The backup mock models image-based appliance and agent jobs (with a boot-check screenshot result) and Microsoft 365 SaaS backup jobs as two job types, field names marked UNVERIFIED; the review is read-only and `backup.retry-job` is the only write (D6-24).

Tests: `tests/py/backup/test_b68_backup.py`, every test named `test_b68_<k>_...` (run: `uv run --frozen pytest -p no:cacheprovider tests/py/backup`).

## Known limits

- Thresholds (24 h window, 2x, 60 minutes, 2 failures, 7 days) are starting values, not tuned on real jobs.
- `adapters.build_adapter` does not yet build a `backup` adapter from a client's config (`adapters/__init__.py` is not in `owns`); until it does, the mock is built with `BackupMock.for_fixture` or from a `BoundBinding`.
- The lever records a request in the mock tenant state; it does not know the job. The workflow checks the job in the client's adapter before dry-running, and a real adapter would re-check at the vendor (STD-LV-8 keeps handlers free of file and cross-client access).
- No ticket is created and no queue proposal is filed here: a person turns a draft and an ok dry-run into those (STD-PR-1).
- No `undo` lever: cancelling a pending retry is a technician action in the backup product.
