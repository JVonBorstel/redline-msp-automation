# B-90 Hosted provider approval gate and Azure OpenAI adapter (mocked)

Status: **built** for the gate, the register and the config checks (tests pass on doubles). The Azure OpenAI adapter is **mocked**: it contains no HTTP client and nothing has run against Azure. Anthropic stays a stub.

> Independently built prototype. Not affiliated with any vendor's or real company's systems. Synthetic data only.

Inventory: `W-TOOL-02`, `W-GOV-02`. Controls: `C-28`, `C-43`, `C-15`, `C-25`. Standards: `STD-SC`, `STD-CF`, `STD-ER`. Depends on `B-55` (redaction gate, data classes) and builds on `B-80` (breaker, budgets, model-call audit). Decisions: D-018 (hosted adapters off, last resort), D6-11 (hosted models stay off until approved in writing; every client defaults to `model_processing: none`).

## Why

Hosted models are the one place client text leaves the machine. Until now the rule was a class check (B55-3) and a switch in `config/models.json`. That does not say who agreed to it, for which client, for what, or until when. For Fabrikam Capital, "a manager flipped `enabled: true`" is not evidence an auditor accepts. B-90 makes a hosted call impossible without a recorded approval, and makes every refusal leave a record.

## Behaviour

### The register (B90-1, B90-4)

`governance/ai-vendor-register.json` (validated by `core/gateway/vendor_register.py`, `extra="forbid"`, version 1) lists vendors. Each entry:

- `id` (short code, the **approval id**), `provider` (`azure_openai` or `anthropic`), `name`, `status` (`pending`, `approved`, `revoked`).
- For an `approved` entry, all of: `allowed_data_classes`, `clients`, `purposes`, `retention_terms`, `review_date`, `approved_by`, `approved_on`, `approval_ref` (where the written approval is kept). Anything missing is a load error. `approved_on` may not be after `review_date`.
- A `pending` or `revoked` entry must allow nothing (empty classes, clients, purposes).
- DC-6 can never be listed. Purposes are short codes (`ticket-summary`), never free text, so a purpose cannot carry a name or ticket content.
- The committed file holds Azure OpenAI and the Anthropic API as `pending` with nothing allowed (B90-4). Adding or changing an entry is an owner step through the AI change process (B-93); no code or agent writes this file.

### The gate (B90-1, B90-3)

A call routed to `azure_openai` or `anthropic` runs after redaction (B-55: classify, block DC-6, replace PHI/NPI/PII spans) and before the breaker and budgets. It is allowed only if **all** hold:

1. config (`providers.azure_openai.approval_id`) names a register entry for that provider, `status: approved`, with `today <= review_date`;
2. the entry lists this **client** (the caller's client record) and that client's record says `model_processing: hosted` (a record without the field, or no client, is refused);
3. the entry lists the text's **data class**;
4. the entry lists the call's **purpose** (a keyword argument of `Gateway.complete`, never read from the text).

Otherwise `Completion(ok=False)` and nothing is sent. DC-4/DC-5 text keeps the B55-3 message (`refused: DC-4 text may not go to hosted provider ...`, audit reason `hosted-refused`) unless the entry lists that class; every other refusal says `refused: hosted provider 'x' has no recorded approval for this call (<code>); nothing was sent` (audit reason `hosted-unapproved`). The decision function (`VendorRegister.check`) reads only its arguments and returns a fixed code: `no-approval-id`, `unknown-approval`, `wrong-provider`, `not-approved`, `review-overdue`, `client-not-approved`, `class-not-approved`, `purpose-missing`, `purpose-not-approved`, plus `register-unavailable` and `client-not-hosted` from the gateway. A missing or invalid register file refuses every hosted call (fail closed).

### Audit

Every hosted-route call, allowed or refused, adds `approval_id` and `purpose` to `params` and `gate` (the code, `ok` when allowed) to `result` of the existing `model.complete` record. Calls to local providers are unchanged (no new fields). Still never written: prompt, completion, a provider's error text, any secret or endpoint value.

### The Azure OpenAI adapter (B90-2, mocked)

`core/gateway/azure_openai.py`. Config (`AzureOpenAISettings`) holds **references**: `endpoint_ref` and `key_ref` match `env:NAME` or `keyvault:NAME`, plus `api_version`. A value (a URL, a key) fails config validation. The adapter fails closed (`ProviderError`) when: disabled; no register or no live approval for its own `approval_id` (it re-checks even if called directly); a reference is missing or does not resolve; the endpoint is not `https://<name>.openai.azure.com` (no userinfo, port other than 443, path, query; look-alike hosts refused); the deployment name is not a plain name; no transport is injected; the transport raises (fixed message, never its text); the reply is not `choices[0].message.content` text. The default resolver reads `env:` from the process environment; `keyvault:` is not built and resolves to nothing.

There is no HTTP client in this repo's adapter. The `Transport` is injected, and the shipped wiring injects none, so the default build cannot send anything. Tests use an in-process double with sockets disabled.

## Acceptance

- **B90-1** a hosted provider loads only when config names an approval id present in the register, approved, with classes, retention terms and an in-date review date.
- **B90-2** the adapter is tested against a test double; no endpoint is ever called. **Deviation from the roadmap wording:** the roadmap says "a fake server on 127.0.0.1". The adapter has no HTTP client, so there is nothing to point at a server; an injected in-process transport is used and sockets are disabled in the tests. A real transport and a loopback fake server test belong to the item that builds the real client.
- **B90-3** DC-4/DC-5 text is refused on a hosted route unless the entry lists that class.
- **B90-4** the committed register starts with Azure OpenAI and the Anthropic API `pending`, nothing allowed; nothing hosted loads; client records require an explicit `model_processing` (schema already has no default; the gate additionally requires `hosted`).

Tests: `tests/py/gateway/test_b90_hosted.py` (`uv run --frozen pytest -p no:cacheprovider tests/py/gateway`), named `test_b90_<k>_...`. Written failing first (first run: import error, no `core.gateway.azure_openai`). They include fooled-caller tests: text that claims an approval; a forged client record; a client not in the register; a purpose not in the register; calling the adapter directly; model output that asks for actions (it stays text).

## Known limits

- **Declared class is trusted when no shape contradicts it.** A caller that declares DC-0 for shapeless PHI prose (no cue word, no number) gets it past the class check, as in B-55. The boundary is the approval: only a client, class and purpose the register names can reach a hosted model. A test documents this.
- The shape scan is a tripwire (B-55), not a guarantee.
- Not verified: Azure OpenAI's real request path, `api-key` header, payload and reply shape, and its endpoint host forms (only `*.openai.azure.com` is accepted; other Azure host forms such as `cognitiveservices.azure.com` are refused until verified). No vendor page was opened.
- No real retention, BAA or zero-data-retention terms were checked; the register holds whatever the approver writes. The register's `approval_ref` is a pointer, not evidence.
- Key Vault resolution is not built. Secret rotation, regional residency and cost are not covered.
- `config/models.json` (protected) was not edited: the shipped config names no approval id and keeps hosted off. Wiring Azure in is an owner step.
- Per-process: the register is read when a `Gateway` is built; a change to the file needs a new `Gateway`.

## Not in this item

- A real HTTP transport, Key Vault client, or the Anthropic adapter (still a stub, and gated the same way).
- The process that adds register entries (`B-93`), and a CLI to approve or revoke.
- Passing `purpose` from workflows into `Gateway.complete`: no workflow calls a hosted route.
