# B-51 SOC 2 evidence bundle and change records

Status: **built** (workflow, CLI, tests), on fixtures. A bundle is a set of files plus a hashed manifest. It is evidence a person can hand to an assessor. It is not a certification, an attestation or a SOC 2 report, and it asserts nothing. Synthetic data only.

> Independently built prototype. Not affiliated with any vendor's or real company's systems. Synthetic data only.

Inventory: `W-CMP-01` (evidence pack drafted from the audit chain), `W-CMP-04`, `W-CMP-05`, `W-CMP-07` (management assertions stay human). Controls: `C-08` (hash-chained audit log), `C-37` (lever change management), `C-38` (access review), `C-39` (audit head pinning; export per client). Depends on `B-42` (per-client audit chains) and `B-49` (access reviews). Standards: `STD-AU`, `STD-DC`, `STD-TS`.

## Why

Audit evidence is collected every month, not rebuilt the week before the auditor arrives. Each month, per client, the bundle freezes what the repo can show: does the audit chain verify, who approved or was denied what, which lever versions existed, which access reviews were done, and which changes were merged.

## Behaviour

`python -m workflows.evidence` (module `workflows/evidence/bundle.py`):

- **`bundle <client> --period YYYY-MM --as <lead> --as-of YYYY-MM-DD`** and **`bundle --msp ...`**. **Dry run by default**: it prints the manifest it would write, with every file hash, and writes nothing. `--write` writes `build/evidence/<period>/<client>/` (or `_msp/`).
- **Client bundle** (`<client>/`), one client only:
  - `audit-verify.json`: the result of `verify_chain` on that client's chain (B-42): `ok`, `broken_seq`, `reason`, whether a head pin exists, and the in-period window (record count, first and last seq, hash of the last in-period record). A broken chain is still written, with `ok: false`: a failure is evidence too.
  - `approvals.json`: for the period, counts by lever and outcome (executed, denied, dry-run, approved, rejected), the distinct approvers (ids only), and the count of records by actor kind. No parameters, no free text.
  - `registry.json`: the levers that may act for this client, each with name, `lever_version`, class, risk class, required role, approval rule.
  - `access-review/`: copies of the B-49 files for the period's quarter (`<client>.json`, `.decided.json`, and sidecars) that exist. Each is re-verified with B-49's `verify`; the result is in the manifest. A missing review is a listed gap, never an invented file.
- **MSP bundle** (`_msp/`): the same four items from the MSP chain, the full registry, the MSP access review (`_msp.json`), and the change records below.
- **Change records** (MSP bundle, `change-records/`): from a local `git log --first-parent`, every merge commit (or `(#N)` squash commit) dated in the period gets `CR-<12 hex of the commit>.json`: title, commit, parents, merged date, author, changed paths, roadmap ids found in the title (`B-nn`), whether guardrail paths were touched (`docs/BLUEPRINT.md`, `scripts/`, `.github/`), and `reviewer`, `ci_result`, `approval`, all `null` with `evidence: "not in local git"`. `merged-prs.json` indexes them. If git or the repo is unavailable the index says so; nothing is invented.
- **Manifest** (`manifest.json` plus `manifest.json.sha256`, `sha256sum` format): every file with path, byte size and SHA-256, sorted; `period`, `as_of`, `scope`, `generated_by`, `data_class` (client bundle DC-3, MSP bundle DC-1), checks (audit ok, access reviews verified), gaps, the fixture-based and not-certified labels, and the management-assertion block (below). Canonical JSON as in B-49. No wall-clock time is in any file.
- **Determinism.** The same inputs and `as_of` give the same bytes and the same manifest hash. The bundle's own audit records (lever `evidence.bundle`) are left out of every count and of the window anchor, so running the workflow does not change what the next run sees.
- **`verify <bundle dir> [--audit-dir <dir>]`**: re-hashes the manifest against its sidecar and every listed file against the manifest, and fails on an unlisted extra file or a missing one. With `--audit-dir`, the manifest hash must be pinned by a successful `evidence.bundle` execute record in the scope's chain, and the chain must verify. Exit 0 match, 1 mismatch, 2 bad input or refused.
- **Who and audit.** Only a lead scoped to the client (for `--msp`, to every client) may build a bundle. Each call after the identity file is read writes one `job.run` record through `AuditRouter` (B-42), dry-run or execute or refused, to the scope's own chain. It carries the manifest hash (grouped in eight blocks of eight hex digits, the form that survives the redactor, as in B-49), counts and the period. A client's bundle names no other client and reads no other client's chain.
- **Management assertion (B51-3).** The manifest has `management_assertion: {"status": "not made", ...}`. The bundle supports a human's assertion and says so. It has no signature field, never signs, and never writes the words "compliant", "certified" or "attested" as a claim of its own.

## Acceptance

- **B51-1** a monthly bundle per period: audit verify output per chain, approvals and denials summary, registry snapshot with lever versions, access-review exports, merged PR list from a local git log, all hashed into a manifest
- **B51-2** re-running for the same period produces the same manifest hash (deterministic, `as_of`)
- **B51-3** the bundle supports a human's management assertion and says so; it never signs or asserts anything (W-CMP-07)
- **B51-4** (added) change records are generated from the local git log, with unknown review fields left null
- **B51-5** (added) a client bundle holds one client only; only a scoped lead may build; refusals are audited; dry run is the default and writes nothing
- **B51-6** (added) `verify` catches an edited, removed or added file, and a manifest not pinned in the audit chain

Tests: `tests/py/evidence/test_b51_evidence.py` (`uv run --frozen pytest -p no:cacheprovider tests/py/evidence`), functions named `test_b51_<k>_...`.

## Known limits (list of what is unverified)

- **Not a certification.** Nothing here is a SOC 2 report, readiness verdict or attestation. No auditor has seen it. Which criteria an assessor would accept this evidence for is UNVERIFIED; the mapping to SOC 2 criteria is the owner's to confirm.
- **Fixture-based.** Every number comes from synthetic fixtures and temporary test chains. There is no production audit data, real client or live tenant behind any of it.
- **Approvals are what the chain records.** The summary counts audit records (`approve`, `reject`, `denied` results, approver ids). It does not prove that a person who approved was the right person, or that a callback happened outside what the record says.
- **Head pin is local.** The chain's head file sits beside the log (C-39 is still planned: no immutable external pin). A verified chain proves internal consistency and agreement with a local file, not that the log was never replaced together with its pin.
- **Change records are from local git.** Reviewer, CI result and approval are not in a local git log and are left null; the real source (GitHub pull requests, CI runs) is not read, and the format of that data is UNVERIFIED. Squash-merge detection by `(#N)` in the title is a heuristic. Commit author and committer dates are whatever the repo says and can be rewritten.
- **Access reviews are copies.** The bundle copies B-49 files if they exist for the quarter; B-49's own limits (Graph shape UNVERIFIED, two mock tenants) carry over. A quarterly review dated after the period's month is still the quarter's review.
- **Period filtering uses the record's own `ts` (UTC, written by the audit log)**, string-matched on `YYYY-MM`.
- **Nothing schedules the run.** The monthly cadence is a convention until an owner schedules it. Retention (six years where HIPAA applies) is not implemented here.
