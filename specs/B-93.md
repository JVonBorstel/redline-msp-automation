# B-93 Model and tool approval process

Status: **built** (record schema, checker, tests) for the machine-checked part; the process page and template are **document-only** for people. The committed sign-offs are role placeholders, not real approvals.

> Independently built prototype. Not affiliated with any vendor's or real company's systems. Synthetic data only.

Inventory: `W-GOV-02` (model and tool approval). Controls: `C-28` (hosted approval gate), `C-43` (vendor and model change control). Depends on `B-90` (vendor register). Standards: `STD-DC`. Decisions: `D6-17` (roles, not names), `D6-11` (hosted stays off until approved in writing).

## Why

New AI tools arrive through a door, not a side window. B-90 made a hosted call impossible without a register entry, but nothing said how an entry, a new model, an MCP tool, a lever namespace or an adapter gets approved, by whom, on what evidence, and nothing failed when one appeared without it.

## Behaviour

- **Process page** `governance/MODEL_TOOL_APPROVAL.md`: what needs a request, who proposes (`technician`, `automation-engineer`, `lead`), who approves (`ai-change-approver`, plus `security-lead` and `compliance-owner` for R2/R3, hosted or DC-4/DC-5), the evidence per kind, the steps, every check code, a worked synthetic example (a hosted Azure OpenAI request for Contoso Dental), and its limits.
- **Template** `governance/templates/ai-change-request.md`: the plain-words field list (inventory id, risk class, data classes, rollback, owner, purpose, evidence, hosted terms, reviewers) and a draft record skeleton whose keys are exactly the record model's fields.
- **Records** `governance/model_tool_approvals.json` (version 1, `data_basis: synthetic`, unknown fields refused), shape in `governance/model_tool_approval.schema.json` generated from `workflows/assurance/approvals.py`. A record has: id (`AC-nnn`), kind (`model`, `provider`, `mcp-server`, `lever-namespace`, `adapter`), subject, owner role, proposer role, purpose, risk class, data classes (never DC-6), hosting, retention terms, BAA and ZDR status, vendor register id, evidence links, reviewer decisions (role, decision, date), rollback, status and dates. A hosted record without retention terms or a vendor id cannot load.
- **Checker** `uv run --frozen python -m workflows.assurance.approvals check [--as-of YYYY-MM-DD]` (exit 0 clean, 1 problem, 2 bad input). It reads `config/models.json`, `levers/registry.json` and `levers/registry.d/*.json`, `adapters/*/`, `mcp/server.py` and `governance/ai-vendor-register.json`, and fails on: a model or enabled provider, lever namespace, adapter or MCP server with no approved in-date record; a record that is draft, revoked, expired or not yet in effect; missing required evidence types or evidence files or test names; reviewer rule breaks; hosting that disagrees with the provider; DC-4/DC-5 on a hosted route without the BAA or ZDR the rule asks for; and any vendor register problem below. `schema [--write]` keeps the JSON Schema in sync.
- **Vendor register link.** A hosted record names a register entry (`vendor_approval_id`) that must exist, match the provider, be approved and in date, and allow no more data classes than the record. An approved register entry must have an `approval_ref` equal to the id of an approved `provider` record that names it. `governance/ai-vendor-register.json` is therefore reachable only through this process; its `_note` says so.
- The committed records (`AC-001` to `AC-028`) are a baseline of what existed on 2026-10-27: 2 providers, 4 models, the MCP server, 15 lever namespaces, 6 adapters.

## Acceptance

- **B93-1** the process names who proposes, who approves and what evidence is needed (retention terms, BAA or ZDR status, eval results) for a model, provider, MCP server or tool
- **B93-2** the AI change request template carries inventory id, risk class, data classes and rollback
- **B93-3** the process is the only way an entry is added to the vendor register (B-90 file)

Tests: `tests/py/governance/test_b93_approval.py` (`uv run --frozen pytest -p no:cacheprovider tests/py/governance -o addopts=`), functions named `test_b93_<k>_...`. B93-1 and B93-3 are enforced by the checker tests (each kind's missing record, expiry, missing evidence, reviewer rules, hosted terms, vendor link); B93-2 by checking the template's labels and that its skeleton validates; the worked example is parsed and run through the checker.

## Deviation from `owns`

The roadmap entry owns only the process page, the template, this spec and the change note. The checker and the records are needed to make the process machine-checked, so these files are added: `workflows/assurance/approvals.py`, `governance/model_tool_approvals.json`, `governance/model_tool_approval.schema.json`, `tests/py/governance/test_b93_approval.py`. One line of `governance/ai-vendor-register.json` (its `_note`) is edited to point at the process. No workflow folder is added (the checker lives in the existing `workflows/assurance/`).

## Known limits

- The committed sign-offs are placeholders written by the builder; the MSP's approver must re-decide them. Who holds each role is UNVERIFIED.
- The checker proves files, names and dates agree. It does not run cited tests, judge an eval report, or compare retention terms with a provider's real contract (UNVERIFIED; no vendor page opened). It is not a certification, an attestation or legal advice.
- Namespace and adapter evidence is shared (registry and runner gate tests, adapter contract table). Risk and data classes in records are declared, not measured.
- Only `config/models.json`, the lever registry, `adapters/` and the MCP server are seen. A tool that appears nowhere in them is not.
- A lever added inside an approved namespace is covered by that namespace's record.
