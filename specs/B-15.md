# B-15 PowerShell lever host module

Status: **built** (`levers/powershell/LeverHost/`, `tests/ps/Test-Modules.ps1`).

> Independently built prototype. Not affiliated with any vendor's or real company's systems. Synthetic data only.

Inventory: `W-TOOL-01` (lever toolkit). Controls: `C-05` (a lever is the only way to act), `C-17` (typed boundary between languages), `C-10` (no stack or secret in what the model or UI sees). Depends on `B-13` (`schemas/lever-request.schema.json`, `schemas/lever-result.schema.json`). `B-16` (Python bridge) calls it.

## Why

Python orchestrates and PowerShell acts. The runner has already decided that a call is allowed. The host is the narrow, boring last step: one JSON request in, one lever function called (as a dry-run unless approved), one JSON result out. If it did more, for example importing a neighbouring module or printing a stack trace, a mistake in one lever for one person (say the MFA reset for Priya Nair at Contoso Dental) could reach other clients or leak into a technician's screen.

## Behaviour

- `Invoke-LeverRequest.ps1 [-ModulesRoot DIR] [-TimeoutSeconds N] [-LogPath FILE]` reads one JSON document from stdin, validates it with `Test-Json -SchemaFile schemas/lever-request.schema.json`, and writes one compact JSON line to stdout. Nothing else is ever written to stdout.
- Exit codes (STD-ER-6): 0 `ok`; 1 `denied` or `error` (a normal outcome); 2 usage or configuration error (stdin empty or not a valid lever-request, unknown `version`, schema file or modules folder missing, the host itself crashed). Exit 2 still prints a result line with `status: "error"`.
- Only `<ModulesRoot>/<entry.module>/<entry.module>.psd1` is imported (default `ModulesRoot` is `levers/powershell`). The module name is limited by the schema to `^[A-Z][A-Za-z0-9]{1,63}$`, so a path cannot be named.
- The function must be in the module's `ExportedFunctions`; otherwise `denied`, "function X is not exported by module Y; nothing ran". A module that is not installed is `denied` too.
- Parameters: each `params` key is turned into a PascalCase parameter (`ticket_id` to `TicketId`). A key the function does not take is `denied`. A key that maps to a common parameter (`ErrorAction`, `Verbose`, ...) or to `Client` / `AsOf` is `denied`. The host itself passes `-Client` (the request's client) and `-AsOf` (the request's `as_of`) when the function declares them (STD-PS-10), so a param can never override the client.
- `mode: "dry-run"` calls the function with `-WhatIf`. A function with no `-WhatIf` parameter is **denied** in dry-run (fail closed, STD-PS-4): the host cannot tell a read from a write, so a function that cannot show a change without making it never runs as a dry-run. Read levers that do not support `-WhatIf` are sent as `mode: "execute"` by the bridge (B-16). `mode: "execute"` runs without `-WhatIf` and with `$ConfirmPreference = 'None'` (the approval already happened in Python; a prompt in a non-interactive host would hang).
- The lever runs in an isolated in-process runspace with a null host and `$ErrorActionPreference = 'Stop'`: the "What if:" text, `Write-Host` and warnings can never reach stdout, and a `Write-Error` counts as a failure. A call that runs longer than `-TimeoutSeconds` (default 30) is stopped: `error`, "<lever> timed out after N seconds".
- Return contract for a lever function: one object (or nothing). If it has a `diff` member, then `data` (optional), `diff` (list of `{op, path, before, after}`, `op` one of add/remove/replace) and `applied` map to the result; otherwise the whole object is `data`. A malformed diff entry is `error`. `applied: true` in a dry-run is `error` ("treat it as not trusted"). `applied` is `true` only when the lever said so.
- Result shape: `status`, `reason`, `lever`, `client`, `mode`, `data`, `diff`, `applied`. That is `schemas/lever-result.schema.json` minus `identity`, `audit_seq` (and `approver`): only Python knows them, because Python writes the audit. **Decision for B-16:** the bridge adds `identity`, `approver` and `audit_seq` to the host result before it becomes an `InvokeResult`; the host never invents them. A test proves that a host result plus `identity` and `audit_seq` validates against the committed lever-result schema, so no schema change is needed.
- A thrown error becomes `{"status":"error","reason":"<lever> crashed: <ExceptionType>"}` (STD-ER-5, STD-ER-7). Only the leaf exception type name is used. The message, path and stack go to `-LogPath` when one is given, and nowhere else.
- The helper module `LeverHost` (`Test-LeverRequestJson`, `New-LeverResult`, `ConvertTo-LeverParameterName`, `Invoke-LeverEntry`) holds the logic so tests can call it; the script is the stdin/stdout/exit-code shell.
- `tests/ps/Test-Modules.ps1 [-ModulesRoot DIR]` runs every `levers/powershell/*/tests/*.ps1` in its own `pwsh`, sums each file's `... tests: N passed, M failed` line, and prints `PS modules tests: N passed, M failed`. A test file that crashes or prints no summary line counts as 1 failed. A module without a tests folder is fine. Exit 0 or 1.

## Acceptance

- **B15-1** `Invoke-LeverRequest.ps1` reads one JSON request on stdin (lever-request schema), imports only the module named in `entry`, calls the function with `-WhatIf` for dry-run, and writes one JSON result (lever-result schema, minus the three fields Python adds) on stdout with exit code 0/1/2.
- **B15-2** A thrown error inside a lever becomes `{status: error, reason: "<lever> crashed: <type>"}` with no stack text on stdout (STD-ER-5, STD-ER-7).
- **B15-3** A request naming a function not exported by its module is refused; `tests/ps/Test-Modules.ps1` runs every `levers/powershell/*/tests` file and prints `PS modules tests: N passed, M failed`.

Tests: `levers/powershell/LeverHost/tests/LeverHost.Tests.ps1` (check names start with the acceptance id), `tests/ps/Test-Modules.ps1`.
