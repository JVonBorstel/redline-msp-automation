# B-71 Monthly client health report with reconciliation

Status: **built** (workflow, CLI, tests). Draft files only: nothing is sent, posted or queued, and nothing in a tenant, PSA, device or backup is changed. Synthetic data only. Every figure is **fixture-based**.

> Independently built prototype. Not affiliated with any vendor's or real company's systems. Synthetic data only.

Inventory: `W-RPT-01` (monthly client health report), `W-SEC-10` (security-awareness lines). Controls: `C-21` (every figure recomputed from its source), `C-27` (per-client isolation), `C-41`. Depends on `B-21` (the ticket set) and `B-50` (baseline findings and drift). Standards: `STD-TS`, `STD-DC`, `STD-ID`.

## Why

A client owner sees, in plain words, what is healthy and what is not. A report like that is only worth sending if every number in it can be traced, so the build refuses to write a report whose numbers differ from their sources, and a person reads it before it goes anywhere.

## Behaviour

`python -m workflows.reporting.health` (package `workflows/reporting/health/`):

- **`build <client> --period YYYY-MM --generated-on YYYY-MM-DD [--out DIR]`** (or `--all`, one separate report per client) writes `<out>/<period>/<client>.draft.html` and `<client>.draft.json` (default `build/client-health`). **`verify <draft.html>`** re-checks a written draft. Exit 0 ok, 1 mismatch, 2 bad input or a report that did not reconcile.
- **Period and dates.** The period is one calendar month. `generated_on` is passed in, never read from the clock inside the library, and may not be before the period. A source dated outside the period is not reported; its section says "no data for this period" and the file is still listed with its hash.
- **Sections and sources** (all committed fixtures, read-only): `tickets` from `fixtures/tickets/phase2/<client>.json` (B-21; tickets created in the month; `labels`, `technician`, subject, body and people are never read); `baseline` from `workflows/reporting/health/data/<client>.baseline.json` (the B-50 findings and drift, reduced to the keys used); `patching` from `data/<client>.patching.json`; `backup` from `fixtures/backup/<client>.json` through that client's `BackupMock` adapter; `awareness` from `data/<client>.awareness.json`. Figures are listed in `policy.METRIC_LABELS`. Percentages are one decimal, half up; a division by zero is shown as `n/a`, never 0.
- **Status.** Each section is `healthy`, `attention` or `no-data`. `attention` comes from the rules in `policy.RULES` (for example a high-severity baseline finding, a device with a critical update waiting, a failed or missed backup, a vault audit score below 70, more than 10% of simulated phishing emails clicked). The thresholds are stand-ins (UNVERIFIED). A section with no source file (Litware Legal has no backup fixture) says so; it is a gap, not a zero.
- **Reconciliation (B71-1).** After rendering, `reconcile.reconcile_html` reads the finished HTML and the raw source files and recomputes every figure with its own code (plain `json` and `Fraction` arithmetic; it does not call the builder's figure code). It fails if any shown figure differs, is missing or is invented; if a section's status or fired rules do not follow from the recomputed figures; if a listed source's hash or date is not what the file has now; or if the summary is wrong. `create_draft` runs it on the final HTML and writes nothing on a mismatch. `verify_draft` also checks the HTML bytes against `html_sha256` in the JSON record.
- **Summary (B71-2).** The text is built from the computed counts (`policy.computed_summary`). With a `Gateway` passed in, the `summarize` route may rephrase it. The rephrase is used only if it keeps every fact phrase word for word, carries exactly the computed text's figures (no more, none changed), spells no figure in words, and has no markup or link; otherwise the computed text is kept and the note says `rephrase rejected: <why>` (or `rephrase skipped` when the model call failed). The validator then runs on the final HTML, so a rephrased summary is checked again. The model sees counts and the client's display name only, at data class DC-2.
- **Isolation (B71-3).** One client per report. Every source file must name that client (`client` field) or the run is refused; a ticket naming another client refuses the run; the backup adapter drops other organizations' rows (the committed backup fixtures carry a decoy row on purpose). A client id must match `^[a-z0-9][a-z0-9-]{0,62}$`. There is no MSP-wide report. A test searches each report and its JSON for every other client's name and ticket ids.
- **Security-awareness lines (B71-4).** Phishing-simulation results (`MP-24`) and the password-vault audit score, enrolment and MFA flag (`MP-23`) come from per-client service-level fixtures. The loader refuses a file whose `level` is not `service` or whose vendor is not `UNVERIFIED`, and the report says "service-level" and "UNVERIFIED" next to the figures. Campaigns are counted by launch date; a month with no campaign shows `n/a` for the click rate.
- **Draft only.** The page and the JSON say `DRAFT`, `reviewed_by` is empty, and the page says "Not sent". The HTML has no script, link or external resource. The package imports no network, mail, queue or lever module (a test checks this).
- **Public interface** (`workflows.reporting.health`, for the QBR and digest workflows): `build_report(client, period, *, generated_on, sources=, gateway=) -> HealthReport` (frozen dataclasses `HealthReport`, `Section`, `Summary`, `SourceRef`; typed figures keyed by `METRIC_LABELS`), `render_html`, `report_to_dict`, `create_draft`, `reconcile_html`, `verify_draft`, `Sources` (where files are read), `SECTION_KEYS`, `HealthError`, `VerifyError`, `Mismatch`. Anything built on top should reconcile its own numbers the same way.

## Acceptance

- **B71-1** one HTML report per client from tickets, baseline, patching, backup and security-awareness fixtures; a validator fails the run if any number differs from its source (C-21 pattern)
- **B71-2** the plain-English summary is generated from computed counts, then (optionally) rephrased through the gateway; the validator runs after the rephrase
- **B71-3** no other client's data appears (isolation test)
- **B71-4** the security-awareness lines (phishing simulation results, vault audit score; MP-23, MP-24) come from per-client fixtures labelled service-level with the vendor UNVERIFIED

Tests: `tests/py/reporting/test_b71_health.py` (`uv run --frozen pytest -p no:cacheprovider tests/py/reporting/test_b71_health.py`), functions named `test_b71_<k>_...`. The expected figures in the tests are recomputed from the raw files by the tests' own code.

## Known limits

- UNVERIFIED: the patching, awareness and baseline fixture shapes are this repository's own. No RMM, patch-tool, phishing-simulation or vault export format was checked against a vendor page; the vendors themselves are UNVERIFIED (`docs/UNVERIFIED.md` U-04). The baseline drift block is written by hand to match the findings, not captured from a TenantBaseline run.
- The ticket set is cut at 2026-10-16, so October's ticket figures are for part of the month; the report states each source's date. Backup, patching and awareness are dated 2026-10-21/22.
- Resolved time uses the ticket's last update as a stand-in for the PSA completed date (as B-74 does).
- Thresholds in `policy.py` are stand-ins, not tuned on real clients. Nothing lists the individual failed backups or unpatched devices; the report gives counts.
- The default mock gateway returns canned text, so with it a rephrase is rejected and the computed summary stays; the accepted path is proven with a model double. No real model was called.
- Reviewing is a person's job outside this package: there is no approve, send or schedule step, and the draft carries no reviewer.
- Only the two clients with a backup fixture have a backup section; Litware Legal shows it as no data.
