# B-64 Device compliance, encryption and LAPS coverage reports; provisioning readiness

Status: **mocked** (workflow, CLI, fixtures, tests). Reports only: nothing is changed on any device and no key or password is ever read. Synthetic data only; every figure is fixture-based.

> Independently built prototype. Not affiliated with any vendor's or real company's systems. Synthetic data only.

Inventory: `W-EP-05` (Intune compliance follow-up), `W-EP-06` (disk encryption status; the recovery-key retrieval half is not built, status only), `W-EP-11` (LAPS; coverage only, no retrieval), `W-ONB-06` (device provisioning: Autopilot readiness). Controls: `C-20`, `C-21`, `C-10`. Depends on `B-61` (the reconciled device list and the Intune adapter). Standards: `STD-SC`, `STD-TS`.

## Why

Gaps on devices are known before a lost laptop becomes a breach: which devices Intune calls non-compliant and why, which disks are not known to be encrypted, which Windows machines have no fresh escrowed local-admin password, and whether the hires starting this month will have a device that enrols cleanly.

## Behaviour

`python -m workflows.device_reports report <client> [--as-of ...] [--out DIR] [--clients DIR]` (module `workflows/device_reports/reports.py`):

- **Devices** are the B-61 reconciliation of the client (RMM, Intune, PSA matched by serial, then name), so the counts reconcile to it and no other client's device is compared.
- **Compliance** per device: `compliant`, `non-compliant` (Intune `complianceState` is not `compliant`; reason `intune-state: <state>`), `stale` (Intune has not synced for `stale_days`, B-61; reason `stale-sync: last sync <time>`) or `not-in-intune` (no Intune record). The four add up to the device count.
- **Encryption** per device from Intune `isEncrypted`: `encrypted`, `not-encrypted`, or `unknown` (no Intune record).
- **LAPS coverage** per device: `covered` (a password backup within `laps_max_backup_age_days`, 35), `stale-backup`, `not-backed-up`, `not-applicable` (an Intune device that is not Windows), `unknown` (no Intune record, or no Entra device id). `applicable` counts the three Windows states. A LAPS record that matches no device of this client is counted in `gaps.orphan_laps_records` and is never coverage.
- **Attention list**: every device that is not compliant, not encrypted or unknown, or without fresh LAPS, with the reasons.
- **Provisioning readiness** per incoming hire (B64-1): `ready` when a device is assigned, its serial is in the client's Autopilot list and its profile status is `assignedInSync`; otherwise `not-ready` with `no-device-assigned`, `serial-not-registered-in-autopilot` or `autopilot-profile: <status>`. A not-ready hire who starts within `starts_soon_days` (7) is `urgent`. Autopilot devices assigned to no hire are counted.
- **Output** (`--out`, default `build/device-reports`): `<client>/<date>.json` and `<date>.md`, each with a `.sha256` sidecar in `sha256sum` format. The JSON is canonical (sorted keys, ASCII, one trailing newline), so the same inputs give the same bytes; the Markdown is rendered from the JSON and carries the JSON's hash. The date is `--as-of`, default the RMM fixture's pinned time, never the clock. Data class DC-3 (it names the user of each device). Each report lists the source files with their SHA-256.
- **`verify <file.json>`** re-checks both files against their sidecars and the Markdown against the JSON (exit 0 ok, 1 mismatch). A Markdown edited together with a fresh sidecar is caught because it must re-render from the JSON.
- **Status only (B64-2).** The LAPS source is read through an allow-list (`LAPS_FIELDS`: id, device name, last backup, next refresh). A password, credential list or recovery key in a source is not copied; the number of ignored fields is shown in `gaps`. `find_secrets` then checks the finished JSON and Markdown (recovery-key shape, long mixed-case base64 run, password shape, secret-named key) and stops the report with nothing written. It is a heuristic that errs towards refusing.
- **Selection.** Without `--clients` the three mocks are built from their fixtures; with it, from the client's bindings, and any non-mock binding fails closed with `real adapter not configured` (exit 2).
- **Where the new data lives.** `fixtures/intune/` and `fixtures/rmm/` are B-61's, so the LAPS, Autopilot and hire data is in `workflows/device_reports/fixtures/<client>.json` (field status in its `SOURCES.md`). The file must name the client and the Intune tenant or it is refused.

## Acceptance

- **B64-1** per client: non-compliant devices with reason, encryption status, LAPS coverage, and Autopilot/enrollment readiness for incoming hires
- **B64-2** recovery keys and LAPS passwords are never retrieved or shown (status only); a test asserts no secret-shaped value in any output
- **B64-3** counts reconcile to the fixtures

Tests: `tests/py/devices/test_b64_device_reports.py` (`uv run --frozen pytest -p no:cacheprovider tests/py/devices/test_b64_device_reports.py`), functions named `test_b64_<k>_...`. The expected counts are computed in the test from the raw fixture files, not from the code under test.

## Known limits

- UNVERIFIED: the Graph `deviceLocalCredentialInfo` and `windowsAutopilotDeviceIdentity` shapes, the join of the LAPS `id` to Intune's `azureADDeviceId`, the enum values, and the permission a real read needs, are written from memory; no vendor page was opened. A real LAPS read must request metadata only; that is a requirement for the real adapter, not something this item can prove.
- The compliance reason is derived (Intune state, stale sync, no record). The managedDevice resource has no reason text; per-setting reasons are not modelled.
- Servers are not told apart from workstations (a server shows as `not-in-intune`). Active Directory LAPS and macOS/mobile encryption are not covered. BitLocker recovery-key retrieval (W-EP-06) and LAPS retrieval (W-EP-11) are deliberately not built here.
- Incoming hires are an invented fixture; where they really come from is open. Readiness checks the Autopilot registration and profile, not apps, network or shipping.
- When one device has two Intune records, the newest sync is used and the duplicate is B-61's finding.
- The run writes report files only; it is not audited and not scheduled.
- `tests/py/evals/test_b79_injection_v2.py` classifies every `workflows/*` package; `device_reports` is not in its list yet (it reads no free text and imports no guard) and that file was out of this item's scope.
