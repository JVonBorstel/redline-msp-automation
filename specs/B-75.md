# B-75 Licence reconciliation, seat and device true-up, renewals, hardware lifecycle

Status: **built** (workflow, CLI, tests) on synthetic fixtures. A report only: nothing is bought, cancelled, assigned or removed. Synthetic data only.

> Independently built prototype. Not affiliated with any vendor's or real company's systems. Synthetic data only. Every figure is fixture-based.

Inventory: `W-VND-01` (licence reconciliation), `W-VND-02` (purchase or reduction: never automated, recommendation only), `W-BIL-02` (per-seat and per-device true-up), `W-VND-03` (renewal alerts), `W-EP-10` (hardware lifecycle and warranty forecast). Controls: `C-21` (no invented numbers: every figure reconciles), `C-27` (one client per run; no other client's rows). Builds on the B-31 licence fixtures and B-77 discovery's licence report (read-only), and on the B-61 RMM and PSA asset fixtures. Standards: `STD-FX`, `STD-TS`.

## Why

Clients should stop paying for seats nobody uses, with proof. Today billing pulls counts from three systems and compares them by hand. This report does that comparison for one client, shows the arithmetic, and turns each difference into a proposal a person approves or drops.

## Behaviour

`python -m workflows.licensing report <client> [--as-of YYYY-MM-DD] [--within-days N] [--inactive-days N] [--device-days N] [--out DIR]` (module `workflows/licensing/report.py`) writes `build/licensing/<as_of>/<client>.json`, `<client>.md` and `<client>.json.sha256` (`sha256sum` format). Same inputs give the same bytes (sorted keys, two-space indent, ASCII). Without `--as-of` the licensing fixture's pinned date is used, never the clock. Exit 0 written, 2 refused (nothing written).

**Inputs** (all read only, all synthetic):

| Data | File |
| --- | --- |
| bought seats (`prepaidUnits.enabled`) and assignments | `fixtures/tenant/<client>/licenses.json` (B-31) |
| directory users, `accountEnabled` | `fixtures/tenant/<client>.json` |
| sign-ins | `fixtures/tenant/<client>/signins.json` |
| devices | `fixtures/rmm/<client>.json` (own site only; the other client's decoy row is dropped) |
| PSA configuration items | `workflows/device_reconcile/psa_assets/<client>.json` (own company only) |
| billed users and devices, unit prices, overlapping SKUs, subscription and domain renewals, hardware purchase and warranty dates | `fixtures/licensing/<client>.json` (new, B-75's own) |

**Seats.** Per SKU: `purchased`, `assigned`, and each assigned seat in exactly one bucket, first match wins:

1. `orphaned`: no user name, user not in the directory, or account disabled. `in_retention` is true when the seat's `retentionEndsOn` is on or after `as_of` (or unreadable: no reclaim is proposed on a guess).
2. `duplicate`: the same SKU assigned to the same user again, or a SKU that overlaps another the user holds (`overlap_groups` in the licensing fixture, first SKU in a group is kept).
3. `unused`: no successful sign-in (`status.errorCode` 0) dated within `--inactive-days` (default 30) up to `as_of`. A failed or future-dated sign-in is not activity.
4. `active`.

`free = purchased - assigned` (negative = over-assigned, raised as a `check-over-assignment` proposal). `floor = active + in_retention`; `reducible = max(0, purchased - floor)`; `monthly_saving = reducible x unit price` (synthetic price, an illustration). A SKU assignment whose SKU the tenant does not list is a gap, not a seat. A missing or non-numeric seat count is a gap (`seat-count-unknown`), never guessed as 0.

**True-up (W-BIL-02).** Users: billed vs enabled directory users (assumption: the agreement bills enabled accounts), with licensed and active-seat user counts alongside. Devices: billed vs RMM active devices (unique hostnames, newest `lastSeen` within `--device-days`, default 30; records of other sites and `deleted` records dropped; duplicate records counted), with the PSA active count alongside and the RMM-minus-PSA difference shown.

**Renewals and hardware (B75-2).** Subscriptions and domains from the licensing fixture and warranties from the hardware list are listed when they end within `--within-days` (default 90, edge day included) or have already ended (`lapsed`). Hardware lifecycle end is `purchased_on + lifecycle_years`: `past`, `ending-soon` (inside the window) or `ok`; `in_rmm` says whether the RMM knows the hostname. An unreadable date is a `bad-date` gap and the row is left out.

**Proposals (B75-3).** Every change is a row with `status: proposed`, `executed: false`, `approval_required: true`, the approver role and the evidence: `reduce-subscription`, `check-over-assignment`, `reclaim-seat` (orphaned, window ended; names `license.remove` after approval), `review-seat` (unused or duplicate), `true-up-billing-users`, `true-up-billing-devices`, `renew`, `replace-hardware`. Seats inside a retention window get none. The module imports no lever runner, adapter, network or process module (a test reads its imports); `executed_changes` is always 0.

**Reconciliation (C-21).** The report lists its own checks (rows = assigned, buckets sum to assigned, purchased - assigned = free, totals = sum over SKUs, device and user deltas, assignments in the file = rows + unlisted-SKU rows) and an overall `ok`. The Markdown is rendered from the JSON values only, and a test parses its tables back and compares every number. A separate test recomputes the counts from the raw fixture files without using the workflow's helpers.

**Isolation (C-27).** The client id must match `^[a-z0-9][a-z0-9-]{0,62}$`. A fixture whose client field is another client's is refused. A client with no licensing fixture (Litware Legal) is refused, not reported as empty. A client's report names no other client.

## Acceptance

- **B75-1** per client: licences bought vs assigned vs active users, unused seats, users and devices for billing true-up; all counts reconcile
- **B75-2** renewals (subscriptions, warranties, domains) due in N days and hardware past lifecycle are listed
- **B75-3** purchases and reductions are recommendations with the evidence; nothing is bought or cancelled (W-VND-02)

Tests: `tests/py/licensing/test_b75_licensing.py` (`uv run --frozen pytest -p no:cacheprovider tests/py/licensing`), functions named `test_b75_<k>_...`.

## Known limits

- UNVERIFIED: no vendor portal, distributor portal, billing system or live Graph/RMM/PSA call was used. The Graph `subscribedSku`/`assignedLicenses` field names are carried from the B-31 fixtures, which mark them as written from memory. The RMM and PSA shapes are inherited from the B-61 fixtures (also unverified).
- UNVERIFIED: the billing model. "Billed users = enabled directory users" and "billed devices = RMM active devices" are this prototype's assumptions; a real agreement may bill by licence, by role, by device class, with minimums or bundles. The billed counts, unit prices, renewal dates, hardware dates and overlap list in `fixtures/licensing/` are invented.
- UNVERIFIED: the overlap rule. `ENTERPRISEPACK` and `O365_BUSINESS_PREMIUM` are listed as overlapping only to prove the flag; whether two real SKUs are redundant for a user is a licensing question the fixture does not answer.
- The sign-in fixtures are a short sample, not a full log. "Unused" therefore means no successful sign-in in that sample and overstates real non-use; on the committed fixtures it makes most seats look unused. A real run would read a sign-in activity report covering the whole window. No Graph `signInActivity` or usage report is modelled.
- `floor` assumes every unused and duplicate seat is confirmed unneeded; it is the best case, not a forecast. Contract terms (minimum commitments, term-locked seats, mid-term reductions) are not modelled, so "reducible" may not be reducible before renewal.
- Money is `seats x a synthetic monthly price`; it is not a quote, not tax-inclusive, and ignores currency, discounts and proration.
- Device identity is by hostname, case-insensitive. The PSA side is counted, not matched (B-61 does the matching), so RMM-minus-PSA is a count difference only. Hardware not in the RMM is flagged, not searched for.
- Only Contoso Dental and Fabrikam Capital have the inputs. Nothing schedules the run. The report is not audit-chained: it is a file with a hash sidecar, not a lever call, and records no requester identity. A lever wrapper (identity check, B-42 audit record) is the next step if this is run on behalf of a person.
- Approvers (`billing`, `account manager`, `lead`) are role names for the reader, not enforced. Nothing here records an approval; carrying out a proposal is a person's job through the existing levers or the vendor portal.
