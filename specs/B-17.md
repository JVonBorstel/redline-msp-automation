# B-17 Audit record v2 and verifier

Status: **built** (audit module, verifier CLI and tests). Wiring the real `actor_kind`, `lever_version` and `request_id` values from the runner, queue and gateway is `B-28` / `B-80`; this item gives every new record the fields with honest defaults.

> Independently built prototype. Not affiliated with any vendor's or real company's systems. Synthetic data only.

Inventory: `W-CMP-05` (audit evidence), `W-CMP-01`. Controls: `C-08` (tamper-evident audit), `C-39`, `C-11` (never-log list). Standards: `STD-AU` (STD-AU-2, STD-AU-6), `STD-VR-2`, `STD-TS`. Drift item closed: `DR-04`. Depends on nothing.

## Why

One request (a triage proposal for Priya Nair's MFA reset, ticket T-3101) produces several records: the dry-run, the lead's decision, the execute. Today nothing ties them together, and nothing says which version of the lever ran. An auditor at Contoso Dental, or the MSP scoping an incident after a lever bug ("every reset run by `user.reset-mfa` v1 between these dates"), needs both. v2 adds them without rewriting a single old record, so the chain built so far stays valid evidence.

## Behaviour

### Record v2 (B17-1)

- `AuditLog.append(...)` writes version 2 records: the eleven v1 fields plus
  - `v`: `2` (integer, STD-VR-2);
  - `event`: one of `lever.invoke`, `lever.pause`, `proposal.add`, `proposal.decide`, `model.complete`, `job.run`;
  - `actor_kind`: `agent`, `human` or `unknown`;
  - `lever_version`: positive integer or `null`;
  - `request_id`: non-empty string, at most 128 characters, redacted like params.
- New keyword arguments `event`, `actor_kind`, `lever_version`, `request_id`, all optional. Defaults when the caller passes none:
  - `event` from the mode: `dry-run` / `execute` / `invalid` -> `lever.invoke`, `approve` / `reject` -> `proposal.decide`, `pause` / `resume` -> `lever.pause`;
  - `actor_kind` -> `unknown` (the audit module cannot know; a wrong guess would be false evidence);
  - `lever_version` -> `null`;
  - `request_id` -> a fresh `req-` + UUID id in its hyphenated form (a bare 32-hex run would be redacted as secret-shaped; GUIDs are kept).
- Odd values never stop a record (STD-AU-6): an unknown event falls back to the mode's default, an unknown actor kind to `unknown`, a `lever_version` that is not a positive integer (including `True`) to `null`.
- Appending to a log that holds v1 records leaves every existing byte unchanged; the new record chains from the last v1 record's hash.

### Verifier (B17-2)

- `verify_chain` and `python -m core.audit.verify` accept a log of v1 records, of v2 records, or of a v1 prefix followed by v2 records.
- A record without `v` after a record with `v: 2` is broken at its seq with the reason `v1 record after a v2 record`, even when its hash and chain are recomputed (a downgrade).
- A v1 record must have exactly the v1 field set; a v2 record exactly the v2 field set, `v == 2`, and known `mode`, `event` and `actor_kind` values, a positive or null `lever_version` and a non-empty `request_id`. `v` other than 2 is `unknown record version`.
- Every P1-2 tamper case (one byte changed, rehashed edit, truncation caught by the head pin, middle record deleted, records swapped, junk line, missing head) is detected on a v2 log and on a mixed v1-then-v2 log, at the same seq as before.
- `VerifyResult` gains `v1_records` and `v2_records`. The CLI OK line keeps its prefix (`OK: <n> records, chain intact and matches the head pin`) and appends `(<a> v1, <b> v2)`.

### Mode literal (B17-3, DR-04)

- `Mode` in `core/audit/chain.py` lists every value actually written: `dry-run`, `execute` (runner), `approve`, `reject` (queue decisions), `pause`, `resume` (pause switch, B-02), and `invalid`.
- DR-04 counted four values; the pause switch (B-02) added two more since, so the literal has six caller values plus `invalid`.
- `invalid`: the runner records a denied call with an unknown mode (for example `--mode yolo`). `append` writes such a record with `mode: "invalid"` and the raw value, capped at 64 characters, in `result.requested_mode`, so the literal stays true and the denial is still recorded.
- `append(mode=...)` is typed `Mode`; mypy strict passes on `core/`. Callers: the queue's `verb` is typed `Mode`; the runner passes its mode through unchanged.
- `MODES`, `EVENTS`, `ACTOR_KINDS` are the runtime tuples of the literals.

## Acceptance

- **B17-1** new records carry `v: 2`, `event`, `actor_kind`, `lever_version` and `request_id` (STD-AU-2), with defaults when the caller does not pass them; v1 records are never rewritten.
- **B17-2** the verifier accepts a v1 prefix followed by v2 records and rejects a v1 record after a v2 one; P1-2 tamper tests pass for both.
- **B17-3** the `Mode` literal lists the values actually written (DR-04) and `append` is typed with it.

Tests: `tests/py/audit/test_b17_audit_v2.py`, every test named `test_b17_<k>_...`.

## Not in this item

- The runner, queue and gateway passing real `actor_kind`, `lever_version` and `request_id` (B-28, B-80). Until then runner records say `actor_kind: "unknown"` and `lever_version: null`, and each record gets its own `request_id`.
- `proposal.add`, `model.complete` and `job.run` records: the values exist; nothing writes them yet.
- Cross-process writers and a head pin outside the writer's reach (STD-AU-7) are unchanged.
