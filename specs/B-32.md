# B-32 GroupOps: group membership with privileged-group refusal

Status: **built** (two PowerShell write levers, mock fixtures, notice templates, tests). Synthetic data only; nothing here talks to a real tenant.

> Independently built prototype. Not affiliated with any vendor's or real company's systems. Synthetic data only.

Inventory: `W-ONB-04`, `W-ONB-16`, `W-IDM-07`. Controls: `C-05`, `C-06`, `C-32`, `C-01`. Depends on `B-28` (runner), `B-16` (PowerShell bridge), `B-19` (family files). Standards: `STD-LV`, `STD-PS`, `STD-FX`.

## Why

Right access on day one and on a move, never admin rights by automation. Access by group is the daily work of onboarding and role change; granting a group that holds a directory role is `W-IDM-07`, which stays with people.

## Behaviour

- **Levers** (`levers/registry.d/group.json`, module `levers/powershell/GroupOps`): `group.add-member` and `group.remove-member`. Params `upn` and `group_id` (a GUID). Technician executes, an agent may dry-run, a lead approves (`approval: lead`), `timeout_s` 15, each is the other's `undo`.
- **Risk class.** The registry holds one `risk_class` per lever, so both are registered **R2**, the stricter. The class of the individual call comes from the group's attribute in the fixture and is returned in the dry-run `data.riskClass`: `R2` when `redlineAccessClass` is `data` (or missing or unknown, fail to the stricter), `R1` when it is `distribution`. The runner does not yet read it for approval counts (see limits).
- **Refusal (W-IDM-07).** Before anything else, a group is refused when `isAssignableToRole` is true, or when its display name (case-insensitive) is in the client's `redlinePrivilegedGroups`. The result is `denied` with a reason starting `Refused (W-IDM-07)` and naming the rule that fired. It applies to dry-run and execute, and to remove as well as add. Nothing is written.
- **Absent is absent.** A group or user that is not in this client's tenant files answers `denied` ("No group/user ... in this client's tenant"); another client's data is never read.
- **Convergent.** Adding a present member, or removing an absent one, is an empty diff ("no change: already in the desired state"). Diff paths are `/groups/<group id>/members/<user id>`, keyed by id.
- **Data.** `fixtures/tenant/<client>/groups.json` (a B-19 family file). Graph `group` property names `id, displayName, description, groupTypes, mailEnabled, securityEnabled, isAssignableToRole, mailNickname, visibility` are VERIFIED against the group resource page (read 2026-10-22). `members` is embedded as `{id, userPrincipalName}` (Graph returns directoryObjects from `/groups/{id}/members`); `redlineAccessClass` and `redlinePrivilegedGroups` are this repo's fields, not Graph's.
- **Host change (outside `owns`).** `LeverHost.psm1` gains one narrow path: a lever that returns an object with a non-empty string `refusal` produces a `denied` result carrying that text (cut at 300 characters). Before, a lever could only throw, and the host reports `crashed: <Type>` with no reason.
- **Notices.** `workflows/notify/templates/group.add-member.md` and `group.remove-member.md`, plain words, same variables as the other templates.

## Acceptance

- **B32-1** `group.add-member` and `group.remove-member` exist as approval-gated PowerShell write levers; R2 when the group grants data access, R1 for distribution only, from the group attribute
- **B32-2** a role-assignable group or a group named in the client's privileged list is refused in dry-run (and execute) with the W-IDM-07 reason; nothing changes; the refusal is audited
- **B32-3** each change is idempotent and each is the other's undo

Tests: `tests/py/groups/test_b32_groupops.py`, named `test_b32_<k>_...`. Those that start `pwsh` skip when it is missing.

## Known limits

- Mock only. A real change needs Graph `GroupMember.ReadWrite.All` (UNVERIFIED here; not re-read) and, for role-assignable groups, `RoleManagement.ReadWrite.Directory`, which this lever must never be given. Per the Graph docs, adding members through Graph works for security and Microsoft 365 groups only; a mail-enabled distribution group is changed through Exchange Online. The mock does not model that difference.
- R1 versus R2 per call is reported, not enforced: the runner takes `risk_class` from the registry. Making approval counts follow a per-call class is a runner change (proposed in `docs/changes/B-32.md`).
- The privileged list is per client in a fixture; a real client list needs an owner and a review cadence.
- Nested groups are not modelled: adding a user to a plain group that is itself a member of a privileged group is not caught. A real adapter must check `transitiveMemberOf` against the same rule.
- Removing a member from a privileged group is refused too, on purpose: both directions of admin access belong to a person.
