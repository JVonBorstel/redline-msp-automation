# B-49 Access reviews: tenant admins and agent/technician identities

Status: **built** (workflow, CLI, tests). Review files only: nothing removes a role or an identity. Synthetic data only.

> Independently built prototype. Not affiliated with any vendor's or real company's systems. Synthetic data only.

Inventory: `W-IDM-09` (quarterly admin access review across tenants), `W-GOV-03` (agent identity and lever permission review). Controls: `C-38` (agent and technician access review; least-privilege delegated access), `C-03` (role-based authorization; agents may only dry-run writes), `C-08` (hash-chained audit log). Depends on `B-42` (per-client audit chains) and `B-28` (runner v3: `actor_kind` in every record). Standards: `STD-ID`, `STD-AU`, `STD-TS`.

## Why

Who can touch each client is reviewed, as SOC 2 CC6.2 and HIPAA 164.308(a)(4) expect. Two populations matter: the people holding directory roles in each client's tenant, and the repo's own identities (technicians, leads, agents) that the lever runner lets act for that client.

## Behaviour

`python -m workflows.access_review` (module `workflows/access_review/review.py`):

- **`export <client> --as <lead> [--as-of YYYY-MM-DD]`** writes `build/access-review/<quarter>/<client>.json` and `<client>.json.sha256`.
  - Rows of kind `directory-role-member`: every member of every directory role in that client's Graph mock (`fixtures/graph/<folder>/directoryRoles.json`, the `GET /directoryRoles?$expand=members` shape; folder per client as in `workflows/factpack`, DR-05). Role name, role template id, member id and type, UPN, display name, and `user_type` (Graph `userType`) and `account_enabled` (Graph `accountEnabled`) when the member object carries them (else `null`, never guessed). Flags on these rows: `guest-holds-role` (`userType` is Guest) and `disabled-account-holds-role` (`accountEnabled` is false). A member with no `id`, or in a role with no `roleTemplateId`, is skipped; an id that is not a safe row key (`ROW_ID`: letters, digits, `: . _ -`, at most 200 characters) is skipped; a member listed twice in one role gives one row. Each skip is counted in the export's `gaps` (`members_without_id`, `members_with_invalid_id`, `duplicate_members`), so row ids are unique and always safe as keys in the decisions file.
  - Rows of kind `repo-identity`: every identity in `config/identities.json` that may act for the client, with its role. Its wider scope is a count (`other_clients`), never a name: a client's export names no other client (STD-ID-6, the B42-2 rule).
  - A client with no Graph mock is refused; nothing is written.
- **`export --msp --as <lead>`** writes `<quarter>/_msp.json`: every repo identity with its role and full client list.
- **Dated and hashed.** Each export carries `as_of`, `quarter` (from `as_of`, never the wall clock in tests), `exported_by`, `data_class` (client export DC-3, because it names tenant users; MSP export DC-1, B-55), and the SHA-256 of each source file it read. The file is canonical JSON (sorted keys, two-space indent, ASCII, one trailing newline), so the same inputs give the same bytes. The sidecar is in `sha256sum` format, so `sha256sum -c` or `Get-FileHash` re-checks it without this code.
- **Decision field.** Every row has `decision: null`; the export lists `decision_options: keep, remove, investigate`. An export with a decision filled in place fails verification.
- **`decide <export> --as <lead> --decisions <file.json>`** takes `{row_id: keep|remove|investigate}` for every row (plus optional notes through the Python API) and writes `<client>.decided.json` with its own sidecar, `export_sha256`, `decided_by` and `decided_on`. A missing, unknown or invalid decision is refused. The export must verify first.
- **`verify <file> [--audit-dir <dir>]`**: re-hashes the file against its sidecar. For a decided file it also rebuilds the original export bytes (decisions emptied, decision metadata removed) and checks them against `export_sha256`, so the reviewed population cannot change. With `--audit-dir`, the file's hash must be pinned by a successful audit record in the scope's chain, and that chain must verify. This catches a decision edited later with a fresh sidecar. Exit 0 match, 1 mismatch.
- **Agent flags.** On agent rows only:
  - `execute-capability`: any registered write lever whose `required_role` an agent satisfies and whose `client_scope` covers a client the agent holds. The client export looks at that client only.
  - `excess-clients`: the agent holds clients its workflow does not need. Needs are declared in `workflows/access_review/needs.json` (agent id, workflow, clients). In the client export the flag does not name the other clients. When the exported client is needed but the agent also holds clients the workflow does not need, the row carries `excess-other-clients` with a `count` only; when the exported client is itself unneeded, `excess-clients` carries `excess_other_clients: N` too.
  - `no-declared-need`: the agent has no entry in `needs.json`.
  - A needs entry for an identity that does not exist is refused.
- **Who and audit.** Only a lead may export or decide. For a client, the lead must be scoped to that client. For the MSP export, the lead must be scoped to every client in the identity file. Every export, decision and refusal after the identity file is read writes one `job.run` record through `AuditRouter` (B-42): a client's events go to `<audit>/<client>.jsonl`, MSP events to `<audit>/_msp.jsonl`. `actor_kind` is `human`, `agent` or `unknown` (B-28). The record carries the scope, quarter, row and flag counts and the file's SHA-256, never the rows. The hash is written as eight groups of eight hex digits because the audit redactor blanks any 32+ hex run (STD-AU-5). Refusals include a missing Graph mock, a bad `needs.json` and a bad registry. Not audited: a malformed client id or `as_of` and an unreadable identity file, which are refused before the caller can be identified. Default audit folder: `.tmp/demo/audit`, the one the lever CLI uses.

## Acceptance

- **B49-1** quarterly per-client export of directory role members (from Graph mock) and of every repo identity with role and client list, dated and SHA-256 hashed
- **B49-2** each row has a lead decision field (keep, remove, investigate); the export is re-verifiable from its hash
- **B49-3** agents with any execute capability or with more clients than their workflow needs are flagged

Tests: `tests/py/access_review/test_b49_access_review.py` (`uv run --frozen pytest -p no:cacheprovider tests/py/access_review`), functions named `test_b49_<k>_...`.

## Known limits

- UNVERIFIED: the Graph `GET /directoryRoles?$expand=members` shape (`value[]` of roles, each with `members[]` carrying `@odata.type`, `id`, `userPrincipalName`, `displayName`, and `userType`/`accountEnabled` only if selected) is written from memory; no vendor page was opened and no live call was made. Real `$expand=members` returns at most 20 members per role and needs paging; the mock does not model that.
- The committed `directoryRoles.json` fixtures carry no `userType` or `accountEnabled` on role members (they exist in `users.json`, which is not joined). Contoso's guest (`#EXT#` UPN) therefore shows `user_type: null` and is not flagged `guest-holds-role`; the flags are proven on test copies. No sign-in activity, last-password-change or MFA state is in the export.
- Directory roles come from the Graph-shaped fixtures (`fixtures/graph/SOURCES.md`); only Contoso Dental and Fabrikam Capital have one. Litware Legal is refused, not reported empty. No live Graph call. Groups that are assignable to roles, PIM eligible assignments and GDAP relationships (B-54) are not in the export.
- `needs.json` is a declaration by the workflow owner, not something measured from usage. The review is where it gets checked.
- "Execute capability" means a write lever. Read levers that an agent may call in execute mode (`ticket.get`, `kb.search`) change nothing and are not flagged. Proposing a write (dry-run) is not execute.
- With today's registry no lever lets an agent execute a write, and `triage-bot`'s two clients match its declared need, so the committed config raises no flag. The flags are proven on copies under `tmp_path`.
- The lead's decisions are recorded, not carried out. `remove` is a person's job through the levers (`group.remove-member`, `user.disable`) or an edit to `config/identities.json`.
- Quarterly is the period the file is named for. Nothing schedules the run.
