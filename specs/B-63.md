# B-63 Software deployment from an approved catalog and third-party patching

Status: **mocked** (catalog fixture, loader, `device.install-app` lever, update review, notice template, tests). Nothing installs; no RMM is called; no real adapter exists. Synthetic data only.

> Independently built prototype. Not affiliated with any vendor's or real company's systems. Synthetic data only.

Inventory: `W-EP-04` (software deployment), `W-PAT-04` (third-party patching). Controls: `C-05`, `C-06`, `C-32`. Depends on `B-61` (RMM mock adapter, device list). Standards: `STD-LV`, `STD-TS`.

## Why

A person gets the app they need without an unvetted installer. The only things that can be deployed are entries of a catalog the MSP vetted, each pinned to one version and one hash, and each approved per client. A newer version of third-party software is reviewed as a proposal per ring before anything moves.

## Behaviour

- **Catalog** `fixtures/catalog/approved-software.json`, loaded by `levers/python/software.py` (`load_catalog`): entries are versioned (digits and dots, no `latest`) and hash-pinned (64-hex SHA-256); each client has an approved list that may only name catalog ids. One bad entry, a duplicate id, an unknown field or an approved id that is not in the catalog refuses the whole file.
- **Lever** `device.install-app` (`levers/registry.d/software.json`, R2, write, lead approval, dry-run, `technician` to execute and `agent` to dry-run, idempotency keys `device_uid` and `package_id`): `package_id` is an enum of the catalog ids, so any other value is refused before the handler runs; the handler then checks the package is in this client's approved list. It records `softwareInstallRequests["<device>:<package>"]` with the pinned version and hash in the client's own state. Asking again changes nothing. A test keeps the registry enum equal to the catalog ids.
- **Review** `propose_updates(client, rmm, catalog=..., installed=...)`: for the client's own RMM devices (another client's record is ignored and counted), each approved package behind the catalog version is proposed per ring, `pilot` then `broad` (`after_ring` set), with the device count and one dry-run call of `device.install-app` per device. A device at the catalog version is not proposed (idempotent); a newer one is never downgraded; an unreadable version, a `hold` device and software the client has not approved are listed as findings, not proposed. It never invokes a lever and writes nothing.
- **Notice** `workflows/notify/templates/device.install-app.md`.

## Acceptance

- **B63-1** `device.install-app` (R2) accepts only catalog ids (enum from the client's approved catalog); an unknown package is refused.
- **B63-2** Third-party updates are proposed per ring with the device count; idempotent when already at the version.
- **B63-3** Deployment is a proposal; nothing installs without approval.

Tests: `tests/py/devices/test_b63_deploy.py`, every acceptance test named `test_b63_<k>_...` (run: `uv run --frozen pytest -p no:cacheprovider tests/py/devices`).
