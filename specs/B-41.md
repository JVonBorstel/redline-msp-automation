# B-41 Rollback from recorded before-state

Status: **built** (`workflows/rollback/`, `tests/py/rollback/test_b41_rollback.py`). Proposes an undo; never executes one. Synthetic data only.

> Independently built prototype. Not affiliated with any vendor's or real company's systems. Synthetic data only.

Inventory: `W-GOV-04`, `W-CMP-04`. Controls: `C-33`, `C-31`, `C-08`. Depends on `B-29` (`user.enable` is the registered undo of `user.disable`). Standards: `STD-PR`, `STD-AU`, `STD-TS`.

## Why

When an automation is wrong, the person is put back first (EU-8, IR-3). The audit record of an applied change already holds what the field was before. This workflow turns that record into a normal proposal for the lever's registered undo, so a lead approves it like any other change; nothing skips approval because it is "only an undo".

## Behaviour

`plan(runner, audit_path, audit_seq, requester, queue=None)` reads one audit record and returns a `Rollback`:

1. The audit chain is verified first; a broken chain refuses (the before-state of a tampered log is not trusted).
2. The record must be an applied execute of a registered write lever (`result.applied` true). Anything else is refused.
3. **Lever with `undo`** (B41-1): the undo lever's params are taken from the recorded params (only the names the undo lever declares). The undo is dry-run through the runner (audited). Its diff must be exactly the recorded changes with before and after swapped. Then:
   - equal: status `proposed`; a `rollback` proposal (`Proposal.new(source="rollback", ...)`) is built, and queued as pending when a queue is given. A lead approves it through the normal queue (four-eyes, verification the undo lever asks for).
   - empty diff: `nothing-to-undo` (already back in the before-state); nothing proposed.
   - any other diff, or a masked value that cannot be compared: `drifted`; nothing proposed; a person reads the current state first.
4. **Lever without `undo`** (B41-2): status `manual`. The workflow prints the lever's README section (`levers/powershell/<Module>/README.md`, heading `## <lever>`) and the recorded before-state, runs no dry-run and proposes nothing. With no README section it says so.

`python -m workflows.rollback <audit_seq> [--as tech-ana] [--state DIR]` prints the result as JSON. Exit 0 = proposed, manual or nothing to undo; 2 = refused or drifted.

## Acceptance

- **B41-1** given an applied audit record whose lever has an `undo`, the workflow builds the undo proposal from the recorded before-state, in dry-run, for normal approval (IR-3)
- **B41-2** for a lever without `undo` it prints the manual undo steps from the lever README and proposes nothing
- **B41-3** a full test: disable, then rollback proposal, approval, execute; the fixture returns to byte-identical state and both actions are in the audit

Tests: `tests/py/rollback/test_b41_rollback.py`, named `test_b41_<k>_...`.

## Known limits

- The audit keeps a masked copy of contact details (DR-02), so a rollback whose diff includes masked values reports `drifted` instead of guessing.
- The proposal id is a hash of lever, client and params (STD-PR-5), so a second rollback of the same user after an earlier executed one hits the queue's existing record; the plan then refuses and says why.
- Byte-identical is measured against the canonical layout the Python `MockTenant` writes (see B-29).
- `source: rollback` is a new member of the `Source` literal (STD-PR-5) and of `schemas/proposal.schema.json`.
