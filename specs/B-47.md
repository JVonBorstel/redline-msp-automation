# B-47 Vulnerability, advisory and emergency-patch relevance

Status: **mocked** (workflow, CLI and fixtures; no RMM, scanner or KEV call is made). Report only: it never deploys. Synthetic data only.

> Independently built prototype. Not affiliated with any vendor's or real company's systems. Synthetic data only.

Inventory (impact chains): `W-SEC-06` (vulnerability scan review and prioritisation), `W-SEC-08` (threat advisory relevance check), `W-PAT-05` (emergency patch for actively exploited vulnerabilities). Controls: `C-21` (output reconciliation, no invented numbers), `C-27` (one client per unit of work). Depends on: nothing. Standards: `STD-FX`, `STD-DC`, `STD-TS`. The MSP stack rows served: MP-25 (Vonahi vPenTest), MP-26 (Tenable Nessus).

## Why

The one exploited bug that matters to this client is found first. An advisory read late, or a scan list of thousands of lines, hides the one internet-facing server with a known-exploited flaw. The code answers "which of this client's devices carry a product on the KEV list" and shows why each row is where it is. A person decides and a lead approves any change.

## Behaviour

`uv run --frozen python -m workflows.advisories [client ...] [--as-of <UTC time>]` prints JSON; with no client it checks every client in `fixtures/advisories/inventory`.

- **Match.** A KEV entry matches a device when the entry's `vendorProject` and `product` equal a software item on the device (case and spacing ignored). The feed has no version range, so every row carries `version_checked: false` and the installed version for a person to check.
- **Join.** Nessus-shaped rows and vPenTest-shaped findings are joined to the match by CVE and by host name. A scanner or pen-test finding of a KEV CVE on a host the inventory does not know still makes a row (evidence `nessus` or `vpentest`, exposure and criticality `unknown`) and the host is listed as not in the inventory. Findings with no CVE, or a CVE not in the KEV feed, are counted and not ranked.
- **Order.** Rows sort by exposure (internet, internal, unknown), then criticality (critical to low, unknown last), then known ransomware use, then KEV due date, then CVE and device. Each factor is printed on the row. `rank` is the position in that order; there is no score.
- **Emergency list.** A row is an emergency row when it is internet exposed or the KEV entry says ransomware use is known. Each gets a proposed change window: the first window the client's inventory file declares that starts after the as-of time and ends before the KEV due date is over; if none ends in time, the next window with `before_kev_due: false` and a reason; if none, no window and a reason. Every proposal carries `deployed: false`.
- **Isolation.** The client is an explicit argument; a file for another client is refused; one client's inventory and findings are never joined to another's. The by-CVE view only collects results made for one client each.
- **Untrusted text.** Scanner and pen-test names, titles and plugin output are never copied into a result; rows carry ids only.

## Acceptance

- **B47-1** a fixture shaped like the CISA Known Exploited Vulnerabilities JSON feed (cited, shape verified on read date) is matched to each client's synthetic software inventory; output lists affected clients and devices per CVE
- **B47-2** prioritisation uses KEV presence, exposure and asset criticality, each shown; no number is invented (counts reconcile to the fixture)
- **B47-3** the emergency-patch list is a report and proposed change windows only; nothing is deployed
- **B47-4** scanner and penetration-test findings come from fixtures shaped like a Tenable Nessus export and a Vonahi vPenTest findings report (MP-25, MP-26; cited, unverified fields marked UNVERIFIED) and are joined to the KEV match by CVE

Tests: `tests/py/advisories/test_b47_advisories.py` (run with `uv run --frozen pytest -p no:cacheprovider tests/py/advisories`).

## Known limits

- The match is by vendor and product only. A patched version is still listed until a person checks it; that false positive is shown, not hidden.
- The inventory is a neutral stand-in, not an RMM schema (Datto RMM, MP-12, is `B-61`). Exposure and criticality are fields a person sets in the fixture; real values need the client's asset register.
- The Nessus columns and the whole vPenTest shape are UNVERIFIED (`fixtures/advisories/SOURCES.md`).
- Product-name drift between a vendor's KEV name and an RMM's software name is the main real-world miss; an alias table is a later step.
- Change windows are fixture data. Real windows come from the client's change policy and a lead's approval (R2).
