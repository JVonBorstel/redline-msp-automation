# B-87 MCP server over approved levers

Status: **built** (stdio server, CLI, tests). The protocol subset is UNVERIFIED against the MCP specification. Nothing executes through it. Synthetic data only.

> Independently built prototype. Not affiliated with any vendor's or real company's systems. Synthetic data only.

Inventory: `W-TOOL-10`. Controls: `C-01` (never-automate list), `C-03` (role-based authorization; agents may only dry-run writes), `C-04` (client scope on every call), `C-43` (token audience validated, no token pass-through). Depends on `B-16` (runner/bridge) and `B-42` (per-client audit chains). Standards: `STD-LV`, `STD-SC`, `STD-ER`.

## Why

Other agents should be able to press only the buttons they are allowed to press. MCP is the common door for that, so the door must add no power: permissions stay on the lever and in the runner (docs/BLUEPRINT.md section 3), and a fooled client can only reach what the registry and its own identity already allow.

## Behaviour

`python -m mcp` (package `mcp/`, files `server.py`, `__main__.py`, `README.md`):

- **Transport.** Newline-delimited JSON-RPC 2.0 on stdin/stdout. No socket, no HTTP, no subprocess (checked by an import scan). Messages over 1 MiB, batches and unparseable lines get a JSON-RPC error and the loop continues. No MCP library is in `uv.lock`, so the protocol subset (`initialize`, `ping`, `tools/list`, `tools/call`, notifications) is implemented in the standard library.
- **Who calls.** Exactly one of `--as <identity>` (fixed; the process owner chose it) or `--auth-config` plus a token in `B87_MCP_TOKEN` (Entra ID token checked by `core.auth.TokenValidator` on every call: signature, issuer, tenant, **audience**, expiry, MFA, mapped person). The caller is never read from tool arguments.
- **What is listed.** Every registered read lever (R0). With `--include-writes` also every write lever, described as proposal only. A lever whose name matches `governance/never-automate.json` is skipped even if a registry somehow held it. An unauthenticated session lists nothing.
- **Tool shape.** Name = lever name with `.` as `_`. Arguments are exactly `{"client", "params"}`; `params` has the lever's own schema with `additionalProperties: false`. No argument can carry a mode, approval, identity or token.
- **Calls.** One `LeverRunner.invoke(lever, params, identity, client, mode="dry-run")`; the mode is a constant and no approval is ever passed. Role, client scope, lever scope, pauses, parameter validation and the audit record are the runner's. The server's own refusals (bad token, a registered lever that is not an exposed tool, malformed arguments) are written to the audit chain as `denied`, `dry-run`, `applied: false`, with the caller's identity (`unauthenticated` when the token failed). A name that is not registered is passed to the runner, which denies and audits it.
- **Results.** First block: trusted facts as JSON (status, reason, lever, client, identity, mode, `applied: false`, `audit_seq`, `injection_flags`). Reads: the lever data in a `core.guard.wrap_untrusted` block, with injection rules flagged by `detect_injection`, never followed. Writes: the diff (masked like the audit copy) in an untrusted block, then a pending-approval proposal (`id` = the queue's `P-<12 hex>` contract, `executes: false`). Data is capped at 64 KiB. The token never appears in any result, audit record or file.

## Acceptance

- **B87-1** the server exposes registered R0 levers by default; write levers are exposed only in dry-run; every call goes through the runner with the caller's identity
- **B87-2** token audience is validated and tokens are never passed through to adapters; an unknown or out-of-scope lever is denied and audited
- **B87-3** runs on stdio or 127.0.0.1 only; the security checks are listed in `mcp/README.md` with their tests

"Write levers are exposed only in dry-run" is built as: not listed unless `--include-writes`, and then only ever dry-run. Stdio is the only transport; 127.0.0.1 is not offered.

Tests: `tests/py/mcp/test_b87_mcp.py` (`uv run --frozen pytest -p no:cacheprovider tests/py/mcp`), functions named `test_b87_<k>_...`. The fooled-client test is `test_b87_2_fooled_client_unregistered_lever_is_refused_and_audited` (with `..._registered_write_lever_that_is_not_exposed_...` and `..._out_of_scope_lever_for_a_client_...`).

## Known limits

- UNVERIFIED: the MCP message shapes (`initialize` fields, `tools/list` and `tools/call` results, `isError`, protocol versions `2025-06-18`, `2025-03-26`, `2024-11-05`, newline framing) are written from memory; no specification page was opened and no real MCP client was run. Unknown tools are reported as a tool error, not a JSON-RPC error.
- The proposal is returned in the result, not written to the approval queue: `core.queue.store.Source` has no value for this server and `core/` is outside this item's files. Proposing it to the queue is a follow-up that needs that one-word change.
- `--as` trusts whoever starts the process. Token mode reuses the B-89 approver map (`oid` to identity) and mock issuer; no real Entra app registration, scopes or token acquisition flow is exercised, and the token is read once from the environment at start (a long-lived session needs it refreshed by restart).
- Listing does not vary by identity; role and scope are refused at call time by the runner.
- The write result omits the lever's `data` (only the masked diff is returned). Untrusted-data wrapping and the injection heuristics are text conventions a client may ignore; they protect only a client that honours them.
- PowerShell-runtime levers go through the same runner and bridge; only Python-runtime read levers and the mock tenant were exercised in these tests.
- Stdio has no caller authentication of its own; the other end of the pipe is whoever launched the process.
