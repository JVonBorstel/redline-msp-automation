# B-35 Onboarding change plan

> Independently built prototype. Not affiliated with any vendor's or real company's systems. Synthetic data only.

Inventory: `W-ONB-01`, `W-ONB-02`, `W-ONB-07`. Controls: `C-05`, `C-06`, `C-07`, `C-29`, `C-35`. Depends on `B-29` to `B-34`. Standards: `STD-LV`, `STD-PR`, `STD-PS`, `STD-TS`. Decisions in force: identity changes are R3 with two signed-in approvers; verification is callback-on-file plus the client's authorized contact (D6-06); the person affected hears about it in a draft a human sends (HO-9).

## Why

A new hire can work on day one only if six separate changes happen in the right order, and only if the request really came from the client. Today that is a ticket and six admin screens. This item turns one structured request into one checked plan the leads can read and approve, and prepares the welcome and manager notes afterwards.

## Design

- **`user.new`** (PowerShell, `Provisioning\New-UserAccount`): R3, `approval: lead`, verification `requester+contact` (as `user.new-tap`). Creates the user (enabled, with department, job title and manager, no credential, no license) and its mailbox record in the mock. Convergent: same values, empty diff; half-finished run, only the missing part; same upn with other values, refused. Params are patterned strings; there is no free text. No undo is registered (`user.disable` does not remove the account). See `levers/powershell/Provisioning/README.md`.
- **The form** (`NewHireRequest`): `client`, `requester`, `upn`, `display_name`, `job_title`, `department`, `manager_upn`, `start_date`, `role`. Extra fields are refused; every text field has a pattern that excludes line breaks and template characters.
- **Roles** (`workflows/onboarding/roles.json`): per client and role, the license SKUs, group ids and whether the archive is switched on. Versioned, cited, synthetic; a missing or invalid file fails closed. The follow-on levers still enforce their own rules (no free seat, privileged groups).
- **`build_plan`**: (1) `contact.check(requester, "new-account")`; not authorized or not checkable raises `PlanRefused` with the lever's words and nothing else runs; (2) dry-run through the runner as the agent identity, in order: `user.new`, `license.add` per SKU, `group.add-member` per group, `mailbox.enable-archive` if the role asks, `user.new-tap`; (3) per step: `proposed` (diff to apply), `blocked` (reason, e.g. no free seat), or already done (empty diff, listed under `already_done`).
- **Simulated steps.** The steps after `user.new` cannot be dry-run until the user exists. While `user.new` has a diff to apply, they run on a scratch copy of the tenant folder with that diff replayed into it, through the same runner checks and the real audit log, and are marked `simulated`. Once the user exists the next build uses real dry-runs.
- **Drafts** (`welcome_and_handoff`): a fresh build must find nothing left to do (else `PlanIncomplete`). Then `welcome.md` (template `user.new.md`, same placeholders and safe-value rule as `workflows/notify`) and `handoff.md` (for the manager, from `workflows/onboarding/handoff.md`) are written atomically to `<state-dir>/onboarding/<plan-id>/`, each starting with the draft header. Plan ids are a hash of the request, so the same request gives byte-identical files. The code has no network import and never reads the sign-in pass.

## Acceptance

- **B35-1** from a structured new-hire request (form fields, never free text) the workflow builds one change plan: `user.new` (R3, dual approval), licenses, groups, mailbox, TAP; each step is a dry-run proposal with its diff
- **B35-2** the plan is refused when `contact.check` says the requester is not authorized
- **B35-3** a welcome and manager-handoff draft is produced after the plan executes (never sent); a plan re-run after partial execution proposes only the remaining steps (idempotent)

Tests: `tests/py/onboarding/test_b35_onboarding.py`, `test_b35_<k>_...` per id; `levers/powershell/Provisioning/tests/Provisioning.Tests.ps1` for the lever itself.

## Limits and open points

- **Not in the proposal queue.** The steps are proposal-shaped (lever, params, risk class, approvals needed, diff, audit sequence) but are not saved to the queue: `Source` in `core/queue/store.py` is `triage|baseline|rollback` and that file is outside this item. Approval is done step by step through the runner. Follow-up for the queue's owner: add an `onboarding` source, then `build_plan` can save each proposed step. This narrows B35-1 ("each step is a dry-run proposal"); it does not remove the dry-run or the diff.
- **Mailbox.** There is no mailbox-create lever; `user.new` creates the mock mailbox record. A real tenant creates the mailbox from the license (UNVERIFIED). Archive stays the separate `mailbox.enable-archive` lever.
- **Verification is not automated.** `contact.check` is evidence only (B-34). The leads still record the callback on file and the contact's confirmation when they approve `user.new` and `user.new-tap`.
- **Pass delivery.** The sign-in pass goes by the out-of-band channel (B-30); the welcome says a technician gives it separately. Nobody is told that it is ready; the technician does that.
- **UNVERIFIED:** the Graph permission `User.ReadWrite.All` for a create, the mock field names for user and mailbox, and the form's source in a real PSA. Role bundles are invented for two demo clients.
- **Start date** is carried into the manager note only. Nothing schedules the account for that date; creating it early is the leads' call.
- **Leaver, mover and password help** are other items of the wave and are not touched here.
