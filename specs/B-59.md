# B-59 Client documentation upkeep and runbook linting

Status: **built** (workflow, CLI, linter, tests). Read-only: nothing edits a documentation page or a runbook; every fix is a draft proposal for a person. Synthetic data only.

> Independently built prototype. Not affiliated with any vendor's or real company's systems. Synthetic data only.

Inventory: `W-KB-02` (client documentation upkeep), `W-KB-03` (runbook quality). Controls: `C-27`, `C-21`. Depends on `B-56` (RAG ingestion: the KB fixtures in `fixtures/kb/` and their loader `rag/ingest/corpus.py`).

## Why

Client documentation rots: a page describes a device that was retired, omits the one that replaced it, or names a contact who left. Runbooks rot the same way, and a runbook that names a lever the registry no longer has, or that has no owner, fails the technician at 2 a.m. This item finds both kinds of drift and proposes fixes; a person applies them.

## Behaviour: documentation upkeep

`python -m workflows.doc_upkeep report <client> [--as-of YYYY-MM-DD] [--out DIR] [--fail-on-findings]` (module `workflows/doc_upkeep/upkeep.py`). Writes `<out>/<client>.json` (with `report_sha256`) and `<client>.md`, default `build/doc-upkeep/`. Same inputs and `as_of` give the same bytes. Default `as_of` is the date pinned in the documentation fixture; the wall clock is never read. Exit 0 done, 1 findings exist and `--fail-on-findings` was given, 2 bad input.

Inputs, all read-only:

- the client's KB pages: `fixtures/kb/<client>/manifest.json`, through `rag.ingest.load_kb` (B-56);
- the documentation fixture `workflows/doc_upkeep/data/<client>.json`: per page a `last_reviewed` date and structured `claims` (kind `device`, `contact` or `license`, a key and attributes), plus `review_months` and `required_tags`. Invented for this prototype to plant stale, missing and contradictory cases; the KB manifests carry no review dates or structured facts of their own;
- observed state through the mock adapters: devices from `RmmMock` (`fixtures/rmm/`), contacts from `PsaMock` (`fixtures/psa/`), licence SKUs and purchased seats from `GraphMock` family `licenses` (`fixtures/tenant/<client>/licenses.json`). Each adapter serves one client, so the other site's decoy devices never reach a report.

Findings, each with `id`, `kind`, `page`, `subject`, `detail`, `sources` (which data it used) and a `proposal` (`action`, `draft` text, `status: draft`):

- **stale**: a page last reviewed more than `review_months * 30` days before `as_of`; a page claim naming a device, contact or licence that observed state no longer shows; a page that documents a device as in service while it has been offline 60 or more days.
- **missing**: an observed device (not dormant), active contact or licence SKU that no page claims; a page with no review date; a `required_tags` topic no page covers; a documentation record for an article the KB does not hold.
- **contradictory**: a page claim that differs from observed state (device category, contact title, licence seats); two pages giving different values for the same claim; a page filed under one client that names another client; observed state that disagrees with itself (two RMM records for one hostname).

Safety: page text is untrusted. It is searched for other clients' names and screened with `core.guard.detect.detect_injection`; a page with instruction-like text is listed in `flagged_pages` and never followed, and no page text is copied into a finding or a draft. Draft text uses only structured values (hostnames, titles, seat counts) that pass a character allow-list. Vault entries (origin `vault/...` or tag `credential-vault`) are counted in `vault_skipped` and their text is never read.

## Behaviour: runbook linter

`uv run --frozen python tools/lint_runbook.py [files] [--as-of YYYY-MM-DD] [--json]` (default targets: `docs/RUNBOOKS.md` and `docs/runbooks/*.md`). Exit 0 clean, 1 findings, 2 bad input. It prints `path:line: rule: message` and a `proposal` line per finding and edits nothing.

| Rule | Fails when |
| --- | --- |
| `missing-section` | no heading starts with one of the words for purpose (`purpose`, `when this runbook`, `scope`), prerequisites (`prerequisites`, `before you start`), steps (`steps`, `checklist`, `procedure`, `IR-n`), rollback (`rollback`, `roll back`, `undo`, `back out`) or verification (`verification`, `verify`, `check`) |
| `missing-owner` | no `Owner: <role>` line with text and no Owner section with text |
| `missing-last-reviewed`, `bad-last-reviewed`, `stale-review` | no `Last reviewed: YYYY-MM-DD` line; the date is not real or is after `as_of`; the date is more than 365 days before `as_of` |
| `broken-link` | a markdown link to a local file that does not exist (resolved from the runbook's folder); `http`, `mailto` and `#anchor` links are not checked |
| `missing-file` | a backticked repo path with a folder part that does not exist (outside code fences; resolved from the repo root, then the runbook's folder). Not checked: bare file names, paths with spaces, `<placeholders>`, `*` globs, and run-time folders `.tmp`, `build`, `audit`, `.venv` |
| `secret` | any line matches the DC-6 credential patterns of `core/guard/classify.py` (keys, tokens, passwords, connection strings). The value is never printed |
| `unregistered-lever` | a `core.levers invoke`, `pause` or `resume` command (anywhere, fences included) names a lever the registry lacks, or a backticked `family.name` whose family is a registered lever family is not itself registered. `<placeholders>`, module names (`core.levers`) and file names are left alone |

Registered levers come from `core.levers.registry.Registry.load()`.

## Unverified and limits

- The documentation fixture is invented. How the MSP's documentation tool stores pages, review dates and structured assets is UNKNOWN; a real documentation adapter would replace the fixture and the claim shape would change.
- Observed state is the mock adapters' fixtures; their field names follow vendor shapes written from memory (see `fixtures/rmm/SOURCES.md`, `fixtures/psa/SOURCES.md`) and are UNVERIFIED against vendor documentation.
- Thresholds (365 days for a runbook review, `review_months` per client, 60 days dormant) are this prototype's choices, not a standard.
- Section matching is by heading words, so a runbook with a differently worded heading is flagged and the fix is to rename it; a heading that matches a word but is empty is not caught. The linter cannot judge whether a step is correct, only that its shape, owner, date, links, files, secrets and lever names check out.
- The lever check sees lever names only in the two forms above; a lever described in prose is not checked.
- Secret detection is the DC-6 regex set; it can miss a secret that has no recognizable shape.
- No drift schedule, alert or ticket is created; running the report is manual.
