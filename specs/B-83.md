# B-83 Operational logs, request ids and monitoring alert rules

Status: **built** (logging, request scope, threading through runner, gateway and audit, alert rules, evaluator, CLI, tests) on synthetic fixtures and test doubles. Nothing sends an alert and nothing is wired to a real log shipper or pager. Synthetic data only.

> Independently built prototype. Not affiliated with any vendor's or real company's systems. Synthetic data only.

Inventory: `W-TOOL-09`. Controls: `C-40`, `C-11` (never-log list), `C-27`. Standards: `STD-SC`, `STD-AU`, `STD-TS`. Depends on `B-80` (the gateway's circuit breaker, budgets and `model.complete` audit record are what the alerts read).

## Why

The MSP should see a problem before the client calls. Two things stood in the way: the lever runner and the gateway wrote audit records but no operational log, so "is the model provider down for Contoso Dental right now" had no answer short of reading chains; and nothing watched the audit stream. B-83 adds a log that can be shipped anywhere because it cannot hold the thing that must not leave (a prompt, ticket text, a secret), a request id that follows one operator action through every component, and alert rules held as data with an evaluator a test can replay.

## Behaviour

### Content-free logs (`core/obs/logs.py`) - B83-1, B83-3

- One line is one JSON object: `v`, `ts` (UTC, second resolution), `level`, `request_id`, `component`, `event`, `outcome`, `client`, optionally `duration_ms`, `fields` and `dropped`. Keys are sorted, output is ASCII.
- **Allow-list, not scrub-list.** Each value is built only from something that passes a shape check for its slot; a value that fails is replaced by a fixed label (`invalid-event`, `invalid-client`, `req-invalid`, outcome `unknown`) or dropped and counted in `dropped`. Nothing is trimmed, truncated or masked into the line.
  - `component`, `event`: lowercase identifiers chosen by the code that logs. `outcome`: `ok denied error skipped unknown`. `level`: stdlib names.
  - `fields`: only names in `FIELD_RULES`. Counts and lengths (non-negative integers: `input_chars prompt_chars completion_chars latency_ms prompt_est completion_est seq count attempts records changes lever_version`), flags (`ok applied`), closed vocabularies (`status provider mode actor_kind data_class reason`; `reason` is the gateway's fixed code set, e.g. `circuit-open`, `budget:client:tokens`), and three config identifiers (`lever task model`). There is no field for free text, and a string with a space, an upper-case letter, a newline or more than 64 characters cannot pass any check.
  - Every accepted string is also run through the audit redactor (`core.audit.redact`); a value it would change (bearer header, `sk-` key, JWT, long hex or base64 run) is dropped.
  - No `repr` or `str` is taken of a value of unknown type; logging swallows its own exceptions so it can neither leak through an error message nor break the lever or gateway call it observes.
- **Client label (B83-3).** `client` is on every line: the call's client id, else the request scope's, else `_msp` (the same name the audit router uses for events not about one client), and `invalid-client` for text that is not a client id.
- **Stdlib records.** A library logging to `redline.ops.*` has its message, arguments, exception text and stack text discarded by `ContentFreeFilter`; one `log.unstructured` line is written in their place. A pre-set line on a record is trusted only if it passes `check_line`.
- **Wiring.** `configure(stream)` adds a handler; with none configured the logger is silent (`NullHandler`). `OpsLogger("component").log(event, outcome, ...)` and `.timed(event)` are the API; timing uses an injectable timer and clock.
- **Where it logs.** `core/gateway/gateway.py` writes one `model.complete` line per call, whatever the outcome and whether or not an audit sink is set (provider, model, task, status, reason code, data class, lengths, estimates, latency; never the prompt, the completion or a provider's error text). `core/levers/runner.py` writes one line per audited call (`lever.invoke`, `lever.pause`, `proposal.decide` as in the audit record): lever name, mode, status, applied flag, change count, actor kind, lever version, audit seq, duration; never params, the diff or the reason text.
- `check_line(line)` re-validates a finished line and returns the problems (never the offending value). It is the oracle in the tests and can be used on a shipped file.

### Request ids (`core/obs/context.py`)

- `with request_scope("req-...", client="contoso-dental"):` (id optional: a fresh `req-<uuid>` is made) sets a context variable. The lever runner, the gateway and both audit stores read it when the caller names no id: `LeverRunner.invoke`, `Gateway.complete`, `AuditLog.append` and the SQLite audit store. An explicit `request_id` argument still wins.
- Result: one operator action that calls the gateway, invokes levers and pauses one writes audit records and log lines that share an id. Outside a scope each call still gets its own id, as before.
- An id must be 1 to 64 letters, digits, `.`, `_` or `-` and must not look like a secret (the audit redactor must leave it unchanged); anything else raises `ValueError` at scope entry. Context variables are per thread and per asyncio task: a new thread starts with no id.

### Alert rules (`workflows/monitoring/`) - B83-2 (partly, see Known limits)

- `rules.json` is versioned data (`version: 1`). Each rule has `id`, `kind`, `severity` (`critical warning info`), `summary` and kind-specific thresholds. Validation refuses unknown kinds and fields, duplicate ids, a version other than 1, non-positive thresholds, an empty rule list. Tuning a threshold is a reviewed edit of the JSON, not a code change.
- Five kinds, all built:
  - `audit-chain-failure`: one alert per chain whose verification failed (`subject` = chain scope, `detail.broken_seq`).
  - `breaker-open`: per provider, at `min_events` `model.complete` records with reason `circuit-open` inside `window_s`.
  - `budget-exhaustion`: per budget scope (and per client for scope `client`), at `min_events` `budget:*` denials inside `window_s`.
  - `approval-backlog-age`: per client, when the oldest pending proposal is more than `max_age_s` old (equal is not over).
  - `dead-letter-growth`: per client, when the dead-letter count rose by `min_growth` within `window_s`; the baseline is the last sample before the window if any, else the first inside it; one sample alone never fires.
- `evaluate(rules, snapshot)` is pure: no clock, file or network. `Snapshot.now` is the only time. Windows are closed at both ends; events dated after `now` are ignored. Output order is severity, rule id, client, subject, so the same inputs give identical bytes whatever order the snapshot lists came in or the rules were written.
- A snapshot holds `audit_events` (ts, client, event, reason code, provider), `chain_checks`, `pending_approvals` and `dead_letter_samples`. It has no field that could carry content. Alerts carry ids, counts and ages only.
- `audit_events_from_log(path)` and `chain_check(path)` build the first two parts from a real chain file (read-only; only the fields above are copied). Approval and dead-letter inputs are supplied by the caller.
- CLI: `python -m workflows.monitoring evaluate --snapshot <file> [--rules <file>]` (0 no alerts, 1 alerts, 2 bad input) and `check-rules`.
- Fixtures in `workflows/monitoring/fixtures/`: `quiet.json` (everything just under its threshold) and one replayed incident per condition plus `incident-all.json`. Times are fixed (`2026-10-27T12:00:00Z`).

## Acceptance

- **B83-1** content-free JSON logs with request_id, component, event, outcome and timing; a test fails if any log line holds ticket text, a prompt or a secret shape. Tests: 12 hostile strings (prompt, ticket text with an SSN, five secret shapes, 500 characters, newlines, injected JSON, a plain two-word string, an empty string) pushed through every channel (event, outcome, client, request id, component, reason, model, task, lever), field names, wrong types, stdlib records with exception text, 300 random inputs through `check_line`, and the real gateway and runner called with hostile prompts and params.
- **B83-2** (as scoped for this build) alert rules over the audit stream and queue state: audit-chain failure, breaker open, budget exhaustion, approval backlog age, dead-letter growth; replayed synthetic incidents fire exactly the expected alerts, the quiet fixture fires none, thresholds are tested at, one under and one over, and a real gateway run into a real audit file raises the breaker and budget alerts and, once the file is edited, the chain alert.
- **B83-3** client id is a label on every log line. Tests: no client, a bad client string, a stdlib record, a scope client, an explicit client.

Tests: `tests/py/obs/test_b83_obs.py` (`uv run --frozen pytest -p no:cacheprovider tests/py/obs`), functions named `test_b83_<k>_...`.

## Known limits

- **B83-2 is narrower than the roadmap wording.** The roadmap entry names denial spikes, after-hours executes, approvals faster than a human could read, and verify failures. This build implements the five conditions the owner asked for instead (chain failure, breaker, budget, backlog age, dead letters). The four roadmap rules are NOT built; chain failure covers part of "verify failures" only. The roadmap entry should not be marked complete on this change.
- **Residual in the logger.** `lever`, `task` and `model` accept any lowercase identifier (`[a-z0-9][a-z0-9._:-]{0,63}`). A caller that passed a one-word lowercase string there, say a prompt that is the single word "hello", would have it logged. The gateway and runner pass only registry, route and config names there; this is pinned by a test (`..._residual_...`), not closed. Every other slot rejects free text structurally.
- The proof of "never logs a prompt" is the allow-list design plus tests over a hostile corpus and 300 random inputs. It is not a formal proof, and the redactor it leans on is itself a heuristic (docs/THREAT_MODEL.md).
- Not every component logs yet. Only the runner and the gateway do. The scheduler, the queue, the MCP server and the workflows do not, and the lever CLI does not open a `request_scope`, so a CLI run still gets one id per call rather than one per session. Nothing sets the scope automatically for a web request or a scheduled job.
- Alerts are computed, not delivered. Nothing pages, emails or posts; `workflows/notify` is not connected. Nothing schedules the evaluator or builds a snapshot from live stores: approval backlog and dead-letter counts must be supplied by the caller (the sources for them are the B-82 SQLite stores; no adapter is written).
- Thresholds in `rules.json` are prototype defaults, not tuned on any real traffic.
- Gateway breaker and budget state is per process and in memory (B-80), so the alerts see only what reached the audit stream, not live breaker state. A breaker that opens and closes between two evaluations leaves `circuit-open` records only for calls that were actually refused.
- Log timestamps are wall-clock UTC at second resolution; `duration_ms` uses a monotonic timer.
- UNVERIFIED: no log shipper, SIEM or monitoring product was used or opened; the line format is this repo's own and is not checked against any vendor's ingestion schema. Behaviour under asyncio and under multi-process writers was not tested beyond the thread-isolation test. Windows only was exercised in this session.
