# B-29 IdentityOps: revoke sessions, enable (undo of disable), mover property changes

Status: **built** (`levers/powershell/IdentityOps/`, `levers/registry.d/identity.json`, `tests/py/levers/test_b29_identity.py`). Mock tenant only; nothing here has run against a real Entra tenant.

> Independently built prototype. Not affiliated with any vendor's or real company's systems. Synthetic data only.

Inventory: `W-ONB-08`, `W-SEC-04`, `W-ONB-16`. Controls: `C-05`, `C-06`, `C-30`, `C-33`, `C-35`. Depends on `B-28`, `B-16`, `B-19`. Standards: `STD-LV`, `STD-PS`, `STD-XL`, `STD-TS`.

## Why

The first real offboarding and mover steps, each reversible: end a person's sessions, turn an account back on, and change the three directory fields a mover touches.

## Design

- PowerShell module `IdentityOps` (functions `Revoke-UserSessions`, `Enable-UserAccount`, `Set-UserProperty`) through the B-15 host and B-16 bridge. Registry fragment `levers/registry.d/identity.json`; all three levers are R2, write, lead approval, dry-run.
- `graph_scopes` (STD-SC-4) becomes a real `LeverDef` field (a tuple of permission names, default empty) so the fragment can declare them; `schemas/lever-registry.schema.json` is regenerated. Each function asserts its scope first (`$env:REDLINE_MOCK_GRAPH_SCOPES`; unset means granted).
- `user.enable` declares `undo_of: user.disable` (new optional `LeverDef` field) and `undo: user.disable`. `Registry` then sets `user.disable.undo = user.enable` when both are loaded. `levers/registry.json` is untouched, so the many tests and evals that load that file on its own still load (a dangling `undo` there broke 77 of them in a first attempt). A conflicting explicit `undo` on the other lever is a load error.
- Session state lives in a new family file `fixtures/tenant/<client>/sessions.json` (`contoso-dental`, `fabrikam-capital`; `litware-legal` has none). `activeSessionCount` is invented for the mock.
- `user.enable` and `user.set-properties` carry `verification: "requester"` (callback on file, D6-05/C-30). `user.revoke-sessions` does not: it is containment and should be fast.
- The PowerShell writer keeps the file's line ending, so a change and its undo give the same bytes on Windows (CRLF) and Linux (LF).

## Acceptance

- **B29-1** `user.revoke-sessions` (R2, `graph_scopes: [User.RevokeSessions.All]`) dry-runs a diff and its README states the documented lag and that it does not apply to guest users
- **B29-2** `user.enable` (R2) is the registered `undo` of `user.disable`; disable then enable returns the fixture to byte-identical state
- **B29-3** `user.set-properties` changes only department, jobTitle and manager (enum of fields); idempotent; Pester or plain-script tests per STD-PS-9 cover dry-run, execute, idempotency and a scope denial

Tests: `levers/powershell/IdentityOps/tests/IdentityOps.Tests.ps1` (plain script, checks named `B29-n: ...`) and `tests/py/levers/test_b29_identity.py` (`test_b29_<k>_...`).

## Limits and open points

- "Byte-identical" is measured against the canonical layout the Python `MockTenant` writes. The committed `contoso-dental.json` is hand-formatted, so the first write by any writer (the existing `user.disable` included) re-lays it out; that is not new, and not hidden.
- Through the host every refusal (guest, unknown user, scope denied, bad manager) shows as `crashed: RuntimeException`; the reason is in the operational log. A host change to carry a safe reason code is a later item.
- The scope check cannot be driven through the runner (the bridge scrubs the child environment); it is tested in the PowerShell script and through the host.
- Graph permission names other than `User.RevokeSessions.All` are UNVERIFIED. The `manager` value is stored as the manager's UPN (mock shape; Graph uses a relationship).
- The Guest user in `fabrikam-capital/sessions.json` (Alex Ward) is a Guest only there; `fabrikam-capital.json` has no `userType` field.
- Risk class: the decisions in force say identity changes are R3; the item's acceptance fixes R2 for these three, and R2 needs one signed-in lead.
