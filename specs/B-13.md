# B-13 schemas/ folder, generator and cross-language drift check

Status: **built** (`schemas/`, `tools/gen_schemas.py`, `tests/py/contract/test_b13_schemas.py`, `tests/ps/Test-Schemas.ps1`).

> Independently built prototype. Not affiliated with any vendor's or real company's systems. Synthetic data only.

Inventory: `W-TOOL-01` (the lever toolkit). Controls: `C-02` (typed lever schemas), `C-21` (validators reconcile what a client sees). Depends on nothing. `B-14`, `B-15`, `B-17` and `B-18` build on it.

## Why

Python orchestrates and PowerShell acts (blueprint section 4). They share data, not code, so each shape they pass is written down once, as JSON Schema, and both sides check against the same file. Without that, a field renamed in Python silently breaks a PowerShell lever at one client (for example a password reset for one person at Fabrikam Capital that fails with a confusing error), and the MSP finds out from the person, not from CI.

## Behaviour

- `schemas/` holds nine JSON Schema files, draft 2020-12 (STD-XL-1). Each declares `"$schema": "https://json-schema.org/draft/2020-12/schema"`, an `$id` and a `$comment` naming its source of truth.
  - **Generated** from pydantic (STD-XL-2) by `tools/gen_schemas.py`: `lever-registry` (`_RegistryFile` with `levers` typed as `LeverDef`), `identities` (`_IdentityFile`), `change` (`Change`), `lever-result` (`InvokeResult`), `proposal` (`Proposal`).
  - **Written by hand** (no pydantic model exists yet): `lever-request` (the bridge request for `B-15`), `audit-record` (v1 as `core/audit/chain.py` writes it, v2 as STD-AU-2 proposes it for `B-17`), `finding` (the existing `TenantBaselineFinding` class, PascalCase as findings.json and the Power BI CSV use it today), `client` (the proposed `config/clients/<id>.json`, for `B-18` and the owner step `W2-E1`).
- `schemas/examples/` holds at least one known-good and one known-bad document per schema: `<name>.good*.json`, `<name>.bad-<why>.json`. Each bad document breaks exactly one rule, named in its file name.
- `uv run --frozen python tools/gen_schemas.py` rewrites the generated files; `--check` writes nothing and exits 1, naming each file that differs from what the models produce; `--out DIR` writes or checks another folder.
- `pwsh -NoProfile -File tests/ps/Test-Schemas.ps1` validates every example and the real config files with `Test-Json -SchemaFile`, probes each validation keyword the schemas use, and prints `Schemas tests: N passed, M failed` (or `skipped` below PowerShell 7.4).

## Acceptance

- **B13-1** `schemas/` holds exactly the nine files `lever-registry`, `identities`, `change`, `lever-request`, `lever-result`, `proposal`, `audit-record`, `finding`, `client` (`<name>.schema.json`), each valid JSON declaring draft 2020-12, with `$id` and `$comment`. `tools/gen_schemas.py` regenerates the five pydantic-sourced files byte for byte (after line-ending normalisation), never writes a hand-written one, and is deterministic. Every schema has at least one good and one bad example. The Python side agrees with every example it can read: pydantic accepts each good and rejects each bad example of a generated schema; `levers/registry.json` and `config/identities.json` are good documents; the good v1 audit example passes `verify_chain` and the bad ones fail it; the `finding` schema's properties are exactly the `TenantBaselineFinding` class properties; the `audit-record` v1 properties are exactly `RECORD_FIELDS`; the `client` schema forbids anything that looks like a secret value (only a `credential_ref` name, STD-CF-7).
- **B13-2** A test fails when a committed schema differs from the generated one: `gen_schemas.py --check` exits 0 on the committed folder, and exits 1 naming the file when a copy of the folder has one generated schema edited or deleted, or has an extra schema file.
- **B13-3** PowerShell `Test-Json -SchemaFile` accepts every known-good and rejects every known-bad example, accepts `levers/registry.json`, `config/identities.json` and every finding of `Get-TenantBaselineReport -Tenant contoso`. A keyword probe proves each validation keyword used anywhere in `schemas/` rejects a document that breaks only that keyword, and fails if a schema uses a keyword the probe does not cover. Result recorded (closing the STD-XL-3 UNVERIFIED note): with PowerShell 7.6.7 (JsonSchema.Net 7.0.0) every keyword we use is enforced except `format`, which is an annotation only; `date-time` values are checked by Python, not by `Test-Json`. The Python suite runs this script when `pwsh` is available.

Tests: `tests/py/contract/test_b13_schemas.py` (`uv run --frozen pytest -p no:cacheprovider tests/py/contract`), `tests/ps/Test-Schemas.ps1`.

## Not in scope

- Loaders that read `client` or `lever-request` documents (`B-18`, `B-15`), and the v2 audit writer (`B-17`). Their items should update the hand-written schema if they change a field.
- Cross-field rules (a write lever needs lead approval, a proposal id is a hash of its content). The schemas carry shape; the Python loaders keep enforcing the rules and stay the gate.
- Adding `tests/ps` to CI (owner step `W2-E1`).
