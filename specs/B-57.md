# B-57 Cited retrieval, refusal and leakage evals

Status: **built** (retrieval, cited answers, lever, eval, tests). Offline: no model is called, no network. Synthetic data only. Retrieval quality numbers are about a word-overlap stand-in, not a language model.

> Independently built prototype. Not affiliated with any vendor's or real company's systems. Synthetic data only.

Inventory: `W-KB-04` (cited question answering, the retrieval half). Controls: `C-26` (per-client isolation at the retrieval layer), `C-27`, `C-41`. Depends on `B-56` (ingestion, namespaced store, `HashEmbedder`). Standards: `STD-LV`, `STD-ID`, `STD-TS`.

## Why

A technician should get an answer they can check, from their own client's articles and the MSP's runbooks, and never from another client's, a vault entry or a poisoned document. Every sentence names the passage it came from, and when nothing supports an answer the system says so instead of guessing.

## Behaviour

Package `rag/retrieve/` (standard library plus this repo's `core` and `rag`; a test checks the imports).

- **`search(store, embedder, client, query, k=5)`** returns `Passage`s (`chunk_id`, `article_id`, `title`, `text`, `score`, `source_id`, `scope`, offsets). The namespace list is exactly `[client:<caller>, msp-internal]` and is handed to `store.search`, so **the filter is applied in the store**. A client id that is not a safe id (blank, wildcard, `client:x`, `msp-internal`) raises `ValueError`. As a second check, a store that returns a chunk from another namespace, or a withheld chunk, makes the call raise `RuntimeError` (fail closed). A client with no documents sees `msp-internal` only. `scope` is `client` or `msp-internal`, never a client's name.
- **`rag.search` lever** (`levers/registry.d/rag.json`, `levers/python/rag.py`). R0, read, no approval, `required_role: agent`, `client_scope: any`, dry-run supported. Params: `query` (max 300 characters) and `k` (1 to 10). There is **no client parameter**: the client is the runner's (`_meta.client`), so text cannot name another one. The runner audits who asked, not the passages. The index is the synthetic corpus of `fixtures/kb/`, built once per process with `HashEmbedder(1024)`.
- **`answer(store, embedder, client, question, threshold=ANSWER_THRESHOLD, max_sentences=3)`**. Extractive: the passages are split into sentences; each sentence is scored (cosine, after removing common function words from both sides) against the question; sentences below the threshold are dropped; the best (at most 3, no duplicates) are returned **word for word, each followed by `[ch-...]` chunk ids**. If none qualifies the answer is exactly `no source found`, with no sentence and no citation. Each candidate sentence is scanned again with the injection tripwire (`detect_injection`); a hit is never quoted and is counted in `Answer.suppressed`.
- **`check_answer(answer)`** re-verifies rendered text: every non-blank line ends with one or more chunk ids, each id was retrieved, and the sentence appears in a cited chunk. `no source found` is valid only alone.
- **`ANSWER_THRESHOLD`** (0.38) is the value `evals/rag/run.py::choose_threshold` returns: the smallest 0.01 step above the best score any **dev** should-refuse question reaches. A test pins the constant to the eval and to `evals/rag/threshold.json`. Changing the embedder, the corpus or the question set means re-running the eval and updating both.
- **Detector namespace.** `core/guard/detect.py` lists lever namespaces so a request to call a lever in untrusted text is flagged (checked by `tests/py/evals/test_b79_injection_v2.py`). `rag` was added to that list for `rag.search`; no other rule changed and the B-79 corpus numbers are unchanged.

## The eval (`evals/rag/`)

`uv run --frozen python -m evals.rag.run` rewrites `report.md` and `threshold.json`; a test checks the committed report equals a fresh run.

- **Corpus**: `fixtures/kb/` (B-56, not edited) plus `adversarial.json`: three prompt-injected documents (one per namespace), one with hidden zero-width characters, two vault-tagged notes, one document with a secret-shaped value (built at run time), and four clean articles. All go through the B-56 pipeline.
- **Questions** (`questions.jsonl`, 50): answerable, unanswerable, cross-client probes, canary probes, injection probes, vault probes; a `dev` and a `holdout` half.
- **Leakage sweep**: every question is asked as every caller (Contoso Dental, Fabrikam Capital, and Litware Legal which has no documents), 150 runs. The answer text, its citations and every returned passage are searched (case-insensitive) for the other clients' canaries, injection markers, vault canaries and secret shapes, and every returned chunk's namespace must be the caller's or `msp-internal`. Done at the chosen threshold and at 0.0 (answer anything).
- **Reported**: threshold sweep, answer and refusal rates per kind and split, groundedness, expected-article rate.

## Acceptance

- **B57-1** `rag.search` (R0) returns passages with article ids from the caller's client and MSP-internal namespaces only; the filter is applied in the store
- **B57-2** answers cite every claim; with no passage above the threshold the answer is `no source found`
- **B57-3** leakage eval: canary strings planted in client B never appear for client A across the whole question set (must be 0); groundedness and refusal rates reported fixture-based

Tests: `tests/py/rag/test_b57_retrieve.py` (`uv run --frozen pytest -p no:cacheprovider tests/py/rag`), functions named `test_b57_<k>_...`. The spy-store test proves the store receives exactly the two namespaces; a deliberately leaky store proves the eval and the fail-closed check notice a broken filter.

## Interpretation notes

- **B57-2, "cites every claim".** Read as: every sentence of an answer is a verbatim quote of a retrieved passage and ends with its chunk id. No text is generated, so there is no uncited claim to find; `check_answer` is the machine check of that.
- **B57-3, "refusal rates reported".** The threshold is chosen on the dev half so no dev should-refuse question is answered; the holdout half is reported, not gated (it is not zero, see below). The gate is leaks = 0, no cross-namespace citation, groundedness 100%, no store error and no dev false answer.
- **"MSP-internal"** is searched for every caller by design (B-56 decision), so the MSP canary is not a leak; client canaries are.

## Known limits

- UNVERIFIED: nothing was run with a real embedding model or a real documentation export. `HashEmbedder` is lexical: a question with no shared words scores about zero (paraphrases q17 and q18 are refused). The threshold, the answer rate and the holdout false answers describe this stand-in and these fixtures; a real embedder needs the eval re-run and the threshold re-chosen.
- Holdout false answers are not zero (see `report.md`): generic wording such as "reference phrase" matches the caller's own or the shared articles. They are never another client's text.
- Removing function words before scoring (`STOPWORDS` in `answer.py`) is a choice for the stand-in; it is harmless for a semantic embedder but not needed.
- 50 questions and the articles were written by one author. The injection documents are ones the tripwire catches by design, so a zero says the pipeline holds when the tripwire works, not that the tripwire catches real attacks. A missed injection would be indexed and could be quoted; the lever registry's permission checks are the control for that.
- Leak detection is exact planted strings. It does not see a paraphrase of another client's text; the namespace check covers that class structurally.
- The answers are quotes, not summaries; whether the quote answers the question is only checked against an expected article.
- No real vector database adapter; the store is in memory. The lever builds its index lazily on first use.
- `evals/gates.json` has no B-57 gate yet (it is owned by B-84); the gate lives in the eval's own pass/fail and in the tests.
