# 30/60/90 plan for the first three months in an AI and automation role

Status: **proposal, document-only**. It orders work that this repo's roadmap, controls and open questions already name. It is not a commitment, a forecast or a schedule: there are no dates, only windows counted relative to day 1. Everything numeric elsewhere is **fixture-based**.

> Independently built prototype. Not affiliated with any vendor's or real company's systems. Synthetic data only.

## Principles

Each window ends in an exit check that a person can run or read. No window promises a result; each says what will have been looked at, decided or measured. Anything that changes state starts as a dry run with an approval record (docs/BLUEPRINT.md). Items marked owner-only need the repository owner or a protected-file change this plan cannot make itself (`CONTRIBUTING.md`).

## Days 1 to 30: look, measure, ask

- Apply the five-question checklist to the existing scripts, read-only, and record a verdict per script with roles instead of names (`docs/AUTOMATION_FRAMEWORK_REVIEW.md`).
- Replace the assumed minutes and runs behind the top three ideas with timings taken from the people who do the work, and keep the fixture and measured columns apart (`governance/ROI_TRACKER.md`).
- Walk leadership through the policy, runbook and intake pages built in B-92, B-94 and B-95, and ask who holds each owner role (`governance/AI_POLICY.md`, `docs/runbooks/ai-incident-response.md`, `governance/RISK_REGISTER.md`).
- Take the high-risk unverified claims to the people who can settle them: audit status, client mix and the tools in use (`docs/UNVERIFIED.md`).
- Exit check: every script found has a review record, every owner role in the register has a holder or an open question, and `uv run --frozen python -m workflows.assurance briefs check` passes (`workflows/assurance/briefs.py`).

## Days 31 to 60: shadow and score

- Run ticket triage suggestions in shadow mode, where a technician sees the suggestion but nothing acts on it, and count accepted, edited and rejected (`workflows/triage/corrections.py`).
- Hold any state-changing autonomy until the evaluation control is met, which asks for a recorded threshold and 30 days of shadow mode for R1 (`map/controls.json`).
- Ask the owner to wire the proposed eval gate into CI, which touches a protected folder (`docs/changes/B-84.ci-eval-gate.yml`, `tools/eval_gate.py`).
- With the owner's approval for any model download, score one local model on the gold tickets so the local-runner rows of the radar can move on a number (`evals/routing/report.md`, `docs/ENVIRONMENT.md`).
- Start the vendor and subprocessor register with the providers that are actually in use, including none if that is the answer (`map/controls.json`).
- Exit check: the shadow counts sit next to the fixture rates in one table, and each radar row that changed names the evidence for the change (`governance/TECH_RADAR.md`).

## Days 61 to 90: decide and extend

- Re-score the intake ideas with the measured numbers and refresh the ranking table, then let leadership choose what is built next (`docs/LEADERSHIP_BRIEF.md`, `governance/intake_rubric.json`).
- Take the first script that passed the checklist through the normal lever process, as a rewrite with a dry run, an undo and an approval rule; the device remediation item B-62 is the planned home (`map/roadmap.json`).
- Rehearse the AI incident runbook with real roles in the room, since the recorded tabletop was one scripted replay (`docs/TABLETOP_2026.md`).
- Plan staff training and the client conversation guide, both still planned documents (`docs/planned/STAFF_TRAINING.md`, `docs/planned/CLIENT_CONVERSATION_GUIDE.md`).
- Exit check: leadership has a decision on the next automation and on hosted providers, written down with the evidence it used (`docs/DECISIONS.md`).

## Not shown

- No outcome is predicted for any window: not time saved, tickets handled, cost or risk reduced (`governance/ROI_TRACKER.md`).
- The windows are a proposal; whether the work fits real workloads, staffing or the MSP's own change process is unknown (`docs/map/05-governance.md`).
- Several steps depend on answers this repo does not hold, such as who owns each risk and which tools are in use (`docs/UNVERIFIED.md`).

## Unverified

- UNVERIFIED: that a 30-day shadow period is enough to judge a suggestion; the control asks for it, nothing here tested it (`map/controls.json`).
- UNVERIFIED: that the owner-only steps can be done inside the window; they depend on the owner's calendar and review (`CONTRIBUTING.md`).
