# B-74 change note: operations metrics, Power BI exports, problem and CSAT analysis

Status: **built** (workflow, CLI, tests) for the exports; the Power BI model is **document-only**. Read-only; synthetic data only; every figure fixture-based. Spec: `specs/B-74.md`.

- `workflows/reporting/` (new package) and `workflows/reporting/ops/`: `ops.py` (loading, metrics, tables, dictionary, manifest, verify, CLI), `__main__.py` (`python -m workflows.reporting.ops export|verify`), `config.json` (cluster thresholds, CSAT theme words), `data/<client>.events.json` and `data/<client>.csat.json` (synthetic overlays for the three Phase 2 clients).

## Why

Leadership sees where time goes (volumes, SLA attainment, time to first response and resolution, reopen rate, repeat problems, CSAT) per client and across the MSP, and nobody is ranked by an AI (NN-03).

## Individual to macro (L1-L4)

- L1: a technician sees a repeat problem (for example the same printer topic raised by several people) listed with a proposed problem record instead of fixing it ticket by ticket; a user's "time until I can work again" is a column, not a guess.
- L2: Contoso Dental's folder holds only Contoso Dental rows, and a test proves no other client's name, ticket id or tenant word appears in it.
- L3: the MSP folder has per-client rows plus a pooled `ALL` row; every file is hashed in a manifest an auditor can re-check with `sha256sum -c`; no column or value identifies a technician.
- L4: shorter recurring-issue loops and a CSAT trend per client, without technician scorecards.

## Honest limits

- Everything is synthetic and fixture-based. The first-response, reopen and "user confirmed working" times and the CSAT answers are a hand-generated overlay I invented (`workflows/reporting/ops/data/`), not a PSA or CSAT-tool capture, so the attainment, reopen and CSAT figures show the pipeline working, not how any real desk performs.
- Reconciliation: the tests recompute every headline figure from the raw fixture files with separate code. That proves the arithmetic matches the inputs, not that the inputs resemble real data.
- Not done from the roadmap text: first-contact resolution and suggestion acceptance/correction rates (B74-1 mentions them; no source data exists yet), a real CSAT-theme method (the themes are a keyword list), audit records for exports, scheduling, a lead-only gate on who may export.

- UNVERIFIED: the repeat-problem rule (3 or more tickets and 2 or more people on one B-23 topic over the whole period) is a configuration choice, not tuned. Litware Legal has no PSA mock, so its SLA cells are empty (`no-sla`), not zero.

## DECISIONS proposal

D-0xx Ops metrics are fixture-based tables with no person dimension (B-74, 2026-10-27). The export never reads the ticket's technician field, refuses person-like column names in code, and a test scans every export for technician and requester values; clusters are proposals only (`PRB-PROPOSED-...`, empty root cause). Dates come from `--as-of`, never the clock. Why: W-TRN-04, NN-03, D6-21. Alternative: a per-technician table behind a lead-only role (rejected: NN-03 never-automate). What would change it: the owner changing NN-03.
