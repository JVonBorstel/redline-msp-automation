# B-41 change note: rollback from recorded before-state

Status: **built** against the **mock** tenant. Synthetic data only. Spec: `specs/B-41.md`.

## What changed

- New workflow `workflows/rollback/` (`plan`, CLI `python -m workflows.rollback <audit_seq>`). It reads one applied audit record. With a registered `undo` it dry-runs the undo (audited), checks the undo's diff is exactly the recorded changes with before and after swapped, and builds a `rollback` proposal for the normal queue. Without an `undo` it prints the lever README section and the recorded before-state, and proposes nothing. It never executes a write lever.
- New tests `tests/py/rollback/test_b41_rollback.py` (11, named `test_b41_<k>_...`).
- Outside `owns`, minimal: `core/queue/store.py` and `schemas/proposal.schema.json` (new `rollback` member of the `Source` literal, STD-PR-5); `levers/powershell/IdentityOps/README.md` (one "Manual undo" line each for `user.revoke-sessions` and `user.set-properties`, so B41-2 has real steps to print).

## Why

When an automation is wrong, the person is put back first (EU-8, IR-3). The audit already records what each field was before; this uses it so a technician does not rebuild the undo by hand under pressure, while a lead still approves it.

## Individual to macro (L1 to L4)

- **L1, one person.** A wrongly disabled person gets sign-in back by a short, checked path. A change with no undo comes with plain manual steps and the old values, not a guess.
- **L2, the client business.** A mistake costs less time; a wrong rollback is blocked by the drift check instead of overwriting what changed since.
- **L3, the MSP.** The undo is a normal proposal: dry-run, lead approval (four-eyes), callback on file where the undo lever asks for it, and both actions in a verified audit chain. Nothing about "it is only an undo" skips a gate.
- **L4, community.** A tested, repeatable way back makes it safer for every client to automate the first step.

## How the tests prove it

The proposal comes from the recorded before-state and is a pending `rollback` proposal after an audited dry-run; the requester cannot approve it (denial audited); an approval without the callback record fails at the runner; an already-restored state and a drifted state propose nothing; a non-applied record, a missing seq and a broken audit chain are refused. A lever without `undo` prints the README steps and the before-state, writes no audit record and queues nothing. Full path: disable, rollback proposal, lead approval, execute; `contoso-dental.json` and its `sessions.json` are byte-identical to the canonical baseline and the audit shows both applied actions.

## Not done, and caveats

- Masked audit values (contact details) cannot be compared, so such a rollback reports `drifted` and a person does it.
- The proposal id is a hash of lever, client and params, so a second rollback of the same user after an earlier executed one finds the old queue record and is refused with that reason.
- Only the two IdentityOps levers got manual-undo lines; other levers without `undo` print their README section if they have one, otherwise a statement that none exists.
- The tests that start `pwsh` skip when it is missing (it was present when they ran here).

## DECISIONS proposal

D-0xx A rollback is a normal proposal built from the audit's recorded before-state (B-41, W3, 2026-10-22). The workflow proposes the registered undo only when its dry-run diff equals the recorded changes with before and after swapped; otherwise it proposes nothing. The undo gets its own lever's approval rules, not a shortcut. `rollback` is a proposal source. Why: IR-3 puts the person back first, but a stale or masked record could make an automatic undo overwrite newer work. Alternative: execute the undo directly for a lead, or propose even on drift with a warning. What would change it: an incident where the drift refusal delayed restoring a person, or an owner call that some undos may run without a second look.
