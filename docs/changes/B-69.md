Status: **built** (restore lever, restore-request proposal, restore-test workflow, evidence files, CLI, notice template, tests). Mock only: nothing real is restored and nothing overwrites an original. Synthetic data only. Every catalog field name is UNVERIFIED. Spec: `specs/B-69.md`.

## Why

The person gets their file back, and the client knows restores actually work. A restore lands beside the original, never over it, and every client gets a recorded, hash-checked proof that a restore works.

## Individual to macro (L1-L4)

- L1: Sam Patel at Contoso Dental (synthetic) deleted the treatment plan template. A technician verifies it is really Sam asking, and a copy comes back next to the original; if Sam wants it put back over the original, that is a separate approval.
- L2: Fabrikam Capital's restore test restores one item each month and the evidence file shows the two hashes match; a failed test is a recorded failure, not silence. Requests and tests only ever name that client's own items.
- L3: the MSP can show an auditor a dated, hashed evidence file per client, pinned in that client's audit chain, and re-verify it with `sha256sum -c` or `python -m workflows.restore_tests verify`.
- L4: restores stop being the moment a client discovers a backup was never usable; no lever can overwrite a live copy, so a bad restore request cannot destroy newer work.

## Honest limits

- The restore is a mock copy of invented text in memory. It proves the pipeline, not any backup product. All field names are invented stand-ins marked UNVERIFIED; no vendor documentation was read.
- Requester verification is the runner's `verification: requester` record. The catalog has no item owner, so "this person owns this item" is not checked.
- The pick is deterministic per client, date and seed (so a re-run is idempotent), not cryptographically random and not tuned.
- The scheduler job is not registered (`core/scheduler/jobs.example.json` and `adapters/__init__.py` are not in `owns`); a workflow function for the scheduler is provided and tested directly.
- Overwriting an original location is out of scope: it needs its own approval outside this item.

## DECISIONS proposal

D-0xx Restores go to an alternate location only, and restore tests leave hashed evidence (B-69, 2026-10-27). `restore.to-alternate` is `R2`, `approval: lead`, `verification: requester`, and its location param must start with `ALT-`; no lever overwrites an original, and the workflow refuses an original location before calling the lever. A scheduled restore test picks one restorable item per client (deterministic per client, date and seed), restores it to a throw-away alternate location in the mock, compares the SHA-256 of what came back with the hash recorded at backup time, and writes canonical JSON evidence with a `sha256sum` sidecar; the hash is pinned in the client's audit chain, a failed test is recorded as failed, and evidence for a day is never overwritten. Why: W-BDR-03, W-BDR-04; C-05, C-06, C-30, C-08; D6-24. Alternatives: an in-place restore lever with a stronger approval (rejected: a restore over live data cannot be undone and hides the cause of the loss); retrying a failed test until it passes (rejected: it hides the failure). What would change it: the MSP naming its real backup products (Q-09) so restore behaviour and fields can be verified.
