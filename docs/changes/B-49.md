## Why

Who can touch each client is reviewed every quarter (SOC 2 CC6.2, HIPAA 164.308(a)(4)). Two populations: the people holding directory roles in each client's tenant, and the repo's own identities (technicians, leads, agents) that the lever runner lets act for that client.

## Individual to macro (L1-L4)

- L1: Ana, a technician, sees on one row exactly which Contoso Dental tenant roles and repo identities exist and a lead marks keep, remove or investigate, instead of nobody noticing a stale admin.
- L2: Contoso Dental's export names only Contoso Dental; the wider scope of an identity is a count, never another client's name.
- L3: the MSP sees every identity with its role and full client list; agents with an execute capability, extra clients, or no declared need are flagged. Every export, decision and refusal is in the client's own audit chain.
- L4: fewer forgotten admin accounts at small practices and firms; an auditor can re-check each file with `sha256sum -c`.

## Honest limits

- Directory roles are read from the Graph-shaped fixtures; the `$expand=members` shape is UNVERIFIED against the real Graph API (written from memory, no vendor page opened). Only Contoso Dental and Fabrikam Capital have a mock; Litware Legal is refused, not reported empty.
- `userType` and `accountEnabled` are carried only where the mock has them (the committed fixtures do not); members without ids are skipped and counted in `gaps`.
- PIM eligible assignments, role-assignable groups and GDAP relationships (B-54) are not in the export.
- `needs.json` is a declaration by the workflow owner, not measured usage.
- With today's registry no lever lets an agent execute a write, so the committed config raises no flag; flags are proven on copies under `tmp_path`.
- Decisions are recorded, not carried out; nothing schedules the run.

## DECISIONS proposal

D-0xx Access review is file-based and tamper-evident (B-49, 2026-10-23). Per-client and MSP exports are canonical JSON with a `sha256sum`-format sidecar; the lead's decisions go in a separate `.decided.json` that must rebuild the export hash, and with `--audit-dir` the file hash must be pinned in a verified audit chain, so a decision edited later with a fresh sidecar is caught. Dates come from `as_of`, never the clock. The audit hash is written as eight groups of eight hex digits to survive the redactor (STD-AU-5). No lever is added because nothing is removed; removal stays a person's job through the existing levers. Why: W-IDM-09, W-GOV-03; C-38, C-03, C-08. Alternative: auto-removal of flagged identities (rejected: R3 identity reach). What would change it: the MSP's real role model and review cadence.
