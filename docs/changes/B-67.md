## Why

Patching becomes a reviewed monthly rhythm with proof per client. The review is no longer hours of reading release notes: each update shows its ring, its known issues and a proposed action. The compliance figure reconciles to the device list instead of disagreeing between tools. The same failed-patch fix is asked for once per batch. A server reboot has a declared window and a notice draft that a lead approves and a person sends. Network firmware is reported, never touched.

## Individual to macro (L1-L4)

- L1: Jamie at the Contoso Dental hygiene bench is not interrupted by a retry nobody approved; the failed install on her PC is in a batch a technician approves once, with a stated reason.
- L2: Contoso Dental's pack names only Contoso Dental devices; a patch record that belongs to another client's site is dropped and counted, never shown. Fabrikam Capital's clean devices raise nothing.
- L3: a lead sees the month in one file per client: updates by ring with known issues, 2 of 6 evaluated devices compliant (fixture-based), failures by error code, the server window, and which firewall is behind an advisory fix. Files are SHA-256 hashed and re-verifiable.
- L4: a monthly review that takes hours at an MSP becomes a read-and-decide step, and the figures an auditor sees can be re-computed from source (C-21), with the human approval point kept (C-37).

## Honest limits

- The patch-state shape is this repo's own. How a real RMM or Intune reports patch state, classification, rings and install errors is UNVERIFIED (`fixtures/patches/SOURCES.md`); the Datto-shaped device list from B-61 is reused only for the device list.
- Error-code meanings (`0x80070005`, `0x800F0922`) are UNVERIFIED, written from general knowledge. A wrong meaning changes a suggestion's wording, not a count.
- Suggested levers (`device.clear-update-cache`, `device.temp-cleanup`) are names. None is in the registry at this commit (device remediation belongs to B-62), so each says `proposed (not in registry)`; `device.clear-update-cache` is not on B-62's current list and would need adding there.
- Fixed UTC offset in the server window: no daylight saving, holidays or business-hours check (B42-4 / B-62). The notice is plain text, not a `workflows/notify` template.
- Product is mapped from the RMM OS string (Windows 11, Windows Server 2022); anything else is `no-patch-data`. No Intune compliance state, no third-party patching (B-63), no emergency patching (B-47).
- Known issues, fixed-in links and firmware versions are the fixture author's, not a vendor feed. No model, no eval, no accuracy claim.
- Not written to an audit chain: it changes no state. No scheduling: the run is on demand.

## DECISIONS proposal

D-0xx The patch pack is a hashed, read-only, proposal-only report per client (B-67, 2026-10-27). One command writes canonical JSON and a Markdown rendering, each with a `sha256sum` sidecar; the Markdown names the JSON hash. Every RMM device of the client lands in exactly one status so counts reconcile to the device list; patch records outside the client's RMM site are dropped and counted. A known issue counts as resolved only when its fix is itself in the release list and its text passed the injection guard. Failed patches are grouped by error code and carry a suggested lever name whose registry status is computed, not asserted. Network firmware is a version report with no lever, schedule or upgrade step (R3). Why: W-PAT-01, -02, -03, -06, -07; C-21, C-05, C-37. Alternatives: writing the pack into the audit chain (rejected: no state changes); proposing retries as dry-run lever calls (deferred until B-62 registers the levers); a compliance score weighted by severity (rejected: an invented number). What would change it: a real RMM patch export to verify the shape, and the registered B-62 levers.
