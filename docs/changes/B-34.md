Status: **built**. Read-only. Synthetic data only. Spec: `specs/B-34.md`.

Without these the SLA report treated the contact list as a client file and failed with `KeyError: 'client'`.

## Why

Stops an outsider from requesting a new account or access in someone else's name. The technician sees at once whether the requester is on the client's own list for that change type, and the answer is kept as evidence next to the callback-on-file. It never verifies anyone.

## Individual to macro (L1-L4)

- L1: a stranger using Sam Patel's name cannot get an account made; Priya Nair, who may only ask for password resets, is sent to her practice manager when she asks for a new account.
- L2: the practice decides who may ask for changes in its name; an unknown requester goes back to its primary contact.
- L3: the MSP's desk gets the same fast answer every time, as evidence for the record; verification stays a person's callback.
- L4: only the client's own list is read; one office's contacts never authorize a request at another.

## DECISIONS proposal

D-0xx Requester authorization is evidence, not verification (B-34, 2026-10-22). `contact.check` answers from the client's own authorized-contacts list (runner's client only, no client parameter); unknown, inactive and wrong-change-type requesters all get `not authorized: confirm with the client's primary contact`; the result carries `sets_verification: false`. Why: C-30, W-IDM-04, C-27. Alternatives: letting a positive answer count as verification (rejected: callback-on-file is a human act, D6-06); different wording per failure (rejected: tells an outsider which guess was close). Would change: a real PSA adapter holding the list, and the approval page printing the evidence.
