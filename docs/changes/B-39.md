## Why

The "why can't I sign in" call is answered in minutes, and the unsafe fix (unlocking an account under attack) is called out before it is made. The sign-in log's IP addresses and places are personal data, so they reach the technician and never a prompt.

## Individual to macro (L1-L4)

- L1: Priya Nair (Contoso Dental, synthetic) is locked out after six failures. The technician sees at once that four came from two foreign cities, so this is guessing, not a typo, and the right step is the security lead, not an unlock. Ana Lopez has not registered MFA; the answer is registration or an MFA reset, not a password reset.
- L2: the practice's front desk is back at work in minutes, and an account that is being attacked is not unlocked by reflex. Only that client's own log is read, only for the one user asked about.
- L3: the MSP's desk gets the same answer every time, with the source table cited and unchecked codes marked UNVERIFIED. The read is audited by who asked about whom; the log data itself is not copied into the audit.
- L4: a pattern of guessing is caught at the first call instead of after a breach; sign-in places and addresses are not put in prompts or shared across clients.

## DECISIONS proposal

D-0xx Read levers see family files; sign-in data stays out of prompts (B-39, 2026-10-21). `MockTenant.load_for_read` gives a read lever the client's own family files under `_families` (each must name the client). `signins.list` needs the technician role; the lockout workflow builds its model text from a prompt view with no IP address, place, time or log text, and counts (never copies) log text that looks like instructions. Why: DC-3 minimum necessary; C-12. Alternatives: letting the agent read sign-ins (rejected: IPs and places are personal data); a lever that takes a path (rejected: STD-LV-8). Would change: a real Graph adapter, where the read goes through the adapter and not the state copy.
