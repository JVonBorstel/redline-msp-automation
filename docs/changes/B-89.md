# B-89 change note: Entra sign-in for approvers (design and mock token validation)

Status: **built** for the token validator, the page gate and the approval record; **mocked** for the issuer (a local RSA key made in memory at run time stands in for Microsoft Entra ID). Nothing has run against a real Entra tenant. Synthetic data only.

## What changed

- `core/auth/` (new package, mypy strict, standard library plus pydantic only, no new dependency):
  - `jws.py`: strict compact JWS parsing (base64url without padding, 8 KiB cap, JSON object header and payload) and RS256 verification (RSASSA-PKCS1-v1_5 with SHA-256). The verifier rebuilds the whole expected encoded message and compares it in constant time; keys under 2048 bits, wrong-length signatures and out-of-range values are refused.
  - `validator.py`: `AuthConfig` (single tenant id, app id as audience, public signing keys in JWK form, the Entra object id to repo identity map, leeway up to 300 s, maximum lifetime, required `amr`) loaded with `load_auth_config` and failing closed; `TokenValidator.validate(token, now)` returns an `ApproverAuth` or raises `AuthError` with a fixed code (`no-token`, `malformed`, `bad-algorithm`, `unknown-key`, `bad-signature`, `wrong-issuer`, `wrong-audience`, `wrong-tenant`, `wrong-version`, `expired`, `not-yet-valid`, `issued-in-future`, `lifetime-too-long`, `missing-claim`, `no-mfa`, `unknown-approver`). Signature before claims; only `RS256`; no `none`, no `HS256` key confusion, no embedded keys, no `crit`.
  - `models.py`: `ApproverAuth` (method `entra-id-token` or `demo-picker`, identity, `oid`, `tid`, `amr`, `sid`, issue and expiry time). A demo record can carry no claims; a token record must carry all of them. It never holds the token.
  - `mock_issuer.py`: `MockIssuer`, labelled MOCK, makes a 2048-bit RSA key in memory (seeded for tests), publishes its JWK and signs synthetic Entra v2.0 ID tokens.
- `tests/py/auth/test_b89_auth.py` (new): 47 tests, `test_b89_1_...` to `test_b89_3_...`.
- `specs/B-89.md` (new): design (target OIDC flow) and acceptance.

### Outside this item's `owns` (minimal, needed to meet B89-1 to B89-3; please review)

- `ui/app.py` (B-03's page): `App(queue, auth=None)`. With a `TokenValidator`, the pending page, the audit page and `POST /decide` need `Authorization: Bearer <ID token>`; the approver is the token's identity, a form `actor` naming someone else is refused, the picker is not rendered and `?as=` grants nothing. A decide with no valid token returns 401 with `WWW-Authenticate`, leaves the proposal pending and writes one audit record (agent `unauthenticated`, status `denied`, `approver not authenticated: <code>`). Without a validator (the demo) the page behaves as before and records `ApproverAuth.demo(actor)`. About 90 lines.
- `ui/__main__.py`: exactly one of `--demo` or `--auth-config FILE` is required; neither (or a config that does not load) exits 2 before any state is created or any port bound; both is an argparse error (exit 2). A second startup line names the sign-in mode. About 25 lines.
- `core/queue/store.py`: `Proposal.approver_auth` (optional, only on decided lines, must name `decided_by`); `decide(..., auth=None)` keeps it on the approved, final and rejected lines and in a reject's audit result. About 30 lines.
- `docs/DEMO.md` and `docs/TRACE_T3101.md`: the approval page command gains `--demo` (one line each). Without it the page now refuses to start, which is the point of B89-1.

## Why

An approval of an MFA reset is a real person's act. Until now the approver was a name picked from a list (STD-ID-7, the D-023 known gap, AIR-10). D6-05 and D-024 require authenticated approvers before any R2 or R3 approval, and B-28 (R3 dual approval, B28-6) builds on this validator.

## Individual to macro (L1-L4)

- L1: before Priya Nair's (synthetic, T-3101) MFA reset runs, the lead who approves it has proven who they are with a signed Entra token that used MFA; the record says which methods and which session, so a stolen picker click cannot reset her phone.
- L2: Contoso Dental's approvals are tied to a signed-in the MSP lead scoped to Contoso, with a session id that can be matched to the tenant's sign-in log, which is what a dental practice's HIPAA review or an RIA's examiner asks for.
- L3: the MSP gets C-44 as tested code (validator, page gate, record), the SOC 2 CC6.1 evidence shape for approvals, and a clean seam for B-28's two-signed-in-leads rule; the demo stays usable but is labelled and recorded as demo.
- L4: the help-desk social-engineering path across hundreds of small-business tenants loses the "anyone at the console can approve" step; an approval has to be a real, MFA-signed person.

## Honest limits

- The issuer is a mock. Claim names, the v2.0 issuer format and the `amr`/`sid` claims follow Microsoft's published ID token reference and are **not verified** against a live tenant (docs/BLUEPRINT.md hard rule 7). Whether a tenant's ID tokens always carry `amr` and `sid` for this app depends on its configuration; if not, the validator refuses (fail closed).
- There is no browser sign-in. The token travels in an `Authorization` header because the page has no script; the OIDC authorization-code-with-PKCE flow, server sessions bound to `sid`, sign-out and key-set refresh from the tenant's published keys are W9 work (`specs/B-89.md`, Design).
- A token can be replayed until it expires (default maximum lifetime 1 hour plus 60 s leeway). The target server session closes this.
- The RSA verification is hand-written on the standard library (about 20 lines) to avoid a new dependency; it is tested against signatures from the mock issuer, not against a Microsoft-issued token.
- The runner's execute audit record does not yet carry the sign-in record or a `demo` mark; that is B28-4 and B28-6 (runner fields). The queue lines and reject records do.
- `App(queue)` with no `auth` still means demo for existing tests; only the CLI forces the explicit choice.

## DECISIONS proposal

**D-0xx (B-89) Approver authentication: Entra ID v2.0 ID tokens, validated offline; the demo picker only behind `--demo`.**
Decision: approvals are accepted only from a person whose Entra ID token validates: RS256 against the configured tenant keys, `iss` = `https://login.microsoftonline.com/<tenant>/v2.0`, `aud` = the approval app's id, `tid` = the tenant, within `exp`/`nbf`/`iat` and a 60 s leeway, lifetime at most 1 hour by default, `amr` containing `mfa`, `sid` present, `oid` mapped to a configured identity. Role and client scope stay in the queue and runner. The approval record keeps method, `oid`, `tid`, `amr`, `sid` and times, never the token. `python -m ui` needs `--demo` or `--auth-config`; demo decisions are recorded as `demo-picker`.
Why: D6-05 and D-024 (authenticated approvers before R2/R3), C-44, GLBA safeguards (c)(5) MFA, HIPAA 164.312(d). Standard library verification keeps STD-PY-2 (no new dependency); the alternative (`PyJWT` plus `cryptography`) is the likely choice for the real W9 integration and needs the owner's approval then.
Exception recorded: B-89 edits `ui/app.py`, `ui/__main__.py`, `core/queue/store.py`, `docs/DEMO.md` and `docs/TRACE_T3101.md` (listed above) because the acceptance lines live in the page and the record.
