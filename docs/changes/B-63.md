## Why

The person gets the app they need without an unvetted installer: only catalog items are deployable, at a pinned version and hash, and only if the client approved them. Updates to third-party software are reviewed as proposals per ring, pilot first, so a bad build reaches a few machines before all of them.

## Individual to macro (L1-L4)

- **L1 a dentist at Contoso Dental (synthetic):** asks for the imaging viewer; it comes from the vetted list, not a download she found.
- **L2 Contoso Dental:** only software the practice approved reaches its PCs; the old PDF tool found on one PC is listed as not approved, not updated.
- **L3 the MSP:** one catalog and one lever replace ad hoc installers; each request is approved, audited and idempotent, and updates arrive as ring proposals with counts.
- **L4 the community:** a client's device or approved list is never used for another client (decoy records prove it).

## Honest limits

- Mock only. No RMM call was made; `device.install-app` records a request in the client's mock state. How a real RMM would receive it (a component, a quick job) is not designed here, and per D6-26 the program does not run RMM components.
- The `sha256` values are hashes of invented text, not of installers. Verifying a downloaded file against the pin is not built. Real vendor hashes and signing checks are UNVERIFIED and need a vetting step before this is used for real.
- The lever's handler cannot see the client's device list (handlers get tenant state only), so a technician could record a request naming a device uid that is not the client's. The review only proposes the client's own RMM devices, and a real RMM would refuse the foreign uid; the mock does not.
- The registry `package_id` enum is static, so it lists every catalog id; the per-client part is enforced in the handler. A test keeps the enum equal to the catalog. A new package needs a catalog entry and a registry enum change together.
- Installed versions and rings are invented fixtures (`installed-software.json`); a real RMM software audit would be the source and its shape is unchecked. Ring order is fixed (pilot, then broad) and nothing yet checks the pilot ring finished before the broad proposal is approved; a lead decides.
- Versions are compared as dotted numbers; vendor formats with letters are reported as unreadable, not guessed.

## DECISIONS proposal

D-0xx Deployments come only from a hash-pinned, per-client approved catalog (B-63, 2026-10-27). `device.install-app` accepts a catalog id only (registry enum), re-checks the client's approved list in the handler, and records the catalog's pinned version and hash; it never accepts a URL, file name or command. Third-party updates are proposals per ring (pilot, then broad) with dry-run calls, never executions. Why: W-EP-04, W-PAT-04, C-05, C-06, C-32. Alternatives: a free-text package name checked against a list at run time (rejected: the schema should refuse before code runs); a per-client enum (not supported by the registry today). What would change it: a registry that can take a per-client enum, or real vendor hashes and a verifying install step.
