# B-36 change note: offboarding change plan with completion proof

Status: **built** (Python workflow, config, synthetic LOB list, tests). Synthetic data only. Spec: `specs/B-36.md`. `tests/py/offboarding` (20) passes locally on 2026-10-22; the full suites run in CI.

## What changed

- `workflows/offboarding/` (new): `offboarding.py`, `__main__.py` (`plan`, `verify`, `reconcile`), `config.json` (step order, lever names, retention and reply settings), `data/lob-apps.json`, `README.md`.
- `plan` orders block sign-in, revoke sessions, mailbox to shared, auto-reply, OneDrive manager grant, group removals and license removals; dry-runs each through the runner; queues one proposal per change for a lead. License removal is `deferred` until its retention window ends. Device steps are `manual until W6`; LOB apps are a checklist.
- `verify` reads every target state (read-only) and writes a sealed completion record that lists each step not in its target state. `reconcile` checks the record against the audit log.
- `tests/py/offboarding/test_b36_offboarding.py` (new): tests named `test_b36_<k>_...` for B36-1, B36-2 and B36-3.
- No file outside Owns was changed.

## Why

A leaver's access is provably gone, with proof tied to the audit records, instead of a hand-ticked checklist.

## Individual to macro (L1-L4)

- L1: when Ana Lopez (synthetic) leaves, sign-in and sessions end, mail is kept as a shared mailbox with a reply for senders, the manager gets time-limited OneDrive access, and the person's access to groups ends. Someone who is wrongly offboarded is stopped by the lead's approval and the dry-run diff.
- L2: the client can show an auditor, and its own insurer, that a former employee has no access to patient or customer data; the license comes back only after the retention window, so nothing is cut early and no seat is paid for forever.
- L3: `W-ONB-08`, `-09`, `-10`, `-11`, `-13` and `-14` become one plan with one proof; nothing is dropped silently (refused and skipped steps are listed); the same plan twice queues the same proposals once.
- L4: the plan and proof shape is the same for every client, with no per-client code; one client's person cannot appear in another's plan (state is read per client).

## Deviations and honest limits

- **LOB source (UNVERIFIED gap).** The roadmap says the checklist comes from the client record, but no client schema or fixture has such a field. The list is a synthetic stand-in in `workflows/offboarding/data/lob-apps.json`. A later item that owns `schemas/client.schema.json` should add the field.
- **Queue source.** `core/queue/store.py` has no `offboarding` source and `core/` is not in Owns, so proposals use `baseline` (`config.json`, `queue_source`). Add `offboarding` to the queue's allowed sources in a later change.
- **Completion record is not an audit entry.** The audit modes and events are closed in `core/audit`. The record pins the audit head hash and lists the plan's seqs; `reconcile` checks them.
- **Verify reads the tenant files directly.** There is no read lever for mailbox or license state (B-33 says so). The file layout is the one the lever modules write; the end-to-end test (needs `pwsh`) runs the real levers and then verifies.
- **The announcement to the person** (wave goal) is not built here: the notify templates exist per lever but this item's acceptance does not call them.
- **Forwarding** is in the `W-ONB-09` name but is not a lever (B-33), so it is not planned.
- Fixture field names are UNVERIFIED against vendor docs.
