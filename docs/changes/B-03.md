# B-03 change note: approval page (verification capture, scoped listing, diff, undo and impact shown)

Status: **built** (queue, seed CLI, page, tests). Synthetic data only. With B-02, demo step 6 now works live on the page again: the lead picks how the caller was verified before approving.

## What changed

- `core/queue/store.py`:
  - `Proposal.verification` (optional): set on the `approved` and final lines of an approved proposal; never on a pending or rejected one.
  - `ProposalQueue.propose(proposal, agent)`: dry-run through the runner as the agent first, queue only an `ok` dry-run (STD-PR-1, DR-15); idempotent on id with no second dry-run.
  - `ProposalQueue.list(status, viewer=None)`: with a viewer, only that identity's clients; an unknown viewer sees nothing (DR-12).
  - `ProposalQueue.refuse(...)`: audits an approval the page turned down; the proposal stays pending (STD-PR-4).
  - `VERIFICATION_METHODS`, `NUMBER_ON_FILE_SOURCES`, `NUMBER_ON_FILE_PREFIX`: one definition for the page and tests.
- `core/queue/__main__.py`: `seed --demo` goes through `propose` as `triage-bot`, prints the dry-run seq, exits 1 if a dry-run is refused; `list --viewer`.
- `ui/app.py`: the demo sign-in is a GET picker (`/?as=<lead>`); the page lists only the viewer's clients. Each pending proposal is a card with the person (UPN), the L1 impact line, the masked dry-run diff from the audit log, the undo lever or `no undo lever: manual undo`, and its own decision form. The form has the verification selects for identity levers. The server enforces the B03-2 rules, refuses unknown form fields and audits each refusal. The B-02 bridge (`verified` with no rules) is replaced.
- `ui/static/app.css`: card, diff and fieldset styles; one column under 600 px (phone).
- `tests/py/queue/test_b03_approval_page.py` (new): 38 tests, `test_b03_1_...` to `test_b03_4_...`.
- `specs/B-03.md` (new).

### Outside this item's `owns` (minimal, needed because B-03 replaces the B-02 bridge)

- `tests/phase1/test_ui.py`: the `decide()` helper also posts `number_source=psa-contact` (one line). Without it, the SC-1 approve-through-the-page test is now correctly refused: a callback with no number-on-file source.
- `tests/py/levers/test_b02_runner_gates.py`: in `test_b02_2_page_bridge_records_the_method_and_refuses_unknown_ones`, an approve with no verification is now refused by the page (400, still `pending`) instead of reaching the runner and ending `failed`. That is two assertion lines plus a comment.

### Visible output changes (list these in the PR)

1. The pending page is now a list of cards, not a table, and shows only the signed-in lead's clients. The sign-in is a GET picker with a Switch button.
2. Approving `user.reset-mfa` or `user.disable` on the page needs a method and, for a callback, the number's source. Without them the page answers `Refused: ...` and nothing changes, where before (B-02) the proposal went to `failed`.
3. `seed --demo` writes three `dry-run` audit records (agent `triage-bot`) before queueing, and each output line ends with `[dry-run seq N]` (or `[already queued]`). A fresh demo audit log therefore starts at seq 4 for the first decision. Its exit code is 1 if a lever is paused.
4. `queue.jsonl` lines now carry `"verification": null` or the verification object.
5. The Decided table adds a "Requester verification" column. The outcome banner names the verification.

## Why

The human approval step becomes the place where the person is protected: verified, scoped and shown exactly what will happen. B-02 made the runner refuse an unverified identity change. Without this item the page had no way to record a verification, so a lead could not approve an MFA reset there at all.

## Individual to macro (L1-L4)

- L1: Ana Lopez (synthetic, T-1001) calls about a lost phone. Before her MFA is reset, the lead sees her UPN, the line "One person loses their MFA methods and must re-register...", which methods will go (types only, no phone number), and that there is no undo lever, so a mistake is fixed by hand. The lead must record that they called her back on the number from the PSA contact record, and that number is never typed or stored.
- L2: Contoso Dental's proposals are visible only to leads who serve Contoso. Every approval of a sign-in change records how the caller was verified and by whom, in the queue file and the audit log.
- L3: the MSP gets C-30 as a working, evidenced control on the page and the runner (not one or the other). Demo proposals now carry the same audited dry-run trail as real ones (STD-PR-1), and a mis-scoped click is denied and recorded.
- L4: the help-desk social-engineering path that attackers use against small businesses meets a required out-of-band check at the approval step, at every client at once.

## Honest limits

- The viewer picker is a demo sign-in (STD-ID-7). Listing is scoped to the chosen lead, but nothing stops someone at the page choosing another lead; the decide checks still apply to whichever lead is chosen.
- The verification is an attestation: the page records the lead's choice, not proof that the call happened.
- The page shows the diff of the latest matching dry-run, which may be older than the current tenant state; execute recomputes it. The page warns, but does not refuse, when no dry-run exists.
- `finding-reference` uses the proposal's `ref`. A ref with characters outside `[A-Za-z0-9._:#/-]` cannot be recorded, so that approval is refused.
- The page reads the whole audit log on each render to find dry-runs (fine for the demo, linear in log size).
- The CLI `python -m core.levers invoke --verified callback-on-file` (B-02) still accepts a callback with no number source. Only the page enforces the source.
- `docs/DEMO.md` step 6 (page path) and `docs/COVERAGE.md` / governance status rows are not in this item's `owns`.
