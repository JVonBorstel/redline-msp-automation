## Why

Ransomware does not find the one mailbox nobody backed up. The report lists, per client, the users, mailboxes and sites no active policy covers, the policies that keep data for less than the client needs or are not immutable, and the DR plan sections nobody has reviewed in N months, and drafts a tabletop exercise outline from them.

## Individual to macro (L1-L4)

- L1: Lena Fischer at Contoso Dental (synthetic) started this month. Her mailbox and OneDrive were never added to the backup policies; the report names her before a deleted mailbox does.
- L2: Contoso Dental's report names only Contoso Dental; Fabrikam Capital's seven-year retention requirement is checked against its own policies (OneDrive keeps three years).
- L3: the MSP gets one weekly-readable page per client with counts that reconcile, and a tabletop outline that already points at the real gaps instead of a generic scenario.
- L4: fewer small practices learn at restore time that a mailbox, a site or an immutable copy was never there; an auditor can re-check each file with `sha256sum -c`.

## Honest limits

- No backup product documentation was read; all field names are invented stand-ins. Retention and immutability requirements and the DR age are synthetic fixture values.
- Coverage is read from policy scope; no job result or restore was checked, and "immutable" is taken as stated.
- The inventory is hand-made, not read from Graph or Exchange Online. Teams, groups, public folders and archive mailboxes are not modelled.
- The DR plan check is by review date only; the report cannot read plan content.
- No audit record or identity check (R0 report on synthetic data); nothing schedules the run.

## DECISIONS proposal

D-0xx Backup coverage and DR plan upkeep are read-only, hashed report pairs (B-70, 2026-10-27). Per client, one fixture gives a report as canonical JSON plus Markdown, each with a `sha256sum` sidecar; the JSON pins the Markdown hash, so a replaced Markdown file is caught. A policy covers an object only when active and in scope; a paused policy covers nothing. Retention equal to the requirement passes; a missing retention or immutability value is reported as "not stated", never assumed fine. A DR section reviewed exactly N months ago is current. The tabletop outline is a draft built from the findings. Dates come from `as_of`, never the clock. Why: W-BDR-05, W-BDR-06, W-BDR-08; C-21, C-39. Alternatives: reading Graph and the backup adapter directly (rejected for now: B-68's fields are unverified and its fixtures hold no policy scope); writing fixtures under `fixtures/backup` (outside `owns`). What would change it: the MSP naming its backup product (Q-09) so policy fields can be verified, and real contract terms.
