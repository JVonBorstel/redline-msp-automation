Status: **built** (stdio server, CLI, tests). MCP protocol shapes UNVERIFIED. Synthetic data only. Spec: `specs/B-87.md`.

## Why

Agents and Claude may press only the buttons they are allowed to. The server adds no permission of its own: each tool call is one `LeverRunner.invoke(..., mode="dry-run")` as the caller, so role, client scope, lever scope, pauses, parameter validation and the audit record are the runner's.

## Individual to macro (L1-L4)

- L1: Ana's request reaches the right read lever through an agent without the agent being able to widen what it does; a write comes back as a diff for a lead, not as a change.
- L2: a tool call for a client the caller is not scoped to is denied and recorded in that client's own chain.
- L3: the MSP can let another agent use the levers and still show an auditor that nothing executed through the door, and every refusal is in the chain.
- L4: a worked pattern for putting an MCP door over governed actions without moving permissions into the door.

## Honest limits

- MCP message shapes, protocol versions and newline framing are written from memory and not checked against the specification or a real client.
- The pending-approval proposal is returned, not queued (`Source` in `core/queue/store.py` has no value for it; `core/` is outside this item).
- Token mode reuses the B-89 validator and mock issuer; no real Entra app, scopes or token flow. The token is read once at start. `--as` trusts the process owner.
- Listing is the same for every identity. Untrusted-data wrapping only helps clients that honour it.
- Gates note: `ruff format --check .` reports 2 files already unformatted on `enterprise` before this change (`workflows/enrichment/enrichment.py`, `tests/py/tools/test_orphan_tests.py`); not touched here.

## DECISIONS proposal

D-0xx The MCP server is a door over the runner (B-87, 2026-10-27). It lists registered read levers by default and write levers only with `--include-writes`, always calls the runner with the constant mode `dry-run` and no approval, builds tool schemas from lever schemas, takes the caller from start-up (fixed identity or a token checked on every call), and audits its own refusals. Why: C-01, C-03, C-04, C-43; permissions on the lever, not the model. Alternatives: an MCP library (none in `uv.lock`; no installs allowed), exposing execute behind approval records (rejected: the door would carry approval credentials), an HTTP transport (rejected: stdio is enough and has no listener). What would change it: the MSP's real agent platform and its MCP client.
