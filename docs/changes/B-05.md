# B-05 change note: triage output shows the impact trace and the verification needed

Status: **built** (text and `--json` output, tested). The runner gate that enforces the verification is `B-02`; the approval page showing the same trace is `B-03`. Synthetic data only.

## What changed

- `workflows/triage/triage.py`: `TriageResult` gains `who_this_affects` (L1-L4 lines), `risk_class` and `before_approval`, set only when a proposal is made, by a new `_lever_trace()` that reads the proposed lever's registry entry. `before_approval` is the constant `CALLBACK_ON_FILE` ("call back on the number on file") when the lever declares `verification: "requester"`. `explain()` prints a `Who this affects` block and a `Before approval:` line after the proposal; `to_json()` adds the three keys (null without a proposal).
- `workflows/triage/__main__.py`: docstring only (says the output now carries the trace). No behaviour change.
- `tests/py/triage/test_b05_trace.py`: 14 tests named `test_b05_<k>_...` for B05-1 to B05-3.
- `specs/B-05.md`: the acceptance ids, refined.

## Why

Step 2 of the demo: the person behind the proposal is visible before anyone approves it, and the lead is told the one check that stops a social-engineered MFA reset.

## Individual to macro (L1-L4)

- L1: Priya Nair (synthetic, T-3101) asks for an MFA reset; the technician sees that a wrong reset locks her out or lets an impostor in, and that she must be called back on the number on file, not a number in the ticket.
- L2: Contoso Dental's lead sees the R3 class and the client-level impact before approving, so an identity change is handled as a security event.
- L3: the MSP's triage output now carries the same trace for every proposal on every client, from one registry entry, which is evidence for C-30 and the explainability rule (STD-PR-6).
- L4: the callback rule is shown at the moment a help-desk attacker would push for speed; doing it every time is the community-level defence against that breach pattern.

## Honest limits

- The callback line is **guidance, not enforcement**: until `B-02`, an approve-and-execute without a recorded verification still runs. The text says the lever requires it; it does not claim it is checked.
- The trace is read from the registry, so it is only as good as the lever's `impact` lines (B-01). A lever without `impact` (possible only when built in code) proposes without a trace; that is tested.
- `risk_class` is shown alongside the trace though the acceptance names only the L1-L4 lines and the callback; it is the same registry source and helps the lead weigh the request.
- `tests/py/triage` is not in the default pytest run until `B-06`; the B05-2 test re-runs the SA-1 to SA-4 tests in a subprocess (the venv's own interpreter), which adds a few seconds.

## DECISIONS note proposal

D-0xx Triage shows the lever's trace (B-05, 2026-10-22). A triage proposal carries `who_this_affects` (the lever's `impact` L1-L4), `risk_class` and `before_approval` ("call back on the number on file" when the lever's `verification` is `requester`), in both the text and the JSON output, read from `levers/registry.json` by lever name only. Why: the lead sees the person and the social-engineering check before approving, and no ticket text can enter those fields (C-14). A flagged ticket gets no lever and no trace.
