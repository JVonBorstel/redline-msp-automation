## Why

Python decides; PowerShell acts. The host is the narrow last step, so that one lever's mistake for one person cannot import a neighbour module, run an unexported helper, set a client by parameter, or print a stack trace into a technician's screen or the audit.

## Individual to macro (L1 to L4)

- **L1, one person.** Priya Nair (synthetic, Contoso Dental) loses her phone. The MFA reset reaches PowerShell as a dry-run that calls the function with `-WhatIf` and returns the diff for the lead to approve. A bug in the lever shows up as "user.reset-mfa crashed: RuntimeException", not as a half-reset account or a stack trace.
- **L2, the client business.** The request's `client` is passed by the host, and a param can never override it, so a dental practice's or a wealth manager's lever call cannot be pointed at another firm by a crafted parameter.
- **L3, the MSP.** One tested host for every PowerShell lever: authors write a function with an approved verb and `-WhatIf`, not their own JSON plumbing. Crash text stays out of the audit (STD-ER-5). `Test-Modules.ps1` gives each module's tests one summary line the build automation and CI can read.
- **L4, community.** A fooled agent or an injected request can only name a function the module exports, with parameters it declares, in the one module it names. The blast radius of a bad request is one function with schema-checked inputs.

## How the tests prove it

- **B15-1.** The real host runs as a child `pwsh` with JSON on stdin: read (exit 0), dry-run with `-WhatIf` (applied false, diff, no "What if:" on stdout), execute (applied true, no confirmation prompt), noisy lever output never on stdout, the as_of and client reach the function. A sibling module is not imported unless named (a live canary shows the check is real). Bad JSON, empty stdin, schema breaks, unknown version, unknown field, path-shaped module name and a missing modules folder exit 2. A missing module, unknown or reserved param, dry-run of a function without `-WhatIf`, a lever claiming `applied` in a dry-run, a malformed diff and a timeout are denied or error with exit 1. Every result plus `identity` and `audit_seq` validates against `lever-result.schema.json`.
- **B15-2.** A `throw` containing a message, a Windows path and a canary string yields exactly `ticket.crash crashed: RuntimeException` on one stdout line, with none of those strings; the detail is in the log file only when `-LogPath` is given. `Write-Error` is a failure, not an ok.
- **B15-3.** A function defined but not exported, a built-in command name, a non-existent function and another module's function are all denied with exit 1 and nothing runs. `Test-Modules.ps1` is tested against a fixture tree (pass, fail, crash, no tests folder, silent): sums are right, a crash or a silent file counts as 1 failed, exit 0 or 1.

## Honest limits and decisions for others

- **`audit_seq` question from B-13:** the host result is lever-result minus `identity`, `approver`, `audit_seq`; **B-16 must add those three** before building an `InvokeResult`. No schema edit was needed.
- **Dry-run needs `-WhatIf`.** A function without it is denied in dry-run (fail closed). The bridge (B-16) should send read levers as `execute`. If that is wrong for the registry (`dry_run: true` reads), B-16 or a later item can add an explicit read marker; the safe default stays.
- **Timeout stops the pipeline, not necessarily native child processes** a lever started. Real levers should not shell out; the timeout is a backstop, not a sandbox. In-process runspace isolation is for output and imports, not a security boundary against a malicious module (modules are reviewed code in this repo).
- The result's `diff` members come from the lever's own object; the host checks shape, not truth. Output reconciliation (C-21) is still a Python-side job.
- Not proven here: PowerShell below 7.4 (tests report skipped), PSScriptAnalyzer (not installed, D-002), Pester 5 style.
- `tests/ps` is still not in CI or the build automation (owner step W2-E1).

## DECISIONS note proposal

D-0xx The lever host is a stdin/stdout JSON process with fail-closed rules (B-15, W2, 2026-10-21). `Invoke-LeverRequest.ps1` validates the request against `lever-request.schema.json`, imports only `levers/powershell/<entry.module>`, requires the function to be exported by that module, maps `params` to declared parameters (never `Client`, `AsOf` or common parameters), calls with `-WhatIf` for dry-run and refuses a dry-run of a function that has none, runs in a null-host runspace with errors terminating, and returns `<lever> crashed: <type>` for any exception. Its result is lever-result minus `identity`, `approver`, `audit_seq`, which Python adds (it writes the audit). Why: the Python runner decides, the host must not widen what it decided. Alternative: let the host infer reads from writes (guesses), or return the full InvokeResult from PowerShell (the host would have to invent an audit sequence). What would change it: a registry field marking a lever read-only (then dry-run of reads could be allowed without `-WhatIf`).
