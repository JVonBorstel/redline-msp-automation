# B-14 change note: registry fragments, Python lever modules, never-automate gate

Status: **built**. Synthetic data only. Spec: `specs/B-14.md`.

## What changed

- `core/levers/registry.py`: `Registry.load` reads `levers/registry.json` plus every `levers/registry.d/*.json` as one registry (name order; a duplicate, a fragment without `version`, an unknown field or any bad lever fails the whole load). New `NeverAutomate` class and the gate in `Registry.load` and `Registry.__init__`. `runtime`/`entry` are taken off a lever entry and resolved before `LeverDef` validation.
- `core/levers/handlers.py`: `resolve_python_entry`, `EntryError`, `PYTHON_PACKAGE`. An `entry` resolves only to a callable defined inside `levers.python`.
- `governance/never-automate.json` (new): the 22 `none-keep-human` inventory ids with lever-name patterns and reasons.
- `levers/python/__init__.py`, `levers/registry.d/README.md` (new): the package and the folder families land in.
- `tests/py/levers/test_b14_fragments.py`: 48 tests, named after B14-1 to B14-4.
- Behaviour for existing code: none. The four levers, their handlers and P1-1 to P1-9 are unchanged. `Registry(...)` built in code now also runs the gate, which no existing lever name matches.

## Why

Many lever families (B-31 onward) must land in parallel without editing one file, and "never automate" had to become something that stops a pull request, not a sentence in a map. Identity changes stay R3 and human-approved (D6-07); the roles, Conditional Access, vault, legal-hold, spend and people-judgement work cannot even be registered.

## Effect, L1 to L4

- **L1 person:** nobody's admin rights, retention hold, vault entry or performance review can be changed by a lever, because no such lever can load. Priya Nair's MFA reset still goes through the reviewed path (verified requester, lead approval).
- **L2 client business:** a practice's tenant keeps its privileged roles and Conditional Access policies under human change control; a new family cannot widen what the agent may do by slipping into a shared file.
- **L3 MSP:** a lever family is one fragment plus one module, reviewable on its own, and the list of what is never automated is one file an auditor can read next to the inventory (a test keeps them in step). Load failures are loud and name the file and lever.
- **L4 community:** the line between what software may do and what only accountable people may do (breach notification, attestations, spending, judgements about technicians) is enforced in code and published, not promised.

## Outside "owns"

None. Two things worth knowing: `schemas/lever-registry.schema.json` is unchanged on purpose (`runtime` and `entry` are removed by the loader before `LeverDef`, so the generated schema still matches; B-15/B-16 should move them into `LeverDef` and regenerate). The never-automate file has a pydantic model but no JSON Schema yet.

## Caveats

- The planned fix lever `ca.block-legacy-auth` (named in `levers/powershell/TenantBaseline` config as planned, DR-10) now matches `ca.block*` and could not be registered. The inventory says a Conditional Access change is never automated (W-IDM-06), so this is intended; the baseline can still report it as a finding for an engineer. Whoever owns that planned item should rename it to a report or drop it.
- Patterns match lever names, not intent. A bad actor could register a human-only action under another name; code review on the registry (W-TOOL-01) remains the second control.

## DECISIONS proposal

"The never-automate list (`governance/never-automate.json`) is a hard gate: the registry loader refuses any lever whose name matches a pattern, with the inventory id and reason in the error. It must list exactly the inventory ids whose pattern includes `none-keep-human`; a test enforces that. Adding or removing an entry needs a DECISIONS entry. Lever families are added as `levers/registry.d/<family>.json` plus `levers/python/<family>.py`; a Python `entry` may only name a callable defined inside `levers.python` (STD-LV-2, STD-LV-10)."
