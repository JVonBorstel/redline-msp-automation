Status: **built** (workflow, CLI, lever, eval, tests). Suggests only; a link needs a lead's approval. Synthetic data only. Spec: `specs/B-23.md`.

## Why

Duplicates are worked twice and a widespread issue is seen as ten small ones. Grouping them first, inside one client, is the cheapest way to give a dispatcher back minutes and to see an outage early. The write is a lever so the same gates apply as everywhere: dry-run diff, a technician who is not the approver, a lead scoped to the client, an audit record.

## Individual to macro (L1-L4)

- L1: Priya Nair and two colleagues at Contoso Dental (synthetic) all report "no internet" within 15 minutes (T-5116 to T-5118). Instead of three technicians each starting from zero, one outage group tells the desk it is one problem, so Priya is told it is known and being worked. The false positive is a person with a different problem filed under someone else's ticket, so the code suggests and a person confirms.
- L2: Fabrikam Capital's market-data feed fails at 7:30 (T-5241 to T-5244); seeing four traders' tickets as one event gets the right escalation before trading opens. Litware Legal's e-filing portal fails with two filings due (T-5350 to T-5352). Tickets are only ever linked inside one client, so no firm's problem is attached to another's.
- L3: fewer duplicate tickets worked twice; an outage is one incident for the whole desk; each link is a registered, `R1`, approved and audited change; the eval is fixture-based and says so (C-41).
- L4: a pattern across tickets is visible to a human at the time it matters, without any ticket text crossing between tenants or reaching a model.

## Honest limits

- Topic words were written with the gold tickets in view, so 100% pair precision and recall is in-sample. The one false outage alarm is shown, not hidden.
- Mock only: `ticket.link` writes to the client's mock tenant tickets; no PSA was called (Q-01). The Phase 2 gold tickets are not in the tenant files, so a live link of those needs the real PSA adapter; the shipped tenant answers "no ticket" and the workflow reports it.
- `draft_notice` needs a `upn` param, so the `ticket.link` notice cannot yet be filled automatically (the template exists; `workflows/notify` is not in `owns`).
- No `undo` lever (an unlink lever is a later item). `adapter: psa` is not a registry field yet, so it is not declared.

## DECISIONS proposal

D-0xx Ticket grouping suggests, per client, and linking is an R1 approved write (B-23, 2026-10-21). Duplicate and outage grouping take the client explicitly and drop every other client's ticket before any comparison; an outage group is N or more tickets of one category, from at least two people, chained within a window (3, 2 and 4 hours in `workflows/duplicates/config.json`); a ticket the injection detector flags is never grouped. Text only selects topics and scores overlap; it never reaches a result, a lever parameter or a reason. `ticket.link` is `R1`, `approval: lead`, an agent may dry-run it, it stores a symmetric `links` map on both tickets, never closes or merges, and answers a foreign ticket like an absent one. Why: W-SD-03 and W-SD-08, C-27, C-05. Alternatives: a model or embedding similarity (rejected for now: not reviewable, needs a gate first); merging tickets (rejected: irreversible and hides a different problem). What would change it: real the MSP tickets showing which categories or windows give false alarms.
