# B-26 change note

Status: **built** (drift fixes with tests, `tests/py/levers/test_b26_fix_levers.py`; status line added 2026-10-27). Synthetic data only.

- What: triage's proposal module now imports `proposal_id`, `Source` and the UTC clock from `core.queue.store` and builds proposals through the queue's `Proposal` model (DR-01). TenantBaseline's config keys tenants by the canonical client ids `contoso-dental` and `fabrikam-capital`, with `fixtureDir` and `aliases` (`contoso`, `clean`), and the report always carries the canonical id (DR-05). The config lists the unbuilt fix levers in `plannedFixLevers` and a test keeps every named lever registered or planned (DR-10). The manifest and the module declare PowerShell 7.4 (DR-09).
- Outside "owns" (minimal, needed for B26-2): `levers/powershell/TenantBaseline/TenantBaseline.psm1` gained `Resolve-TbTenant` (id or alias to client id, display name, fixture folder), reads the fixture folder from it, writes the canonical id into `tenant`, and its `#requires` and help example moved to 7.4 / `contoso-dental`. No check logic changed; SB-1 to SB-4 still pass (81 checks).
- Why: the drift table found two definitions of the proposal contract and a second set of client ids. Later waves (B-27 mypy, baseline-to-queue, per-client views) would key on the wrong id or a contract that could drift.
- Behaviour change to note: findings.json, findings.csv `Tenant` and the result object now say `contoso-dental` / `fabrikam-capital` even when run with `-Tenant contoso` or `clean`. Nothing in the repo read the old value.
- L1 person: a finding about Dana at Contoso Dental carries the same client id as her tickets, her proposals and the lead's queue view, so it lands on the right lead and the right client record. L2 client business: one id per client means a baseline result cannot be filed under another client. L3 MSP: one proposal contract means triage and the queue cannot disagree about what a valid proposal is; a planned lever is listed, not silently missing. L4 community: honest labels on what is built versus planned.
- Decision proposal: "Client ids are canonical everywhere (STD-ID-5). Tools that predate them keep their old names only as explicit aliases in config, the output always carries the canonical id, and an alias is removed when the last caller (docs/DEMO.md, README.md, the fixture folder names, DR-22) moves." And: "A config that names a lever not yet in levers/registry.json must list it under `planned`; registering it removes it from that list (DR-10)."
