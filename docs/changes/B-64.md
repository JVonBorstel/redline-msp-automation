# B-64 change note: device compliance, encryption and LAPS coverage reports; provisioning readiness

Status: **mocked** (workflow, CLI, fixtures, tests). Reports only; nothing is changed on a device and no key or password is read. Synthetic data only; figures are fixture-based. Spec: `specs/B-64.md`.

## What changed

- `workflows/device_reports/` (new): `reports.py` (report, secret guard, hashing, verify), `__main__.py` (`python -m workflows.device_reports report|verify`), `config.json`, `README.md`, `fixtures/<client>.json` (LAPS metadata, Autopilot identities, invented hires) and `fixtures/SOURCES.md` (per-field status).
- `tests/py/devices/test_b64_device_reports.py` (new): tests named `test_b64_<k>_...`; expected counts are computed from the raw fixture files.
- `specs/B-64.md` (new).
- **Outside `owns`:** none. The overlay fixtures sit inside the workflow because `fixtures/intune/` and `fixtures/rmm/` are B-61's. Reads, never writes: B-61's adapters, fixtures and reconciliation.
- **Follow-up for the owner:** `tests/py/evals/test_b79_injection_v2.py` fails its "every workflow folder is classified" check until `device_reports` is added to `NO_GUARD_IMPORT` (the workflow reads no free text and imports no guard). That file was out of scope here and was not edited.

## Why

Gaps on devices are known before a lost laptop becomes a breach: non-compliant devices with the reason, disks not known to be encrypted, Windows machines without a fresh escrowed local-admin password, and hires whose device is not yet ready to enrol.

## Individual to macro (L1-L4)

- L1: Ana, a technician, opens one Markdown page for Contoso Dental and sees which devices need a follow-up and why, instead of clicking through three consoles.
- L2: the report is built from one client's adapters and one client's fixture file; a LAPS record of another client is counted as a gap, never as coverage.
- L3: the MSP gets the same hashed report shape for every client, so coverage can be compared and re-checked with `sha256sum -c`.
- L4: fewer unencrypted laptops and unmanaged local-admin passwords at small practices and firms; new hires start on a device that enrols.

## Honest limits

- UNVERIFIED (no vendor page opened): the Graph `deviceLocalCredentialInfo` and `windowsAutopilotDeviceIdentity` shapes, the LAPS-to-Entra-device join, enum values, the permission a real read needs. A real LAPS adapter must request metadata only.
- The compliance reason is derived; Intune's managedDevice has no reason text and per-setting reasons are not modelled.
- Servers are not told apart from workstations; AD-based LAPS, macOS/mobile encryption, key retrieval and LAPS retrieval are not built.
- Hires are an invented fixture; their real source is open. No committed device is non-compliant or unencrypted, so those paths are proven on copies.
- `find_secrets` is a heuristic. The run is not audited or scheduled.

## DECISIONS proposal

D-0xx Device reports are status-only and tamper-evident (B-64, 2026-10-27). Compliance, encryption and LAPS coverage are reported per client from B-61's reconciled device list as canonical JSON plus Markdown with `sha256sum` sidecars; the Markdown must re-render from the JSON. LAPS data is read through a field allow-list so a password or recovery key in a source is never copied, and a secret-shape check stops any output that contains one. Provisioning readiness is a report on Autopilot registration and profile, not an action. Why: W-EP-05, W-EP-06, W-EP-11, W-ONB-06; C-20, C-21, C-10. Alternative: retrieving keys or LAPS passwords for the technician (rejected here: that is a separate R3 lever with approval, not a report). What would change it: the MSP's real Intune, LAPS and hire sources.
