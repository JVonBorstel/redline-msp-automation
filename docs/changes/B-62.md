## Why

Tier 1 fixes take a remote session today. With these levers a technician or the triage agent proposes one named script for one device, the lead sees what would run and the exact diff, one approval executes it, the module checks the result, and the audit chain keeps who approved what.

## Individual to macro (L1-L4)

- L1: Ana's front desk printer queue at Contoso Dental (synthetic) is stuck; the spooler is restarted and Ana prints again. A reboot costs unsaved work, so the approval says so.
- L2: the practice keeps working without waiting for a remote session; a server restart waits for the maintenance window on the client record.
- L3: six common fixes move from remote sessions to approved, audited, rate-limited steps (3 to 10 an hour per client, 2 for servers); the session that diagnosed the problem is linked to the proposal.
- L4: a device of another client, or another site, answers like an absent one; no lever accepts a script, a path or a command, so a fooled model can only press the seven buttons.

## Honest limits

- Nothing ran on a real device or RMM and nothing was checked against the Datto RMM or Splashtop documentation. The module is a mock over JSON files; it proves the control shape (vetted scripts, identical diffs, approval binding, verification, caps, windows), not the Windows commands.
- The roadmap says the runner refuses the reboot "inside the client's business hours"; B-42 implements `window: business-hours` as allowed only inside business hours. The flags follow the roadmap's wording and the runner's behaviour is tested as built. Which direction a workstation reboot should have is an open point for the owner.
- The notify module cannot draft a device notice yet (it needs a `upn` param); the templates exist so each write lever has one.
- The "vetted script" steps are descriptions with a hash, not real scripts. Promoting a real RMM component into the registry (D6-26) is a reviewed code change, not a feature here.
- Quarantined temp files are never purged; a reboot is not repeatable in real life even though the mock treats a repeat as no change.
- A refusal inside a lever is returned as the host's `denied` with the sentence intact (the `refusal` channel), except a failed verification, which the runner records as an error after the audit record.
- When the lever runs from the CLI with the default tenant folder, execute writes the committed `mock/` files (as the mailbox levers write `fixtures/tenant`); the tests always work on a copy.

## DECISIONS proposal

D-0xx Tier 1 device fixes are vetted, hash-pinned scripts behind seven fixed levers (B-62, 2026-10-27). Each lever runs one script from `vetted-scripts.json`; the module refuses all of them if any step list no longer matches its hash. The change is a field-edit list that the dry-run shows and execute applies, so the two cannot differ. Reboots carry the runner's windows (`business-hours`, and `maintenance` for servers) and the module holds no time logic. Rollback is a proposal for a person, not an undo lever: spooler, drive and service restarts need none, the Outlook profile and temp cleanup keep a dated backup or quarantine, and reboots cannot be undone. Risk is R1 for spooler, drive, temp and service, R2 for the Outlook reset and both reboots. Why: W-SD-11, W-EP-03, W-EP-07; C-05, C-06, C-17, C-32, C-41; D6-08, D6-26. Alternatives: irreversible R3 for reboots (rejected: nothing is lost that a person could not also lose with a remote restart, and the roadmap wants one approval), an `undo` lever per fix (rejected: nothing to restore for most, and the backups are for a person to use), running existing RMM components by name (rejected by D6-26 until vetted). What would change it: the MSP's real RMM (INFERRED as Datto RMM, UNKNOWN for jobs) and how its jobs report results.
