# B-17 change note: audit record v2 and verifier

Status: **built** (audit module, verifier CLI, 52 tests). Synthetic data only. Spec: `specs/B-17.md`.

## What changed

- `core/audit/chain.py`: new records are version 2. They keep the eleven v1 fields and add `v: 2`, `event`, `actor_kind`, `lever_version` and `request_id` (STD-AU-2). `append` takes the four new fields as optional keyword arguments. When the caller passes nothing, the defaults are: `event` from the mode, `actor_kind: "unknown"`, `lever_version: null`, and a fresh `request_id` (`req-` + a hyphenated UUID). The verifier accepts v1 records, v2 records, or a v1 prefix followed by v2 records. It rejects a v1 record after a v2 one, an unknown `v`, a wrong field set, and unknown `mode`/`event`/`actor_kind` values. `Mode` now lists every value written (DR-04), and `append(mode=...)` is typed with it. The runtime tuples are `MODES`, `EVENTS` and `ACTOR_KINDS`.
- `core/audit/verify.py`: the OK line keeps its prefix (the demo and `docs/DEMO.md` match on it) and adds `(<a> v1, <b> v2)`.
- `core/audit/__init__.py`: exports the new names.
- `tests/py/audit/test_b17_audit_v2.py` (new): 52 tests, all named `test_b17_<k>_...`. The P1-2 tamper cases run on both a pure v2 log and a mixed v1-then-v2 log.

### Outside this item's `owns` (minimal, needed for mypy strict once `append` is typed)

- `core/queue/store.py`: two lines. It imports `Mode`, and `verb` is annotated `Mode` (in `decide` and in `_audit`'s signature).
- `core/levers/runner.py`: one line. `mode=str(call["mode"])` became `mode=call["mode"]` in `_record`. The `str()` would have widened the value back to `str`. `append` already guards unknown values at runtime.
- `tests/phase1/test_audit.py`: one line. `test_records_carry_every_field_and_chain` expected the exact v1 field set. It now also expects the five v2 fields. No other phase test changed.

## Why

One request should be traceable across every record it causes, and an auditor should see which version of a lever ran. Take Priya's MFA reset on ticket T-3101: the rehearsal, the lead's decision and the change. The MSP can then scope an incident after a lever bug: "every `user.reset-mfa` v1 run between these dates, at which clients". v2 adds those fields without rewriting a byte of the existing chain, so the evidence already collected stays valid.

## Individual to macro

- **L1 Priya (one person):** each record about her reset can carry one correlation id. If she asks what happened to her account, the answer comes from records that provably belong together. Her request id cannot be stripped later: removing the v2 fields from a record makes it "v1 after v2", and the verifier rejects that.
- **L2 Contoso Dental (the client business):** the practice's audit export can show which lever version acted on its staff. A downgrade or an edit anywhere in its log is caught at the exact seq, on old and new records alike.
- **L3 the MSP:** incident scoping by lever version and request id, across every client, once B-28/B-80 pass the real values. Old logs keep verifying, so the upgrade needs no migration.
- **L4 The community:** a tamper-evident, versioned audit trail is what regulated small businesses (dental, financial, legal) need from an MSP using automation. A trail that cannot be thinned out after the fact keeps "the AI did it" from becoming an unanswerable question.

## Honest limits

- **DR-04 said "four values"; the literal has seven.** The pause switch (B-02) writes `pause` and `resume`, added after DR-04 was written. The runner also records a denied unknown mode. Writing that raw value (`yolo`) would make the literal untrue, so `append` writes it as `invalid` and keeps the raw value, capped at 64 characters, in `result.requested_mode`.
- **Defaults are honest, not complete.** Until B-28 (runner) and B-80 (gateway) pass real values, records say `actor_kind: "unknown"` and `lever_version: null`, and each record gets its own `request_id`. So the three records of one T-3101 run are not linked yet. The fields are not fake data: `unknown` and `null` mean "not passed".
- **`request_id` is redacted like params.** A bare 32-hex id would be replaced as secret-shaped, so the default uses the hyphenated UUID form, which redaction keeps. Callers that pass their own id should use the same form or a short readable one (`req-T3101-0001`).
- **`lever.pause` is a new event name**, not in STD-AU-2's list (see the proposal below). `proposal.add`, `model.complete` and `job.run` are allowed values, but nothing writes them yet.
- The verifier checks the shape and values of v2 fields. It does not check that `lever_version` matches the registry, and it does not check that `actor_kind` matches the identity's role. Those are writer-side duties (B-28).

## DECISIONS note proposal

D-0xx Audit records are version 2, additive (B-17, 2026-10-21). New records carry `v: 2`, `event`, `actor_kind`, `lever_version`, `request_id`. v1 records are never rewritten, and the verifier accepts v1 then v2, never the reverse. Missing caller values default to `unknown` / `null` / a fresh id rather than a guess. An unknown mode is written as `invalid` with the raw value in `result.requested_mode`. `lever.pause` joins the STD-AU-2 event list for pause and resume. Why: correlation and lever version are what audits and incident scoping need. A forward-only version rule stops a record being downgraded to hide them, and honest defaults keep the record true before every caller is wired. Alternatives: a v2-only verifier with a one-time migration (rewrites evidence, and breaks the chain's value as proof); guessing `actor_kind` from the mode (wrong for a technician's dry-run). What would change it: a v3 schema, or a deployment that pins heads outside the writer's reach (STD-AU-7).
