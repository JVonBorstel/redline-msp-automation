# B-82 change note: SQLite queue and append-only audit store

Status: **built** (library and tests; not wired in, JSONL stays the default). Stdlib `sqlite3` only. Synthetic data only. Spec: `specs/B-82.md`.

## What changed

- `core/queue/sqlite_store.py` (new): `SqliteJobQueue` (idempotency keys, leases with fencing, retries with backoff, dead letters, per-client isolation) and `SqliteApprovalStore` (compare-and-set decisions for the existing `Proposal` model), WAL, numbered migrations, injectable clock.
- `core/audit/sqlite_store.py` (new): `SqliteAuditStore` (per-client hash chains byte-identical to the JSONL writer, UPDATE/DELETE/fork/gap refused by triggers, verification with the JSONL verifier, export to and import from JSONL) and `python -m core.audit.sqlite_store verify`.
- `tests/py/storage/test_b82_sqlite.py` (new): 60 tests, written first and committed failing (import error) before any code existed. They include process-kill crash recovery and thread and process writer races.
- `specs/B-82.md` (new).
- **Outside `owns`:** none. No existing file was edited. `core/queue/__init__.py` and `core/audit/__init__.py` deliberately do not export the new stores (B82-3).

## Why

Many leads and many jobs at once, without a forked chain or a double decision. Where the JSONL stores rely on one file lock, SQLite gives atomic transactions across processes and rules the database itself enforces.

## Individual to macro (L1-L4)

- L1: two leads click Approve on the same proposal; one decision is recorded, the other sees "already decided".
- L2: a job claimed by a worker that then crashes comes back after its lease and is retried; a job that keeps crashing workers ends in the dead letters for a person to look at, instead of looping.
- L3: Contoso Dental's audit chain and queue are separate from Fabrikam Capital's; an exported client chain contains only that client and verifies with the existing verifier.
- L4: tampering, deleting the newest records, or dropping the protection is detected or reported, which is the evidence a SOC 2 reviewer asks for, subject to the limits below.

## Unverified

- **Dropping the triggers is possible for anyone who can write the file.** The store detects the common cases (edited line, deleted record, truncated tail, missing or edited triggers), but an attacker with file access who rewinds records and head together and re-creates the triggers is detected only if you kept a head pin elsewhere (`head()` and `verify(expected_head=...)`). Nothing in the repo stores such a pin yet. No claim is made that the file is tamper-proof.
- **Only run on this Windows 11 machine**, Python 3.12.15, bundled SQLite 3.53.1. Not run on Linux or macOS, on a network or synced folder (WAL needs shared memory and is not safe on network file systems), or in a sandbox. The triggers use upsert-in-trigger syntax, which needs SQLite 3.24 or newer; older libraries are untested.
- **Durability** relies on `synchronous=FULL` meaning a real fsync on this OS and disk. Not tested with a power cut; the crash tests kill the process (`os._exit`), which exercises SQLite's rollback, not hardware.
- **Performance and scale are not measured.** `verify` reads and dumps a whole chain, and `append` opens a connection per call; the B-84 load test (10,000 calls across 300 clients) has not been run against this store. Everything was tested with small numbers (up to 120 records, 60 jobs, 5 processes).
- **Time and clocks.** Leases use the clock of whatever process calls; workers on machines with skewed clocks can steal or lose leases early. Backoff has no jitter. Tests use a fake clock or the real clock plus an offset.
- **Not integrated:** `ProposalQueue`, the runner and the UI do not use these stores. The approval store does not check roles or client scope and writes no audit record by itself; whoever wires it must keep the runner's re-check and audit of each decision. No audit records are written for queue events (enqueue, claim, dead letter).
- **Payloads and results are stored as written** (only error text is redacted). Callers must not put secrets in job payloads.
- `import_jsonl` without a head pin accepts a JSONL chain that was truncated before import (it cannot know); pass the head file.
- Antivirus locking of the `.db-wal` and `.db-shm` files is untested; open and write errors surface as `SqliteAuditStoreError` or `JobQueueError` (failing closed).
- The existing `ruff format --check .` was already failing on two files not touched here (`tests/py/tools/test_orphan_tests.py`, `workflows/enrichment/enrichment.py`); see the gate results in the commit report.

## DECISIONS proposal

D-0xx SQLite stores are built but off (B-82, 2026-10-27). `SqliteJobQueue`, `SqliteApprovalStore` and `SqliteAuditStore` exist beside the JSONL stores and share the record format byte for byte; the JSONL stores stay the default until a later entry switches them. Switching needs: an external head pin for each client chain, a decision on where the database lives, wiring of `ProposalQueue` and the runner, and the B-84 load result. Why: C-08, C-09, C-39, C-07. Alternative: stay on JSONL with file locks (works for one host and few writers). What would change it: measured contention on the JSONL locks, or more than one host.
