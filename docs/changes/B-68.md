Status: **built** (adapter mock, fixtures, review workflow, CLI, `backup.retry-job` lever, notice template, tests). The review is read-only; a retry is an R2 write that a lead approves. Synthetic data only. Every backup field name is UNVERIFIED. Spec: `specs/B-68.md`.

## Why

A failed backup is fixed the same day, not discovered during a restore. The MSP sells backup and disaster recovery and managed Microsoft 365 backup, and the review is the highest-leverage chain (D6-24).

## Individual to macro (L1-L4)

- L1: Sam Patel at Contoso Dental (synthetic) would otherwise learn the imaging server (DENTAL-SRV01) was not backed up on the day he needs a restore. The morning review shows it failed two nights running for lack of disk space, and the front-desk PC's image finished but would not boot. The cost of a wrong retry is a slower server while staff work, so a lead approves it.
- L2: Fabrikam Capital's file server failed three nights running and a Microsoft 365 job failed on throttling; one ticket draft each, not five. A client's recovery point is repaired the same day. Review and retry only ever name that client's own jobs.
- L3: the MSP stops finding out from restores. Counts reconcile (every job in exactly one bucket), a retry is a registered, approved, audited change, and three failed nights are one request.
- L4: one reviewer can read every client's morning in minutes; a pattern such as "the same error on many appliances" becomes visible without any client's job data crossing into another's view.

## Honest limits

- All field names and values are invented stand-ins, marked UNVERIFIED; no vendor documentation was read and no vendor is claimed. The thresholds (24 h, 2x, 60 min, 2 failures, 7 days) are starting values, not tuned on real jobs.
- The lever records a request in the mock tenant state and does not know the job. The workflow checks the job in the client's own adapter before it dry-runs (STD-LV-8, STD-LV-9).
- `adapters.build_adapter` has no `backup` system yet (`adapters/__init__.py` is not in `owns`), so the mock is built with `BackupMock.for_fixture` or a `BoundBinding`.
- No ticket is created and no queue proposal is filed here; a person turns a draft and an ok dry-run into those.

## DECISIONS proposal

D-0xx The daily backup review is read-only, per client, and its one write is an R2 approved retry (B-68, 2026-10-21). The review reads one client's jobs through that client's own adapter and puts every job in exactly one bucket (healthy, in-progress, failed, missed, long-running) so counts reconcile; a finished backup whose boot check failed counts as failed; error text that the injection detector flags is withheld and listed for a person. Repeated failures of one protected item are one ticket draft, and one dry-run retry. `backup.retry-job` is `R2`, `approval: lead`, an agent may dry-run it, it is convergent, and the workflow can only dry-run it. Why: W-BDR-01, W-BDR-02, C-27, C-05, D6-24. Alternatives: letting the review retry automatically (rejected: a retry can load a production server and is a change); one ticket per failed run (rejected: three failed nights would become three tickets). What would change it: the MSP naming its real backup products (Q-09) so the fields can be verified, and real job data showing better thresholds.
