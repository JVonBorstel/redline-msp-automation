# B-83 change note: operational logs, request ids and monitoring alert rules

Status: **built** (code, rules, fixtures, tests) on synthetic fixtures and test doubles. Nothing is delivered to a pager or shipper; nothing schedules the evaluator. Synthetic data only. Spec: `specs/B-83.md`.

- **Outside `owns`** (small edits to existing files, needed to thread the id and emit the lines; all other behaviour unchanged):
  - `core/audit/chain.py` and `core/audit/sqlite_store.py`: when no `request_id` is passed, take the enclosing `request_scope` id before generating a fresh one (one line each, plus the import).

  - `core/levers/runner.py`: `invoke` takes the scope id when there is one, and `_record` writes one ops log line per audited call (a `started` timestamp is added to the internal `call` dict for the duration; it is not written to the audit record).
  - No config, schema, registry, `map/roadmap.json` or guardrail file was touched.

## Why

Problems should be seen by the MSP before the client calls. The runner and gateway had audit records but no operational log, one operator action had no single id across its calls, and nothing watched the audit stream or queue state. Now the log can be shipped without holding a prompt, ticket text or secret; one id follows an action through gateway, runner and audit; and the five conditions that matter first (a broken audit chain, a provider breaker open, budget exhaustion, a stale approval, growing dead letters) are rules in a JSON file with an evaluator a test can replay.

## Individual to macro (L1-L4)

- L1: Ana, a technician at Contoso Dental, sees a failed request and quotes `req-...`; every log line and audit record for that request carries it.
- L2: every log line names its client (or `_msp`), so Contoso Dental's lines can be pulled without reading Fabrikam Capital's, and no line holds what a client's staff typed.
- L3: the MSP lead gets alerts per client and per provider from the same stream the auditors read, and can retune a threshold with a reviewed one-line JSON change.
- L4: fewer silent outages and stale queues at small practices; the log and the alert inputs are safe to hand to a vendor or an auditor.

## Honest limits

- Roadmap acceptance **B83-2 is only partly met**: denial spikes, after-hours executes, approvals faster than a human could read, and verify failures are not built; the five conditions requested for this change are. Do not mark the roadmap item complete on this change.
- The logger's `lever`, `task` and `model` slots accept any lowercase identifier; a one-word lowercase prompt passed there would be logged. Callers pass only registry, route and config names. Pinned by a test, not closed. Every other slot rejects free text structurally.
- Only the runner and the gateway log. The scheduler, queue, MCP server, workflows and lever CLI do not, and nothing opens a `request_scope` for a CLI session, web request or scheduled job yet.
- Alerts are computed, not sent. Backlog and dead-letter inputs must be supplied by the caller; no adapter reads the B-82 stores. Thresholds are prototype defaults.
- UNVERIFIED: no shipper, SIEM or monitoring product was used; the line format is not checked against any vendor schema. Behaviour under asyncio and multi-process writers is untested beyond one thread-isolation test. Exercised on Windows only.

## DECISIONS proposal

D-0xx Logs are allow-listed, not scrubbed (B-83, 2026-10-27). Every ops log line is built from shape-checked slots; a value that fails is replaced by a fixed label or dropped and counted, never masked in place. Free text has no slot, so a prompt cannot be logged by accident, and stdlib records lose their message and exception text. The request id lives in a context variable that the runner, gateway and audit stores read when the caller names none. Alert rules are JSON data with a pure evaluator whose only clock is the snapshot's `now`. Why: W-TOOL-09; C-40, C-11, C-27. Alternative: a regex scrub of free-text log messages (rejected: a scrub list fails open on the shape it did not think of). What would change it: a real log pipeline that needs richer fields, each of which would be added to `FIELD_RULES` with its own shape check.
