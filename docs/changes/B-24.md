## Why

The person who has waited longest is only helped if someone sees the deadline coming. A queue that is sorted by age hides the difference between a 30-minute and an 8-hour promise; a report that applies each client's own SLA numbers, and chases tickets that are stuck waiting on a client or vendor, turns a silent breach into a call made in time. Every number is re-counted from the raw fixtures, so the report cannot say something the data does not.

## Honest limits

- Hours are wall-clock; no business-hour calendar is modelled (the watch warns early, never late). The MSP's real SLA terms and pause rules are UNKNOWN; the `slaSettings` entity itself is an UNVERIFIED stand-in (B-18).
- First response for file tickets is inferred from `status != new`; there is no first-response timestamp in the fixtures, so a late response that already happened is invisible. PSA note times are not compared with `as_of`.
- Litware Legal has no PSA fixture, so it has no SLA matrix and no contact line in `fixtures/notify/contacts.json`; its drafts say "reply here".
- `config/clients` does not exist yet (a protected owner step). The CLI falls back to synthetic demo bindings written under `<state>/sla/clients/`; with the owner's real config directory present it uses that.
- The drafts are not a record that anyone chased a ticket; there is no send log and no audit event for the report run (it is read-only on fixtures).

## DECISIONS note proposal

D-0xx SLA numbers come from the PSA's SLA matrix through the per-client adapter, and every reported count is re-derived from raw fixtures (B-24, 2026-10-21). The breach watch uses `created + hours` from the client's own SLA entity, treats wall-clock hours as the conservative reading, pauses only the `waiting-client` resolution clock, and lists already-breached deadlines apart from upcoming ones. `validate_report` recomputes everything from the raw JSON without the workflow code and fails the CLI (exit 1) on any difference. Follow-ups are templates with trusted fields only and are never sent. Why: a lead acts on this report, so a wrong or invented number is worse than none (C-21); one client's SLA must never be applied to another's tickets (C-27). Alternative: a model summarises the queue (friendlier, but needs the same validator). What would change it: the MSP's real SLA contract terms (business hours, pause states) replacing the stand-in matrix, or a real first-response timestamp from the PSA.
