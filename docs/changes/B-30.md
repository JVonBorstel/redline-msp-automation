# B-30 change note: password reset and Temporary Access Pass with out-of-band delivery

Status: **built** on the **mock** tenant. Synthetic data only. Spec: `specs/B-30.md`.

## What changed

- `levers/powershell/CredentialOps/` (new): `Reset-UserPassword` and `New-UserTap`. The value is generated with `RandomNumberGenerator` and written only to `.tmp/oob/<client>/<target id>-<type>.json`.
- `levers/registry.d/credential.json` (new): levers `user.reset-password` and `user.new-tap`, both R3, `verification: "requester+contact"`, with the L1 to L4 impact trace.
- `core/levers/oob.py` (new): the reader for the out-of-band file (human, scoped to the client, optionally the named requester, once, expiry) and the secret-shape helpers the sweep uses.
- `workflows/notify/templates/user.reset-password.md`, `user.new-tap.md` (new): notices that say the value comes separately.
- `tests/py/levers/test_b30_oob.py` (new): 27 tests named after B30-1 to B30-4. `specs/B-30.md` (new).
- **Outside `owns`:** `core/levers/bridge.py`, one line: `REDLINE_OOB_DIR` added to the environment the child process may inherit (without it the module cannot find the test's out-of-band folder; the default `.tmp/oob` works without it).

## Why

Password help is the most common lockout fix and the one attackers impersonate. The AI and the audit can prove a credential was issued, to whom and for how long, without ever holding it.

## Individual to macro (L1 to L4)

- **L1, one person.** Priya or Ana gets a new password or a one-time pass from a technician by phone or in person, forced to change at first use; the message she receives never contains it, and a caller who only knows her birthday gets nothing.
- **L2, the client business.** An impostor cannot get a working sign-in for a client account without a callback to the number on file and the client's own authorized contact; admin-role accounts are refused outright; a TAP lives for the shortest time the tenant policy allows.
- **L3, the MSP.** The audit shows who approved, how they signed in, which account and what kind of credential with what lifetime, and it holds no secret, so an audit log can be shared with the client or an assessor without leaking access.
- **L4, community.** A common recovery step handled the same careful way at every client removes a routine opening for help-desk social engineering across the sector.

## How the tests prove it

Each id has tests that run the real runner and the real PowerShell module offline on a private copy of the mock tenant and a private out-of-band folder. The sweep reads the issued values from the files and checks that no audit record, queue line, result, notice, tenant file or log line contains them, and that none contains a secret-shaped string. Values are random per run and are never printed. Result: 27 passed with `pwsh` installed.

## Not done, and caveats

- UNVERIFIED: the Graph shape of a TAP (`isUsableOnce`, `lifetimeInMinutes`), the policy minimum (default 10 here) and the default length (8 here). Confirm before a real adapter.
- The queue cannot execute a `requester+contact` lever until B-65 wires policy and contact confirmation into it; the sweep puts proposals in the queue and runs the levers through the runner.
- The audit has no `data` field, so the "credential issued (type, expiry, target id)" entry is the diff's `pendingCredentials/<type>` marker (path has the target id; `expiryMinutes`). Putting a dedicated `credential_issued` object in the record would be a runner change.
- A pending marker has no clock, so a second credential of the same type is not issued until a future revoke lever clears it.
- The out-of-band file has no operating-system permissions in the mock.

## DECISIONS proposal

D-0xx Generated credentials leave only by the out-of-band channel (B-30, W3, 2026-10-22). Password reset and TAP are PowerShell R3 levers requiring `requester+contact` verification; the generated value is written once to the out-of-band file and never to a result, diff, tenant file, audit record, queue line, notice or prompt; the audit shows the issue through the diff's pending-credential marker (type in the path, expiry in minutes, target id); a TAP is single-use with the tenant policy's shortest lifetime. Why: D6-06, D6-07; the secret never touches the AI. Alternative: have Entra generate the TAP and return it (still must be kept out of the result). What would change it: the real adapter's behaviour, or a runner field for credential-issue events.
