# B-01 change note: registry fields (risk class, undo, impact trace, verification rule)

Status: **built** (fields, load rules and tests). Runner enforcement of `verification` is `B-02`; the approval page showing `impact` and `undo` is `B-03`. Synthetic data only.

## What changed

- `core/levers/models.py`: `LeverDef` gains `risk_class` (R0-R3), `reversibility` (`reversible` | `irreversible` | `n/a`), `undo` (lever name or null), `lever_version` (strict int >= 1), `impact` (new `Impact` model, `L1`-`L4`, one line of 1-200 characters each) and `verification` (`"requester"` or null). Class defaults: a read lever is `R0`/`n/a`; a write lever is `reversible`. Validators make an unsafe combination unconstructable: read must be `R0` and `n/a` with no `undo` or `verification`; write must be R1-R3 and not `n/a`; `irreversible` must be `R3` and cannot name an `undo`; a lever cannot be its own undo. `Approval` gains an optional `verification` (new `Verification` model: `method` in `callback-on-file` | `in-person` | `manager-confirmed` | `finding-reference`, `by`, timezone-aware `at`, short `ref`, required for `finding-reference`; extra keys rejected).
- `core/levers/registry.py`: each entry is validated on its own, so every error names the lever; `Registry.load` requires `risk_class` and `impact` on every write lever; the registry rejects an `undo` that is not a registered write lever.
- `levers/registry.json`: all four levers declare the new fields. `user.reset-mfa` and `user.disable` are `R3` (D-024), `reversible`, `undo: null` (manual undo until a `user.enable` lever exists; MFA is re-registered by the person) and `verification: "requester"`. Names, params, roles, approval and dry-run are unchanged. Registry `version` stays 1 (additive, STD-LV-10).
- `tests/py/levers/test_b01_registry_fields.py`: 70 tests named `test_b01_<k>_...` for B01-1 to B01-4.
- `specs/B-01.md`: the acceptance ids, refined.

## Why

Permissions already live on the lever. The trace from one person to the community and the social-engineering rule now live there too, so a reviewer and (from B-03) an approving lead read them in the same place, and a write lever cannot be registered without saying how bad a mistake is and who it hurts.

## Individual to macro (L1-L4)

- L1: Priya Nair (synthetic, ticket T-3101) asks for an MFA reset; the lever now says that a wrong reset locks her out or lets an impostor in, and that her identity must be verified out of band first.
- L2: the client's identity changes are classed R3 and carry their impact, so a dental practice or an RIA can see why an MFA reset is treated as a security event.
- L3: the MSP can show auditors, per lever, its risk class, version and verification rule (C-29, C-30 evidence), and the load fails closed if a write lever leaves them out.
- L4: MFA resets are the step attackers talk their way through (W-IDM-02/W-IDM-04 chains); a rule on the lever holds for every client at once.

## Honest limits

- `verification: "requester"` is **declared, not enforced**: today an execute with or without `Approval.verification` behaves as before (tested). B-02 adds the runner gate.
- A lever built in code (not loaded from the file) is checked for class/risk agreement but not for the presence of `risk_class` and `impact`, so the Phase 1 tests that build test levers in code pass unchanged (B01-4). The program only loads levers from the file.
- `pyproject.toml` limits the default pytest run to `tests/phase1` (RF-04); run this suite with `uv run --frozen pytest tests/py/levers` until B-06 adds `tests/py/Test-Py.ps1`.
- Governance 6.1 still lists `user.reset-mfa` and `user.disable` as R2; D-024 settled R3. The governance table and the STANDARDS "proposed" rows need a docs follow-up by their owning item.

## DECISIONS note proposal

D-0xx Registry fields from B-01 (2026-10-21). Every lever declares `risk_class`, `reversibility`, `undo`, `lever_version` and `impact` (L1-L4); a write lever without `risk_class` or `impact` fails the registry load, naming the lever. Class and risk agree (read = R0, write = R1-R3; irreversible = R3 with no undo). `undo` must name a registered write lever, otherwise null means manual undo. `verification: "requester"` marks levers whose execute will need an approval carrying out-of-band verification `{method, by, at, ref}` (C-30; enforced from B-02). Why: puts the person-to-community trace and the social-engineering rule on the lever, where permissions already live. Presence is enforced at file load, not in `LeverDef`, so levers built in code by tests keep working (B01-4).
