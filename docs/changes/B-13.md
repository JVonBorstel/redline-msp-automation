## Why

Python orchestrates and PowerShell acts. They share data, not code, so each shape crossing the bridge is now written down once and checked from both sides. Without this, a renamed field in Python breaks a PowerShell lever quietly, at one client, during one person's request.

## Individual to macro (L1 to L4)

- **L1, one person.** Take Morgan Reyes (synthetic) at Fabrikam Capital, who asks for an MFA reset. Their request reaches the PowerShell lever in exactly the shape that lever expects: the right `upn`, `mode: dry-run` unless approved, and an `entry` naming one exported function. A mangled request is refused at the boundary. It never half-runs against their account.
- **L2, the client business.** The proposed client record carries the PSA company id, the regimes the compliance owner set (GLBA Safeguards, Regulation S-P), `model_processing` with no silent default, and bindings that name a credential, never hold one. A wealth manager's data rules are written in one checked place.
- **L3, the MSP.** One shape per contract means a Python change that would break a PowerShell lever fails CI first (`--check`, the drift test), not a technician's ticket. Lever authoring (W-TOOL-01) gets a written contract that B-14, B-15, B-17 and B-18 can build against in parallel.
- **L4, the community.** Typed boundaries are how an automation stays safe when it is fooled: an injected value or an unknown field is refused by both languages, and the refusal is provable (C-02). The format gap is recorded instead of assumed away (C-21 spirit: no claim without a check).

## How the tests prove it

- **B13-1.** Exactly nine files, each declaring draft 2020-12 with `$id` and `$comment`. Five are generated and four are hand-written, and each says which in its `$comment`. The generator is deterministic, its properties equal `model_json_schema()`, and it never writes a hand-written file. Every schema has good and bad examples. Pydantic accepts each good example and rejects each bad one. `levers/registry.json` and `config/identities.json` validate. The good v1 audit example passes `verify_chain` and the bad ones fail it. Audit v1 fields equal `RECORD_FIELDS`. The `finding` fields and severities equal the PowerShell class. The hand-written `LeverName`, `ClientId`, `mode` and `CredentialRef` rules equal the Python ones. `credential_ref` rejects secret-looking values, which the test builds at runtime.
- **B13-2.** `--check` passes on the committed folder. It fails, naming the file, when a generated schema is edited, when a generated or hand-written schema is deleted, or when an unknown one is added. Line endings alone are not drift. The command-line exit codes are 0 and 1.
- **B13-3.** `Test-Json -SchemaFile` accepts every good example and rejects every bad one. It accepts the real registry, the real identities and all 14 Contoso baseline findings. Real Python output (a dry-run `InvokeResult`, a denied one, its `Change`, a `Proposal.new`, and both audit records the runner wrote, including the denial) passes in PowerShell. Tampered copies fail. A keyword probe shows that each of the 24 validation keywords used rejects a document that breaks only that keyword. The probe fails if a schema starts using a keyword it does not cover.

## Recorded result (closes the STD-XL-3 UNVERIFIED note)

With PowerShell 7.6.7, which bundles JsonSchema.Net 7.0.0, every validation keyword the schemas use is enforced: `type`, `properties`, `required`, `additionalProperties`, `pattern`, `enum`, `const`, the length, number and item bounds, `uniqueItems`, `minProperties`, `propertyNames`, `anyOf`, `oneOf`, `allOf`, `$ref`/`$defs` and `if`/`then`/`else`. **`format` is not enforced.** It is an annotation only, so `"format": "date-time"` lets `"not-a-date"` through. Today that affects one field, `proposal.verification.at`. Python rejects a bad date-time; PowerShell readers must parse dates themselves (TenantBaseline already does). The suite checks this behaviour, so a future PowerShell that starts enforcing `format` will fail the check and prompt a docs update.

## Honest limits

- **Shape, not rules.** Cross-field rules stay in Python. Examples: a write lever needs lead approval, a proposal id is a content hash, the audit chain links. A schema-valid document can still be refused by the loader, and that is by design.
- **Four hand-written schemas are proposals until their readers land.** `lever-request` (B-15), `client` (B-18, W2-E1) and audit v2 (B-17) have no reader yet. The tests pin their shared patterns to the Python ones, but field choices beyond the roadmap text (`entry`, `as_of`, `adapter`, `retention_class` values, `schedule` syntax, industry list) are this item's proposal. The owning items should edit these files if they need a different shape, and the change note of that item should say so.
- **`lever-result` is the runner's `InvokeResult`.** It requires `lever`, `client`, `identity`, `mode` and `audit_seq`. The PowerShell host in B-15 cannot know `audit_seq`, because Python writes the audit. B-15 needs either a host-side subset schema or the runner filling those fields in after the call. That is B-15's decision; this item does not invent it.
- **`finding` keeps PascalCase keys** (STD-XL-5 asks for snake_case) because findings.json and the Power BI CSV already use them. Renaming them is a breaking change for a later item.
- **Integer edge.** JSON Schema treats `1.0` as an integer, but pydantic `StrictInt` does not. A PowerShell writer should emit integers without a decimal point (`ConvertTo-Json` does).
- **tests/ps is not yet in CI or the build automation.** That is owner step W2-E1. Until then, `test_b13_3_the_powershell_schema_suite_passes` runs it from `tests/py` whenever `pwsh` exists, so CI's Python job covers it on a runner with PowerShell. Without PowerShell those two tests are skipped, never passed.

## DECISIONS note proposal

D-0xx One schema per bridge shape; Python generates, both languages check (B-13, W2, 2026-10-21). `schemas/` holds draft 2020-12 JSON Schemas for the nine shapes Python and PowerShell share. Five are generated from the pydantic models by `tools/gen_schemas.py`, and a test fails on drift. Four are hand-written until a pydantic model exists, and their shared patterns are tested against the Python ones. PowerShell validates with `Test-Json -SchemaFile`. JsonSchema.Net 7.0.0 in PowerShell 7.6.7 enforces every keyword used except `format`, which is annotation-only, so date-times are checked in Python. Why: one written contract lets B-14, B-15, B-17 and B-18 land in parallel without drifting. Alternative: a shared code library, which is not possible across Python and PowerShell, or JSON Schema as the source with generated pydantic models, which needs a new dependency and loses the validators. What would change it: a pydantic model for `client` or `lever-request` (move that schema to generated), or a PowerShell release that enforces `format`.
