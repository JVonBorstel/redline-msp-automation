# B-77 change note: client discovery pack, offboarding runbook, migration pre-flight

Status: **mocked**. Read-only over synthetic fixtures. Spec: `specs/B-77.md`. Synthetic data only; independently built prototype.

## What changed

- New `workflows/client_lifecycle/`: `python -m workflows.client_lifecycle discover --client <id> [--as-of DATE] [--out DIR]` runs the read-only TenantBaseline (child `pwsh`, fixed command, values as environment), the B-61 device reconciliation and a licence report, and writes a discovery pack that lists every gap (stable ids, severity, next step, data class, sha256). `preflight --client <id> [--plan FILE]` runs three read-only checks on a migration plan: mailbox sizes against the destination quota, licence seats in the target SKU, and conflicting destination addresses.
- New `workflows/client_lifecycle/data/migrations/` (`contoso-dental` with one seeded problem per check, `fabrikam-capital` as the clean twin). The plan shape is this repo's own and every field is UNVERIFIED against any real migration tool.
- New `docs/runbooks/client-offboarding.md`: the human checklist for ending an MSP relationship (documentation export, credentials handed back, GDAP removed, tooling removed, written confirmation). Nothing is automated.
- New `specs/B-77.md` and `tests/py/projects/test_b77_client_lifecycle.py` (51 tests; the 2 real-B-61 tests and the 2 pwsh tests skip only where B-61 or pwsh is missing). No shared ledger or existing file was edited.

## Why

A new client starts with a clear baseline; a departing client leaves cleanly (W-PRJ-01, W-PRJ-02, W-PRJ-03). Missing data is shown as a gap, never an all clear. Executing migrations stays in `NN-04` (not now), so there is no execute command.

## Effect by level

- **L1 person**: mailboxes move without surprise (too big, no seat, address taken is known first); a leaving client's staff keep access to their own data.
- **L2 client business**: the baseline gaps are known on day one; on exit the client holds its own credentials and documentation.
- **L3 MSP**: discovery that took weeks is one command; access is shown to truly end, checked by a second engineer.
- **L4 community**: a small pattern for read-only intake and pre-flight checks.

## Caveats

- **B-61 (PR #62) is on main**: the device step runs the real RMM, Intune and PSA mocks, and its tests assert `ran` and the exact gap ids and counts. It reports `not-run` (a High gap) only if B-61 is absent, tested with a stand-in. Stale device ages use the RMM snapshot's time, not `--as-of`, so the device `counts.as_of` can differ from the pack `as_of`.
- Missing or invalid data is a gap, not a guess: unknown seat count (`LIC-SEATS`), unreadable retention date (`LIC-BADDATE`, the pack still completes), unknown account state (`LIC-ACCOUNTSTATE`), no user name (`LIC-NOUPN`). In pre-flight a missing mailbox size or recipient type fails its check, a non-numeric size raises `PreflightError` (exit 2), and a destination SKU with more assigned than enabled seats is reported as its own over-assignment.
- The package exports the pre-flight function as `run_preflight` so it no longer shadows the `preflight` submodule.
- Vendor field names in the fixtures and the plan, GDAP/Partner Center screens, the documentation-tool export, and whether a shared mailbox needs a licence are UNVERIFIED.
- Discovery and pre-flight write no audit record (no lever is called).

## DECISIONS proposal

**D-B77-1 Client exit and migration execution stay human.** Offboarding a client from the MSP (credentials, GDAP, agents, documentation) has no lever, workflow command or queue source, and migration tooling stops at read-only pre-flight checks; executing a migration needs its own item once the MSP names its tool (`NN-04`). Basis: W-PRJ-02 "none-keep-human"; NN-04. Revisit when the MSP defines its offboarding procedure or migration tool.
