## Why

The secrets pattern a managed-services team would run, reviewed as code: no credential where an identity will do, one RBAC-only vault per environment with soft delete and purge protection, audit events in Log Analytics.

## Individual to macro (L1-L4)

- L1: Ana, a technician, knows where a client credential lives and how it is named, instead of asking in chat.
- L2: a binding for Contoso Dental can only name `client-contoso-...` secrets, not Fabrikam Capital's.
- L3: the MSP gets read audit of the vault in one workspace and a deploy path that is validate and what-if only.
- L4: fewer credentials in tickets, scripts and repos at small practices and firms.

## Unverified (honest list)

- Nothing compiled or linted: syntax, property names and types in every `.bicep` and `.bicepparam` file are unchecked. The static tests read text.
- Resource API versions (KeyVault 2023-07-01, OperationalInsights 2023-09-01, ManagedIdentity 2023-01-31, Authorization 2022-04-01, Insights 2021-05-01-preview, Network 2023-09-01) and the built-in role id for Key Vault Secrets User are from memory; no vendor page opened.
- `@minValue(90) @maxValue(90)` on vault retention is a choice, not a verified platform rule.
- Whether `bypass: 'None'` interferes with diagnostic settings, and whether a private endpoint without a private DNS zone is usable, are unchecked. The private endpoint block is untested against any real subnet.
- The log workspace allows public query and ingestion (not restricted); `disableLocalAuth` effect on agents is unchecked.
- `uniqueString(resourceGroup().id)` makes the vault name differ per resource group; the 24-character `take` may cut the suffix.
- `credential_ref` is a proposal; no adapter reads it.
- No what-if output exists. The expected create-only result in the README is a prediction.
