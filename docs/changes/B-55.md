## What changed

- `core/guard/classify.py` (new): `DataClass` DC-0 to DC-6, `INDUSTRY_FLOOR` (dental DC-4; financial, ria, legal, accounting, other DC-5), `floor_for(client)`, the secret and PHI/NPI/PII shape rules, `classify(text, client=, declared=)`.
- `core/guard/redact_prompt.py` (new): `redact_prompt` normalises, classifies, blocks DC-6 (no text returned) and replaces every span with a typed, numbered placeholder.
- `core/gateway/gateway.py`: `complete(task, text, *, client=None, data_class=None)` runs the gate first. DC-6 is blocked before any provider. Hosted providers refuse DC-4/DC-5. Providers receive the redacted text only. `Completion` gains `data_class` and `redacted` (kinds, never values).
- `evals/redaction/` (new): `report.py`, committed `report.md`, and three synthetic client records under `clients/`.
- `tests/py/guard/test_b55_redaction.py` (new): 67 test cases named `test_b55_<k>_...`.

## Why

A patient's name in a printer ticket never reaches a model it should not. The governance rules (unknown is high, highest class wins, the industry sets the floor) are now code in the one place every prompt passes through.

## Individual to macro (L1-L4)

- L1: a Contoso Dental front-desk worker writes "patient Rosa Delgado (DOB 04/12/1958)" in a ticket; the model reads `patient [PATIENT_NAME_1] (DOB [DATE_OF_BIRTH_1])`.
- L2: a Fabrikam Capital ticket with an SSN-shaped string or account number is DC-5 and can never be routed to a hosted model, even if someone enables one in config.
- L3: the MSP can show one gate, one test file and one eval for C-25. A technician who pastes a password into a ticket gets a blocked call, and no model sees it.
- L4: regulated clients' patients and investors are not exposed to third-party model providers through a help-desk tool.

## Honest limits

- Rules only. Names need a cue word. Bare dates, personal email and street addresses are not redacted.
- No caller passes `client=` yet (`grep` finds none in `workflows`, `ui` or `core`). Until callers pass it, triage and the other workflows get the DC-5 default floor. That is stricter than the dental floor, never looser.
- `model_processing` and `regimes` from the client record are not read by the gate. D6-11 lets DC-4/DC-5 go to a hosted route only with a vendor-register entry (`B-90`, B90-4); no register exists yet, so the gate refuses DC-4/DC-5 on every hosted route without exception. Which item makes the gate read `model_processing` is unknown (not named in `docs/ROADMAP.md`).
- Hosted providers are still stubs, so "refused" is proven before a stub that could only fail anyway. The refusal sits ahead of the provider call, so it holds when a real adapter replaces the stub.

## DECISIONS

- D-0xx Industry `other` and a call with no client record take the DC-5 floor (B-55, 2026-10-23). Why: governance rule 1 says unknown is high ("treated as DC-4/DC-5"); DC-5 is the higher of the two and the highest class a model may ever see. Alternatives: DC-4 for `other` (rejected: no basis to pick the lower). What would change it: the MSP's compliance owner sets a floor per client.
- D-0xx The gateway refuses DC-4 and DC-5 on hosted routes whatever `config/models.json` says (B-55). Why: B55-3, governance BA-3 and GLBA-3 (no hosted processing without a BAA or provider due diligence). What would change it: a per-client approved-provider record (D6-11) that an owner sets.
- D-0xx Placeholders are typed and numbered and not reversible (B-55). Why: a mapping back to values would itself be PHI/NPI held next to the prompt. What would change it: a vault-backed re-identification step with its own approval.
