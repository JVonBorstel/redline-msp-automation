## Why

Offboarding and movers are where leftover access piles up. After this item a technician can cut off a session, close an account and reopen it exactly as it was, and change a mover's department, title or manager through one approved, audited path with a dry-run diff.

## Individual to macro (L1 to L4)

- **L1, one person.** A leaver's open sessions end; a person disabled by mistake gets sign-in back with nothing lost; a mover's profile changes without a ticket sitting for days. A wrong target costs a person their access or approvals.
- **L2, the client business.** The client can contain a stolen session without disabling the account, and reverse a wrong disable. Honest limits are stated: revocation lags, and it does not cover guests.
- **L3, the MSP.** Each step is registered, scoped, dry-run first, approved by a lead (callback on file for enable and mover changes) and audited; `user.disable` now names its undo, so the approval page can show it. `graph_scopes` gives the least-privilege review a place to read from.
- **L4, community.** Containment and mover cleanup done the same tested way at every client shrinks the window an attacker, or a forgotten account, has. Nothing here is client-specific.

## How the tests prove it

PowerShell script: dry-run writes nothing, execute applies exactly the dry-run diff, a repeat is empty, a guest and an out-of-client user are refused, only the three fields can be set, a missing Graph permission is denied before any file is read, and the host reports a denial without message text. Python: the registry, scopes, templates, undo pairing, the runner path for each lever, the closed field enum, and disable then enable giving back the same bytes.

## Not done, and caveats

- Byte-identical is against the canonical layout the Python writer produces; the committed `contoso-dental.json` is hand-formatted (see spec).
- Through the host all refusals read `crashed: RuntimeException`.
- Risk class is R2 per the item's acceptance although decisions in force treat identity changes as R3; the owner may want R3 (two approvers) for `user.enable` and `user.set-properties`.
- Graph permission names (except `User.RevokeSessions.All`) and the `manager` shape are UNVERIFIED.

## DECISIONS proposal

D-0xx IdentityOps levers are R2 and reversible by design (B-29, W3, 2026-10-21). `user.revoke-sessions` (no verification, containment), `user.enable` and `user.set-properties` (callback on file) run as PowerShell levers; `user.enable` and `user.disable` name each other as undo; `graph_scopes` is a registry field. Why: the item's acceptance and the need to make containment fast and reversible. Alternative: R3 with two signed-in approvers for enable and mover changes, as D-024 treats other identity changes. What would change it: the owner's call on whether enabling an account is a change to identity under D-024, or an incident where a mistaken enable or manager change caused harm.
