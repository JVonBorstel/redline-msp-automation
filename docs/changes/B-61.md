## Why

One true device list per client, which billing, patching and security all need. Three systems each keep their own list; the reconciliation says which device each record is and what does not add up.

## DECISIONS proposal

D-0xx Device reconciliation matches by serial, then by name, and never guesses (B-61, 2026-10-23). For one client the RMM devices (serial from the hardware audit), Intune managed devices and PSA configuration items are matched by a usable serial first; a record without one is matched by name only when exactly one device carries that name; records with different serials are never merged. Every record is in exactly one device, and each device that one system alone knows, each record not seen for 30 days and each device held twice by one system is listed. Adapters of different clients, or an RMM site linked to another PSA company, are refused before anything is compared. Why: W-EP-01, C-27, C-21, D6-01. Alternatives: matching by name first (rejected: reimaged and renamed machines collide); fuzzy name matching (rejected: a guess presented as a match). What would change it: real device data from the MSP's tools showing serials are often missing, or a link field (Autotask `rmmDeviceUID`) that is reliably filled.

D-0xx Existing RMM components are listed, never run (B-61, 2026-10-23; implements D6-26). The RMM adapter has no method that runs a job, quick job or component; the inventory marks every component `vetted: false`, `run_by_program: false`. Why: D6-26, CISA AA22-131A. What would change it: B-62 vetting a script into the registry as a lever, which the program then runs as a lever, never as a component.
