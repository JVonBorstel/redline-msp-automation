# B-20 change note: prompt library and prompt standards

Status: **built** (loader, three prompt files, standards page; 53 tests). Synthetic data only. Nothing calls a model.

## What changed

- `prompts/__init__.py` (new): the loader. `load(task, version)` (no default version), `load_library()` (fails as a whole), `versions(task)`, `render(prompt, values)` (exact inputs, untrusted ones through `core.guard.wrap_untrusted`), `output_errors(schema, value)` (small JSON Schema subset), `content_hash(text)`.
- `prompts/library/classify.v1.md`, `summarize.v1.md`, `reason.v1.md` (new): the gateway's three instructions as reviewed files with front matter. `classify.v1` is `active` and names `evals/triage/report.py`; the other two are `draft` with `eval: none-yet` because nothing measures them yet.
- `prompts/library/LOCK.json` (new): SHA-256 of each released file, so a released version cannot change in place.
- `prompts/STANDARDS.md` (new): PS-1 structure, PS-2 untrusted text, PS-3 minimum necessary (BA-4), PS-4 output schemas, PS-5 versioning, PS-6 the eval path for a prompt change (C-41).
- `specs/B-20.md`, `tests/py/prompts/test_b20_prompts.py` (new).

No file outside the item's `owns` was touched (`LOCK.json` sits inside `prompts/library/`).

## Why

Prompts lived as a dict in `core/gateway/ollama.py`. A reviewer could not see what a prompt needs, which version a model saw, or prove that ticket text stays inside its data block. Now each prompt is a file with a contract, and the loader enforces the contract.

## Individual to macro

- L1, one person (Priya Nair at Contoso Dental, synthetic): the words of her ticket reach a model only inside a labelled data block, and the prompt asks for the ticket text only, never her phone or name as a separate field. A ticket that says "ignore your instructions" cannot move out of the block.
- L2, client business: each prompt declares what client data it takes and why (BA-4), so a HIPAA security officer at a practice, or the compliance officer at an RIA such as Fabrikam Capital (synthetic), can read the list. One prompt, one client (ISO-3, review rule).
- L3, MSP: a prompt change is a new version with a hash, reviewed in a pull request and promoted only through its eval (C-41). The rendered prompt carries its id and hash, so an eval report names exactly which text was measured. Prompts never name a model, so switching provider stays a config change (C-16).
- L4, community: the same wrapped, minimum-necessary prompt is used at every tenant, so a prompt-injection trick or an over-sharing prompt cannot quietly spread across hundreds of small businesses.

## Honest limits

- Nothing uses the library yet. `core/gateway/ollama.py` still has its own table; a test pins that the v1 files start with the same instruction, so wiring it later is a no-op. Proposed owner: `B-22` or a gateway item.
- The v1 system text adds its own data-notice line where the gateway appends a slightly different one. Same intent, different words; switching over is a prompt change and should go through the triage eval once.
- The personal-identifier check is on input names only, a heuristic. Content redaction is C-25, planned.
- `output_errors` covers a small JSON Schema subset on purpose. Anything richer needs a decision.
- No CI gate blocks an unmeasured prompt from being pinned; the "an active prompt names its eval" rule is the only enforced part of C-41 here.
- No prompt quality is claimed. No prompt here was run against a real model.

## DECISIONS note proposal

D-0xx Prompts are versioned files with a hash lock and a pinned version (B-20, 2026-10-21). Each prompt is `prompts/library/<task>.v<n>.md` with front matter (inputs with trust and why, output schema, owner, status, eval). `LOCK.json` pins each file's SHA-256, callers pin `(task, version)`, and untrusted inputs render only through `wrap_untrusted`. Why: a prompt is code that touches client data; it needs review, a version a report can name, and a guaranteed data wrap. Alternatives: prompts as Python constants (no per-prompt contract, harder to review); a template engine such as Jinja (a new dependency and expression power a prompt does not need). What would change it: a prompt registry shared across repos, or per-tenant prompt variants (then the lock becomes per tenant).
