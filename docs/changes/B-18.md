## Why

The MSP's real PSA is still open (Q-01). The seam where it plugs in is built first, with isolation inside it: an adapter is built for one client from that client's binding, holds nothing of another client's, and never raises to its caller. A binding names a credential by reference only, and a real implementation fails closed.

## Individual to macro

- **L1 Priya Nair (one person at Contoso Dental):** T-3101 is read from Contoso's PSA company and only that. A lookup of Fabrikam's T-3201 from her client's adapter answers "no such ticket for this client", the same words as an absent ticket, so nothing about another firm's people leaks through a lookup.
- **L2 Contoso Dental (the client business):** the practice's PSA data and its credential name sit in one binding. A mis-wired binding (another client's data under its name) is refused at construction rather than quietly serving the wrong practice.
- **L3 the MSP:** moving to the real PSA is a binding change (`implementation`, external id, credential name) behind one interface. A ConnectWise or Halo adapter uses the same seam (D6-01). Config errors name the file and never echo a pasted secret.
- **L4 The community:** a thousand small differences between tenants cannot become one cross-client leak, because the one-client rule is in the base class every vendor inherits (TEN-04).

## Honest limits

- Mock only. No Autotask call was made; auth, paging, query filters and user-defined fields are not imitated.
- Ticket numbers (`T-3101`) follow this repo's fixtures, not Autotask's real numbering. Status, priority, queue and type numbers are invented placeholders.
- `config/clients/<id>.json` files are not created (`config/**` is protected, owner step W2-E1). Until they exist `build_adapter` fails closed with a message naming the missing file; tests use private copies under `tmp_path`.
- The adapter is read-only. Writing to the PSA needs its own lever, approval and audit item.
- Adapter calls are not audited here: reads are not written to the audit (STD-AU-4.3), and the audited path is the lever runner that will call the adapter.
- `ClientConfig` mirrors `schemas/client.schema.json` by hand; a test compares the shared patterns. Full schema-from-model generation is B-13's territory (the schema is hand-written there).

## DECISIONS proposal

D-0xx Adapters are one-client objects built from bindings (B-18, 2026-10-21). An adapter is constructed from one `BoundBinding` for one client; a binding of another client or another system is refused at construction (`AdapterError`); calls return `AdapterResult(ok, reason, data)` and never raise; a lookup of another client's object answers exactly like an absent one. A binding holds a credential reference name that must start with `client-<own id>-`; a value-shaped string fails validation and is never echoed. Any implementation other than `mock` fails closed with `real adapter not configured`. Why: TEN-04, STD-ER-1, STD-CF-7; the real PSA is Q-01. Alternatives: a registry of adapters keyed by client with a runtime client argument per call (one forgotten argument is a cross-client read); passing the credential through config (violates STD-CF-7). What would change it: the MSP's real PSA and a vault design (D6-10) that needs a different lookup.
