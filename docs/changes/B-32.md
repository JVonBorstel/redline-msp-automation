## Why

Day-one access and role moves are daily work, and the wrong group is a data exposure; a group that holds an admin role is the one thing automation must never touch. The lever refuses it before it computes anything, so even a correct approval cannot grant admin rights through this door.

## Individual to macro (L1-L4)

- L1: Priya Nair (Contoso Dental, synthetic) gets Front Desk Staff the day she starts, without waiting; asking for the IT admin role group is refused with a clear reason and nothing changes.
- L2: the practice's records stay limited to people who need them; membership follows the job, and removal on a move is as easy as addition.
- L3: access requests become one approved, audited, reversible change; no automated path exists to grant admin rights.
- L4: the same least-privilege rule at every client; a client's own privileged list is honoured, so one weak habit at one office does not become a way into the others.

## DECISIONS proposal

D-0xx Group membership levers refuse privileged groups in the module, and report per-call risk (B-32, 2026-10-22). `group.add-member` and `group.remove-member` are R2 in the registry; the call's own class (R2 data access, R1 distribution only) is returned in the dry-run data. A group with `isAssignableToRole` true, or named on the client's privileged list, is refused in dry-run and execute, in both directions, with a W-IDM-07 reason. The PowerShell host gains a `refusal` return so a reason survives. Why: `W-IDM-07` is never-automate; the reason must reach the technician and the audit. Alternatives: a Python pre-check in the runner (rejected: it would need the family files and group rules in core); throwing from the lever (rejected: the host hides the message by design). Would change: a runner that reads a per-call risk class so an R1 call needs fewer approvals (open; today both need the R2 floor), and a real adapter that also checks `transitiveMemberOf`.
