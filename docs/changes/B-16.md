# B-16 change note: Python bridge and runner dispatch by runtime

Status: **built**. Synthetic data only. Spec: `specs/B-16.md`.

## What changed

- `core/levers/bridge.py` (new): `PowerShellBridge` starts `pwsh -NoProfile -NonInteractive` on the B-15 host with one `lever-request` on stdin, reads and verifies one `lever-result` line, kills the child at `timeout_s`, scrubs the environment, and returns a typed `BridgeResult` instead of raising. `PowerShellEntry`, `parse_entry` for `<Module>\<Verb-Noun>`.
- `core/levers/runner.py`: `LeverRunner(..., bridge=None)`; `_run` dispatches by runtime after every existing check; `_run_powershell` (read as `execute`; write as dry-run, audit, real call, diff must match); `_record` can carry `request_id` and `lever_version` (used for PowerShell levers; Python levers are unchanged).
- `core/levers/registry.py`: `runtime: "powershell"` with `entry: "Module\\Function"` now loads (module folder must exist); `Registry.runtime`, `Registry.powershell_entry`, `Registry.load(powershell_root=...)`. The four Python levers, the live registry and the generated schemas are unchanged.
- `levers/powershell/Sample/` (new): `Sample.psd1`, `Sample.psm1` (`Get-SampleUser`, `Set-SampleUserTitle`), `Sample.registry.json` (not loaded by default), `README.md`.
- `tests/py/levers/test_b16_bridge.py` (new): 56 tests named after B16-1 to B16-3.
- `specs/B-16.md` (new).

## Why

Every identity, device and Microsoft 365 lever after this is a PowerShell function and one registry entry, with no core change, and no permission decision ever moves out of Python. The decisions (role, client scope, four-eyes approval, pause, requester verification, audit) are made before a process exists; PowerShell gets one validated request for one client.

## Individual to macro (L1 to L4)

- **L1, one person.** Priya Nair (synthetic, Contoso Dental) asks for a change to her account. The lead sees a dry-run diff produced by a `-WhatIf` run, approves that exact diff, and the real call must apply exactly it. If it does not match, or the process hangs, the ticket shows an error, not a half-applied account.
- **L2, the client business.** The client id travels only as the request's `client`; the sample lever resolves one tenant file from a validated slug, so a call for a dental practice cannot read or change an investment firm's directory (tested). A hung script is killed instead of holding the practice's queue.
- **L3, the MSP.** A new lever family is a PowerShell function plus one registry entry. The audit trail is the same hash chain, now with `request_id` (also sent to the host) and `lever_version`; the audit-first order and the second record for a failed apply are the same as for Python levers. The child process gets no token or secret from the environment.
- **L4, community.** A fooled agent or a crafted parameter cannot widen what a PowerShell lever may do: parameters are schema-checked before the process starts, the host answer is verified (right lever, client, mode, exit code), and anything odd is discarded as an error. The same checks protect every client the MSP serves.

## How the tests prove it

- **B16-1.** Denials (unknown lever, bad params, unknown identity, wrong client, agent executing a write, missing approval, non-lead approver, mismatched approval, four-eyes, paused) leave no process started (a recording bridge sees zero calls) and the tenant bytes unchanged. A spy on `Popen` shows `-NoProfile -NonInteractive`, the host script and a child environment without a secret-shaped variable (also proven from inside a real child). A fake host script returns malformed, doubled, empty, mismatched and over-trusting answers, each discarded. Registry load rejects malformed entries, a missing module and a reused name; the bridge patterns equal the committed request schema.
- **B16-2.** A fixture module that sleeps 120 seconds is killed at 4 s (dry-run) and at 6 s (during the real call, which also leaves the tenant bytes unchanged and a second audit record saying nothing was applied); the child process is verified gone.
- **B16-3.** The sample read returns the user without contact or sign-in details and cannot see another client's user. The sample write's dry-run diff equals the diff of a Python twin lever on the same state, for `replace` and for `add`; an execute changes the tenant file by exactly the dry-run diff (verified with `json_diff` and a whole-file comparison), leaves other clients' files byte-identical, leaves no temp file, and a second execute is "no change".

## Honest limits and decisions for others

- **Two host calls per write execute** (about one second each for `pwsh` start-up). Accepted for audit-first plus an exact-diff check; a long-lived host process is a later optimisation.
- **Kill covers the `pwsh` process, not a native child it started** (as noted in B-15). Real levers should not shell out.
- **"Nothing applied" after a kill is a contract, not a proof.** The sample applies in one atomic replace at the end of the function, so a kill before it leaves nothing; a real lever against a network API could be killed after the remote side acted. The second audit record says what was reported, and the reason tells the technician to check the target before retrying. Real levers should be idempotent (STD-LV-6), which makes a retry safe.
- **The sample reads the tenant folder from `REDLINE_MOCK_TENANT_DIR`**, which the bridge sets from the runner's `MockTenant`. This is a mock-only path; a real adapter lever will receive its binding in the request's `adapter` object instead, and no env var.
- **Timeout includes `pwsh` start-up** (about 1 s here), so PowerShell levers should declare `timeout_s` of 5 or more; the sample uses 15.
- **Read levers run in `execute` mode** at the host. A read that changes state is only detected, not prevented, because there is no state copy to diff. Reads are reviewed code, and the diff or `applied` it reports makes the call an error.
- `Test-Json` and the host need PowerShell 7.4+; the bridge reports "not installed" otherwise and the pwsh tests skip.

## DECISIONS proposal

D-0xx PowerShell levers run through one bridge with the checks in Python first (B-16, W2, 2026-10-21). A lever with `runtime: "powershell"` and `entry: "<Module>\\<Verb-Noun>"` is authorised entirely by the Python runner; the bridge then starts `pwsh -NoProfile -NonInteractive` on the lever host with a scrubbed environment, kills it at `timeout_s`, and treats any answer that is not exactly one well-formed result for the same lever, client and mode with a matching exit code as an error. A write's execute is a host dry-run, the audit record, then the real call, which must report exactly the dry-run diff as applied; a mismatch or failure adds a second audit record. Reads are sent to the host as `execute`. Why: permissions cannot drift into PowerShell, and a hung or misbehaving script cannot apply a change nobody approved. Alternative: pass the state to PowerShell and apply the diff in Python (breaks for real adapters, where PowerShell does the acting). What would change it: a long-lived host process, or a registry field marking a read lever so its dry-run can use `-WhatIf`.
