# B-81 change note: scheduler with per-client fan-out and job keys

Status: **built** (library and tests, in-memory stores only). Proposes and reports; it cannot run a lever. Synthetic data only. Spec: `specs/B-81.md`.

## What changed

- `core/scheduler/` (new): `models.py` (config, unit, result, record, period and key), `stores.py` (`JobStore`, `ProposalSink`, `UnitAudit` Protocols, in-memory implementations, `RouterAudit`), `scheduler.py` (`Scheduler.tick`), `jobs.example.json`, `__init__.py`.
- `tests/py/scheduler/test_b81_scheduler.py` (new): 59 tests, named `test_b81_<k>_...`.
- `specs/B-81.md` (new).
- **Outside `owns`:** none. No existing file was edited. Imports, never edits: `core.levers` (registry, schema, `ClientId`), `core.audit.router`, `core.queue.store.proposal_id` (a function; the queue store and the audit store are not changed). The B-82 SQLite queue and audit store are not touched.

## Why

Daily baselines and monthly or quarterly reviews have to run for every client without anyone remembering, and a retry or a crashed client must not double a result or stop the others.

## Individual to macro (L1-L4)

- L1: Ana no longer starts the Contoso Dental baseline by hand; it is a keyed unit that runs once per day.
- L2: each client's run is its own unit with its own audit record in its own chain; one tenant failing does not touch another.
- L3: the MSP sets caps (global, per client, per job) in config, so 300 clients are admitted over several ticks instead of all at once (C-32).
- L4: fewer missed baselines and reviews at small practices; every result is a report or a proposal a lead approves, never a silent write.

## Honest limits

- Only in-memory stores exist; B-82's SQLite queue is not used. A key left `running` by a crash is never reclaimed. A failed unit is not retried in its period.
- Caps are per-tick admission limits, not parallel workers. UTC only; client business hours and daylight saving are not modelled.
- The proposal sink is in-memory. Wiring to `ProposalQueue` needs a new `source` value there (queue code, not changed here) and its dry-run step is not exercised.
- No real workflow is registered and there is no CLI or loop; `jobs.example.json` is an example. Nothing was run against a live clock or two processes.

## DECISIONS proposal

D-0xx Scheduler is a tick-driven, key-idempotent fan-out that only proposes (B-81, 2026-10-27). A job is config; `tick(now)` starts one unit per eligible client keyed `job/client/period`, skips keys already stored (failed ones included), defers units over the global, per-client or per-job cap to a later tick, and fails one unit without touching the rest. Workflows return a report and proposed levers; each is checked against the registry (registered, client in scope, params valid, write levers dry-run capable) before it reaches a `ProposalSink`, and the scheduler has no runner. Storage sits behind a `JobStore` Protocol so B-82 can replace the in-memory one. Audit params hold job and period, not the key, because the redactor blanks long mixed runs (STD-AU-5). Why: W-TOOL-09, W-IDM-09, W-M365-11; C-32, C-18, C-27. Alternatives: automatic retry of failed units (rejected: a person should look first), threads for real concurrency (rejected: nondeterministic tests, no durable store yet). What would change it: the durable queue's lease model (B-82) and the MSP's real run windows.
