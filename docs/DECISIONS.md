## D-016 Permissions live in the lever runner, and every call is audited (Phase 1, 2026-10-20)
Why: the model only proposes. `core/levers/runner.py` checks registration, schema, role, client scope and approval, in that order, and writes one audit record per call, allowed or denied. Agents may dry-run write levers but never execute them. An approval is bound to the exact lever, client and parameters and comes from a different lead with access to that client; self-approval is refused. Alternative considered: checks inside each lever, rejected because one forgotten check would be a hole.

## D-017 Audit log: canonical-JSON SHA-256 chain plus a head pin (Phase 1, 2026-10-20)
Why: each record's hash covers canonical JSON (sorted keys, no spaces) including the previous hash, so a one-byte edit names its seq. A separate head file pins the newest record, so deleting from the end is caught too. Read results are not logged, to keep personal data out; params are redacted by key name and by secret-looking values. Limit: one writer process per log.

## D-018 Model gateway: mock by default, Ollama on loopback only, hosted adapters off (Phase 1, 2026-10-20)
Why: client data never leaves the machine unless the owner turns a hosted adapter on (they are stubs today). The Ollama base URL must be exactly 127.0.0.1, localhost or ::1; userinfo, look-alike hosts and redirects are refused. A provider that is down returns an error object, never an exception. The gateway returns text only and never turns model output into a tool call.

## D-019 Injection detection is a tripwire, not the control (Phase 1, 2026-10-20)
Why: transparent, named regex rules after NFKC and invisible-character stripping, plus structural checks (hidden HTML, styles, markdown image exfiltration, base64). Precision and recall are 100% on a 50-case synthetic corpus written alongside the rules, so that is not a real-world claim. Known misses: look-alike letters, paraphrases, other languages. The real control is D-016: flagged or not, the model can only reach registered levers within scope.

## D-020 Slice B is read-only, deterministic, and its summary is machine-checked (Slice B, 2026-10-20)
Why: findings come from mock Graph v1.0-shaped fixtures with a pinned as-of date, so runs are byte-identical. Inactivity uses lastSuccessfulSignInDateTime, because lastSignInDateTime also counts failed attempts (a password spray would make a dormant account look active). Fixes are proposed only as lever names, in dry-run. `Test-SummaryReconciles.ps1` fails if any number in the plain-English summary differs from the findings; any later model rephrasing must still pass it. `-UseGraph` refuses before any connection and lists the read-only scopes (Secure Score would also need SecurityEvents.Read.All). Nothing has run against a real tenant.

## D-021 The repo has a GitHub home, CI and a public release (2026-10-20, supersedes D-010)
Why: pull requests and GitHub Actions run the lint, type and test suites on clean runners. The repository was first private. It is published after a sanitising export that carries only synthetic data and no private workflow files; publishing stays the owner's decision.

## D-022 Triage: the model names a category; rules choose the lever (Slice A, 2026-10-20)
Why: the injection scan runs on the raw ticket first, then the text is wrapped as untrusted data before the gateway sees it, and the reply must be one of a fixed list of categories. A fixed table maps category to at most one lever, and the parameters come from the ticket's form fields (affected user, client), never from ticket text or model output. The lever is dry-run as triage-bot and proposed as the ticket's technician. A flagged ticket goes to the security queue with no lever. Accuracy is fixture-based on the mock: the tickets and the mock's keyword rules share an author, so this shows the pipeline works end to end, not model quality.

## D-023 Approval queue and viewer: stdlib, loopback, approve-then-execute (Slice C, 2026-10-20)
Why: no installs and a small attack surface. The server binds 127.0.0.1 only and also checks the Host header; decisions are POST-only with a per-process CSRF token; every value is HTML-escaped; the Content-Security-Policy allows only the page's own stylesheet, and there is no script. A proposal is marked approved before it executes, so a crash can't run it twice. Only a lead for that client who is not the requester may decide, and refused attempts are audited. Known gap: "demo sign-in" is an identity picker over synthetic users, not authentication; a real deployment would sit behind Entra ID sign-in.

## D-024 The master map comes before building; three open map questions settled (2026-10-21)

## D-026 Levers declare their risk, undo and impact trace (B-01, W1, 2026-10-21)
Why: the person-to-community trace and the social-engineering rule belong on the lever, where permissions already live. Every lever declares `risk_class` (R0-R3), `reversibility`, `undo`, `lever_version`, `impact` (L1-L4, one line each) and optionally `verification: "requester"`. Validators make unsafe combinations unconstructable (read = R0; write = R1-R3; irreversible = R3 with no undo; `undo` must name a registered write lever, null means manual undo). A write lever without `risk_class` or `impact` fails the registry load, naming the lever; presence is checked at file load, not in the model, so levers built in code by tests keep working. `user.reset-mfa` and `user.disable` are R3 (D-024) and need requester verification. An approval can carry `verification {method, by, at, ref}`.

## D-027 The runner pauses levers and refuses unverified identity changes (B-02, W1, 2026-10-21)
Why: AIR-11 and IR-2 enforced in code, not only documented. Pauses live in `pauses.json` beside the audit log, so every runner on one state folder shares them. Only a lead may pause or resume; pausing needs no approval; a global pause wins over a client pause; an unreadable pause file denies every call (fail closed). A `verification: "requester"` lever executes only with an approval whose verification is by a known identity scoped to the client and not future-dated, and it is written to the result. The audit copy of a diff keeps only type and id for authentication methods and masks contact keys and `+`-phone strings (STD-AU-4 item 6); the caller keeps the full diff. Exception recorded: small edits to `core/queue/store.py`, `ui/app.py` and Phase 1 test helpers kept the suites green until B-03.

## D-028 The approval page scopes, explains and records the callback, never the number (B-03, W1, 2026-10-21)
Why: the human approval step is where the person is protected. The page lists only the signed-in lead's clients (DR-12); a decide for another client stays a 403 and is audited. Each card shows the UPN, the L1 impact line, the masked dry-run diff from the audit log and the undo lever (or manual undo). Approving a requester-verified lever needs a method and, for a callback, the number's source from a fixed list, recorded as `ref = number-on-file:<source>`; there is no free-text field and unknown fields are refused, so a phone number cannot be recorded. `seed --demo` proposes as `triage-bot`, so demo proposals have an audited dry-run first (STD-PR-1). Limits: demo sign-in is a picker (C-44 is W2); the verification is an attestation, not proof of the call; the CLI `--verified callback-on-file` path does not yet require the number's source. Exception recorded: two lines each in `tests/phase1/test_ui.py` and `tests/py/levers/test_b02_runner_gates.py`.

## D-029 Notices to the affected person are template-filled, never model-written (B-04, W1, 2026-10-21)
Why: a notice is client-facing text about a security change, so it must be reviewable once and testable for length, reading grade, secrets and phone numbers. Only `executed` proposals get a draft, and its first line says a person reviews and sends it. What would change it: per-client wording or languages that templates cannot cover. Sending and the send record are not built.

## D-033 One repo root and a checked config version (B-12, W2, 2026-10-21)
Why: a command must give the same result from any folder (STD-CF-9), and a reader must refuse a format it does not know (STD-CF-4). `core.paths.REPO_ROOT` is the default root for the gateway config loader and its CLI; the reader accepts `version: 1`, refuses any other value (including look-alikes such as `true` or `1.0`) and names the file, and accepts an absent version only until `config/models.json` and `config/routing.json` carry it (owner step; then absent becomes a rejection). The gateway and guard modules gain `from __future__ import annotations` (STD-PY-6). Alternative: a required `root` argument and no version (every caller must get the root right; a future format is half-read). What would change it: packaging the repo, where `importlib.resources` replaces a file-system root. Exception recorded: the `__future__` line and the CLI default in `core/gateway/__main__.py`, `core/gateway/__init__.py`, `core/guard/__init__.py`, `core/guard/normalise.py`.

## D-034 One schema per bridge shape; Python generates, both languages check (B-13, W2, 2026-10-21)
Why: Python orchestrates and PowerShell acts, so the shapes they share must be written once and checked from both sides. `schemas/` holds nine draft 2020-12 JSON Schemas: five generated from pydantic by `tools/gen_schemas.py` (`--check` fails on drift), four hand-written (`lever-request`, `audit-record`, `finding`, `client`) until a pydantic model exists, with their shared patterns tested against the Python ones. PowerShell checks with `Test-Json -SchemaFile`; JsonSchema.Net 7.0.0 in PowerShell 7.6.7 enforces every keyword used except `format`, which is annotation-only, so date-times are checked in Python (recorded result, replaces the STD-XL-3 UNVERIFIED note). Schemas carry shape, not cross-field rules. Alternatives: JSON Schema as the source with generated pydantic (new dependency, loses validators). What would change it: a pydantic model for a hand-written shape, or a PowerShell that enforces `format`.

## D-035 Lever families are fragments; the never-automate list is a hard gate (B-14, W2, 2026-10-21)
Why: many lever families must land in parallel without one shared file, and "never automate" had to stop a pull request, not sit in a map. `Registry.load` reads `levers/registry.json` plus `levers/registry.d/*.json` as one registry; a duplicate, an unversioned fragment, an unknown field or one bad lever fails the whole load. A Python `entry` may only name a callable defined inside `levers.python` (STD-LV-2, STD-LV-10). `governance/never-automate.json` lists exactly the 22 `none-keep-human` inventory ids (a test keeps them in step); the loader refuses any lever whose name matches a pattern, naming the inventory id and reason. Adding or removing an entry needs a DECISIONS entry. Limit: patterns match names, not intent; registry code review stays the second control. Known effect: the planned `ca.block-legacy-auth` fix lever now cannot register (W-IDM-06 says Conditional Access stays human); its owner should make it a report.

## D-036 The PowerShell lever host is a stdin/stdout JSON process with fail-closed rules (B-15, W2, 2026-10-21)
Why: the Python runner decides; the host must not widen what it decided. `levers/powershell/LeverHost/Invoke-LeverRequest.ps1` validates the request against `lever-request.schema.json`, imports only the named module, runs only a function that module exports, maps `params` to declared parameters (never `Client`, `AsOf` or common parameters), calls with `-WhatIf` for dry-run and refuses a dry-run of a function without it, runs in a null-host runspace, and returns `<lever> crashed: <type>` for any exception (detail only in an optional log). Exit 0/1/2. Its result is lever-result minus `identity`, `approver`, `audit_seq`, which Python adds. `tests/ps/Test-Modules.ps1` runs every module's tests with one summary line. Limits: the timeout stops the pipeline, not native children; runspace isolation is not a boundary against a malicious module (modules are reviewed repo code).

## D-037 PowerShell levers run through one bridge, with every check in Python first (B-16, W2, 2026-10-21)
Why: permissions cannot drift into PowerShell, and a hung or misbehaving script cannot apply a change nobody approved. A lever with `runtime: "powershell"` and `entry: "<Module>\\<Verb-Noun>"` is authorised entirely by the runner (role, scope, approval, four-eyes, pause, verification, params) before any process starts. `core/levers/bridge.py` starts `pwsh -NoProfile -NonInteractive` with a scrubbed environment, kills it at `timeout_s`, and treats any answer that is not exactly one well-formed result for the same lever, client and mode as an error. A write's execute is host dry-run, audit record, real call; the real call must report exactly the dry-run diff, and a mismatch or failure adds a second audit record. Reads go to the host as `execute`, and a read that reports a change is an error. Limits: two `pwsh` starts per write execute (about a second each); "nothing applied" after a kill is a contract (levers must be idempotent), not a proof. Alternative: apply the diff in Python (breaks for real adapters). Exception recorded: `core/levers/registry.py` (loader accepts `runtime: "powershell"`).

## D-038 Audit records are version 2, additive and forward-only (B-17, W2, 2026-10-21)
Why: correlation and lever version are what audits and incident scoping need ("every `user.reset-mfa` v1 run between these dates, at which clients"). New records carry `v: 2`, `event`, `actor_kind`, `lever_version`, `request_id`; v1 records are never rewritten, and the verifier accepts v1 then v2, never the reverse, so a record cannot be downgraded to hide the new fields. Missing caller values are written as `unknown` / `null` / a fresh hyphenated id, never a guess; an unknown mode is written as `invalid` with the raw value (capped) in `result.requested_mode`; `lever.pause` joins the STD-AU-2 event list. Until B-28 and B-80 pass real values, the records of one T-3101 run are not yet linked. Alternative: a v2-only verifier with a migration (rewrites evidence). Closes DR-04. Exception recorded: typing lines in `core/queue/store.py`, `core/levers/runner.py` and one assertion in `tests/phase1/test_audit.py`.

## D-039 Adapters are one-client objects built from bindings (B-18, W2, 2026-10-21)
Why: the MSP's real PSA is open (Q-01; Autotask is the likely one, 07-msp-profile), so the seam is built first with isolation inside it (TEN-04, STD-ER-1, STD-CF-7). An adapter is constructed from one `BoundBinding` for one client; a binding of another client or system is refused at construction; calls return `AdapterResult(ok, reason, data)` and never raise; another client's object answers exactly like an absent one. A binding holds a credential reference name that must start with `client-<own id>-`; a value-shaped string fails validation and is never echoed. Any implementation other than `mock` fails closed with `real adapter not configured`. The PSA mock follows the public Autotask REST entity shapes; picklist values are placeholders and the SLA entity is UNVERIFIED. `config/clients/<id>.json` does not exist yet (owner step W2-E1), so `build_adapter` fails closed. Alternative: one registry keyed by a per-call client argument (one forgotten argument is a cross-client read).

## D-040 Per-family Graph state lives beside the client file (B-19, W2, 2026-10-21)
Why: lever families land in parallel without a shared edit hot-spot, and a family file is only ever read for its own client (C-04). Family state is `fixtures/tenant/<client>/<family>.json`, must carry `_meta.client` equal to its folder's client, and is read only by that client's `GraphMock`; the adapter has no write method, so state changes only through the runner's diff-and-save path (SL-04). Limits: mock only; the runner still saves only the base file, so the first family item teaches it families; `build_adapter` still says no `m365` adapter, use `build_graph_adapter`. What would change it: real Graph, where state lives in the tenant.

## D-041 Prompts are versioned files with a hash lock and a pinned version (B-20, W2, 2026-10-21)
Why: a prompt is code that touches client data; it needs review, a version a report can name, and a guaranteed data wrap. Each prompt is `prompts/library/<task>.v<n>.md` with front matter (inputs with trust, why and size limit; output schema; owner; status; eval). `LOCK.json` pins each released file's SHA-256, callers pin `(task, version)` with no "latest", untrusted inputs render only through `wrap_untrusted`, and an `active` prompt must name its eval (the enforced part of C-41). `prompts/STANDARDS.md` holds PS-1 to PS-6. Prompts never name a model (C-16). Limit: nothing calls the library yet; `core/gateway/ollama.py` keeps its table, and a test pins that the v1 files carry the same instruction, so wiring it is a prompt change through the triage eval. Alternatives: Python constants (no per-prompt contract), Jinja (new dependency).

## D-042 Phase 2 gold set and the third client, Litware Legal (B-21, W2, 2026-10-21)
Why: a set large enough to measure summaries, duplicates, SLA risk, cited replies and redaction, and a third tenant for isolation tests, following the MSP's market (financial, RIA, legal; D6-13). 210 synthetic tickets in `fixtures/tickets/phase2/` (Contoso Dental 50, Fabrikam Capital 80, Litware Legal 80), one file per client with an `as_of`, kept apart from the Phase 1 set so the triage eval and its report stay byte-identical. Labels add duplicate group, SLA tier, summary facts (verbatim substrings), reply sources (same-client KB) and sensitive spans; every sensitive shape is fictional by construction (`00-` accounts, `000-` SSN area, 555-01xx phones). `fixtures/tenant/litware-legal.json` adds 9 synthetic staff and 10 KB articles. Limits: one author wrote tickets and labels, so later scores are pipeline checks, not model quality; no Litware identity exists in `config/identities.json` yet. What would change it: real, consented, scrubbed the MSP tickets for a second, non-fixture score.

## D-043 Intake proposals and escalation packages are lookups and quotations (B-22, W2, 2026-10-21)
Why: closes the wrong-client and invented-step failure modes in code, not prompt wording (C-12, C-13, C-27). A ticket's client and contact are proposed only by matching the sender address against each client's own PSA contact list (one adapter per client); a model, the ticket text and the ticket's own `client` field never choose them, and an address that is a contact at two clients proposes nothing. The escalation package is made only of `Fact(label, value, source)` lines copied from the cited field and re-traced before return. A flagged ticket is summarised as flagged and contributes no free text. Fixture eval: 210 of 210 matched and traced, 0 unsupported facts (fixture-based; recall is high because sentences are quoted). Limits: reads go to the adapter directly with no audit record (proposed follow-up: `ticket.related` and `user.devices` read levers); package text can hold PHI/NPI-shaped strings until redaction (C-25). Alternative: a model writes the package (rejected until it passes the same trace check).

## D-044 Ticket grouping suggests per client; linking is an R1 approved write (B-23, W2, 2026-10-21)
Why: duplicates are worked twice and an outage looks like ten small tickets; grouping inside one client is the cheapest early signal (W-SD-03, W-SD-08). Grouping takes the client explicitly and drops every other client's ticket before any comparison; an outage group is 3 or more tickets of one category from at least 2 people within 4 hours (`workflows/duplicates/config.json`); a flagged ticket is never grouped; ticket text selects topics and never reaches a result, a parameter or a reason. `ticket.link` (`levers/registry.d/ticket.json`) is R1, `approval: lead`, agent may dry-run, stores a symmetric `links` map, never closes or merges, and answers a foreign ticket like an absent one. Eval (fixture-based, in-sample): 33 of 33 pairs, 0 false pairs, 7 of 7 outages, 1 false alarm shown. Limits: no unlink lever yet; the notice cannot be auto-filled (needs `upn`). Alternatives: embeddings (not reviewable yet), merging (irreversible). Exception recorded: the W2 integration relaxed B-16's shipped-registry pin so `ticket.link` can ship.

## D-045 SLA numbers come from the client's own SLA matrix, and every count is re-derived (B-24, W2, 2026-10-21)
