# Ticket summaries, intake matching and escalation packages (workflows/summary)

Status: **built** (B-22). Synthetic data only; nothing is saved to a PSA and nothing is sent.

> Independently built prototype. Not affiliated with any vendor's or real company's systems.

**Purpose.** Two things a dispatcher or the next technician would otherwise do by hand. (1) An **intake proposal**: which client, which contact, and a short summary. (2) An **escalation package**: what is already known about the ticket (ticket facts, steps tried, related tickets, device facts), each line citing the field it was copied from, so nobody re-asks the end user what already happened.

**Run.**

    uv run --frozen python -m workflows.summary T-5116 --state .tmp/demo

Writes `<state>/summary/<ticket>.md` (proposal, then package) and prints it. Exit 0 = proposal and package; 1 = proposal only (no client matched, or the ticket is not in that client's PSA); 2 = unknown ticket or bad data. The state folder's `tenant/` is used when present.

**How the proposal is made (never by a model).**
1. The sender address is compared with the contacts of each client's own PSA adapter (`adapters.PsaAdapter`, read-only, one adapter per client). Exact address at one client: that client and contact (`email`). At two or more clients: nothing is proposed (`ambiguous`). Unknown address with a domain only one client uses: that client, no contact (`domain`). Otherwise `none`.
2. The affected user, if different from the sender, is matched only against the proposed client's contacts. Another client's person is never looked up (`not-a-contact-of-this-client`).
3. The ticket's own `client` field is not read. An inactive PSA contact is proposed and flagged.
4. The summary is the subject plus up to three body sentences, quoted, joined with ` | `, at most 400 characters. An optional summariser hook `(subject, body) -> str` (a model later; it must wrap the text, C-12) can replace the summary text. Its output is length-limited and scanned, and it can change nothing else; bad output falls back to the quoted summary.
5. A ticket flagged by `detect_injection` is summarised as `Flagged: ... (rules: ...)`, never reaches the summariser, and its package carries metadata only.

**How the package is made.** From the proposed client's PSA adapter and tenant only. Every `Fact(label, value, source)` copies `value` from the field `source` names (`psa:ticket/T-5116#description`, `psa:ticket-note/91001#description`, `psa:contact/41001#title`, `tenant:user/<upn>#authentication.methods[1].displayName`). `build_package` re-checks every fact against its source and raises rather than return an untraceable line. Sections with nothing say `none recorded`. Steps tried are PSA ticket notes plus requester sentences containing words such as tried, restarted, rebooted. Related tickets are this client's tickets with the same contact in the previous 30 days, or with at least two shared significant words created within four hours (at most 5). Notes and related tickets whose text is flagged are withheld and counted.

**Data.** `data/psa/<client>.json` is PSA-shaped (Autotask-like Companies, Contacts, Tickets, TicketNotes, Resources) and generated by `evals/summary/build_psa.py` from the tenant users, the ticket files (labels dropped) and 12 hand-written synthetic notes (`evals/summary/notes.json`). A test checks the files equal a fresh build. Status codes are placeholders; `affectedUserEmail` is a local field (both UNVERIFIED against Autotask).

**Eval (fixture-based).** `uv run --frozen python -m evals.summary.report` writes `evals/summary/report.md`: 210 of 210 clients and contacts proposed correctly, fact recall 100% (319 of 319 labelled facts), 0 unsupported facts in 2921, 15 of 15 injection tickets summarised as flagged.

**Known limits.**
- Packages copy ticket text, including any PHI/NPI-shaped strings it contains (account numbers, names). They are for the receiving technician at the same client; redaction before any prompt is C-25 (planned), and anything sent to a model must be wrapped.
- No RMM adapter exists, so device facts are registered sign-in devices only (no laptop health, patches or backup). They are read from the tenant fixture directly, not through a registered lever, because `levers/registry.json` has no read lever for them (proposed in `docs/changes/B-22.md`).
- Related tickets by contact are noisy (193 of 210 packages list at least one); a technician reads them, nothing acts on them.
- Recall is high because every description sentence is quoted; precision and usefulness to a technician are not measured. The scores say nothing about a model, and `summarize.v1` stays `draft`.
- The ticket has to exist in the PSA data; a brand-new ticket would need the live adapter.
