# Use-case intake and scoring rubric

Status: **built** (typed intake, scorer, checker and tests; the example intakes are synthetic)

> Independently built prototype. Not affiliated with any vendor's or real company's systems. Synthetic data only.

This page is generated by `uv run --frozen python -m workflows.assurance generate --write` from the intake model, `governance/intake_rubric.json`, `governance/roi_fixtures.json` and the examples in `fixtures/governance/intakes/`. Do not edit it by hand; `check` fails when it drifts.

An idea for an automation is written as one JSON file in the shape below. A script scores it the same way every time and lists the rule behind each part of the result. The score ranks ideas for a conversation with leadership. It approves nothing: a person reads every intake, and an approved idea still goes through the lever change process (C-37). Synthetic prototype. The weights and bars are proposals for leadership to set (UNVERIFIED: no the MSP value, risk-appetite or ranking policy is known, GQ-01).

## Submit an idea

1. Copy an example from `fixtures/governance/intakes/` and change every field. Use a role, never a person's name; use synthetic client ids only.
2. Run `uv run --frozen python -m workflows.assurance score fixtures/governance/intakes/UC-001.json` (no argument scores the whole folder; `--json` prints the full reasons).
3. A person reads the result and the free-text problem statement together. The score never sees the free text.

| `id` | string: pattern `^UC-\d{3}$` | Intake id, UC-nnn. |

| `submitter_role` | string: min length 1, max length 80 | Role of the submitter, never a person's name. |

| `data_classes` | list of `DC-0`, `DC-1`, `DC-2`, `DC-3`, `DC-4`, `DC-5`, `DC-6` | Every data class the idea touches (DC-0 to DC-6). |

| `proposed_levers` | list of string | Lever names the idea would use or add. |

| `runs_per_month` | integer: at least 1, at most 1000000 | ASSUMED occurrences per month. |
| `effort_days` | number: more than 0, at most 365 | ASSUMED build effort in days. |
| `roi_row` | string or null | Id of a row in governance/roi_fixtures.json whose fixture rate applies; null if unmeasured. |

## How the score is made

Weights and bars are in `governance/intake_rubric.json`. They are proposals; no the MSP ranking policy is known.

**Risk class** (R0 read, R1 reversible and low impact, R2 reversible and high impact, R3 irreversible, broad or identity access; definitions in `docs/map/05-governance.md` section 6.1):

- `RC-1` the `effect` field sets the base class: `read-only` = R0, `reversible-one-object` = R1, `reversible-access-or-many` = R2, `irreversible-or-identity-or-tenant-wide` = R3.
- `RC-2` an effect other than `read-only` across `many-clients` is at least R3.
- `RC-3` any `DC-6` data class makes it R3.

Risk weight: R0 = 1, R1 = 2, R2 = 4, R3 = 8.

**Data sensitivity** (`DS-1`): the highest data class named, banded DC-0 = low, DC-1 = low, DC-2 = moderate, DC-3 = moderate, DC-4 = high, DC-5 = high, DC-6 = prohibited.

**Value band** (`VB-1`): assumed hours per month = minutes per run x runs per month / 60; high at 20 or more, medium at 5 or more, else low. Assumed and unadjusted.

**Acceptance** (`AC-1`): never typed by the submitter. `roi_row` names a row of `governance/ROI_TRACKER.md`, whose rate is read from a committed eval report on synthetic fixtures. No row means unmeasured.

**Never-automate and other blocks** (checked first; a blocked idea gets no priority and no rank):

- `BL-NEVER` a proposed lever name matches a pattern of `governance/never-automate.json`, or an inventory id is on that list (the same matcher the lever registry uses).
- `BL-DC6` secrets (`DC-6`) never enter a prompt, a log or a model route.
- `BL-HOSTED` a hosted model route with `DC-4` or a higher class is refused until provider terms are approved (C-28, planned).

**Verdict**, first rule that applies:

1. `blocked` (`VD-BLOCK`).
2. `design-review-required` (`VD-R3`): R3 needs a written change plan, two approvers and never runs unattended.
3. `needs-inventory-mapping` (`VD-MAP`): no lever and no inventory id, so the never-automate check had nothing to read.
4. `needs-measurement` (`VD-MEASURE`): no linked fixture rate, so no priority.
5. `below-acceptance-bar` (`VD-BAR`): fixture acceptance under 90%.
6. `candidate` (`VD-OK`).

**Priority** (`PR-1`), when not blocked and a fixture rate is linked: `(assumed hours per month x fixture acceptance) / (assumed effort days x risk weight)`, two places. The same function fills `governance/ROI_TRACKER.md`.

## Limits

- The never-automate check reads the declared lever names and inventory ids only. An idea that hides what it does behind vague fields passes that check; the reviewing person is the control (RR-3 in `governance/RISK_REGISTER.md`).
- Minutes, runs and effort are the submitter's assumptions. Acceptance is a fixture rate with author-written gold labels, not a technician's acceptance of real output.
- The weights, bars and bands are proposals. Nothing here says which idea the MSP should build.
